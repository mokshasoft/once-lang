## The two results worth carrying forward

### 1. FORD THE COMPONENT, NOT THE PAIR (§14)

The reusable trick, and the one that makes a pair index cheap. A
constructor fixes only its SORT, so its constraint is
`Id Nat (fst ⟨i⟩) t`. Fording the whole index would need
`Id (Σ' Nat Nat) ⟨i⟩ (pair t d)` — which forces you to PIN `d`, the one
component that must stay free. `iι` already targets the ambient `i`, so
the depth simply RIDES: unconstrained and unmentioned.

### 2. FORDING AND NESTING ARE DIFFERENT MECHANISMS (§12)

Stated because a previous commit got it wrong. Fording converts a
computed INDEX into an equality CONSTRAINT; `icw-imu` makes a field's
TYPE a family. `Examples/Scoped` now uses both, one line apart:
`Fin`'s own target index is Forded, and only `var`'s field needs the new
row.

⚠ **`icw-imu` is NOT forced by the `RTm` knot** — an earlier commit
message claimed it was, and `Examples/Mutual` refutes that. Fold the
knot into one tagged family and every cross-reference is `iρ`, a
recursive field. What `icw-imu` buys is MODULARITY (`Fin` stays its own
description instead of being absorbed into the syntax's mutual block)
and genuinely NESTED types. Real, verified, but not a necessity
argument. The correction is inline in §12.

## Where item 7 stands, and the ONE thing that is newly open

Item 7 is no longer gated on any kernel question. What remains is the
ENCODING — writing the knot's description at the scale of the real
`RTm`, and defining `sz` over it by `ielim`.

⚠ **`⊢amrec`'s carrier is a SINGLE TYPE** — `AmTΠ` takes `A : RTy ⌊ Δ ⌋`
with `μ : A → Nat`. An indexed family is not one type, so measure
recursion over `Tm n` for VARYING `n` would need the index bundled into
the carrier. **Checked: item 7 does not need that.** The four signatures
are

    prog   : (n : ℕ) {t : RTm ε} {T : RTy ε} → ◇ ⊢ t ∷ T → sz t ≤ n → Prog t
    usplit : (n : ℕ) {c : RTm ε} → ◇ ⊢ c ∷ U → sz c ≤ n → UProg c
    trS    : (m : ℕ) {dM : RTm (ε ∙)} {p e : RTm ε} … sz dM + sz p + sz e ≤ m
    ordtrS : (m : ℕ) {a t u p q : RTm ε} … sz a + sz t + … ≤ m

`prog`/`usplit` are at `RTm ε` outright. `trS`/`ordtrS` carry TUPLES —
and `trS`'s `dM` lives at `ε ∙`, not `ε` — but every context in them is
FIXED, so the carrier is a `Σ'` of concrete index instances and the index
never varies over the recursion. Single type either way.

  ⇒ ARCHITECTURE.md's "applies VERBATIM" holds for its own customers,
    and no bundling is on the critical path.

  ★ It does pin one requirement, though: `trS`'s measure needs `sz` at
    BOTH `ε` and `ε ∙`, so `sz` must be `sz : (d : Nat) → K (tm, d) → Nat`
    — one `ielim` over the pair-indexed family. That is exactly what §14
    enables, and it is why the pair index was worth measuring before the
    encoding rather than during it.

⚠ A second, smaller thing the encoding will pay: at a concrete index
`pair t d` the payload types read `fst (pair t d)`. `fst`/`snd` are TERM
FORMERS stepping by `βfst`/`βsnd`, not definitional projections, so every
such spot needs an explicit conversion (`ξ-El`/`ξ-⌜Id⌝ˡ` at a constraint
field, `ξ-IMu` at a recursive one). Boilerplate, not proof. If it gets
tedious, generate it (cf. `tools/gen-clauses.py`).

⚠ A blocker on `⊢amrec` reuse that is NOT new: `amrec-unfold-Id` is
CONDITIONAL on `StepExt`, "the CALLER's to discharge and which nothing in
this tree supplies yet" (`Lib/Amrec.agda` header). Any item-7 work that
needs the INTERNAL unfolding inherits that obligation.
