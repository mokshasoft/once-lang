## 3. ★ THE DECISION — type formation in the kernel

**Take this before `fund`, after consolidating.** The analysis below is complete;
it does not need re-deriving.

### 3.1 The problem, in one line

`⊩` is not total over `RTy` (`SpikeSNK.¬⊩elLam`), and `⊢lam` puts no condition on
its domain, so **a normalization theorem for `_⊢_∷_` as it stands is not
provable.**

The witness: `El (lam (var vz))` is a *normal* type — `El-⌜base⌝`/`El-⌜Π⌝`/
`El-⌜Σ⌝` all need the code to BE a constructor, and `ξ-El` needs it to step, but
`lam (var vz)` is normal — whose code is not neutral either. No constructor of
`⊩` applies. `fund` can then neither *produce* `⊩ (subTy σ A)` for `⊢lam`'s
domain, nor *take it as input* (`⊢app` would need one for `Π A B` before it has
it).

### 3.2 How narrow the leak actually is

Worth knowing before deciding, because it bounds the severity:

- **This is not an inconsistency.** Consistency (`Tm ε ⊥ → Empty`) is untouched;
  it is a well-formedness defect. What the kernel currently admits is judgments
  at meaningless types, e.g. `Γ ⊢ lam t ∷ Π (El (lam x)) B`.
- **Bad types never arise from well-typed codes.** `lam s ∷ U` is *not*
  derivable: `⊢lam` concludes at a `Π`, and the only other route is `⊢conv` with
  `Π A B ≅ᵀ U`, which fails by `Π-reduct` + confluence (both already in
  `NbEPDirDBInj`). So the only leaks are `⊢lam`'s unconstrained domain and
  contexts that may hold garbage — exactly what a type-formation judgment closes.

### 3.3 The options

**A — INTRINSIC.** Add `Γ ⊢ty A` (and `⊢ Γ`), with premises on `⊢lam`/`⊢app`/
`⊢pair`.

**B — EXTRINSIC.** Keep `_⊢_∷_` as is; add `⊢ Γ`/`⊢ty` as separate judgments and
state normalization under a well-formedness side condition.

⚠ **B is worse than it looks, and the reason is specific.** Plain syntactic
validity (`⊢ Γ → Γ ⊢ t ∷ A → Γ ⊢ty A`) is **not provable** for the current
`⊢lam`: its premise is `(Γ ▹ A) ⊢ t ∷ B`, and if `t` never uses the variable,
nothing recovers `Γ ⊢ty A` — the garbage sits unused in the context. So B's side
condition cannot be `Γ ⊢ty A`; it has to be a predicate over *derivations*,
requiring well-formedness at every subderivation. **That is A's information
stored externally** — a parallel structure to keep in sync, an extra argument on
every downstream theorem, and drift risk. Its only genuine advantage is that
nothing existing changes today.

**C — RESTRICT THE SYNTAX** so `El` takes codes rather than arbitrary `RTm`.
✗ **REFUTED.** Not closed under reduction: `El (app (var f) c)` is well-shaped,
and substituting `f := lam d` then β-reducing can land at `El (lam …)`. The bad
shape is reachable, so no syntactic restriction excludes it.

### 3.4 ★ The cascade is MUCH smaller than PLAN §2 implies — measured

This is the fact that should drive the decision, and it was measured, not
assumed. Modules that **induct** on the committed kernel's `_⊢_∷_`:

- `NbEPDirDBType` — the definition site;
- `NbEPDirDBSubj` — `ren-lemma`, `sub-lemma`, `gen-*`, `sr`.

**That is all.** `NbEPDirDBFull`/`Sig`/`Univ` are standalone demos with their own
judgments; `DTT`/`DTTCh`/`DepModel`/`DepTy` are the other line. And critically:
**`Conf`, `Inj`, `SR`, `Dec` never mention `_⊢_∷_` at all.**

> PLAN §2's "adding constructors cascades; budget six modules" warning is about
> extending `RTm`/`RTy`, which forces re-proving **confluence and subject
> reduction**. Adding *premises to typing rules* touches nothing on the
> reduction side — confluence, Church–Rosser, Π-injectivity and `dec-conv` are
> statements about raw syntax. **The warning does not apply to this change.**
> Two modules, not six.

`NbEPDirDBSubj` already has the `Ren⊢`/`Sub⊢` machinery to hang the `⊢ty`
versions of `ren-lemma`/`sub-lemma` on.

### 3.5 Recommendation

**A, landed as one cascade after consolidation** (the dHoTT-32/33 pattern).
B stores the same information worse, C is refuted, and A additionally makes
validity provable and the kernel well-formed-by-construction — the presentation
every real implementation uses.

Knock-on if A is taken: the final theorem reads `⊢ Γ → Γ ⊢ t ∷ A → WN t`.
`dec-conv` is unaffected — it consumes `t ⟶* n` and `IsNormal n` and never sees
a typing derivation.

## 5. ★ NEGATIVE RESULTS — do not re-attempt these

Each was tried and refuted *this session*, two of them after I had recommended
them one step earlier. The exact errors are recorded so nobody pays twice.

**(a) Spine inversion for head expansion** (`SpikeSNX` §5). Not "bulky" —
unstateable. `_·_` is a function, so `app (lam s) u · sp` with `sp` a variable is
a STUCK term, and a stuck term can never be unified against a constructor
pattern:

```
SplitError.UnificationStuck
I'm not sure if there should be a case for the constructor β …
  app (lam t) u ≟ app (lam s) u₁ · (sp ▸ x)
```

Restructuring the inversion datatype does not help (its own proof needs the same
split), nor does cons-shaping `_·_`. Superseded by JM (`SpikeSNJ`).

**(b) An unstratified `U` clause carrying reducibility** (`SpikeSNK` finding 2):

```
NotStrictlyPositive
⊩_ is not strictly positive, because it occurs
  in the second argument of _×_ in the second clause
  in the definition of _⊩∋_, which occurs
  to the left of an arrow in the type of the constructor ⊩Π
```

`⊩Π`'s function field puts `⊩∋` negatively, so a `⊩` in `⊩∋`'s result makes `⊩`
occur negatively in its own definition. W1a's knot and this one are each fine
alone and not together. **Stratification by universe level is forced**, and it
terminates at two levels only because the kernel's universe is predicative —
codes are `⌜base⌝`/`⌜Π⌝`/`⌜Σ⌝` with *no code for `U`*.

**(c) The Kripke action** (`SpikeSNX` §1). Struck, not built. `fund` is
substitution-based: its λ-case extends `σ : Sub Γ Δ` to `σ,u : Sub (Γ ∙) Δ`, so
the *target* context never grows and nothing is weakened. The one place Kripke
is classically forced is CR1 at `Π` — removed by carrying `SN t` as a conjunct in
the `Π` clause, a decision `SpikeSNU` took for an unrelated local reason.

**(d) Erasure as a shortcut to term SN** — refuted earlier (dHoTT-37, PLAN §5),
restated here because it is adjacent: the erased simple type is not
conversion-stable.
