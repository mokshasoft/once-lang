# Plan 0.6.2: Polymorphic Schema Instantiation (D044 follow-up)

## Context

D044 landed the classifier route for NT builtins but kept parser-
level desugarings in `Once.Parser.Inline.expandBuiltins` as a
fallback for nested classifier-hostile cases (e.g. `compose f (pair
…)` where `pair`'s per-NT infer-mode fails). The fallback path is
semantically correct but keeps two architectures in the tree.

Root cause: user-polymorphic definitions (`swap = pair snd fst`)
are handled by **inlining their raw body at every call site**, via
`inlineAllWithPoly` in `Once.Parser`. The inlined body then flows
through the typechecker as an anonymous expression, losing its
connection to `swap`'s declared schema. When the classifier's
check-mode needs to infer a sub-expression (e.g. `g` in compose),
the inlined poly body can't always be inferred on its own.

Option C from the D044 alternatives closes this gap by replacing
inlining with **polymorphic schema instantiation at call sites**:
`swap` stays as a name in a `PolyCtx`; each use instantiates its
schema against the call site's expected type and compiles the body
*once* at that ground instantiation. This is the approach used by
monomorphizing type systems (Rust, template instantiation in C++).

## Goal

Replace the inlining pipeline (`inlineAllWithPoly`, `expandBuiltins`,
`betaReduceApps`, `polySeedDefs`) with schema-instantiation. Net
result:

- Polymorphic user defs typecheck the same way as polymorphic
  builtins (via schema + instantiation at call sites).
- `Parser.Inline.expandBuiltins` becomes empty and removable.
- Error messages point at `swap`'s definition, not an inlined-body
  sub-expression.
- Each unique ground instantiation compiles once (specialization
  cache).
- D043/D044's "universal-property desugaring" concerns are fully
  subsumed.

## Critical files

- `formal/Once/Type.agda` — add `instantiate : PolyType → Type → Maybe

## Phases

### Phase 1 — Schema instantiation primitive (load-bearing POC)

Add to `Once.Type`:

```
Subst : Set
Subst = List (String × Type)

lookupSubst : String → Subst → Maybe Type
extendSubst : String → Type → Subst → Maybe Subst  -- Nothing if conflict

instantiate : PolyType → Type → Maybe Subst
instantiate (PTVar x)  t subst = extendSubst x t subst
instantiate PUnit      Unit = just []
instantiate (A P* B)   (t1 * t2) = instantiate A t1 >>= instantiate B t2
-- etc.
instantiate _ _ = nothing

applySubst : Subst → PolyType → Maybe Type
```

Acceptance: `instantiate (a * b → b * a) (Int * Str → Str * Int)`
returns `just [("a", Int), ("b", Str)]`. Mismatched schemas return
`nothing`. Total function.

*Estimated commits*: 1 (primitives + unit tests).

### Phase 2 — Add PolyCtx layer

Introduce `PolyCtx = List (String × PolyType × RawExpr)` alongside
`NamedCtx`. Populated from `PolyFunInfo`. Thread through
`compileAllFuns` and `inferElab` / `checkElab`.

At this phase the typechecker still doesn't USE the PolyCtx — it's
just plumbed through. Tests: existing fixtures green with PolyCtx
empty.

*Estimated commits*: 1.

### Phase 3 — RVar lookup extension

In `checkElab-RVar` / `inferElab` for `RVar x`:

- After lookupLocal / lookupImport, try `lookupPoly ctx x`.
- On hit: use the classifier-style check-mode — instantiate schema
  against expected type, typecheck the body at the ground
  instantiation, emit a compiled specialized reference.

For infer mode (no expected type), poly lookup fails (we can't
guess the instantiation — same as bare builtins in infer mode).

Two design questions to settle during implementation:

1. **Body compilation site**: compile each specialization once and
   cache? Or inline at every call site?

   *Decision*: cache by (name, ground type). Each
   `swap : Int*Str → Str*Int` is one compiled function; two call
   sites reuse it. Single compilation per specialization.

2. **Specialization scope**: do polys reference each other? I.e.,
   can `swap`'s body call another poly function?

   *Decision*: yes — the PolyCtx is available during specialization
   compilation, so recursive poly references work.

*Estimated commits*: 2 (lookup extension + cache).

### Phase 4 — Judgment rule + proofs

New rule:

```
t-var-poly-instantiate : ∀ {ctx x schema body T subst Ψ}
  → lookupLocal ctx x ≡ nothing
  → lookupImport (NamedCtx.imports ctx) x ≡ nothing
  → lookupPoly ctx x ≡ just (schema, body)
  → instantiate schema T ≡ just subst
  → /* body typechecks at T */
  → ctx ⊢ᶜ RVar x ∶ T ⨾ zeroUsage
```

The premise "body typechecks at T" is the specialized derivation.
Ψ = zeroUsage because poly bodies are closed at user-ctx level.

Completeness: `check-complete (t-var-poly-instantiate …)` calls
a helper that threads the lookup chain + instantiation + body
derivation through `rewrite`.

Soundness: analogous — given elab success, reconstruct the
derivation via the new rule.

*Estimated commits*: 2 (judgment + soundness / completeness proofs).

### Phase 5 — Remove inlining pipeline

Delete from `Parser.agda`:
- `inlineAllWithPoly`
- `polySeedDefs`

Delete from `Parser.Inline.agda`:
- `expandBuiltins`
- `betaReduceApps`
- `subst`
- `inlineReferences` (if no other users remain)
- All the `$pair_x` / `$compose_x` / `$curry_x` / `$curry_y` /
  `$apply_p` fresh-var constants

Update `Compile.agda`:
- `compileAllFuns` takes `FunInfo + PolyFunInfo` (via PolyCtx).
- Ground funs compile as before; at each `RVar x` that hits
  PolyCtx, the new elab path handles specialization.

*Estimated commits*: 1–2 (depending on how independent the
pipeline clean-up is from the elab change).

## Verification

Each commit must leave:
- `make frontend` clean
- `make malonzo` extracts without OOM (use `ulimit -v 7500000`)
- `make -C compiler build` clean
- `tests/poly-defs.once` green

At the end of Phase 5 specifically:
- `Parser.Inline.agda` contains no desugaring code.
- `compose f (pair g h)`-style nestings typecheck via the
  classifier + schema instantiation path, not via desugaring.
- Error messages for `swap` typecheck failures point at swap's
  def line, not `$compose_x` / `$pair_x`.

## Risks

- **Schema instantiation recursion**: if poly `A` references poly
  `B` which references `A`, specialization loops. Mitigation:
  Once has no recursion-via-RVar currently (recursion goes through
  `μ-type` / `Cata` etc.); add a cycle check as defence-in-depth.
- **Specialization cache growth**: pathological usage could generate
  many specializations. Mitigation: cache is per-compilation and
  bounded by call-site count, not combinatorial.
- **Proof coverage**: `t-var-poly-instantiate` has a nested
  derivation premise — proofs need care to thread correctly.
  Pattern already exercised by POC-2's `t-pair-check`.

## Non-goals

- **Generic polymorphism** (HM, let-generalization) — still out.
  Polymorphism enters only via user-declared schemas, same
  constraint as today.
- **Meta-variables / unification** — `instantiate` is structural
  template matching against a ground type, not full unification.
  Agda-friendly and D007-compatible.
- **Changing the inliner's role for ground funs** — ground
  `FunInfo` bodies don't get inlined anyway (they're compiled
  separately and referenced by name); nothing to change there.
