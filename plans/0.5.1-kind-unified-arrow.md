# Plan 0.5.1: Kind-Unified Arrow Type

## Context

Currently `Once.Type` has two distinct exponential-like type formers:

```agda
data Type : Set where
  ...
  _⇒[_]_ : Type → Quantity → Type → Type   -- quantified pure arrow
  Eff    : Type → Type → Type               -- effectful arrow (D032)
```

With corresponding IR morphism constructors:

```agda
apply    : ∀ {A B q} → IR ((A ⇒[q] B) * A) B
applyEff : ∀ {A B}   → IR ((Eff A B) * A) B
arr      : ∀ {A B}   → IR (A ⇒[Many] B) (Eff A B)
```

This is **categorically redundant**. In a CCC we have ONE exponential
object `A ⇒ B` and ONE apply morphism. The `Eff A B` vs
`A ⇒[Many] B` distinction is purely type-level (D032): both have
semantic interpretation `⟦A⟧ → ⟦B⟧` and identical codegen
(`compile-ir' applyEff = apply-instrs`).

The redundancy manifests at the proof layer:

1. `applyEff-placeholder` postulate in `Once.CCC.Machine.Dispatcher`
   — a transport proof we'd need to write to delegate `applyEff`'s
   runtime to `apply`'s.
2. Every WF module that case-splits on IR constructors has a
   separate `applyEff` clause doing the same work as `apply`.
3. Future effect-related IR constructors would multiply the
   redundancy (Plan 0.5's Phase C / F3 partial fix).

This plan **eliminates the redundancy by unifying the type-level
annotations** (quantity + effect) under a single "arrow kind"
structure, reducing IR to one apply morphism.

## Categorical framing

Effects aren't a natural CCC structure — they're a type-discipline
layer. In the CCC `⟦A⟧ → ⟦B⟧`, `Eff A B` and `A ⇒[Many] B` are the
**same object** (isomorphic via `arr` and its inverse; in fact
definitionally equal at `⟦_⟧`). D032 introduced the type-level tag
to **enforce pure/effectful separation at type-check time**, not to
represent a new categorical object.

The quantity `q` in `A ⇒[q] B` is already a type-level annotation
on the exponential (QTT-style). Effect-vs-pure is another. Both
decorate the same underlying CCC morphism. Unifying them under a
single "arrow annotation" is categorically aligned:

- **One exponential** type former, parameterized by kind.
- **One apply** morphism in IR, parameterized by the same kind.
- **Distinction preserved at type level** via kind, satisfying D032.

## Design

Introduce an `ArrowKind` structure carrying both quantity and
effect information as **orthogonal** annotations:

```agda
data Purity : Set where
  pure : Purity
  eff  : Purity

record ArrowKind : Set where
  constructor mk-kind
  field
    quantity : Quantity
    purity   : Purity
```

**Design rationale: quantity and effect are categorically
independent annotations.**

Linearity is a property of the arrow's **use**: `A ⇒[One] B`
requires the argument to be consumed exactly once by the morphism.
Effect is a property of the arrow's **execution**: `Eff A B` signals
that evaluating the morphism's body has observable side effects.

In the CCC, these are independent decorations on the same
exponential object `A ⇒ B`:
- `One` vs `Many` constrains the morphism's use of its input.
- `pure` vs `eff` constrains the morphism's execution behavior.

No structural law couples them. All four combinations are coherent
morphism types:
- `A ⇒[ mk-kind Many pure ] B` — unrestricted pure arrow.
- `A ⇒[ mk-kind One pure ] B` — linear pure arrow.
- `A ⇒[ mk-kind Many eff ] B` — unrestricted effectful arrow (current `Eff A B`).
- `A ⇒[ mk-kind One eff ] B` — linear effectful arrow.

Encoding them as a **record** reflects this independence. A
sum-typed alternative (quantity XOR effect) would impose an
artificial coupling — the assumption "if effectful, then
unrestricted" has no categorical justification; it would just
happen to match one pragmatic subset we currently use. Once's
design philosophy is to follow structure, not coincidence: the
record is the principled choice.

**Current `Eff A B` migrates to `A ⇒[ mk-kind Many eff ] B`** — one
specific combination in the larger space.

### New Type

```agda
data Purity : Set where
  pure : Purity
  eff  : Purity

record ArrowKind : Set where
  constructor mk-kind
  field
    quantity : Quantity
    purity   : Purity

data Type : Set where
  ...
  _⇒[_]_ : Type → ArrowKind → Type → Type
  -- (no `Eff` constructor)
```

### Surface syntax (no change for user-facing code)

Parser accepts both forms and maps to the unified Type:

| User writes | Parses to |
|---|---|
| `A -> B` or `A ⇒ B` (q=Many, pure default) | `A ⇒[ mk-kind Many pure ] B` |
| `A -o B` or `A ⇒[q] B` (pure, linear) | `A ⇒[ mk-kind q pure ] B` |
| `Eff A B` | `A ⇒[ mk-kind Many eff ] B` |
| `IO A` | `Unit ⇒[ mk-kind Many eff ] A` |

Future syntax (NOT IN THIS PLAN, but expressible):
| Future syntax | Parses to | Meaning |
|---|---|---|
| `A -o Eff B` (hypothetical) | `A ⇒[ mk-kind One eff ] B` | linear effectful arrow |

D032 satisfied: typechecker rejects `f : A ⇒[ mk-kind Many pure ] B`
used where `A ⇒[ mk-kind Many eff ] B` expected (purity differs) and
vice versa. Records of unequal fields don't unify at type-check.

### IR

```agda
data IR : Type → Type → Set where
  ...
  -- ONE apply constructor:
  apply : ∀ {A B k} → IR ((A ⇒[ k ] B) * A) B
  -- (no `applyEff` constructor)

  -- arr becomes: a morphism between two arrow types of different kinds:
  arr : ∀ {A B} → IR (A ⇒[ mk-kind Many pure ] B) (A ⇒[ mk-kind Many eff ] B)
  -- (codegen: identity / no-op — the "embedding" is purely type-level)
```

The `applyEff-placeholder` postulate in `Dispatcher.agda` **vanishes
by elimination** — the constructor doesn't exist, nothing to prove.

### Semantic interpretation

```agda
⟦ A ⇒[ _ ] B ⟧ = ⟦A⟧ → ⟦B⟧
-- (uniform regardless of kind; kinds are type-level only)
```

## Migration strategy

### Phase 1a: Vocabulary (additive only) — **LANDED 2026-04-23 (0c5230e1)**

1. Add `Purity` data type and `ArrowKind` record in `Once.Type`.
2. Add `_≟p_`, `_≟k_` decidable equalities.
3. Add `pureK`, `effK`, `showPurity`, `showArrowKind` conveniences.
4. Verify `make frontend` passes — no breaking change.

This establishes the vocabulary for the refactor without touching
any existing code. Safe checkpoint.

### Phase 1b: Type refactor (breaking change) — MULTI-SESSION

Initial scope estimate was ~1 day; investigation revealed the
actual surface area is **15–20 hours of focused work across ~23
files**. Per-site work is mechanical (transform pattern `A ⇒[ q ] B`
to `A ⇒[ mk-kind q pure ] B`, `Eff A B` to
`A ⇒[ mk-kind Many eff ] B`) but non-sed-able because each site
has semantic constraints on the exact kind pattern needed.

Sub-phased along file-dependency lines; each sub-phase is a
dedicated focused session (~2-3 hours), with synonym shims keeping
the tree green between sub-phases.

#### Phase 1b-i: `Once.Type` internals

1. Change `_⇒[_]_` to take `ArrowKind`.
2. Remove `Eff` constructor.
3. Add `_⇒q[_]_` and `Eff` as function synonyms for RHS use.
4. Update internal patterns in `Type.agda`: `showType`, `embed`,
   `typeEqBool`, `instantiateAcc`, `applySubst`, `purityEqBool`.
5. Verify `make typecheck` passes with all other files using
   pre-migration patterns (shims cover RHS; only downstream
   patterns will break, to be fixed in subsequent sub-phases).

#### Phase 1b-ii: `Once.CCC.IR` and direct dependents

1. Update `apply`, `curry`, `arr` signatures to take ArrowKind.
2. Remove `applyEff` IR constructor (now `apply` with `effK`).
3. Update `Once.Functor.Translate` patterns.
4. Verify typecheck.

#### Phase 1b-iii: Surface layer

1. `Once.Surface.Syntax` — update `lam`, `app`, `effApp` signatures.
2. `Once.Surface.Elaborate` — update `effApp` elaboration to use
   `apply {k = effK}` instead of `applyEff`.
3. `Once.Surface.Semantics` — pattern-match updates.
4. `Once.Surface.Correct` — correctness theorem threading.
5. Verify `make frontend` up to Surface passes.

#### Phase 1b-iv: `Once.TypeCheck.Elaborate` (largest file)

~60+ sites: arrow-pattern matches on specific quantities, `Eff _ _`
patterns across many pattern tables (`_≟T_` combinations,
`checkCompose` type-filtering, `checkCurry` signatures, `asFun` /
`asInt` dispatch, `ahv-*` classifier dispatches).

Single focused session, ~3 hours.

#### Phase 1b-v: Remaining `Once.TypeCheck.*` files

1. `Judgment` — judgment rule patterns.
2. `Completeness`, `Soundness`, `Determinism`, `Totality`, `ErrorProofs`, `Verified`.
3. Each file's patterns mirror the main Elaborate.agda changes.

#### Phase 1b-vi: `Once.CCC.Machine.*` and backends

1. `ClosureWellFormed`, `SimpleWF`, `Dispatcher`.
2. Per-IR-constructor WF modules: `ApplyWF`, `ComposeWF`, `CurryWF`,
   `PairWF2`, `SumRecWF`, etc.
3. Backends: `X86-64`, `X86-32`, `RiscV64` `Compile.agda`,
   `DirectSimulation.agda`, `Correct.agda`.

Largest sub-phase. May warrant further sub-splitting.

#### Phase 1b-vii: Clean up synonyms

1. Remove `_⇒q[_]_` and `Eff` function synonyms.
2. Migrate remaining RHS uses to direct `mk-kind q pure` form.
3. Verify all tests pass with the pure structure.
4. Provide convenience synonyms (if desired):
   ```agda
   _⇒q[_]_ : Type → Quantity → Type → Type     -- A ⇒q[ q ] B = A ⇒[ mk-kind q pure ] B
   Eff     : Type → Type → Type                 -- Eff A B = A ⇒[ mk-kind Many eff ] B
   ```
   These can be transparent synonyms (`_⇒q[_]_ A q B = A ⇒[ mk-kind q pure ] B`),
   letting existing source-level references compile unchanged during
   migration. Remove synonyms once all call sites are migrated.
5. Update `⟦_⟧T`, `showType`, `PolyType`, `typeEqBool`,
   `instantiateAcc`, `applySubst` to handle the new kind.
6. Verify `make typecheck`-formal passes.

## Success criteria

- `Once.Type` has no `Eff` constructor; unified `_⇒[_]_` with
  `Purity` kind.
- `Once.CCC.IR` has no `applyEff` constructor.
- `applyEff-placeholder` postulate in `Dispatcher.agda` is gone
  (not transported; eliminated).
- `make frontend` + `make compiler` + `make malonzo` clean.
- `tests/poly-defs.once` passes end-to-end.
- D032's pure/effectful discipline preserved (typechecker still
  rejects pure-where-effectful-expected).
- Zero new postulates introduced.
- Net IR machinery line reduction (estimate: ~200-400 lines from
  applyEff clause elimination across ClosureWellFormed, SimpleWF,
  Dispatcher, and 3 backends).

## Risks

1. **Type migration breaks everything at once.** Using synonym
   shims during Phase 1 mitigates: old `Eff A B` source continues
   compiling while call sites migrate incrementally.
2. **Kind parameter propagation may cascade into PolyType
   instantiation and surface-level type inference.** Need to verify
   the poly-def instantiation path (plan 0.6.2's work) handles
   kinded types correctly.
3. **Backend compile-correct proofs may need non-trivial adaptation**
   if they pattern-match on apply vs applyEff as distinct cases.

## Relationship to other plans

- **Supersedes 0.5 Phase C**: the applyEff-placeholder postulate
  closure is no longer needed; the constructor is eliminated.
- **Builds on 0.5 Phase A/B**: the `IRHead` structure from Phase B
  continues to work; one fewer head (`h-applyEff` → `h-apply`).
- **Relates to D032** (effects): preserves D032's intent via kind
  parameter, supersedes D032's "Eff is a distinct Type constructor"
  implementation choice.
- **Blocks/unblocks nothing in the active tree**: 0.2.4 Layer 0
  work and 0.4 completeness work are orthogonal to this refactor
  (they don't depend on Eff/arrow distinction mechanics).

## Estimated scope

~1 day of focused work, comparable to plan 0.6.2 Phase 4. Type
refactor is load-bearing but small in LoC; IR / Surface / Proof
machinery updates follow via compiler-guided mechanical edits.

## Non-goals

- Adding user-facing syntax for linear effectful arrows. The
  `ArrowKind` record makes them expressible at the type level,
  but surface syntax only exposes existing combinations. A future
  plan can add syntax when there's a use case.
- Reorganizing effect semantics beyond removing the IR-level
  redundancy. `eff` remains a type-level phase tag for D032's
  purpose.
- Touching backend machine code generation; codegen is already
  uniform (`compile-ir' applyEff = apply-instrs`), so this refactor
  only SIMPLIFIES the codegen side.
