# Plan 0.55 — shared physical-register namespace ⇒ definitional CCC/arith disjointness

## The problem (found during 0.54 register-naming cleanup)

The arith block subroutine (`once_arith.block.*`) runs mid-CCC-code and must not
clobber registers CCC keeps live across the `call`. Today that "PreservesCCC"
property is **assumed inside the postulate `x86-flat-from-obs`**
(`Once/Adequacy/ArchCorrectness/X86-64.agda:44`, via its `asm-trace-correct`
field) — never proven — and the register choice is only an informal comment in
`Once/Arith/Backend/X86-64/Emit.agda`.

Worse, the comment is **partly false**. Concrete-register audit (x86-64):

| | registers |
|---|---|
| CCC actually emits (live set) | `rax rsp rdi rcx rbx rbp rsi` + `r12` (closure ptr) + `r15` (heap-top ptr) |
| CCC never emits (free) | `rdx r8 r9 r10 r11 r13 r14` |
| arith uses (`XR0..XR3`→) | `r12 r13 r14 r15` (compile-go uses only `XR0`,`XR1` = `r12`,`r13`) |

So `XR0→r12` **overlaps** CCC's closure register (arith's accumulator, used
constantly), and the declared `XR3→r15` overlaps CCC's heap-top pointer (latent:
only unused because compile-go stays in regs 0-1). `rdi`/`rax` are shared **on
purpose** (Input1 in / Output out).

## Why not unify the machines (settled in 0.54 analysis)

CCC is a location/heap machine (registers hold `StoredValue` incl. `SV-Ptr`,
state carries two memories + a bump allocator); arith is a value machine
(`Store = ℕ → Maybe ℕ`, never allocates, zero CCC imports). Merging them would
force boxing + heap-invariant obligations arith is designed to avoid, and the
proven `block-correct` would have to be re-derived over a heavier state. The two
machines meet at exactly one `call`, with a 2-register + 1-encoding interface.

## The design — one register declaration, two machines "acquire" from it

Keep the two machines distinct. Extract the per-arch **physical register type**
into a shared top-level module, and add an **ownership partition** so disjointness
is definitional (a `refl`, not a proof over string equality or a postulate):

1. `Once/Target/<arch>/PhysReg.agda` (top-level, shared): the physical `Reg`
   type (re-home CCC's `Reg`) + `showReg` rendering + an ownership tag
   `owner : Reg → RegClass` where `RegClass = ccc | arith | shared-io | free`.
   - `ccc`: `rcx rbx rbp rsi r12 r15` (+ `rsp`) — CCC-live across a SigOp.
   - `arith`: 4 of the CCC-free set, e.g. `r13 r14 r10 r11`.
   - `shared-io`: `rdi` (Input1/arith-input), `rax` (Output/arith-output).
   - `free`: the rest.
2. CCC Emit/AbstractToX86/Semantics use the shared `Reg` (moderate rewire; CCC
   already imports its own `Reg`).
3. Arith Emit maps `XReg → Reg` (into the `arith` class) and renders via the
   shared `showReg` — this is the "extract the emitters" step (shared rendering,
   arith stops emitting raw strings).
4. **Definitional disjointness:** `owner (arith-reg XRn) ≡ arith` by `refl` for
   each `n`; CCC's live registers all have `owner ≡ ccc`/`shared-io`. So
   `arith-writes ∩ ccc-live ⊆ {Output}` reduces to constructor distinctness —
   the PreservesCCC obligation inside `asm-trace-correct` becomes a computation,
   not a postulate.

## Steps

- [x] 0.54 abstract rename `XR12..XR15 → XR0..XR3`.
- [x] A. x86-64: shared `Once.Target.X86-64.PhysReg` (Reg + showReg + `owner`);
  CCC `Syntax` re-exports `Reg`, CCC `Emit` shares `showReg`; apex green,
  byte-identical → no CCC behavioral change.
- [x] B. arith x86-64 `arith-reg : XReg → Reg` maps `XR0..XR3 → r8-r11`
  (caller-saved ∧ CCC-never-emits); `arith-disjoint : owner (arith-reg x) ≡
  arith` is `refl` (definitional). Renders via shared `showReg`. Apex green.
- [ ] C. Extend to the other arches — **NOT uniform** (per-arch register audit,
  2026-07-02):
  - **riscv64:** arith's `t1-t4` **overlap CCC hard** (CCC emits `t1` 45×,
    `t2/t3/t4` ~10× each — its address-computation temporaries). Free
    caller-saved regs exist (`t5 t6 a3 a4 a5`; CCC uses `t0 t1 t2 t3 t4 a0 a1 a2
    a6 a7 s1-s4`), so the **disjointness** approach applies: shared RiscV `PhysReg`
    + remap arith `XR0..XR3 → t5 t6 a3 a4` + `owner`. Behavioral change ⇒
    re-extract + retest.
  - **x86-32:** CCC emits **all 8 GPRs** (eax ecx ebp edx ebx esp esi edi) — there
    are **zero CCC-free registers**. Arith already borrows CCC regs and
    **saves/restores them (push/pop)**. So PreservesCCC here is *"the pushed
    registers are restored"* — a **save/restore** property, NOT disjointness. The
    `owner` partition can still share the `Reg`/`showReg` declaration, but the
    proof obligation is different (restore-correctness lemma over the prologue/
    epilogue push/pop), and there is nothing to make "definitional".

  **General insight:** PreservesCCC has two forms — (1) *disjointness* on
  register-rich arches with ≥4 free regs (x86-64, riscv64), definitional via
  `owner`; (2) *save/restore* on register-poor arches (x86-32), a restore lemma.
- [~] D. Re-verify once-test (266/266) — x86-64 emitted asm changed (r8-r11), so
  CLI rebuilt + tested. **In progress** (MAlonzo re-extract + cabal test-x86).
  NOTE: apex CANNOT validate this (the register fact is what `x86-flat-from-obs`
  postulates) — once-test is the only real check.
- [ ] E. (Phase B tie-in) feed `owner`/`arith-disjoint` into the eventual
  `asm-trace-correct` decomposition so `x86-flat-from-obs` stops hiding it.

## Risk / note

Touches proven CCC codegen (Reg extraction ripples to Syntax/Emit/Semantics) and
changes emitted asm (arith register remap) — needs apex + once-test re-run. The
arith register remap alone is also a **latent-bug fix** (moves the accumulator
off CCC's `r12`).
