# Plan 0.67 — wire the arith proofs: the last link, not the proof

**Status**: OPEN, written 2026-08-06.

## The finding, stated precisely

The arith development is **not** an unwired subsystem. Almost all of it is on
the certified path already:

    REACHABLE   Once.Arith.Backend.Correct              (the width-parametric refinement)
    REACHABLE   Once.Arith.Backend.X86-64.Dispatch      (dispatch-arith, dispatch-arith-preserves)
    REACHABLE   Once.Arith.Backend.X86-64.StatePreserve (PreservesCCCState)
    REACHABLE   Once.Arith.Backend.X86-64.ExecArith
    REACHABLE   Once.Arith.SigOp.Block                  (block-semM)
    REACHABLE   Once.Adequacy.CPU.X86-64

What is orphaned is the **capstones** — the four modules that would actually
close the apex's arith obligation, plus three re-export shells:

    ISLAND  ArithSimX86-64          366   the x86-64 instance of ArithSimCore
    ISLAND  ArithSimX86-32          374
    ISLAND  ArithSimRiscV64         359
    ISLAND  ArithDispatchX86-64      71   `arith-dispatch-correct` — the capstone
    ISLAND  ArithDispatchX86-32      45
    ISLAND  ArithDispatchRiscV64     54
    ISLAND  Arith.Backend.{X86-64,X86-32,RiscV64}.Correct   14 each — pure
            `open import Once.Arith.Backend.Correct 64 public` shells

So: **the proof is finished and the last link is missing.** That is a much
better position than it looks from a reachability count, and a much worse one to
leave alone — a finished proof nothing consumes rots exactly like `CataNat*`
did.

(This sharpens plan 0.64's Group D, which said the cluster was "connected to
nothing". The *cluster* is; the machinery underneath it is not.)

## The gap — three tasks, and only the first is hard

### A1. `arith-env-x86-64` must be DEFINED. This is the whole blocker.

`Once/Adequacy/CPU/X86-64.agda` postulates it as an opaque
`X64S.Program → RT.ArithEnv val-x86-64` and never defines it. The contract's
first conjunct is `env (once-symbol-path (name si)) ≡ just pl` — a claim ABOUT
that function. **No proof about a function with no definition exists**, which is
why the contract is a stub and not a deferred proof.

The conditioning (`env ≡ arith-env-x86-64 (compile-trace prog)`) is CORRECT and
must stay — it was added 2026-07-30 because over an arbitrary `env` the
conclusion is refuted by `λ _ → nothing`. It is not the problem; it is what
EXPOSED the problem.

**The definition**: look up the emitted arith block by its `once-symbol-path`
symbol in the compiled `Program`. The emitter already puts it there — Plan 0.20
Phase G emits `arith.block.<digest>`. So this is a lookup function over a
`Program` plus the lemma that the emitter's insertion and this lookup agree.

Two siblings fall to the same task and should be done together (ledger #4, #11):

- `ev-x86-64` — read the observable value out of the argument registers at a
  `call-sym`, matching abstract `event-of`. Unblocks `external-sigop-contract`.
- `step-budget-x86-64` — the event-count ↦ machine-step fuel map. Unblocks
  `conc-fuel`.

**`conc-fuel` must NOT become a resource parameter.** It asserts adequacy of
`step-budget-x86-64`; making it a parameter would launder a definitional gap
into a resource bound. A stub is not an invariant — define the function.

### A2. Bridge `PreservesCCCState` → `CompiledCorr`

The island's post-condition and the apex's differ in shape: `PreservesCCCState`
says the registers and memory CCC keeps live across the call site are preserved;
`CompiledCorr` is the full correspondence record (`rdi-eq`, `rsi-eq`, `rax-eq`,
`rbx-eq`, `r14-eq`, `r15-eq`, `halt-eq`, `rsp-eq`, `dom-*`, `heap-eq`, `lo-le`,
`untouched`, `stack-eq`, plus `pc-off`).

Write this as an ordinary lemma: given `CompiledCorr hv prog fs s` and
`PreservesCCCState … s s'` and the `rax` value equation, produce
`CompiledCorr hv prog (flat-exec-instr (instr-sigop si) prog fs) s'`. The
abstract side writes `block-semM e (toWord sh env)` into `Output`; the concrete
side has it in `rax`; `rax-eq` is where they meet.

**Watch `untouched` and `stack-eq`** — these are the layout components D090
reworked, and `PreservesCCCState` predates them. If the arith block writes stack
scratch, `untouched` has to survive it, and that may need the arith frame's own
region model (`ASX.WF`) to say the scratch is inside the reservation. Do not
weaken `untouched` to make this go through; that field is what makes allocation
freshness a consequence rather than an assumption.

### A3. Discharge the island's preconditions from `CompiledCorr` + `RunAt`

    0 < readReg (regs s) rsp + N        from the layout (rsp is above lo, lo ≥ hfront)
    All (InFrame N) (emit-program …)    an EMITTER fact — the same class as
                                        `emitted-shape-check`; may need a walk
                                        over `compile-abs`
    ASX.WF s                            the arith frame's calling-convention
                                        contract; from `CompiledCorr` + `RunAt`
    ASX.R-input N (init env) s          "the call site laid the Int input at rdi"
                                        — the CCC arg-passing convention, which
                                        `rdi-eq` should give directly

## Sequencing — this matters

1. **A1 first, alone.** It is a DEFINITION task, not a proof task, and it is the
   highest-leverage move on the whole board: three residuals (#3, #4, #11)
   are conditioned on these three functions and cannot be attacked before they
   reduce. Land the definitions as their own commit with the tree green.
2. **A2 + A3, x86-64 only.** `arith-sigop-contract` becomes a theorem;
   `ArithDispatchX86-64` and `ArithSimX86-64` stop being islands. Ledger #3
   moves to DONE.
3. **`external-sigop-contract`** via `ev-x86-64` — same shape, ledger #4.
4. **x86-32 and riscv64 last, and only after plans 0.65/0.66.** Their
   `ArithDispatch*`/`ArithSim*` islands have nowhere to plug in until those
   arches have a correspondence at all — today they postulate the whole
   simulation, so wiring an arith slice into it would discharge nothing. Wiring
   them earlier just relocates a stub.

one line of content: `open import Once.Arith.Backend.Correct 64 public`. The

Apply plan 0.64's content test: they prove nothing the apex postulates, and they

`Correct 64` (not 32) is either a bug or evidence they were never used. **Delete
all three**, and grep the reachable tree for their names first — several
reachable modules mention `Arith.Backend.*.Correct` in comments.
