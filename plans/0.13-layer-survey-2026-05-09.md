# Plan 0.13: Cross-layer failure-mode survey (2026-05-09)

## Why this exists

Before committing to any one fix (closure-realm ABI for Layer 1 user
functions, IRTraceCorrect frontier discharge, etc.), survey the
landscape: which layers run, which fail, and which fixes unlock
which layers. A single fix that unblocks N layers is more valuable
than N independent layer-specific fixes.

## Survey method

For each categorical layer, write a minimal program exercising its
distinguishing morphism, compile through the current toolchain, and
record the failure mode. Cross-reference against
`formal/Once/CCC/Codegen/IRToTrace.agda` (codegen stubs) and
`formal/Once/CCC/Codegen/IRTraceCorrect.agda` (verification
postulates).

## The two distinct codegen failure modes

**Failure mode A — closure-realm ABI dangling-pointer** (Plan 0.2.4.5
D1 frameless `%rsp` ABI).

Triggers: every `apply` whose body returns a value that was
allocated in the body's `%rsp`-relative frame. Closure records,
returned closures from user-defined functions, returned pairs from
user pair-handling functions all hit this.

Affects:
- Layer 1 user fns (any `f : T1 → T2` with non-trivial body).
- Layer 4 user curried fns (`f : T1 → T2 → T3`).
- Effectively: **every user-defined function** that isn't a bare
  ground morphism. The morphism-realm bypass (Plan 0.2.4.5 D2)
  routes Layer 0 ground programs *around* this bug; it doesn't
  fix the bug.

Fix paths:
- (A1) **Heap-pool returned closures** — closures emit to a `.bss`
  bump pool; pointer survives `addq %rsp; ret`. Cons: no GC,
  pool exhaustion silent.
- (A2) **Caller-pre-allocated out-param** — caller reserves slots,
  passes pointer via `Input2`, callee writes there. Principled,
  matches SysV "return large struct via out-param" convention.
  Cons: ABI churn through every closure-returning function and
  through `CurryStackWF`'s proofs.
- (A3) **Top-level user-fn lifting** — typechecker emits a user-
  defined ground morphism `f : A → B` as `lift-morphism (sigop-like
  reference to once_<name>)`. Sidesteps closure-realm entirely for
  this *common* case. Doesn't help genuine higher-order use
  (closures stored in vars, returned from cases).
- (A4) **Closure-ABI fix** (combination of A1/A2). Multi-day work
  including proof refactor (CurryStackWF, ApplyWF, DirectSimulation
  correspondences).

**Failure mode B — codegen stubs**.

Triggers: any IR primitive whose `ir-to-trace'` clause is
`n , l , [] , []` (empty trace + no bodies).

Affects:
- Layer 2 entirely: `inl`, `inr`, `case` all empty.
- Layer 5/6 mostly: `In`, `Cata`, `Para`, `in-ν`, `Ana`, `Hylo`,
  `Fuse` all empty. (`out-μ`/`Out` are real `mov-to-output`.)

Fix path:
- (B1) Implement real lowerings per the layout in
  `docs/design/ir-stack-layout.md`:
  - **Sums**: tag at `[slot]`, data inline at `[slot+1]` (static)
    or pointer at `[slot+1]` (runtime-sized). `inl`/`inr` write
    the tag + data; `case` reads the tag and dispatches.
  - **μ-types**: layout per recursion-scheme requirement —
    worklist-based for `Cata`/`Para` (already have
    `worklist-init/push/pop/check` instructions). Significant
    work per scheme.

## Independence of the fix paths

Failure modes A and B are **independent**:

- Fixing closure-ABI (A) does NOT help Layer 2 codegen (B is still
  empty traces).
- Fixing Layer 2 codegen (B1) does NOT help Layer 1 user fns (A is
  still dangling pointers).
- A and B don't share code paths or proofs.

## Implication for "should we test Layer 2 first?"

Testing Layer 2 with the current toolchain produces uniform
exit=0 results — the stubbed codegen makes every Layer 2 program
look identical at runtime. Until B1 lands, **Layer 2 testing is
indistinguishable from no testing**. The same is true for Layer 5/6.

So:
- **Layer 2 deserves real codegen (B1) before testing.**
- **Layer 4 and Layer 1-with-user-fns deserve A (closure-ABI fix)
  before testing the user-function path.**
- **Layer 0 and Layer 1-ground are already testable today** —
  that's the morphism realm working.

## Recommended priority

Two reasonable orderings:

**Priority by "unblocks most of language semantics"**:
1. (A3) top-level user-fn lifting — narrow, ~1-2 days, unblocks
   the *common* case of user-defined helpers in Layers 1 and 4.
2. (B1) Layer 2 codegen — sums are needed for any non-trivial
   program (booleans, options, errors). Estimate: 2-3 days for
   inl/inr/case proper.
3. (A4) full closure-ABI fix — covers genuine higher-order use.
   Multi-day proof refactor.

**Priority by "verification gap closure"**:
1. (Plan 0.2.4.7) Discharge `ir-to-trace-correct-{compose,pair,
   curry,apply}` — frontier-mismatch postulates. ~3-4 days.
2. (Plan 0.13 sub-task) Split the
   `ir-to-trace-correct-non-layer0` catch-all into per-IR
   postulates, then discharge as B1 lands.

The runtime-priority path produces visible language progress
(more programs work). The verification-priority path produces
audit-visible postulate counts. Both are legitimate; pick based
on what matters more right now.

## Out of scope

- Specific implementations of any of A1-A4 / B1.
- Verification work for the stubbed layers (deferred until codegen
  is real).
- Layer 5/6 parser support (separate concern; currently μ-types
  reachable only at the type level, not in expressions).
