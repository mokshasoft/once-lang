# Plan 0.86 — Allocation is mechanical: no surface annotation, no IR mode

## 0. Write the decision entry FIRST

**D142 is written** (`docs/compiler/decision-log.md`), superseding D012, D013
and D014, and it is the authority for everything below. It records the
annotation's motivation at FULL strength — a dead value trapped behind a
longer-lived one — so this is never re-litigated from a weaker version, and
then why the feature could not serve it. Read D142 before this plan.

**The rule.** Nothing in the language, and nothing in the IR, chooses where a
value lives. Placement follows from the value's role:

    IR inputs and outputs      -> stack, or REGISTERS for linear values
                                  that fit (QTT gives linearity, `FitsInReg`
                                  gives fitness)
    internal, bounded          -> frontier scratch
    internal, unbounded        -> heap, FREED BY THE IR ITSELF

**The invariant this buys.** What crosses an IR boundary is stack-resident;
heap is strictly IR-internal and reclaimed before return. So **every IR has net
heap delta zero** — the `StackPure` property that used to be a per-use-site
mode tag becomes a global law, proven once instead of twice per constructor.

## 1. What is removed, and why it is not a regression

**`@stack` / `@heap` / `@arena` / `@pool` / `@const` leave the surface
language.** D012 (annotation in the implementation), D013 (outputs only) and
D014 (the `--alloc` default) are superseded.

The motivation for the annotation was real and must be stated so this is not
re-litigated from a weaker version: **a dead value can sit trapped on the stack
behind a longer-lived one**, wasting its slots for the rest of the enclosing
computation. The annotation let a programmer push such a value to the heap.

It is removed because the same effect is obtained mechanically, and because the
annotation could not reach the case anyway:

  * **`let` is where trapped values come from.** `let x = e1 in e2` elaborates
    to `e2 ∘ ⟨ id , e1 ⟩` — the `id` keeps the whole environment alive, so
    nested lets accumulate `((Γ,x),y)`. A binding used early and dead later is
    a dead component of a live product.
  * **Most of those are elaborated away** (§2), and an unread binding is
    already removed by the optimizer via `π₁ ∘ ⟨f,g⟩ ≡ f` — no liveness
    analysis needed, pure CCC rewriting.
  * **The annotation is scoped to function OUTPUTS (D013)**, and the trapped
    value is a `let`-binding. There is no syntax that names its placement. The
    feature could not express the fix for the one case that motivated it.

## 2. Elaborate so the problem does not arise — **STRUCK, see D146**

**This section is superseded.** Its premise ("`e2 ∘ ⟨ id , e1 ⟩` — the `id`
keeps the whole environment alive") was fixed by D143: the clause now emits
`restrictEnv (⊑ᵘ-+ˡ Ψ₂ …)` and `_↾_` drops `Zero` slots, so a dead binding is
not in the body's environment type. The slots are still not reclaimed, but
`let` PLACEMENT is not why — `ir-to-trace'` threads its frontier additively, so
`ir-stack-budget` is total-intermediates rather than peak-live and sinking
changes it by zero. What licenses reclamation is the boundary convention
(§4/§5, step D), not a source transform. Read D146 before reviving anything
below.

**Sink each `let` to the dominator of its uses.** Instead of

    let x = e1 in let y = e2 x in e3 y        -- x trapped under y during e3

elaborate as though it were

    let y = (let x = e1 in e2 x) in e3 y      -- x is scratch of y's computation

`x` never becomes a component of the outer environment. Three side conditions,
all decidable with information the elaborator already holds:

  * sink to the DOMINATOR of the uses, never to each use — otherwise `e1` is
    duplicated;
  * never sink across a binder (lambda body, cata algebra) — that turns one
    evaluation into per-call;
  * respect effect order when `e1` is effectful (`Purity` in `ArrowKind` makes
    this a local check; pure bindings are unconditionally safe).

`Ψ₁ Ψ₂ : Usage n` on `Surface.Syntax.let'` already carries the usage, and
`Once.Surface.Thinning` already provides order-preserving embeddings with one
`rename` lemma. The information is present; it is not being used for this.

**Residual, accepted deliberately.** A value used early AND late, dead in
between and buried below newer values, cannot be sunk — its dominator spans the
gap — and reclaiming it means repacking everything above it. That trade
(waste N slots vs copy M) is not worth compiler machinery for a case this
shaped.

## 3. Warn instead of optimising

Emit a warning when a value is dead and trapped after elaboration. This turns
an optimisation problem into a REPORTING one: no proof obligation, no policy in
the pipeline, no IR parameter. It needs liveness plus layout, both of which the
compiler computes anyway. Because §2 removes the common cases, a warning that
fires is informative rather than noise.

## 4. ENCODE the invariant — do not leave it as prose (OCP-0005 rung 1)

OCP-0005's ladder: (1) type-level invariant — violation is ill-typed;
(2) proof obligation; (3) lint; (4) documentation-only. Its Motivation section
is exactly our situation — "prose decisions are silently violable", and the
masquerade guard is enforced only because purity is a GRADE on the arrow, not a
sentence in the log.

**Net heap delta zero is encodable at rung 1, and the mechanism already
exists.** Plan 0.17 gave every producer a `bump` (delta on `next-slot` AND
`next-heap-ref`), made `final-alloc = apply-bump bump alloc` a DERIVED
projection, and made `alloc-correct` tie the trace to the bump.

**The encoding is a SUBTRACTION: drop the heap delta from `bump`.** Then an IR
that leaked heap cannot state its own result — `final-alloc` has the same
`next-heap-ref` as `alloc`, and `alloc-correct` fails to typecheck for a
leaking trace. The record gets SMALLER, and `IRHeapBudget`'s reason to exist
mostly goes with it ("Stack-only IRs fill the heap sub-record trivially" —
under this model every IR does).

**The one trap: net, not gross.** Heap-neutral is NOT heap-untouched. An IR may
allocate transiently and free inside its own trace, and a compositional IR may
free a sub-IR's output that it consumes locally. `alloc-correct` must relate
the trace's NET heap effect to the bump. Stating it grossly rejects legitimate
implementations — this is the error the existing note on `StackPure` warns
about, and it is easy to make while simplifying.

**Deliverable:** the field is gone, `alloc-correct` is net-stated, and D142
names the type that enforces it — per OCP-0005, "the current rule + the chosen
mechanism + a pointer to the type/theorem/check that enforces it".

## 5. Consequences in the IR and the proofs

**`AllocMode` leaves the IR — this lands plan 0.2.4.5**, whose audit finding
was that `AllocMode` "drifted into a vestigial layout tag with almost no
operational consequence". Six constructors lose a parameter (`⟨_,_⟩`, `inl`,
`inr`, `curry`, `In`, `in-ν`).

**The per-mode module pairs collapse.** ARCHITECTURE.md: "Each value-producing
IR has exactly two implementations — one for Stack mode, one for Allocator
mode." With one mode there is one implementation:

    CurryStackWF + CurryAllocWF        -> one curry module
    SumRecWF + SumInlAllocWF + SumInrAllocWF -> one sum module

Of the 91 `SMP.!!` holes in the parked `*WF` cluster, **~33 are allocation
bookkeeping or `ValidAtWF Heap`** — the mode-specific half. 0.2.4.5's promise
in its own words: "one proof obligation discharged once, valid across stack /
mempool / arena / heap / region".

**`--alloc` STAYS, repurposed.** It no longer selects a mode (there is none).
It selects WHICH ALLOCATOR BACKS the dynamic calls — bump, malloc, mempool,
arena. That is a Place-time choice of which symbol to emit, exactly as 0.2.4.5
describes, and it is what makes the proven allocators in `Once/Allocator/*`
(plan 0.35) reachable.

## 6. What is NOT settled

**A value that escapes a DEFINITION boundary.** Within a definition the
frameless model makes escape a non-issue: `FrameFreeTrace` proves no emitted
trace contains a frame op, the backend brackets the whole body with one
`subq $budget*8, %rsp` / `addq`, and `ResultPlace.at-loc` puts every result
BELOW the frontier, so a produced value is simply a lower offset that nothing
pops underneath. But the closing `addq` tears the region down, so a closure
returned from a top-level function cannot live in it.

That is a real call boundary, and it is the one placement decision that is not
mechanical. It is the same question as `Once.Escape` / `Once.Escape.Correct`
(plan 0.64 group E: the analysis is LIVE, its correctness proof is a red
island). ~~Settle it before step D below.~~

**SETTLED — D147.** It is plan 0.2.4.5's DESTINATION PASSING (stages A–C
already landed), which §5 above already names as what step D lands. The result
location is the caller's to choose (register when `FitsInReg`, else caller-provided slots),
sized from the statically known result type. That location is
`BeforeFrontier` in the caller's alloc state by construction, which is exactly
what `ResultPlace.at-loc`'s second frontier obligation asks for. And since
`ResultPlace` is indexed by the `AllocMode` step D deletes, **D and B' are one
change** — see the amended order below.

## 7. Order of work — STRICTLY TOP-DOWN

Make the top-level change first and let the typechecker enumerate the ripple;
never pre-build supporting lemmas. Each step below is a TOP-LEVEL change, and

  * **B'. Enforce the boundary convention** — an IR materialises its result
    into a caller-designated output location (registers when `FitsInReg`, else
    caller-provided slots), so interior slots are dead at return BY THE
    CONVENTION. This is what later licenses `g` restarting at `f-start`
    (budget → peak-live) and gives `free-heap` a producer. Gated on D.
  * **C. The trapped-value warning** (`Once.Warnings`).
  * **D + B'. `AllocMode` out of the IR, WITH the output convention** —

  * **F. `--alloc` selects the allocator backend**; wire `Once/Allocator/*`
