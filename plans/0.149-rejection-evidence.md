# Plan 0.149 — A rejection carries the proof of which typing rules fail

## Summary

When the compiler refuses a program, it says why. Today that reason is chosen by hand at each place the
type checker gives up, and nothing checks that it is the real reason: a wrong message would still pass
every proof. This plan makes the type checker hand back, with each refusal, evidence that the program has
no typing in the language definition: for every place where it fails, the rule that would type that
expression and the condition of the rule that does not hold. The messages are printed from that evidence,
so they name real rules of the language by construction, and a proof says the evidence is right.

All failures are kept, not only the first. A person reading in a terminal sees a friendly default (where,
what was expected, what was found, and a hint when one is written). A person or an LLM agent that wants
everything gets every failure, also in a structured form.

## 1. Why

D407 made the messages name the rule a program breaks, but by hand: each `failure` in
`Once.TypeCheck.Elaborate` picks a `TypeError` variant, and failure soundness is `tt`. A message is held
in place only by a D368 test on one program. So a message can drift from the Spec silently: a new route in
the elaborator, a changed rule, or a variant reused at a new site, and the text names the wrong rule with
every proof still green. The Spec's typing is the language; the reason for a rejection should be a fact
about it, stated and proved, not a string the elaborator chose.

Friendly messages, in the style of Elm, come from three things: the position in words ("the 2nd operand of
`+.`"), the expected and the found type, and a hint for a known mistake. The first two come from the
evidence for free. The hint is a human sentence, written where one helps.

## 2. Where we are

Checked 2026-11-12 on `0.139-squashed` (251d46eea), counts rechecked 2026-11-13 on master (ae74cb663):

- The Spec's surface typing is three mutually defined judgments in `formal/Once/Spec/Surface/Typing.agda`:
  synthesis `L ⊢ e ⇒ A ↝ t`, checking `L ⊢ e ⇐ A ↝ t`, and the domain-given form
  `L ⊢ e ⇐ A ⇒[ π ]↦ B ↝ t`; 65 rules (29 `s-`, 24 `c-`, 12 `d-`), 38 of them per generator. Some
  expressions match more than one rule (the mode switches `c-sub`, `d-infer`; `compose`'s two routes,
  D230). Plan 0.151 reshapes this into one rule per form and mode, with the generators as a table.
- Usage (linearity) is part of the Spec: the surface rules produce a core term, and `Spec.Surface.Program`
  requires the core judgment `Δ ⊩ Γ ⊢[ Ψ ] t ∷ A ! π` (`Spec/Core/Typing.agda`), which counts uses. A program
  that uses a linear value twice has no typing in the Spec; it fails a core rule, not a surface one. The
  implementation checks it in `Once.TypeCheck.Use` (`Use⇒ d Ψ`).
- The elaborator's results: `InferElabResult` / `CheckElabResult` (`Elaborate.agda:188`, `:195`), each
  `success … | failure : TypeError → …`; 169 `failure (` sites. `TypeError` and `renderError` are in
  `Once.TypeCheck.Error`; after D407 every variant is produced.
- Soundness (`ElaborateSound`): a success is a Spec derivation. On failure it proves nothing (`tt`).
- Completeness (`Once.TypeCheck.Completeness`, plan 0.122): an expression the Spec types, with its usage,
  is accepted at the same type and usage. Its contrapositive already gives "a failure means there is no
  derivation with a usage". It does not say which rule.
- `Once.TypeCheck.ErrorProofs` pins a few failure paths to their variants (e.g.
  `initial-app-infer-is-InitialInInferMode`), as equalities on the computed error, not as facts about the
  Spec.
- Program-level rejections (parse, resolution, the driver's Spec checks such as D323's "no type of its
  own") are outside the elaborator and outside this plan's first scope.

## 3. Decisions

- **D1, the form of the evidence.** Refutation data, not only a negation: per judgment, a datatype whose
  constructors say "the rule for this expression is R, and its premise P fails", with the sub-refutations,
  and a theorem that it rules out every derivation. Decided 2026-11-13 (the user: "I like the cleanliness
  of the general way to really know that the compile failed by _this_ rule (or these)").
- **D2, where rule names and sentences live.** Outside the Spec. Rule names are implementation-side labels
  of the refutation constructors; the Spec does not change for error reporting. Each (rule, premise) may
  have a human sentence: a `Maybe`, because not every rule needs one; without one the message has the
  generic form (position, expected, found). Decided 2026-11-13, the user.
- **D3, several failures.** Every independent failure is kept: both operands of `a + b` may fail, and every
  definition and sibling expression is checked. A premise that depends on a failed one (it needs that
  premise's type) is recorded as blocked, not as a failure of its own, so one mistake is not reported many
  times. Choosing what to show is the renderer's job: the first failure (or a few) by default, all of them
  on request. With plan 0.151 an expression has one rule per mode, so there are no competing candidate rules
  to pick from. Decided 2026-11-13 (the user: first failure "maybe as a default, but for LLM agents all
  failures can be helpful (as well as for some humans)").
- **D4, usage.** Same treatment: a refutation of the core judgment's usage condition (which variable, how
  often it is used, what its quantity allows), since this is a Spec rule like the others. Decided
  2026-11-13: required, after the surface typing.
- **D5, output forms.** (a) Human default: Elm-style text, the first failures. (b) All failures, same text.
  (c) Structured (JSON): per failure the rule, the premise, the source position, expected and found, the
  sentence if any, and what it blocks. Recommended: all three, (c) printed directly from the evidence.
  Flag names and the JSON schema open.

## 4. Steps

1. **Inventory.** Start from plan 0.151's rule table (rules, premises and their kinds). Add, for each
   premise kind, what its refutation records (expected, found, the side condition), and map the
   elaborator's `failure` sites onto the new rules. Mark the premises that depend on an earlier one (D3).
   Output: a table in this plan. No code.
2. **The cheap half.** Prove `inferElab-failure-sound : inferElab … ≡ failure err → ¬ (∃ derivation with
   usage)` as a corollary of completeness and determinism. It is a check that later steps must not weaken.
   It does not depend on the rule shapes, so it can be done before plan 0.151 if useful. Gate:
   `make certified`.
3. **Refutation types** (D1, D2, D3) in a new implementation-side module next to the Spec, with the theorem
   `refutes⇒¬derivable` per judgment, proved by inversion on the Spec's rules. One rule per form (0.151)
   makes the inversion direct. Gate: the module alone, inside the 3 GB / 50 s budget (D373).
4. **The elaborator returns refutations**, one judgment form at a time (synthesis, then checking, then
   domain-given), collecting all independent failures. `failure` carries the refutation; `TypeError`
   becomes a function of it (`errorOf : Refutation → TypeError`), so `renderError` and the tests are
   unchanged in each stage. The failure-soundness clauses go from `tt` to the refutation's proof. Gate per
   stage: `ElaborateSound`, `Completeness`, `make certified`, `cabal test` (texts unchanged).
5. **Messages from the evidence** (D5). The renderer reads the rule, the premise and the position from the
   refutation, with the optional sentence. Add the all-failures mode and the structured output. Retire the
   per-site `ErrorProofs` lemmas that this subsumes. The D368 tests pin rule names. A changed text is a
   modified expectation and gets a decision entry.
6. **Usage** (D4), as steps 3–5 for the core judgment's usage condition.
7. **Extraction, gates, decision entry**: re-extract MAlonzo, the exit tests on all three arches,
   `make merge-gate`, the AST dumps (the refutation proofs are type-checked, not extracted, D334. Check
   that RUNS ∖ PROVED does not grow).

Risk: `Elaborate` and `ElaborateSound` are already among the larger modules. Refutation proofs at every
failure site may push them over the per-module budget. Read the Agda perf catalog first, and split per
judgment form as `Completeness.Rules` / `Routes` do.

## 5. Done when

Every elaborator failure carries a refutation that is proved to rule out a Spec derivation, listing every
independent failure with the dependent ones marked blocked. Every rendered type error is computed from that
refutation and names a Spec rule, with the human sentence where one exists. No failure-soundness clause is
`tt`. Usage failures are the same. The structured output is available.
