# Plan 0.149 — A rejection carries the proof of which typing rule fails

## Summary

When the compiler refuses a program, it says why. Today that reason is chosen by hand at each place the
type checker gives up, and nothing checks that it is the real reason: a wrong message would still pass
every proof. This plan makes the type checker hand back, with each refusal, evidence that the program has
no typing in the language definition: for the expression where it fails, the rule that would type it and
the condition of that rule that does not hold. The message is printed from that evidence, so it names a
real rule of the language by construction, and a proof says the evidence is right.

## 1. Why

D407 made the messages name the rule a program breaks, but by hand: each `failure` in
`Once.TypeCheck.Elaborate` picks a `TypeError` variant, and failure soundness is `tt`. A message is held
in place only by a D368 test on one program. So a message can drift from the Spec silently: a new route in
the elaborator, a changed rule, or a variant reused at a new site, and the text names the wrong rule with
every proof still green. The Spec's typing relation is the language; the reason for a rejection should be
a fact about it, stated and proved, not a string the elaborator chose.

## 2. Where we are

Checked 2026-11-12 on `0.139-squashed` (251d46eea):

- The Spec's surface typing is three mutually defined judgments in `formal/Once/Spec/Surface/Typing.agda`
  (311 lines): synthesis `L ⊢ e ⇒ A ↝ t`, checking `L ⊢ e ⇐ A ↝ t`, and the domain-given form
  `L ⊢ e ⇐ A ⇒[ π ]↦ B ↝ t`; 53 rule constructors (`s-…`, `c-…`), e.g.
  `s-neg : L ⊢ e ⇒ Int ↝ t → L ⊢ RNeg e ⇒ Int ↝ prim p-neg t`. Usage (QTT) is a separate annotation,
  `Once.TypeCheck.Use` (`Use⇒ d Ψ`), not part of the Spec's judgment.
- The elaborator's results: `InferElabResult` / `CheckElabResult` (`Elaborate.agda:188`, `:195`), each
  `success … | failure : TypeError → …`. `TypeError` and `renderError` are in `Once.TypeCheck.Error`;
  after D407 every variant is produced.
- Soundness (`ElaborateSound`): a success is a Spec derivation. On failure it proves nothing (`tt`).
- Completeness (`Once.TypeCheck.Completeness`, plan 0.122): an expression the Spec types, with its usage,
  is accepted at the same type and usage. Its contrapositive already gives "a failure means there is no
  derivation with a usage". It does not say which rule, and it needs the usage side as well.
- `Once.TypeCheck.ErrorProofs` pins a few failure paths to their variants (e.g.
  `initial-app-infer-is-InitialInInferMode`), as equalities on the computed error, not as facts about the
  Spec.
- Program-level rejections (parse, resolution, the driver's Spec checks such as D323's "no type of its
  own") are outside the elaborator and outside this plan's first scope.

## 3. Decisions

- **D1, the form of the evidence.** (a) Refutation data: per judgment, a datatype `e ⊬⇒ …` whose
  constructors say "rule R would type `e`, and its premise P fails" (recursively, with the sub-refutation
  for the premise), and a theorem that it implies `¬ ∃ t. L ⊢ e ⇒ A ↝ t`. (b) Only the negation, with the
  `TypeError` chosen as today. Recommended: (a). With (b) the message is still hand-chosen, and the
  negation alone already follows from completeness (§2). Open.
- **D2, where the rule names live.** The Spec's rules are constructors with no printable name. (a) An
  implementation-side `RuleName` with the refutation constructors indexed by it, so the Spec does not
  change. (b) A Spec-side name per rule. Recommended: (a). MERGE.md allows a Spec change only for a
  language-level decision or a new observable, and a rule's name in an error message is neither. Open.
- **D3, several rules apply.** Bidirectional routes give an expression more than one candidate rule
  (`compose`'s two routes, D230; check mode falling back to synthesis). The evidence must refute every
  candidate. The message names one of them. Recommended: the one D407 names today (the first route that
  determined a type), so the texts stay, and the others go in the evidence for tooling. Open.
- **D4, usage.** QTT violations (`UsageViolation`) are about `Use`, not the typing judgment. (a) Same
  treatment, a refutation of `Use`, in a second phase. (b) Leave them as hand-chosen errors. Recommended:
  (a), after the typing side is done. Open.

## 4. Steps

1. **Inventory.** For each of the 53 rules, the failure sites in `Elaborate.agda` that reject an expression
   of its shape, and the `TypeError` each gives. Note the rules with more than one candidate (D3).
   Output: a table in this plan. No code.
2. **The cheap half first.** Prove `inferElab-failure-sound : inferElab … ≡ failure err → ¬ (∃ derivation
   with usage)` as a corollary of completeness and determinism. It costs little, and it is a check that
   later steps must not weaken. Gate: `make certified`.
3. **Refutation types** (D1, D2) in a new module next to the Spec, implementation-side, with the theorem
   `refutes⇒¬derivable` per judgment, proved by inversion on the Spec's rules. Gate: the module alone,
   inside the 3 GB / 50 s budget (D373).
4. **The elaborator returns refutations**, one judgment form at a time (synthesis, then checking, then
   domain-given). `failure` carries the refutation; `TypeError` becomes a function of it
   (`errorOf : Refutation → TypeError`), so `renderError` and the tests are unchanged in each stage. The
   failure-soundness clauses go from `tt` to the refutation's proof. Gate per stage: `ElaborateSound`,
   `Completeness`, `make certified`, `cabal test` (texts unchanged).
5. **Messages from the evidence.** `renderError` reads the rule and the failed premise from the
   refutation. Retire the per-site `ErrorProofs` lemmas that this subsumes. The D368 tests pin rule
   names. A changed text is a modified expectation and gets a decision entry.
6. **Usage** (D4), as steps 3–5 for `Use`.
7. **Extraction, gates, decision entry**: re-extract MAlonzo, the exit tests on all three arches,
   `make merge-gate`, the AST dumps (the refutation proofs are type-checked, not extracted, D334. Check
   that RUNS ∖ PROVED does not grow).

Risk: `Elaborate` and `ElaborateSound` are already among the larger modules. Refutation proofs at every
failure site may push them over the per-module budget. Read the Agda perf catalog first, and split
per judgment form as `Completeness.Rules` / `Routes` do.

## 5. Done when

Every elaborator failure carries a refutation that is proved to rule out a Spec derivation. Every rendered
type error is computed from that refutation and names a Spec rule. No failure-soundness clause is `tt`.
The usage side is the same, or D4 recorded (b).
