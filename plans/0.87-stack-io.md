# Plan 0.87 — Stack-resident IR inputs and outputs

## 0. Why this is its own plan

Plan 0.86 states the destination:

    IR inputs and outputs      -> stack, or REGISTERS for linear values that fit
    internal, bounded          -> frontier scratch
    internal, unbounded        -> heap, FREED BY THE IR ITSELF

Plan 0.2.4.5 stage G was scoped as a SIGNATURE change — "drop `AllocMode` from
IR signatures … naturally subsumed once F lands". Those are not the same thing,
and conflating them is what this split corrects.

Dropping the mode while keeping the heap lowering is behaviour-preserving and
costs nothing: `lea-slot` stays unemitted, `FrameFreeTrace` and `FlatStackPtr`
are untouched, and the flat<->concrete correspondence is not reopened. It even
RETIRES a postulate (see §2).

Moving I/O to the stack is a different thing entirely, and this plan prices it.

## 1. The cost, measured before starting

`lea-slot` is **the only instruction in the machine that creates a stack
pointer** (`Once.CCC.Machine.FrameFree`: "the ONE INSTRUCTION THAT CREATES A
STACK POINTER … nothing else in the machine does"). It is emitted only by the
stack-mode lowerings of `⟨_,_⟩`, `curry`, `inl`, `inr`.

Three things rest on it never being emitted:

  1. `FrameFreeI (lea-slot _) = ⊥` and `EmittableI (lea-slot _) = ⊥`.
  2. `FlatStackPtr`'s invariant, which is why it could be **collapsed to
     "there is no stack pointer"**.
  3. The flat<->concrete correspondence on ALL THREE architectures
     (X86-64, RiscV64, X86-32 — plan 0.65, D105/D106/D107), which runs over
     the heap-moded path.

So this plan's real content is: **re-prove the machine correspondence in the
presence of stack pointers.** That is the estimate. It is not a mode drop.

One piece of good news, established by experiment (2026-09-06): `lea-slot` does
NOT belong in `FrameFreeI`'s bottom set on the merits. That predicate means "no
instruction moves the frame", and the four `instr-*-stack` / `*-frame`
instructions are the only writers of `Registers.frame-slots` — `lea-slot`
writes a REGISTER. Admitting it there is honest, and it makes
`frame-free-trace'`'s pair case a PROOF rather than an absurd pattern (verified
green). The burden then lands where it belongs: a real pointer-bounds invariant
in `FlatStackPtr`, replacing the collapsed one.

## 2. The postulate this plan must retire, and must not falsify

`main-heap-moded : ∀ (ir : IR Unit Unit) → HeapModed ir` is a **postulate** in
all three arch modules. Since `IsHeap Stack = ⊥`, it is already FALSE for any
program containing a stack-mode node — the stack path was never covered by the
correspondence, it was assumed away. Same disease as the `trace-is-ir-to-trace`
gaps, one layer up.

  * Removing `AllocMode` while keeping heap lowerings makes `HeapModed`
    trivially true, so the postulate becomes a proof (or the predicate is
    deleted outright). **Do that first — it is a free win.**
  * Switching the lowerings to stack while `HeapModed` still means "heap"
    makes the postulate false. **Never land that state.**

The ordering constraint is therefore: finish the mode removal across every
constructor, retire `main-heap-moded`, and only then start moving lowerings.

## 3. Design constraint: the mode does NOT come back

D142 removed placement tags from the IR; 0.86's rule is that placement follows
from ROLE. A future second placement strategy must therefore live in the
**lowering layer** — one IR, with the decision made by the destination-passing
machinery stage F is building (`ResultPlace` / `InputPlace` / `Place`) — and
NOT as a revived `AllocMode` field on constructors. Keeping the structure
"general enough for a new alloc mode" means keeping the LOWERING pluggable, not
re-tagging the IR.

Concretely, the generality lives in:
  * `Place` — where the caller wants the result;
  * `InputPlace` / `ResultPlace` — where a value actually is;
  * `ir-to-trace'` — one clause per IR, reading the destination.

## 4b. BLOCKER discovered 2026-09-06 (D150) — read before stage E

`trace-is-ir-to-trace` cannot be closed for any slot-reserving handler until
`AllocState.next-slot` stops doing two jobs at once. At runtime it moves only
via `instr-alloc-stack`; at construction time it is the frontier `ir-to-trace'`
threads as `n`. They agree only because WF traces contain `instr-alloc-stack`,
which the emitter NEVER emits (`EmittableI (instr-alloc-stack _) = ⊥`).

Measured: the only handler that proves the field (`SimpleWF`) is the only one
that never mentions `instr-alloc-stack`. See D150 for the table.

There is a second, independent cause for COMPOSITE constructors: the WF trace
splices the opaque `IRResultAWF.trace` of a sub-result where the emitter has
`ir-to-trace' … f`. `RecDispatcherWF` must return the sub-result's own
`trace-is-ir-to-trace` so the `++` composes. This blocks `compose`, `pair`,
`case`, `apply` alike.

Both are prerequisites for this plan's stage E, and both are ALSO prerequisites
for closing any handler's correspondence under plan 0.86 stage G. They belong
to whichever plan gets there first; they are recorded here because stage E
cannot start without them.

## 5. What NOT to do

Do not begin E before A–D. The pair migration attempt on 2026-09-06 started at
E, and the divergence only surfaced because `frame-free-trace'` happened to have
an absurd pattern that stopped compiling. Had that clause not existed, a stack
lowering would have landed under a `trace-is-ir-to-trace` proof gap with the
correspondence still claiming no stack pointers exist.

That is the lesson worth carrying: **close the correspondence gap for a
constructor BEFORE changing its lowering**, so the typechecker — not a lucky
absurd pattern — is what catches the divergence.
