# Plan 0.74 — `Int` gets its width, and out-of-range literals are errors

**Status**: OPEN, written 2026-08-20. Follows plan 0.73 on branch
`plan-0.72-float-parameter` (or its successor).
**Implements D115.** Pays the D054/D059 width bill for `Int`.

## The two things, and why they are one plan

**1. The width is THREADED, not baked.** Fixing `Int`'s signed denotation
(`b2908563`) baked `Word64` into four modules that serve all three targets,
one of which is 32-bit. Right about signedness, wrong about width.

**2. An out-of-range literal is a TYPE ERROR.** `2001` does not compile on an
8-bit target; the signed range is `−2^(w−1) … 2^(w−1)−1`, so `127` is the
largest. Not a warning — Once has no warning channel — and not a silent wrap.

They are one plan because the check needs the width and the denotation needs
the width, and there is exactly one place the width should come from.

## WHERE A LITERAL BECOMES A MACHINE WORD — the architecture question

Raised 2026-08-21. Recorded because it was nearly decided twice on wrong
grounds, once in each direction.

### Two claims of mine that were wrong, corrected first

**"There are 21 conversion sites."** There are FOUR: `SMCore.lit-value`
(abstract) and the three per-arch emitters. The other ~17 modules MENTION
`lit-value` in a statement or proof — they are the obligation that the four
agree, not four more chances to get it wrong. Counting obligations as defects
inverts their purpose.

**"D054 says the payload must not be a `ℤ`."** It does not. What D054 killed
was TWO DENOTATIONS with a bridge between them — `semI : ℤ` alongside
`semM : Word`, and proofs that they agree under a no-overflow side condition.
There is one denotation now (`⟦ Int ⟧ = Carrier`), no decode direction, and no
agreement proof between value levels. A literal's PAYLOAD being source syntax
is not that bridge — it is exactly the payload/denotation distinction D113
drew for `Float`, and failing to apply it to `Int` is the same error D112 made.

### The actual question

The pipeline is lexer → parser → typechecker → elaborator → arith → codegen.
A literal starts as digits and ends as a machine word. WHERE does it convert?

**Late (the machine/backend converts).** The frontend stays generic; the IR
carries source syntax; `lit-value` and the emitters apply the target's width
and format.

**Early (the frontend converts).** The elaborator takes the target's numerics
and the IR carries machine words.

### Why LATE is right

**1. It keeps the arch out of the IR's TYPE.** Converting early makes the IR
arch-specific in fact but not in type: nothing stops an IR built for x86-32
being compiled for x86-64, and the only real fix is to index `IR` by the arch —
which infects every IR-mentioning signature in the codebase. Late conversion
localises arch-dependence to the boundary that ALREADY carries a per-arch
record (`FrameSemantics`).

**2. It matches how target-dependent widths are handled elsewhere.** Once's
`Int` is "the target's word", like Rust's `isize` or C's `intptr_t` — not like
C's `int`, whose width the LANGUAGE fixes. Compilers with a language-fixed
width do bake it early; compilers with a target-fixed width carry the literal
typed and lower it at codegen. Rust's MIR does exactly this.

**3. The frontend's proofs stay target-free.** `checkElab` soundness and
completeness, `realize-agrees`, `faithful` — none of them gains a parameter,
and none of their lemmas has to be re-stated per target.

### What LATE owes, and how it pays

**The obligation must be STATED, never conventional.** `ArithSimX86-32` is the
warning: it opens `Word64` in an x86-32 module whose machine wraps at 2^32, and
nothing caught it because nothing said the two must agree. Late conversion is
only safe where the agreement is a premise discharged by `refl` — `bits-eq`
(derived from `word-eq`) and `fmt-agree` (compares the whole `TargetNum`). H5
must bring the arith path under the same discipline or it will rot again.

### Where the RANGE CHECK goes — and a `supportedWidths` list is NOT the answer

**A rejected proposal, recorded so it is not retried.** I suggested the
frontend check a literal against a `supportedWidths` list, mirroring
`accept?`'s `supportedFormats`. That is backwards coupling of the same kind as
indexing `IR` by the arch: it makes the FRONTEND depend on which BACKENDS
exist, so adding a narrow target retroactively rejects programs that were fine
for every existing one.

**And it is not hypothetical — the float side has this defect TODAY.**
`16777217.0` is exactly representable at `binary64` and NOT at `binary32`
(verified: it does not round-trip through a 32-bit float). Once rejects it, so
you cannot write it even when targeting x86-64, purely because a 32-bit backend
exists. The error message states the rationale outright:

> "Once accepts only literals exact at every target's float format — `Float`'s
> width is a target property, so a rounded literal would denote a different
> number on different machines."

**D113 removed that rationale.** The meaning is now arch-indexed; a literal
DOES denote different bits on different machines, and that is correct rather
than a problem. What matters is that at EACH target it denotes the right value
FOR that target. The rule outlived its reason.

(Separately, `16777216.0` = 2^24 is exact at `binary32` too and is ALSO
rejected — that is the unnormalised-significand conservatism already recorded
in HANDOFF, a second and independent over-restriction.)

### The design: each backend lowers, with a PARTIAL conversion

The backend knows its width; let it do the check where the fact lives:

    inRange? : (bits : ℕ) (z : ℤ) → Dec (InRange bits z)
    toWord   : (bits : ℕ) (z : ℤ) → InRange bits z → Word

A decision plus evidence plus a total conversion under that evidence — rather
than `ℤ → Either String Word` — because it keeps `fromℤ`'s wrap from ever
being reachable as semantics, and because it is provable. It is also EXACTLY
the shape `accept?` already has (`representableAt?` / `RepresentableAt` /
`encode`), so for `Float` this is a MOVE, not a build.

**The consequence to accept deliberately: the meaning is PARTIAL per target.**
A program whose literal does not fit the target has no meaning THERE. That is
already the apex's shape — `⟦_⟧⊥ : Source → Arch → Maybe Behavior` — so
rejecting such a program is consistent with the completeness conjunct ("if
`src` has a meaning, the compiler accepts it"): it has none at that target.

**This refines D115.** The error is a compile-time error raised during
LOWERING, not a TYPE error. It cannot be a type error: the constraint is
genuinely target-specific and the type system is target-generic — which is the
whole reason the frontend must not know the width. D115's "type error" should
be read as "rejected at compile time, never silently wrapped".

**What this costs elsewhere:** `accept?` should move to the backends by the
same argument, which is a change to landed 0.71/0.72 work (the `Accepted`
evidence carried in `g-float` derivations, `accept?-complete`, and the
frontend's float error path). Flagged, not scheduled — but "Ints and Floats
are handled the same way" cuts both ways, and leaving the float check in the
frontend while the int check is in the backend would be the incoherent
outcome.

### The two types, side by side — identical by construction

| | `Float` (landed) | `Int` (this plan) |
|---|---|---|
| IR payload | `Dyadic` | `ℤ` |
| frontend check | `accept?` — exact at every supported FORMAT | in range at every supported WIDTH |
| materialised by | `encode (float-format FS)` | `fromℤ (8 * frame-word FS)` |
| per-arch pin | `fmt-eq`, `fmt-agree` | `bits-eq` (derives from `word-eq`) |
| frontend knows the target? | no | no |

"Handled the same way" is not an aspiration here; it is the same four rows.

## The template already exists — do not design a new one

Plan 0.73 threaded the target's FLOAT FORMAT end to end. Every piece has an
`Int` analogue, and the shapes are known-good:

| Float (landed, 0.73)                    | Int (this plan)                        |
|-----------------------------------------|----------------------------------------|
| `arch-float-format : Arch → FloatFormat` | the width's analogue — see below       |
| `FrameSemantics.float-format`            | **already there**: `8 * frame-word FS` |
| `LitPayload fits-float = Dyadic`         | `LitPayload fits-int = ℤ`              |
| `lit-value fits-float d = encode fmt d`  | `lit-value fits-int z = fromℤ bits z`  |
| `fmt-eq  : float-format FS ≡ binaryNN`   | the width's analogue, per arch         |
| `fmt-agree : float-format FS ≡ arch-…`   | likewise, between the two channels     |
| `accept? ` rejects `3.14`                | an integer sibling rejects `2001`      |

**ONE map, not two.** `⟦_⟧ˢ` already threads a `FloatFormat`; widen that
parameter to a target-numerics record carrying BOTH the int width and the
float format, rather than adding a second parallel channel. The threading is
already in place — only the parameter's TYPE and its handful of use sites
change, so this is much cheaper than 0.73's was.

## Sequencing — TOP-DOWN, same rules as 0.73

Read plans/0.73 §"How this plan is sequenced". Same six rules; they worked.

### H0 — change the top-level statements, then STOP and read the red
  (a) the threaded target parameter becomes the numerics record;
  (b) `LitPayload fits-int = ℤ` — the payload is SOURCE SYNTAX, as `Float`'s
      is, so the elaborator stops needing a width it cannot know.
Then typecheck the apex roots and write the red list into HANDOFF.

### H1 — the width reaches the machine
`lit-value fits-int z = fromℤ (8 * frame-word FS) z`. No new `FrameSemantics`
field: `frame-word` is 8/4/8 bytes and already a parameter of the machine.

### H2 — the width reaches the meaning
`⟦ int n ⟧ˢ` / `⟦ g-int n ⟧ᵍ` / `⟦ t-int n ⟧ᵢ` use `fromℤ (int-bits …) n`, and
the `Word64` bake in `Denotation/Meaning` and `Denotation/SourceDenote`
disappears. This is the cheap half — the parameter is already threaded.

### H3 — codegen materialises the literal
Each arch's `compile-const fits-int` emits `imm (fromℤ bits z)` at its own
width, mirroring what `compile-const fits-float` already does with `encode`.

### H4 — the RANGE CHECK, and it is a real error
An integer sibling of `Once.Float.Representable.accept?`: a literal is
accepted iff it lies in the target's signed range. Target-blind like
`accept?` (representable at EVERY supported target) keeps a literal's
ACCEPTANCE arch-free — note this does NOT make its VALUE arch-free, since
`−5` is `2^w − 5` and still width-relative. The frontend must report a real
error, with the offending literal and the bound.

### H5 — the arith path, and it is NOT all arch-specific

**Surveyed 2026-08-20, after H0–H3 landed.** Every remaining `Word64` is in
the arith path, but "in the arith path" does not mean "harmless":

| site | verdict |
|---|---|
| `Adequacy/CPU/X86-64` | FINE — x86-64 really is 64-bit |
| `ArchCorrectness/ArithSimRiscV64` | FINE — riscv64 really is 64-bit |
| `Arith/SigOp/Builders` | **GENERIC** — `add-info` etc. are closed `SigOpInfo`s shared by all three targets |
| `Arith/SigOp/Block` | **GENERIC** — `block-semM`, likewise |
| `Arith/SigOp/BlockSemBridge` | **GENERIC** — likewise |
| `ArchCorrectness/ArithSimCore` | **GENERIC** — the name says so; the shared correspondence core opens `Word64`'s ops |
| `ArchCorrectness/ArithSimX86-32` | **WRONG WIDTH** — see below |

**The one to look at first.** `ArithSimX86-32.agda:45` is `module W =
OnceWord.Word64`, and it is LOAD-BEARING: `val-x86-32` — the concrete x86-32
arith interpreter the correspondence is stated over — computes
`rd s d W.⊕ rd s src` and `W.fromℤ z` with 64-bit operations. Meanwhile
`CCC/Target/X86-32/Semantics.agda:33` is `module W = W32.Width 32`, so the
MACHINE wraps at 2^32. An arch-specific module is modelling its own target at
the wrong width. Establish whether the two ever meet before assuming this is
merely cosmetic.

**Then the generic ones.** `SigOpInfo`'s `semM` is a CLOSED function, so
threading a width means the arith descriptors gain one, which ripples into the
elaborator that builds them. That is the D059 bill proper and the reason this
phase is last.

### H5b — the original scoping note, kept
`add-semM`/`sub-semM`/`mul-semM`/`neg-semM` bake `Word64`, as `block-semM`
always has. `SigOpInfo`'s `semM` is a CLOSED function, so threading a width
means the arith descriptors gain one. Largest phase; do it last, and only
after H0–H4 have shown the shape.

## Tests that already exist and must keep passing

`TraceSpec`'s three negative-argument cases (`-5`, `3 - 8`, mixed signs) pin
the machine's behaviour, and `signedAt` reads a trace word as the signed value
it represents. They pass today; they are the regression net for all of the
above. `FloatEmitSpec` is the model for a per-arch value test that stays
general — expectations DERIVED from an arch table, never transcribed.

New tests this plan owes:
  * an out-of-range literal is REJECTED (the `accept?`-style acceptance suite
    already has the shape — see `FloatSpec`'s `accepts`/`rejects`);
  * a negative argument observed on ALL THREE arches, not just x86-64, which
    `buildAndRunTraceOn` now makes possible and which would have caught a
    width divergence between the denotation and the machine.

## Done means

No module that serves more than one target names a width. An `Int` literal
outside the target's signed range is a compile error naming the literal and
the bound. `−5` denotes `2^w − 5` at the target's `w`, and the machine agrees
on all three arches.
