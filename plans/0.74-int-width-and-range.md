# Plan 0.74 — `Int` gets its width, and out-of-range literals are errors

**Status**: OPEN, written 2026-08-20. Follows plan 0.73 on branch
`plan-0.72-float-parameter` (or its successor).
**Implements D115.** Pays the D054/D059 width bill for `Int`.

## The two things, and why they are one plan

**1. The width is THREADED, not baked.** Fixing `Int`'s signed denotation
(`b2908563`) baked `Word64` into four modules that serve all three targets,
one of which is 32-bit. Right about signedness, wrong about width.

**2. An out-of-range literal is a TYPE ERROR.** `2001` does not compile on an
8-bit target; the signed range is `−2^(w−1) … 2^(w−1)−1`, so `127` is the
largest. Not a warning — Once has no warning channel — and not a silent wrap.

They are one plan because the check needs the width and the denotation needs
the width, and there is exactly one place the width should come from.

## The template already exists — do not design a new one

Plan 0.73 threaded the target's FLOAT FORMAT end to end. Every piece has an
`Int` analogue, and the shapes are known-good:

| Float (landed, 0.73)                    | Int (this plan)                        |
|-----------------------------------------|----------------------------------------|
| `arch-float-format : Arch → FloatFormat` | the width's analogue — see below       |
| `FrameSemantics.float-format`            | **already there**: `8 * frame-word FS` |
| `LitPayload fits-float = Dyadic`         | `LitPayload fits-int = ℤ`              |
| `lit-value fits-float d = encode fmt d`  | `lit-value fits-int z = fromℤ bits z`  |
| `fmt-eq  : float-format FS ≡ binaryNN`   | the width's analogue, per arch         |
| `fmt-agree : float-format FS ≡ arch-…`   | likewise, between the two channels     |
| `accept? ` rejects `3.14`                | an integer sibling rejects `2001`      |

**ONE map, not two.** `⟦_⟧ˢ` already threads a `FloatFormat`; widen that
parameter to a target-numerics record carrying BOTH the int width and the
float format, rather than adding a second parallel channel. The threading is
already in place — only the parameter's TYPE and its handful of use sites
change, so this is much cheaper than 0.73's was.

## Sequencing — TOP-DOWN, same rules as 0.73

Read plans/0.73 §"How this plan is sequenced". Same six rules; they worked.

### H0 — change the top-level statements, then STOP and read the red
  (a) the threaded target parameter becomes the numerics record;
  (b) `LitPayload fits-int = ℤ` — the payload is SOURCE SYNTAX, as `Float`'s
      is, so the elaborator stops needing a width it cannot know.
Then typecheck the apex roots and write the red list into HANDOFF.

### H1 — the width reaches the machine
`lit-value fits-int z = fromℤ (8 * frame-word FS) z`. No new `FrameSemantics`
field: `frame-word` is 8/4/8 bytes and already a parameter of the machine.

### H2 — the width reaches the meaning
`⟦ int n ⟧ˢ` / `⟦ g-int n ⟧ᵍ` / `⟦ t-int n ⟧ᵢ` use `fromℤ (int-bits …) n`, and
the `Word64` bake in `Denotation/Meaning` and `Denotation/SourceDenote`
disappears. This is the cheap half — the parameter is already threaded.

### H3 — codegen materialises the literal
Each arch's `compile-const fits-int` emits `imm (fromℤ bits z)` at its own
width, mirroring what `compile-const fits-float` already does with `encode`.

### H4 — the RANGE CHECK, and it is a real error
An integer sibling of `Once.Float.Representable.accept?`: a literal is
accepted iff it lies in the target's signed range. Target-blind like
`accept?` (representable at EVERY supported target) keeps a literal's
ACCEPTANCE arch-free — note this does NOT make its VALUE arch-free, since
`−5` is `2^w − 5` and still width-relative. The frontend must report a real
error, with the offending literal and the bound.

### H5 — the arith `semM` family, the D059 bill proper
`add-semM`/`sub-semM`/`mul-semM`/`neg-semM` bake `Word64`, as `block-semM`
always has. `SigOpInfo`'s `semM` is a CLOSED function, so threading a width
means the arith descriptors gain one. Largest phase; do it last, and only
after H0–H4 have shown the shape.

## Tests that already exist and must keep passing

`TraceSpec`'s three negative-argument cases (`-5`, `3 - 8`, mixed signs) pin
the machine's behaviour, and `signedAt` reads a trace word as the signed value
it represents. They pass today; they are the regression net for all of the
above. `FloatEmitSpec` is the model for a per-arch value test that stays
general — expectations DERIVED from an arch table, never transcribed.

New tests this plan owes:
  * an out-of-range literal is REJECTED (the `accept?`-style acceptance suite
    already has the shape — see `FloatSpec`'s `accepts`/`rejects`);
  * a negative argument observed on ALL THREE arches, not just x86-64, which
    `buildAndRunTraceOn` now makes possible and which would have caught a
    width divergence between the denotation and the machine.

## Done means

No module that serves more than one target names a width. An `Int` literal
outside the target's signed range is a compile error naming the literal and
the bound. `−5` denotes `2^w − 5` at the target's `w`, and the machine agrees
on all three arches.
