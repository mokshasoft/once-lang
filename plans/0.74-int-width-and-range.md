# Plan 0.74 — literals are lowered by the BACKEND, and out-of-range is an error

**Status**: OPEN, rewritten 2026-08-21 after the architecture was settled.
Follows plan 0.73 on branch `plan-0.72-float-parameter` (or its successor).
**Implements D115** (as refined below) and **corrects `accept?`**.

## The rule, in one line

**The frontend is target-generic. Each backend lowers a literal at its own
width/format, and rejects what it cannot represent.**

The ARCHITECTURE is identical for `Int` and `Float`. The FAILURE MODES are
not, and D116 says why: an `Int` literal must FIT or it is an error, while a
`Float` literal always lowers — it ROUNDS. **This plan is therefore the `Int`
half only.** Floats are not touched; see "what this plan does NOT do".

---

## What is already landed (the width threading)

Committed `d7a7aef5`, gate green. The literal payload is SOURCE SYNTAX at both
numeric types and the machine materialises it:

    LitPayload fits-int   = ℤ          LitPayload fits-float = Dyadic
    IR.const : … → ⟦ ℤ , Dyadic ⟧-baseI A → IR Unit A
    intLit n = const fits-int n ∘ terminal          -- converts NOTHING
    lit-value fits-int z = fromℤ (8 * frame-word FS) z
    lit-value fits-float d = encode (float-format FS) d

`TargetNum` (`Once.Target.Arch`) carries the width and format together;
`fs-numerics FS` derives them from facts the machine already had
(`frame-word`, `float-format`); `fmt-agree` pins the machine's view to the
apex's; `bits-eq` derives from `word-eq`.

**This plan does not revisit any of that.** It adds the missing half: nothing
yet REJECTS a literal the target cannot hold.

---

## Three rejected designs, recorded so they are not retried

**A `supportedWidths` list in the frontend.** Backwards coupling: the frontend
would depend on which BACKENDS exist, so adding a narrow target retroactively
rejects programs that were fine for every existing one. Not hypothetical —
`accept?` does this today and `16777217.0` (exact at `binary64`, not at
`binary32`) cannot be written even when targeting x86-64. Its error message
gives the rationale — "a rounded literal would denote a different number on
different machines" — and **D113 removed that rationale**: the meaning is
arch-indexed now, so denoting different bits on different machines is correct.

**Converting in the frontend (arch-aware elaboration).** Makes the IR
arch-specific in fact but not in type; the only real fix is indexing `IR` by
the arch, which infects every IR-mentioning signature. Also throws away a
target-free elaborator and target-free frontend proofs.

**A partial denotation (`⟦ int n ⟧ˢ` returns `Maybe`).** Rejected on the
principle the codebase already follows once: an ill-typed program does not get
a `nothing` meaning, it is excluded by `Typed`, and `⟦_⟧ˢ` is TOTAL behind that
gate. "Does 1001 fit in 8 bits" is the same kind of question — static,
decidable, about EXPRESSIBILITY, not about what the program computes — so it
belongs with well-formedness. Making `⟦_⟧ˢ` `Maybe`-valued would stack a
second monad, whose failures have nothing to do with values, on top of the
trace monad `T`, and every structural clause would thread it.

## The design

### Two well-formedness judgments, and the layering says something true

    Typed        — target-FREE.     The type system. Unchanged.
    Admissible   — target-RELATIVE. New. "this typed program can be
                   expressed at this target"

`Admissible arch tp` holds iff every `Int` literal in `tp` is in range at
`arch-int-bits arch`. Decidable, structural, and IN THE SPEC. **Float literals
place no condition on it** — they always lower (D116).

**Why it must be in the spec, not merely implemented.** Without an
admissibility predicate in the meaning, a compiler that rejects EVERY program
satisfies soundness vacuously; only completeness rules it out, and completeness
is stated against the meaning. So the meaning has to say which programs are
admissible at a target, or "reject everything" is a correct compiler.

`⟦_⟧ˢ` stays TOTAL. `fromℤ`'s modulus reduction remains a totality device that
no admissible program can reach.

### What is checked, and what is not (D116)

| literal | at this target | outcome | where |
|---|---|---|---|
| `1001` | doesn't fit 8-bit signed | **compile error** | backend, `InRange` |
| `1001` | fits 16-bit | lowers | backend |
| `100 + 100` overflows | — | **wraps, no error** | nowhere — D054, arithmetic is modular by promise |
| `3.14` | not dyadic at any format | **rounds** (warn) | backend — NOT this plan |
| `16777217.0` | exact at `binary64` | lowers exactly | backend — NOT this plan |
| `16777217.0` | not exact at `binary32` | **rounds** (warn) | backend — NOT this plan |

`Int` has no target-free constraint at all — every `ℤ` fits SOME width — so it
gets no frontend check. `Float` needs no gate either, because it never fails.
The admissibility judgment below is consequently **`Int`-only**.

### What this plan does NOT do — and why not

**It does not touch `accept?`.** Under D116 that rejection is an INTERIM,
"sound but incomplete", and it is scheduled for DELETION once rounding lands.
An earlier draft of this plan moved it to the backend for symmetry. That was
wrong twice over: it would relocate something about to be removed, and it would
keep rejecting `16777217.0` on x86-32 where the design says ROUND.

**So `16777217.0` stays rejected on every target until the rounding work.**
That is a known, dated interim, not this plan's business. The fix is rounding,
not a per-target representability check.

The float half is phases K1–K4 below. It is sequenced AFTER the `Int` half
because it is strictly larger and because J0–J4 establish the shape it reuses.

### The vocabulary, mirrored

    InRange  : ℕ → ℤ → Set
    inRange? : ∀ bits z → Dec (InRange bits z)
    toWord   : ∀ bits z → InRange bits z → Word

Decision + evidence + total conversion under evidence — not `ℤ → Either String
Word`. It keeps `fromℤ`'s wrap unreachable as semantics, and it is provable.

(`Float`'s counterpart is `round`, which is TOTAL and therefore needs no
decision and no evidence — the whole point of D116.)

### THE ONE THING THAT MUST NOT ROT

**The admissibility gate and the codegen must dispatch on the SAME decision
procedure**, not two implementations that happen to agree. `ArithSimX86-32` is
the standing warning: it opens `Word64` in an x86-32 module whose machine wraps
at 2^32, and nothing caught it because nothing SAID the two must agree.

### K0 — the finding that sizes the float half: THE PAYLOAD IS WRONG

**`3.14` is not a `Dyadic` at all.** `3.14 = 157/50`, and 50 is not a power of
two, so no dyadic rational equals it. `accept?` rejects it at the EXACTNESS
step, before representability is even consulted.

That has a structural consequence 0.73 did not face, because 0.73 only ever
handled literals that WERE dyadic: if `3.14` must reach the backend, the
literal's payload cannot be a `Dyadic`. **It must be the DECIMAL the programmer
wrote** — the `(i , f , l)` triple the lexer already produces.

    LitPayload fits-float = Dyadic        -- today; cannot hold 3.14
    LitPayload fits-float = Decimal       -- K1; holds every literal

This is the same principle that made `Int`'s payload a `ℤ`: the payload is
SOURCE SYNTAX, and source syntax for a float literal is a decimal, not a
dyadic. `Dyadic` was source syntax only for the subset that happened to be
exact — which is exactly the subset `accept?` was restricting us to.

**The payload type — mirror `Dyadic` at base ten:**

    record Decimal : Set where
      constructor _/10^_
      field
        sig   : ℤ      -- SIGNED, so -0.5 is `-5 /10^ 1`
        exp10 : ℕ

`Dyadic` is `sig /2^ shift`; this is the same record in base ten, and it holds
EVERY decimal literal EXACTLY — `3.1` is `31 /10^ 1`, no rounding. That is the
property being bought: with an exact payload there is exactly ONE rounding, at
the backend, at the target's format. `Dyadic` cannot do this (`31/10` keeps a
factor of 5 forever, which is why `accept?` rejects `3.1`), and neither can any
binary payload.

**Two alternatives, both rejected, and why:**

  * **Agda's `Float`.** It would force a rounding BEFORE the backend's, so a
    literal is rounded twice. For binary32-via-binary64 that happens to be
    harmless (Figueroa: an intermediate of `p₂` bits is innocuous for a `p₁`-bit
    target when `p₂ ≥ 2p₁+2`, and 53 ≥ 50) — but it CAPS PRECISION at the
    payload's format, so a binary128 or x87-extended target could never be
    served correctly. It is also D109/D112's exact mistake — a format baked
    where all targets must be served — and `primFloatToWord` is a primitive
    with no equational theory, which is what left D109's encoder's faithfulness
    unstateable in the first place.
  * **`(ℤ , ℕ)` — integer part and fraction part.** Two defects, the second
    silent: `3.14` and `3.014` both give `(3 , 14)` unless the DIGIT COUNT is
    carried too (which is why `RawExpr.RFloat` carries three numbers); and
    `-0.5` has integer part `-0 = 0`, so THE SIGN IS LOST. Putting the sign on
    the significand instead of the integer part is what avoids this.

**Bonus: this subsumes most of plan 0.73's F3.** Negative float literals are
just a negative `sig`, so the parser's fold is a negation rather than new
machinery.

**Caveat to state, not to rely on:** unnormalised, so `0.5` and `0.50` are
distinct records (`5 /10^ 1` vs `50 /10^ 2`) — the same non-normalisation
`Dyadic` already documents. They must round to the same word; that is a lemma
to prove, not a coincidence to assume.

### K1 — `round`, and why it is the hard kernel

    round : FloatFormat → Decimal → Word

Decimal-to-binary conversion with correct rounding — the `strtod` problem. It
is known-subtle and it is the reason this half is not a footnote: a naive
"divide and truncate" is wrong for exactly the inputs that motivated the
change. Round-to-nearest-EVEN, and the carry out of the significand can
increment the exponent (`1.111…1` rounds to `10.000…0`).

`encode` today TRUNCATES — `sigFieldN`'s `modPow … (sig-bits F)` drops the low
bits — and is correct only because `accept?` guarantees nothing is there to
drop. `round` subsumes it, and must agree with it on exact inputs.

**What compiler correctness actually needs is small.** Both the denotation and
the codegen call the SAME `round`, so the correspondence is `refl`-shaped and
needs no rounding theorem. What a rounding theorem buys is that `round` is the
RIGHT function — IEEE round-to-nearest-even — which is a SPEC-quality question,
not a compiler-correctness one.

**So state it as a NAMED obligation, D114's lesson applied.** `round`'s
IEEE-conformance is a trust point of the same kind as `assemble-correct`: named,
visible to `make postulates`, and dischargeable later. What must NOT happen is
the version where nobody states it and the compiler is "correct" about a
rounding nobody checked — that is `emit`'s low byte again.

### K2 — the exponent range: ±∞ and subnormals

`accept?`'s other two conditions are `exp-lo` and `exp-hi` — the value must
land in the NORMAL exponent range. Deleting them means answering what happens
outside it, and IEEE's answers are subnormals below and ±∞ above. Whether Once
models infinities at all is a real question and NOT settled by D116; if the
answer is no, then the exponent bounds stay as errors while the significand
bound becomes rounding, and that split must be stated rather than discovered.

Do K2 only after K1 has landed, so the two failure modes are not conflated.

### K3 — delete `accept?`'s representability half

`RepresentableAll` / `supportedFormats` / the `Accepted` witness carried in
`g-float` go. `ExactDecimal` goes too — under rounding there is nothing to be
exact about. Expect the red where the witness was carried:
`accept?-complete`, `checkG-RFloat-aux`, the `RealizeAgrees`/`Completeness`
float rows. `16777217.0` compiles everywhere after this: exactly on the 64-bit
targets, rounded on x86-32.

### K4 — the WARNING CHANNEL, and it reports the ERROR

Once has none, and its absence is why the interim rejection exists. Proposed
shape: warnings are a PURE QUERY over the module at an arch —

    roundingWarnings : Arch → Module → List Warning

— NOT an effect threaded through `compile`. Warnings do not change what is
compiled, so they must not change the pipeline's type; keeping them a separate
observation is what stops them leaking into `correct`.

**The warning carries the ERROR, exactly.** With an exact `Decimal` payload and
an exact dyadic result, the difference is an exact rational and needs no
floating point to compute:

    error = stored − sig/10^exp10        -- both sides exact

Report the STORED VALUE, the ABSOLUTE ERROR, and the error in ULPs. Leading
with absolute is deliberate — here is `3.1` at three formats:

| format | stored as | absolute error | ulps |
|---|---|---|---|
| binary64 | `3.1` | +8.9e-17 | +0.2 |
| binary32 | `3.0999999046325684` | −9.5e-08 | −0.4 |
| 4-bit significand | **`3.0`** | **−0.1** | −0.4 |

The ULP figure is ~0.4 in ALL THREE. **A ulp-only warning would hide exactly
the case that matters** — a 3% error on a narrow target — which is the case a
warning exists for. Report both; lead with absolute.

### J6 — a negated numeral must be ONE literal (found by J4's tests)

**`-2147483648` is refused on x86-32, and it fits.** The compiler says "Int
literal 2147483648 does not fit x86-32's signed 32-bit range" about a program
whose only value is the least `Int` that target has. A program the target CAN
express is rejected — the one failure mode `correctR-complete` exists to rule
out — and the proof does not catch it because the SPEC shares the blind spot,
exactly as both sides of the observable shared `isInt?` before D114.

**The cause is upstream of the gate.** `Once/Parser/Expr.agda:1012` parses `-N`
as `RUnaryOp OpNeg (RInt N)`, so the only literal in the tree is the MAGNITUDE.
Nothing folds the sign back in: the elaborator has no constant folder. The
machine therefore materialises 2147483648 at 32 bits, `lit-value`'s `fromℤ`
WRAPS, and a wrapping literal is what D115 forbids. **So the gate is right and
the AST is wrong** — as elaborated, this program really does need an
unrepresentable literal. The defect is that it should not have to.

Note the IR is not the obstacle: `Once/IR.agda`'s `const` already carries a
`ℤ`, so it can hold `-2147483648`. It simply never does.

**WHERE THE TRUTH GOES — SETTLED, do not re-litigate.** Not the parser. At the
level of GRAMMAR `-` really is a prefix operator and `Parser/Expr.agda` is
right to say so; making `ParsesUnary` fold would need either an ambiguous
relation (both `pu-neg` and a `pu-neg-lit` apply when the operand is `RInt`) or
a function in the constructor's conclusion index, which breaks downstream
pattern matching. What a negative NUMERAL means is a fact about the LANGUAGE,
so it is stated in the SPEC and the front end bridges to it.

**Half 1 LANDED** — `Once.Denotation.Admissible` now says it:

    negLits (RInt n) = (- n) ∷ []
    negLits e        = rawIntLits e

deliberately narrow (minus applied DIRECTLY to a numeral; `- x`, `- (a + b)`,
`- (- 5)` stay arithmetic and wrap). `ResolverLits` gained the obligation this
creates — `negLits` asks a question `rawIntLits` does not, namely "is this
operand a numeral", so the resolver must preserve that and not merely preserve
the literals. It does, bluntly: `canonExpr` only rewrites names and rebuilds
every other node with its own head. Pinned meanwhile by `LitRangeSpec`'s
`negatedLiteralDefect` group, which asserts the CURRENT behaviour and fails the
day the fold lands.

**A CLAIM THAT WAS IN THIS PLAN AND IS FALSE, corrected here so it is not
reused.** It used to say "semantically either is sound: `⊝ (fromℤ n) ≡ fromℤ
(- n)`, because `fromℤ` is a ring hom onto ℤ/2^w". That is true of `Width w`'s
own `⊝`. It is NOT the obligation the fold actually incurs, because the
elaborated negation is not `Width w`'s `⊝` — it is a SigOp whose semantics is
baked at 64 bits. See "J6 step 3" and "J5" below; the real obligation is false
at `w = 32` and J5 is what makes it true.

### J6 half 2 — THE EVIDENCE MUST BE CONSUMED, and that is the larger half

Landing half 1 turned nothing red, and THAT is the finding. The apex accepted
a changed admissibility predicate after one local proof repair, because nothing
downstream consumes it:

  * `lit-value` (`SMCore.agda:1646`) takes no evidence and calls `fromℤ` raw;
  * `Once.Word.Width.toWord`, the evidence-taking conversion J2 built for
    exactly this, was called from NOWHERE;
  * the only `InRange` uses outside the spec were two `subst`s in
    `Compile.agda` that carry the witness across resolution and then drop it.

**So the gate was decorative with respect to the machine.** It refused
programs, but nothing forced an accepted program's literals to materialise
faithfully. A compiler could accept `2147483648` at 32 bits and silently mean
`-2147483648`, and no proof in the tree would object.

**The fix, in the shape of "carry the map, don't postulate it":**
`instr-load-const` (and the IR's `const`) must DEMAND the `InRange` witness at
the target's width, so `lit-value` cannot be called without one. The IR is
arch-generic, so the witness cannot live in the IR — it is supplied at LOWERING
time from the admissibility witness, which means the pipeline carries
`AdmissibleM` into codegen instead of discarding it at the gate.

Then `-2147483648` becomes a type error in the right place: the spec says it is
admissible, the elaborator hands codegen `const 2147483648`, and the arch
cannot produce `InRange 32` for it. The red lands on the elaborator, which is
where the bug is — the frontend fold becomes FORCED rather than chosen.

**It also collapses J5 into this obligation.** `BlockSemBridge.toWord` is
`Word64.fromℤ` at every int leaf, unchecked, on all three targets. Same missing
proof, one layer down — and `Word64` has no business in code shared by three
targets. Once literals can only be lowered under evidence at the TARGET's
width, the bake cannot survive.

### What step 2 actually proved: `correct` is FALSE, and that is the finding

Threading the IR gate up stopped at `correct-gm-adm`, one lemma below
`correct` — the grand theorem, stated UNCONDITIONALLY. It cannot be threaded
without making the top-level claim conditional on a premise that is currently
false, so it was left red rather than weakened by stealth. For `src`
containing `-2147483648` at x86-32:

    compile arch doOpt src  =  nothing      -- the IR gate refuses
    ⟦ src ⟧⊥ arch           =  just ⟦ir⟧    -- the source gate accepts

and `Pointwise _≋_ nothing (just _)` is false. The theorem this project exists
to hold does not hold for a compiler whose elaborator turns a representable
literal into an unrepresentable one. **The gate did not break it. The gate made
it visible.**

`ElabPreservesLits` is stated as a PREMISE and not postulated, deliberately:
the counterexample above is explicit, so postulating it would postulate a false
proposition and make the development inconsistent.

### WIDTH: three channels, one fact — the recurring question, named

Every width incident so far has been two of these three disagreeing. D109 was
one. D113 was one. J5 and J6 are two more.

| # | channel | how it is reconciled |
|---|---|---|
| 1 | the meaning — `arch-numerics arch : TargetNum` | — |
| 2 | admissibility — `arch-int-bits arch` | same source as (1); fine |
| 3 | the machine — `8 * frame-word FS` | **an assumed premise**: `fmt-agree : fs-numerics FS ≡ arch-numerics arch` (`FlatFromObs.agda:71`), plus per-arch `bits-eq`/`word-eq` |

…and J5 adds a fourth that is not even reconciled: the arith `semM` family,
hard-wired to 64 and never compared with anything.

`TargetNum` exists precisely so a target's numeric facts "cannot drift apart",
but the machine does not TAKE one — it reconstructs one from `FrameSemantics`
and then we assume the two agree. **Don't postulate what the model can make
true**: have `FrameSemantics` carry a `TargetNum` rather than carry
`frame-word` + `float-format` separately. Then `fs-numerics` is a projection,
`fmt-agree` is `refl` by construction rather than a per-arch premise, and there
is exactly one width in the system. That is item 5, and it is the most
principled single change on this list.

### Spec-shape options, considered 2026-08-23

Is `Admissible` the right SHAPE? It is a side predicate, and nothing forces it
to be the domain on which the meaning is actually defined.

  * **A — status quo + fix.** Total `⟦_⟧ˢ`, side predicate, prove
    `ElabPreservesLits`. Cheapest; the connection is re-proved at each layer.
    **This is what items 3–4 do.**
  * **B — dependent meaning.** `⟦_⟧ˢ : (arch) (tp) → Admissible arch tp →
    Behavior`, witness consumed at literals via `tn-lower`. Then `Admissible`
    IS the domain by construction. Note this is DEPENDENT, not `Maybe`-valued,
    so the objection recorded in `Once/Denotation/Admissible.agda`'s header
    ("WHY A PREDICATE AND NOT A PARTIAL `⟦_⟧ˢ`" — that a `Maybe`-valued meaning
    would stack an admissibility monad on the trace monad `T` and force every
    structural clause to thread it) does not apply to it.
    It is the same principle as `tn-lower` applied one layer up, and having one

**Verdict on "is the spec wrong?"** — the spec is RIGHT about literals (D115
already decided that `-128` on 8-bit is fine) and WRONG about arithmetic (J5).
So it is not purely "something internal": `Word64` in `Arith/SigOp/Builders`
sits inside the meaning itself.

The FLOAT half of the contract is deliberately absent from step 1: a float
literal always lowers, ROUNDING when the target cannot hold it (D116), so its
obligation is totality plus an ERROR BOUND, not a domain restriction. That
bound is what the K-series builds, and half a bound is worse than none.

### J6 step 3 — `-5` IS A LITERAL. It is not `5` plus a runtime negation.

Everything above reached this through the range gate, which makes it sound like
a range-checking concern. It is not. Strip the gate away and the compiler is
still doing something indefensible:

    elaborate m (neg e) = negIR ∘ elaborate m e     -- Surface/Elaborate.agda:254
    negIR               = SigOp neg-info            -- "arith.neg.int"

So for the source text `-5`, the compiler emits **load 5, then call
`arith.neg.int`** — a RUNTIME negation of a value it knew at compile time. No
range check is needed to see that this is wrong. `-5` is a literal; the
compiler should emit `const (-5)`.

**The division of labour is otherwise right, and this is the one place it slips.**
Literals are NOT SigOps — `intLit n = const fits-int n ∘ terminal`, a plain IR
`const`. Arithmetic IS SigOps, because plan 0.20's arith lowering turns closed
arith subtrees into `arith.block.<digest>` that each backend lowers, and that is
a good design for RUNTIME arithmetic. Applying it to a compile-time constant is
the error.

**The fix**: elaboration of `RUnaryOp OpNeg (RInt n)` produces the literal `-n`
— one `const`, no SigOp. Once it does:

  * `irIntLits` reports `-2147483648` where it used to report `2147483648`, so
    `AdmissibleIR` agrees with `AdmissibleM` and `ElabPreservesLits` becomes
    provable;
  * the threaded premises come back out and `correct` is unconditional again;
  * one arith SigOp disappears from every program that writes a negative
    literal, which is a small codegen win and not the reason to do it.

**Where to fold — SETTLED BY A FAILED ATTEMPT, recorded so it is not retried.**

The obvious shape is a smart constructor over the SURFACE syntax:

    negFold : Expr Γ Ψ Int → Expr Γ Ψ Int
    negFold (int z) = int (- z)
    negFold e       = neg e

**It does not typecheck.** `Expr` is indexed by usage and type, and the
catch-all forces a split over every constructor; `var` gets
`SplitError.UnificationStuck` (`singleUse i One ≟ Ψ`, `lookup Γ i ≟ Int`).
Enumerating instead of catching-all does not help — `var` is the stuck case
either way.

So the fold dispatches on the RAW operand, where the datatype is plain:

    inferElabV ctx (Raw.RUnaryOp Raw.OpNeg e) = inferElabV-neg-dispatch ctx e

    inferElabV-neg-dispatch ctx (Raw.RInt n) = success Int _ (int (- n)) … , t-neg (t-int n)
    inferElabV-neg-dispatch ctx e            = inferElabV-RUnaryOp-aux ctx e (inferElabV ctx e)

as a NAMED aux (the file's own convention — `inferElabV-RApp-dispatch` is the
precedent), so the reduction that stops being definitional is confined to that
one function rather than to `inferElabV` itself.

**The follow-on cost, measured not guessed**: `TypeCheck/Completeness.agda`'s
`infer-complete (t-neg d)` and `iFromInfer (t-neg d)` induct on the derivation
and must agree with the new dispatch. Nothing else reads `t-neg`
(`CanonPolyTransport` / `CanonReflectPolyTransport` just rebuild it).

**WAS BLOCKED ON J5; NO LONGER.** The obligation the fold incurs is that the
folded and unfolded forms mean the same thing:

    semM neg-info tn (fromℤ w n)  ≡  fromℤ w (- n)

With `neg-semM x = Word64.⊝ x` this read `2^64 − 5 ≟ 2^32 − 5` at `w = 32` —
false, and not even statable at the right width. J5 fixed that, and the
theorem is now PROVED:

    Once.Word.Width.⊝-fromℤ : ∀ z → ⊝ (fromℤ z) ≡ fromℤ (- z)

at every width, `bits ≡ 0` included, via `⊝-invol-norm`. The `+ zero` case is
not `refl`: `⊝ 0` goes through `norm modulus`, which is `0` rather than
`modulus`, and that is exactly what makes negation total instead of one-off
wrong at zero.

### J5 — the arith path. NOT proof hygiene: THE SPEC IS WRONG ON x86-32.

**This section was mis-scoped and is corrected here.** It was filed as a
cleanup — "modules that serve three targets should not name a width" — and
deferred until J0–J4 had shown the shape. It is not a cleanup. The bake is
inside the MEANING, and on x86-32 the meaning is wrong.

    Arith/SigOp/Builders.agda:44   module W = OnceWord.Word64
    Arith/SigOp/Builders.agda:91   neg-semM x = W.⊝ x

    Denotation/Meaning.agda:215    ⟦ t-int n ⟧ᵢ fmt dγ = returnT (fromℤ (int-bits fmt) n)
    Denotation/Meaning.agda:232    ⟦ t-neg d ⟧ᵢ fmt dγ = … >>=T λ v → returnT (semM neg-info v)

`fmt` is threaded into the sub-derivation and then DROPPED. So within a single
expression the spec uses the TARGET's width for literals and 64 bits for
arithmetic. On x86-32:

    ⟦ int 5 ⟧        =  5                    -- 32-bit, correct
    ⟦ neg (int 5) ⟧  =  2^64 − 5             -- not even a 32-bit word

The correct answer is `2^32 − 5`. The same holds for `add`/`sub`/`mul`, whose
`semM`s all open the same `W = Word64`.

**Why nothing caught it, and it is a shape this project has now seen three
times.** The machine's `block-semM` bakes 64 as well, and `ArithSimX86-32`
states the x86-32 correspondence at 64 bits. Both sides say `2^64 − 5`, agree,
and the proof goes through — while the hardware says `2^32 − 5`. That is
D114's `isInt?` (both sides of the observable narrowed so they could be proved
equal) and the `absℤ` negative-literal bug (elaborator and denotation took the
absolute value TOGETHER) in a third costume. **Two sides wrong together is not
a coincidence to be noticed; it is the failure mode to design against.**

An earlier revision of this plan asked whether the `ArithSimX86-32` bake was
cosmetic and said to "establish whether the two layers ever meet before
assuming it is". They meet in the denotation. It is not cosmetic.

**What J5 must do**: `SigOpInfo`'s `semM` is a CLOSED function, so threading a
width means the arith SigOp descriptors gain one, which ripples into the
elaborator that builds them and into `⟦ t-neg ⟧ᵢ` / `⟦ neg e ⟧ˢ`, which must
pass the `fmt` they already receive. Then `ArithSimX86-32` can be stated at 32
bits and `CCC/Target/X86-32/Semantics.agda`'s 2^32 wrap is what it corresponds
to.

**J5 now blocks J6 step 3** (the fold's correctness obligation is false at 32
bits until this lands) and is the substance of the recurring "how do we handle
different word widths" question.

## Done means

No module serving more than one target names a width — INCLUDING inside the
meaning, which was the miss: `Arith/SigOp/Builders`' `semM` family is reached
by `⟦ t-neg ⟧ᵢ`, so a `Word64` there is a wrong ANSWER on x86-32, not just an
untidy import. A negative numeral is ONE literal at every layer: the spec says
so (`negLits`), the elaborator emits one `const` and no `arith.neg.int` SigOp,
and `irIntLits` and `moduleIntLits` therefore agree. An `Int` literal the
target cannot hold is a compile error naming the literal and the bound; the
same literal compiles for a wider target. Arithmetic still wraps. And the gate
the spec states is the same decision the backend runs — one procedure, two
callers.

And for floats (K): every literal the programmer can write compiles. `3.14`
and `16777217.0` both do, rounded where the target cannot hold them exactly,
with a warning saying so. `accept?` is gone, not relocated.
