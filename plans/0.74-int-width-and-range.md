# Plan 0.74 — literals are lowered by the BACKEND, and out-of-range is an error

**Status**: OPEN, rewritten 2026-08-21 after the architecture was settled.
Follows plan 0.73 on branch `plan-0.72-float-parameter` (or its successor).
**Implements D115** (as refined below) and **corrects `accept?`**.

## The rule, in one line

**The frontend is target-generic. Each backend lowers a literal at its own
width/format, and rejects what it cannot represent.**

The ARCHITECTURE is identical for `Int` and `Float`. The FAILURE MODES are
not, and D116 says why: an `Int` literal must FIT or it is an error, while a
`Float` literal always lowers — it ROUNDS. **This plan is therefore the `Int`
half only.** Floats are not touched; see "what this plan does NOT do".

---

## What is already landed (the width threading)

Committed `d7a7aef5`, gate green. The literal payload is SOURCE SYNTAX at both
numeric types and the machine materialises it:

    LitPayload fits-int   = ℤ          LitPayload fits-float = Dyadic
    IR.const : … → ⟦ ℤ , Dyadic ⟧-baseI A → IR Unit A
    intLit n = const fits-int n ∘ terminal          -- converts NOTHING
    lit-value fits-int z = fromℤ (8 * frame-word FS) z
    lit-value fits-float d = encode (float-format FS) d

`TargetNum` (`Once.Target.Arch`) carries the width and format together;
`fs-numerics FS` derives them from facts the machine already had
(`frame-word`, `float-format`); `fmt-agree` pins the machine's view to the
apex's; `bits-eq` derives from `word-eq`.

**This plan does not revisit any of that.** It adds the missing half: nothing
yet REJECTS a literal the target cannot hold.

## Three rejected designs, recorded so they are not retried

**A `supportedWidths` list in the frontend.** Backwards coupling: the frontend
would depend on which BACKENDS exist, so adding a narrow target retroactively
rejects programs that were fine for every existing one. Not hypothetical —
`accept?` does this today and `16777217.0` (exact at `binary64`, not at
`binary32`) cannot be written even when targeting x86-64. Its error message
gives the rationale — "a rounded literal would denote a different number on
different machines" — and **D113 removed that rationale**: the meaning is
arch-indexed now, so denoting different bits on different machines is correct.

**Converting in the frontend (arch-aware elaboration).** Makes the IR
arch-specific in fact but not in type; the only real fix is indexing `IR` by
the arch, which infects every IR-mentioning signature. Also throws away a
target-free elaborator and target-free frontend proofs.

**A partial denotation (`⟦ int n ⟧ˢ` returns `Maybe`).** Rejected on the
principle the codebase already follows once: an ill-typed program does not get
a `nothing` meaning, it is excluded by `Typed`, and `⟦_⟧ˢ` is TOTAL behind that
gate. "Does 1001 fit in 8 bits" is the same kind of question — static,
decidable, about EXPRESSIBILITY, not about what the program computes — so it
belongs with well-formedness. Making `⟦_⟧ˢ` `Maybe`-valued would stack a
second monad, whose failures have nothing to do with values, on top of the
trace monad `T`, and every structural clause would thread it.

## The design

### Two well-formedness judgments, and the layering says something true

    Typed        — target-FREE.     The type system. Unchanged.
    Admissible   — target-RELATIVE. New. "this typed program can be
                   expressed at this target"

`Admissible arch tp` holds iff every `Int` literal in `tp` is in range at
`arch-int-bits arch`. Decidable, structural, and IN THE SPEC. **Float literals
place no condition on it** — they always lower (D116).

**Why it must be in the spec, not merely implemented.** Without an
admissibility predicate in the meaning, a compiler that rejects EVERY program
satisfies soundness vacuously; only completeness rules it out, and completeness
is stated against the meaning. So the meaning has to say which programs are
admissible at a target, or "reject everything" is a correct compiler.

`⟦_⟧ˢ` stays TOTAL. `fromℤ`'s modulus reduction remains a totality device that
no admissible program can reach.

### What is checked, and what is not (D116)

| literal | at this target | outcome | where |
|---|---|---|---|
| `1001` | doesn't fit 8-bit signed | **compile error** | backend, `InRange` |
| `1001` | fits 16-bit | lowers | backend |
| `100 + 100` overflows | — | **wraps, no error** | nowhere — D054, arithmetic is modular by promise |
| `3.14` | not dyadic at any format | **rounds** (warn) | backend — NOT this plan |
| `16777217.0` | exact at `binary64` | lowers exactly | backend — NOT this plan |
| `16777217.0` | not exact at `binary32` | **rounds** (warn) | backend — NOT this plan |

`Int` has no target-free constraint at all — every `ℤ` fits SOME width — so it
gets no frontend check. `Float` needs no gate either, because it never fails.
The admissibility judgment below is consequently **`Int`-only**.

### What this plan does NOT do — and why not

**It does not touch `accept?`.** Under D116 that rejection is an INTERIM,
"sound but incomplete", and it is scheduled for DELETION once rounding lands.
An earlier draft of this plan moved it to the backend for symmetry. That was
wrong twice over: it would relocate something about to be removed, and it would
keep rejecting `16777217.0` on x86-32 where the design says ROUND.

**So `16777217.0` stays rejected on every target until the rounding work.**
That is a known, dated interim, not this plan's business. The fix is rounding,
not a per-target representability check.

**The float half needs its own plan**: `round : FloatFormat → Dyadic → Word`,
its correctness proof (CompCert has one), and the WARNING CHANNEL Once does not
yet have — which is the actual reason the interim rejection exists. With no way
to say "this rounded", refusing was the only honest option available.

### The vocabulary, mirrored

    InRange  : ℕ → ℤ → Set
    inRange? : ∀ bits z → Dec (InRange bits z)
    toWord   : ∀ bits z → InRange bits z → Word

Decision + evidence + total conversion under evidence — not `ℤ → Either String
Word`. It keeps `fromℤ`'s wrap unreachable as semantics, and it is provable.

(`Float`'s counterpart is `round`, which is TOTAL and therefore needs no
decision and no evidence — the whole point of D116.)

### THE ONE THING THAT MUST NOT ROT

**The admissibility gate and the codegen must dispatch on the SAME decision
procedure**, not two implementations that happen to agree. `ArithSimX86-32` is
the standing warning: it opens `Word64` in an x86-32 module whose machine wraps
at 2^32, and nothing caught it because nothing SAID the two must agree.

## Sequencing — TOP-DOWN. The typechecker produces the work list.

Plan 0.73's six rules apply verbatim; re-read
`plans/0.73-float-follows-d054.md` §"How this plan is sequenced". In short:
change the top-level STATEMENT first; let the red be the plan; follow it from
the APEX ROOTS ONLY (`Once/Certified.agda`, `Once/Target/{X86-64,X86-32,
RiscV64}.agda`) and never from `check-all`; never build ahead of the red; name
residuals at their USE SITE; and never narrow a claim to make a proof go
through.

### J0 — change the two top-level statements. Then STOP and read the red.

Two edits, no others:

**(a) `Once/Adequacy.agda` — the spec gains the gate.**

    Admissible : Arch → Typed → Set

and `correct`'s two conjuncts mention it:

    soundness    … → Σ[ tp ] ((src ⊢ tp) × Admissible arch tp
                              × (exec arch bytes ≈ ⟦ arch ⟧ˢ tp))
    completeness ∀ tp → src ⊢ tp → Admissible arch tp
                     → Σ[ bytes ] (compile arch doOpt src ≡ just bytes)

`Typed` and `_⊢_` stay TARGET-FREE. Do not put the arch on `_⊢_`: parsing and
typing genuinely do not depend on the target, and saying they do would be the
arch-indexed-IR mistake in another costume.

**(b) There is no (b).** An earlier draft made `Accepted` lose its
target-relative half here; D116 removed that — `accept?` is deleted by the
rounding plan, not amended by this one. J0 is ONE edit.

Then typecheck the apex roots and WRITE THE RED LIST INTO HANDOFF. Fix nothing
while producing it.

Expect the red at `Once.Compiler`, which can no longer fill `correct`, and
then wherever `⟦_⟧⊥`/`correctR` mention the meaning's domain.

### J1 — `Admissible`, in the spec

Define it structurally over the typed program, decidably. It belongs in the
`Once.Spec.Meaning` cone because `correct` mentions it — same argument that
put the observable there in D114. Export the DECISION, so J3 can dispatch on
the very same procedure rather than a copy.

### J2 — the numeric vocabulary

`InRange` / `inRange?` / `toWord` in `Once.Word`, beside `fromℤ`. State
`toWord`'s agreement with `fromℤ` under evidence (`toWord bits z ev ≡ fromℤ
bits z`) so the machine's total `lit-value` and the backend's checked lowering
are the same number by a lemma, not by inspection.

### J3 — the backends lower, and reject

`compileFromModule` dispatches on `inRange?` at its own width; a `no` becomes
a `CompileResult` error carrying the literal and the bound. The ABSTRACT machine's `lit-value` stays TOTAL — it runs only
admissible programs, and that is the gate's job, not a second check.

### J4 — the apex composes

`Once.Compiler` fills `Admissible` with J1's predicate at `arch-numerics arch`.
The obligation that closes the loop: **codegen succeeds iff `Admissible`
holds** — proved, not assumed. When `Once/Certified.agda` is green the design
is landed, and not before.

## Tests

**Already green, and the regression net for all of the above:** `TraceSpec`'s
three negative-argument cases (`-5`, `3 - 8`, mixed signs), which pin that the
machine is right about signed values; and `FloatEmitSpec`, the model for a
per-arch value test that stays general — expectations DERIVED from an arch
table, never transcribed.

**This plan owes:**

  * an `Int` literal beyond the target's signed range is rejected with an
    error naming the literal and the bound — and the SAME literal compiles for
    a wider target. That pair is the sharpest statement of the whole plan.
  * `100 + 100` still compiles and wraps — arithmetic is not checked.
  * a negative argument observed on ALL THREE arches (`buildAndRunTraceOn`
    makes this possible now), which would catch a width divergence between the
    denotation and the machine.

## Done means

No module serving more than one target names a width. An `Int` literal the
target cannot hold is a compile error naming the literal and the bound; the
same literal compiles for a wider target. Arithmetic still wraps. And the gate
the spec states is the same decision the backend runs — one procedure, two
callers.

Floats are exactly as they were: still rejected when inexact, still an interim,
still waiting on rounding and a warning channel (D116).
