# Plan 0.11: Parameterize Proofs Over the Trusted Base (`--safe` Proof Modules)

## Context

Today's verification chain has postulates scattered across many modules:
runtime contract, frame ops, syscall semantics, escape analysis, plus
intermediate "stopgap" postulates introduced while top-down derivations
are still in flight. Some examples currently present in the tree:

- `compile-correct` (`Once.CCC.Codegen.CompileCorrect`) — Plan 0.10's
  top-level theorem, postulated at Phase A pending Phase E discharge.
- `ir-to-trace-correct-sigop` (`Once.CCC.Codegen.IRTraceCorrect`) —
  named postulate for the SigOp branch of `ir-to-trace-correct`.
- `sigop-codegen-faithful` (per-arch DirectSimulation) — named
  postulate for the codegen↔abstract correspondence on SigOps.
- `sigOpInfo-name-coherence` (`Once.CCC.SigOp.Info`) — axiom on
  SigOpInfo equality.
- `add-semM`, `add-semI`, `neg-semM`, … (`Once.Arith.SigOp.Builders`) —
  arithmetic semantics postulated until 0.2.4.2 makes them
  definitional.
- `frame-capacity-after-mov`, escape-survives, RuntimeContract entries,
  syscall ABI postulates, etc. — operational axioms scattered through
  per-arch backends.

Two problems compound:

1. **No clear trusted-base boundary.** A postulate inside `Eval.agda`
   sits next to definitional code; a postulate inside an X86-64
   simulation file sits next to discharged simulation lemmas. The
   *role* of each postulate (axiom vs. stopgap) is documented in
   comments, not enforced structurally.

2. **`--safe` cannot be enabled anywhere.** Agda's `--safe` flag
   forbids `postulate`. Today, every proof module transitively imports
   a module with a `postulate`, so no proof module can opt in. There
   is no syntactic guarantee that any specific theorem is actually
   axiom-free — only `make postulates-grep` audited by hand.

This plan turns the trusted base into a **parameter** rather than a
scatter. Proof modules take the trusted base as a module parameter or
record argument, contain no `postulate` keyword themselves, and can
enable `--safe`. The trusted base concentrates in one (or a few)
clearly-marked modules outside `--safe`. The top-level extraction
point (the `compile` binary) supplies the concrete trusted base — and
that's the one place a reader needs to look to see what's trusted.

This is related to Plan 0.10 but **orthogonal**:

- 0.10 closes the verification gap by deriving more theorems (replacing
  postulates with proofs).
- 0.11 reshapes the *layout* so the postulates that remain are
  parameter-isolated and `--safe`-enforceable.

Either plan can land first, but 0.11 makes 0.10's audit story tight:
"these N axioms in `Once.TrustedBase` are the trust boundary, and
every other proof module is `--safe`".

## Goal

After this plan:

```
formal/Once/TrustedBase.agda         -- {-# OPTIONS --no-safe #-}
                                     -- the only place `postulate` appears
                                     -- record TrustedBase : Set where field …

formal/Once/CCC/Codegen/CompileCorrect.agda    -- {-# OPTIONS --safe #-}
formal/Once/CCC/Codegen/IRTraceCorrect.agda    -- {-# OPTIONS --safe #-}
formal/Once/CCC/Target/X86-64/CompileCorrect.agda -- {-# OPTIONS --safe #-}
…                                              -- {-# OPTIONS --safe #-}

formal/Once/Compile.agda             -- the extraction point
                                     -- imports TrustedBase and instantiates
                                     -- the proof chain at module-load time
```

Concretely:

1. A `TrustedBase` record (or interface module) collects all current
   "axiomatic" postulates: RuntimeContract, FrameOps, syscall ABI,
   escape-survives, sigOp-proof, `sigOpInfo-name-coherence`, etc.
2. Each proof module becomes parameterized over `TrustedBase`. Either:
   - `module ProofModule (T : TrustedBase) where` (module parameter), or
   - `record TrustedBase` carried as a regular record argument.
3. Proof modules add `{-# OPTIONS --safe #-}`. Build fails if any
   `postulate` slips in.
4. The trusted-base module is the **only** non-`--safe` module in the
   verification path (excluding standard library, MAlonzo runtime, etc.).
5. `Once.Compile` instantiates the trusted base and re-exports the
   verified `compile` and its theorems.

Not in scope: replacing trusted-base axioms with real proofs (that's
0.10 Phase D/E and beyond). 0.11 only reshapes where they live.

## Methodology: Outside-In

We do NOT refactor every module simultaneously. We work from the
boundary inward:

1. **Catalog every current `postulate`** across `formal/Once/`. Bin each
   into one of three categories:
   - **(a) Trusted-base axiom**: represents something genuinely outside
     the formal system (CPU ABI, OS syscall, runtime contract). Goes
     into `TrustedBase`.
   - **(b) Stopgap pending derivation**: a postulate that *should* be
     derived but is parked while upstream work lands. Tagged with the
     plan that closes it. Goes into `TrustedBase` *temporarily*, with
     a `--TODO 0.10/E` style annotation.
   - **(c) Auxiliary working axiom**: postulates inside e.g. test
     fixtures that aren't on the verification path. Excluded from
     `TrustedBase`.

2. **Define `TrustedBase`** with the union of (a) and (b). Initially
   it's a record with ~15-30 fields, each a typed axiom statement.

3. **Refactor leaf modules first.** Pick a proof module that has zero
   `postulate`s of its own and only imports from modules-with-postulates.
   Make it parameterized (or open the trusted base at module top).
   Mark `--safe`. Verify.

4. **Cascade upward.** Each module's immediate dependents get the same
   treatment. The cascade ends at `Once.Compile` (or a sibling
   extraction point), which takes the concrete `TrustedBase` and
   re-exports.

5. **Enforce.** A CI check greps for `\bpostulate\b` outside
   `Once/TrustedBase.agda` and fails the build if found in a `--safe`
   module.

## Phase A — Catalog (1 commit, 1 day)

1. `grep -rn "^postulate\|^  postulate" formal/Once/ > /tmp/postulates.txt`
2. Walk the list, categorize each into (a) / (b) / (c).
3. Write `docs/compiler/trusted-base-catalog.md` — flat table of:

   | Postulate | File:Line | Category | Plan that retires it (if (b)) | Notes |
   |---|---|---|---|---|

4. Decision log entry **D051: trusted-base catalog** — single sentence
   summary plus pointer to the doc.

**Deliverable:** the catalog. No code changes.

## Phase B — Design `TrustedBase` (1 commit, 1-2 days)

Design choices:

1. **Module parameter vs. record.** Module parameters are ergonomic at
   the top of each module (`module M (T : TrustedBase) where`) but
   produce verbose `M T` references at use sites. Record arguments are
   uglier at definition time but compose better. Recommend module
   parameters, with a top-level convenience module that opens the
   parameter.

2. **One record vs. structured records.** A single flat `TrustedBase`
   with all axioms as fields is simple but couples unrelated concerns
   (a SigOp postulate sitting next to a frame-op postulate). A
   structured record (`record TrustedBase : Set where field
   runtime : RuntimeContract; frame : FrameContract; …`) reflects
   the actual structure. Recommend structured records, mirroring the
   layered architecture (CCC layer / per-arch layer / per-domain
   layer).

3. **Where the (b) stopgaps live.** Put them under a sub-record
   `TrustedBase.Pending : PendingDerivations` so it's visible in the
   type that these are *not* permanent. As Plan 0.10 etc. discharge
   them, fields move out of `Pending`.

**Deliverable:** `formal/Once/TrustedBase.agda` skeleton with the
record types. Build green. Nothing else changes (no module is yet
parameterized).

## Phase C — Refactor one leaf proof module (1 commit, 1 day)

Pick a small proof module that's "leaf-ish" — depends on postulates
upstream but contains no `postulate` of its own and few dependents.
Candidates:

- `Once.CCC.SigOp.Helper` — `PrimHelper` module, takes `FrameSemantics`
  parameter; trivial to also take `TrustedBase`.
- `Once.Arith.SigOp.Proofs` — already parameterized; absorb `TrustedBase`.
- `Once.CCC.SigOp.RelaxedContract` — a recent addition, no internal
  postulates.

Concrete change:

```agda
-- Before
module Once.CCC.SigOp.Helper where
  -- imports …
  module PrimHelper {FS : FrameSemantics} (program-bound : ℕ) where
    …

-- After
{-# OPTIONS --safe #-}
module Once.CCC.SigOp.Helper (T : Once.TrustedBase) where
  open Once.TrustedBase T
  -- imports … (no `postulate` in the import graph after T is open)
  module PrimHelper {FS : FrameSemantics} (program-bound : ℕ) where
    …
```

Verify: `make agda MODULE=Once/CCC/SigOp/Helper.agda` green with
`--safe` set.

**Deliverable:** one module is `--safe`, parameterized, axiom-free at
the syntactic level.

## Phase D — Cascade (multi-commit, 1-2 weeks)

Repeat Phase C outward. Each immediate dependent of the newly-`--safe`
module gets refactored: take `TrustedBase`, open it, mark `--safe`.
Order by dependency depth — deepest first.

Track progress in `docs/compiler/trusted-base-rollout.md`:

| Module | `--safe`? | Date | Notes |
|---|---|---|---|

The cascade ends at the top: `Once.Compile.compile`, which receives
the concrete trusted base and is itself the only module that touches
extraction.

**Deliverable:** all proof modules `--safe`, except `Once.TrustedBase`.

## Phase E — Top-level instantiation (1 commit, half day)

`formal/Once/Compile.agda` (the MAlonzo extraction point) instantiates
the trusted base concretely:

```agda
module Once.Compile where
  import Once.TrustedBase as TB
  -- TB.trusted : TrustedBase  -- the concrete instance
  open import Once.CCC.Codegen.CompileCorrect TB.trusted
  -- compile-correct in scope, fully derived
```

The concrete `TB.trusted` is just a record literal whose fields are
the postulate names. The top of the file remains non-`--safe`.

**Deliverable:** the chain typechecks; `compile` and `compile-correct`
are exported with `--safe` proofs and a single non-`--safe`
`TrustedBase` module under them.

## Phase F — Enforcement (1 commit, half day)

1. CI rule (Makefile target):
   ```
   audit-postulates:
       @if grep -rn '^postulate\|^  postulate' formal/Once/ \
              | grep -v 'Once/TrustedBase.agda' ; then \
           echo "ERROR: postulate outside TrustedBase"; exit 1; \
       fi
   ```
2. Document: `docs/compiler/trusted-base.md` describes the layering and
   the rule.
3. Decision log entry **D052: --safe proof modules + TrustedBase
   parameterization**.

**Deliverable:** structural guarantee. Adding a `postulate` outside
`TrustedBase.agda` fails the build.

## Postulate Audit Trajectory

| Phase | Postulates outside TrustedBase | What changes |
|---|---|---|
| Today | ~30+ scattered | — |
| Phase A | ~30+ scattered (cataloged) | Catalog written |
| Phase B | ~30+ scattered | TrustedBase skeleton exists but unused |
| Phase C | ~30+ minus 1 module's worth | One leaf module `--safe` |
| Phase D | shrinking each commit | Each refactored module `--safe` |
| Phase E | 0 | Top-level instantiates; chain green |
| Phase F | 0 (CI-enforced) | Build fails if (re-)introduced |

After Phase F: a reader confirming "is `compile-correct` axiom-free
modulo the trusted base?" needs only to look at `Once.TrustedBase`.
That single file is the proof's trust boundary.

## Risks

1. **Module parameterization is contagious.** Every transitive importer
   of a parameterized module becomes parameterized too. The cascade is
   mechanical but voluminous. Mitigation: use convenience re-exporter
   modules where useful; budget time, don't try to land in one commit.

2. **Some postulates may live mid-module, intertwined with definitional
   code.** Extracting them cleanly into `TrustedBase` may require
   non-trivial refactoring of the source module. Mitigation: catalog
   in Phase A flags these for a one-pass cleanup before Phase C.

3. **`--safe` may surface lingering issues** that were previously
   silently absorbed: e.g. `--no-positivity-check` in scope, or
   `--type-in-type` accidentally enabled in a transitive import. Each
   surfaced issue is a real bug; Phase D budget should anticipate
   ~1 such surprise per 5 modules.

4. **Stopgap (b) postulates muddle the trusted-base story.** If
   `TrustedBase.Pending` swells, the boundary becomes "sometimes
   axiomatic, sometimes parked work-in-progress" and audit clarity
   degrades. Mitigation: every (b) entry must reference a plan that
   retires it; periodic reviews demote `Pending` entries that have no
   active discharge plan into either real axioms (a) or open issues.

5. **Coordination with Plan 0.10.** As 0.10 discharges postulates,
   their `TrustedBase` fields disappear. Mid-flight 0.11 work needs
   to track 0.10's progress to avoid re-parameterizing modules that
   are about to become non-axiomatic. Mitigation: do 0.11 *after* the
   bulk of 0.10's Phase E lands, OR coordinate per-module so each
   `--safe` switch happens once.

## Relationship to other plans

- **Independent of** Plan 0.10. Either can land first; coordination
  helps but is not required. 0.10 makes 0.11's Pending sub-record
  shrink; 0.11 makes 0.10's audit story crisp.
- **Depends on** the existing per-module `OPTIONS` mechanism (Agda
  2.8.0) supporting `--safe`. Verified — already in use elsewhere in
  the tree.
- **Blocks** any future plan that wants to assert "this theorem is
  axiom-free": today's only mechanism is hand-grep; after 0.11 it's a
  module-level `--safe` declaration.

## Success criteria

- `formal/Once/TrustedBase.agda` is the only `formal/Once/**/*.agda`
  containing `postulate` outside test fixtures.
- All other modules under `formal/Once/` (excluding test fixtures and
  `TrustedBase.agda`) opt into `{-# OPTIONS --safe #-}`.
- `make audit-postulates` passes on `master`.
- `make compiler-all` and `make malonzo` remain green throughout the
  cascade and after Phase F.
- `docs/compiler/trusted-base.md` documents the boundary and lists
  every axiom with its justification (a-vs-b).

## Author's note

The leak we discovered (`exec-abstract (instr-sigop _) = s , alloc`)
wasn't a postulate — it was a wildcard pattern silently producing a
trivial body. `--safe` wouldn't have caught it. **Confirmed: Agda 2.8
emits no `UnusedVariable` warning for regular pattern variables**, so
even renaming `_` → `si` (for greppability) doesn't produce a
machine-checkable signal. `--exact-split` only fires on multi-shape
catch-all collapse, not on single-clause wildcards.

The class of leak this represents — *trivial body for a clause whose
type should depend on the discarded payload* — is invisible to every
flag we have. The only structural fix is from-above: Plan 0.10's
top-down derivation forces the body to depend on the payload because
otherwise the derived theorem doesn't typecheck. 0.11 contributes
visibility for postulates; 0.10 contributes visibility for trivial
bodies. The pair together is what makes "verified compiler"
structurally meaningful:

- A trivial body for a clause with non-trivial type can't satisfy a
  derived theorem from above (0.10 catches this).
- A stopgap postulate to paper over the hole would have to live in
  `TrustedBase.Pending`, where it's visible (0.11 catches that).

0.11 alone is housekeeping; together with 0.10 it's verification with
teeth.

## Addendum (2026-06-09) — a *visible* axiom can still be abused

Plan 0.36's effectful-cata bug (compiled, typechecked, ran wrong — exit 64 not
7; caught by a runtime test, NOT by the proof) sharpens this plan. Unlike the
`instr-sigop` wildcard leak in the Author's note, **this one *was* routed
through a postulate** — `generic-semI`/`generic-semM` (`Builders`). So it is
squarely in 0.11's wheelhouse... and yet 0.11 *as written* would not have stopped
it. The lesson:

**Visibility (postulate-in-`TrustedBase`) is necessary but NOT sufficient.**
`generic-sem` is a *legitimate* axiom (opaque semantics for genuine external
primitives). The fault was a new producer (an `extract-morph-eff` clause in the
cata path) feeding it an **internal** user function re-typed as an external
`IR.SigOp (generic-info name)` — so "this denotes `seven`" became "`generic-sem
"seven"` ≡ `seven`", unrefutable-by-postulate and false. Putting `generic-sem`
in `TrustedBase` makes it *visible* but it is still **reachable by anything** —
a catch-all axiom over arbitrary `String`s is a laundering vector regardless of
where it's filed.

Three refinements to the plan's success criteria, so the bug *class* is closed,
not just made visible:

1. **Confine each axiom; ban catch-alls.** A `TrustedBase` axiom must be
   reachable only by its *genuine* producer, not by arbitrary code. `generic-sem
   : String → Sem` (any name) must be **eliminated**, replaced by per-producer
   contracts gated behind a "genuine-external" token only a real declaration can
   mint (see Plan 0.38). A `String`-indexed catch-all axiom is itself a finding.

2. **Obligation local to construction.** A SigOp's contract (`PreservesCCC` +
   semI/semM coherence + impl⊨semM) must be a **field/argument of constructing
   the SigOp**, not discharged "somewhere downstream." Then an uncontracted /
   mis-identified SigOp is a *type error* — Agda screams. Generalize: every
   construction or **conversion** (`extract`/`compile`/`lower`) that could be
   unsound must carry its discharge in its type. The bug's signature: a
   conversion returning a bare value with **no relational/faithfulness proof**
   tying output to input (`extract-morph : … → Maybe (∃ m → Ψ ≡ zeroUsage)` — an
   `m` and a *usage* equation, but never `source ≈ m`). That missing relational
   component is the greppable-by-type smell; the structural fix is to require it.

3. **Producer model.** Internal producers (arith) **prove** their contract;
   external producers (syscalls) **postulate** it, co-located with the impl, per
   (SigOp × target) — Plan 0.38. So the SigOp slice of `TrustedBase` is a set of
   honest per-producer axioms, not one omnipotent catch-all.

The north star this clarifies: **"valid" should mean "Agda accepts + read
`compile`'s parameter list" — zero proof inspection.** That holds iff the trusted
base is (i) the explicit parameters of `compile` (CPU model + CCC laws), plus
(ii) a *confined, per-producer* set of external axioms each unreachable except by
its genuine producer. A visible-but-reachable-by-anything catch-all (today's
`generic-sem`) breaks (ii) even under full 0.11 layering — which is exactly why
0.38 (eliminate the catch-all; per-producer contracts) is the companion this
plan now requires.
