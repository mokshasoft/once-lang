# Plan 0.15: Split `alloc.next-slot` from `AllocState` (principled Bridge A close)

**Date created:** 2026-05-18
**Status:** Planned for future execution; the hybrid (Plan 0.14 Phase 2A) closes the same outcome with less surgery first.

## Motivation

`alloc.next-slot` currently conflates two unrelated jobs:

1. **Job A — runtime slot counter:** bumped by `instr-alloc-stack` at execution.
2. **Job B — proof-side IR start frontier:** "where this IR's scratch starts," threaded through `RecDispatcherWF`.

These got fused because `instr-alloc-stack` happened to update both. When PairAllocWF emits `instr-alloc-stack pair-heap-overhead` in its setup-trace, jobs A and B align trivially. When `IRToTrace` drops the instruction (function prologue allocates the entire frame upfront), jobs A and B diverge but share a single field — synthetic `alloc-after-scratch` values appear in proofs to compensate, and the proof and runtime sides drift apart.

Plan 0.14 Phase 2A's hybrid (η + trace-state-alloc-coherent lemma) closes Bridge A's *trace-shape* gap by making `instr-alloc-stack` an alloc-no-op. But job B's bookkeeping remains coupled to `AllocState`: producers still construct `record alloc { next-slot = N+k }` and pass it to sub-IR `rec-wf`. The synthetic value persists; the hybrid relies on a coherence lemma to bridge it.

**Plan 0.15 removes the coupling structurally.** Job B becomes an explicit parameter; `AllocState` keeps only the fields exec-trace genuinely reads/writes.

## Target shape

```agda
record AllocState {FS : FrameSemantics} : Set where
  field
    current-frame : Frame
    next-heap-ref : ℕ
  -- next-slot removed

RecDispatcherWF bound = ∀ {A B} (mIn : AllocMode) (ir : IR A B)
  (start-slot : ℕ)              -- ⟵ NEW: explicit slot frontier
  (ir<bound : ir-size ir < bound)
  (x : ⟦ A ⟧) (input-loc : ValueLocation FS)
  (s : LocState FS) (alloc : AllocState {FS}) → ...

IRResultAWF (m : AllocMode) (ir : IR A B) (start-slot : ℕ)
            (x : ⟦ A ⟧) (s : LocState FS) (alloc : AllocState {FS}) : Set
```

After the migration:
- `alloc.next-slot` ceases to exist.
- Producers receive `start-slot` as an explicit parameter and use it to place their scratch slots.
- For sub-IR dispatch, producers call `rec-wf` with `start-slot + scratch-size`.
- No `alloc-after-scratch` synthetic value; the proof reasoning matches runtime exactly.
- `trace-is-ir-to-trace : trace ≡ ir-to-trace-at-frontier start-slot ir` becomes a definitional refl in every producer (because the start-slot threaded through proof and IRToTrace are unified by construction).

## Migration order

1. **AllocState surgery** (1-2 sessions)
   - Remove `next-slot` from the `AllocState` record (SMCore.agda:383).
   - Update `mkAllocState` constructor sites (4 occurrences).
   - Update `exec-abstract` for `instr-alloc-stack/-dealloc/-reclaim`: only modifies `regs.stackSlot`, no alloc effect.

2. **RecDispatcherWF + IRResultBase signatures** (2-3 sessions)
   - Add `start-slot : ℕ` parameter to `RecDispatcherWF` in `ClosureWellFormed`.
   - Add `start-slot : ℕ` parameter (or field) to `IRResultBase` / `IRResultAWF`.
   - Update `trace-is-ir-to-trace` to reference `start-slot` instead of `next-slot alloc`.
   - Update `result-place.continuation-alloc` to compute start-slot via record update on `start-slot` parameter, not `alloc.next-slot`.

3. **Allocation module + frontier predicates** (1-2 sessions)
   - `BeforeFrontier alloc loc` becomes parameterized on start-slot for `AtStack` cases:
     - `BeforeFrontier start-slot heap-ref alloc loc` with `AtStack f k` requiring `k < start-slot`.
     - Or split into two predicates: `StackBeforeFrontier start-slot loc` and `HeapBeforeFrontier alloc loc`.
   - `stack-alloc-advances`, `frontier-monotone`, etc. — rephrase with start-slot.

4. **Per-producer migration** (~1 session each × ~12 producers):
   - SimpleWF (8 entries): id/fst/snd/terminal/arr/free-heap/out-μ/Out.
     - Add `start-slot` parameter (mostly unused for simple ops).
   - ComposeWF: thread start-slot through f and g; g sees `start-slot + f-scratch`.
   - PairStackWF (Stack pair): `backup-slot = start-slot`, `fst-slot = start-slot + 1`, etc.; f at `start-slot + pair-overhead`.
   - PairAllocWF (Heap pair): same pattern with `pair-heap-overhead = 4`.
   - CurryStackWF, CurryAllocWF: scratch slots at `start-slot..start-slot+1`; body at `start-slot=0` (fresh frame).
   - ApplyWF: pair-slot at start-slot; closure body uses fresh frame.
   - SumRecWF (Stack inl/inr/case): sum-slot at start-slot.
   - SumInlAllocWF, SumInrAllocWF (Heap): payload-stash at start-slot, sum-stash at start-slot+1.
   - AnaWF, ParaWF, RecCoreWF, RecTrace: recursion schemes — start-slot threaded as appropriate.

   For each producer:
   - Replace `next-slot alloc` with `start-slot` in scratch slot computations.
   - Replace `record alloc { next-slot = N }` for sub-IR dispatch with passing `N` as start-slot.
   - `trace-is-ir-to-trace = refl` should work after migration.
   - Update `alloc-correct` chain: alloc only tracks `next-heap-ref` changes now.

5. **Dispatcher migration** (1 session)
   - `run-ir-wf` threads start-slot from caller.
   - `make-rec-wf` builds the RecDispatcherWF with start-slot.
   - Each clause that calls `make-rec-wf` passes the appropriate start-slot.

6. **IRTraceCorrect + Compile.agda + EntryPointCCC** (1-2 sessions)
   - IRTraceCorrect's bridges reference `start-slot` instead of `next-slot alloc`.
   - Top-level callers (compile-correct, EntryPointCCC) pass `start-slot = 0` (function frame starts fresh).

7. **MAlonzo re-extraction + cabal build + runtime tests** (1 session)
   - All 8 Layer 0/1/2 tests must pass.
   - `trace-is-ir-to-trace = refl` verified everywhere.
   - No new postulates introduced.

**Total estimate: 12-18 sessions.**

## Risk surfaces

1. **`BeforeFrontier` on stack locations.** Currently `BeforeFrontier alloc (AtStack frame k)` checks `k < next-slot alloc`. After: split into `StackBeforeFrontier start-slot (AtStack frame k)` (= `k < start-slot`) and `HeapBeforeFrontier alloc (AtDynamic …)`. Producers' validity proofs are sensitive to the predicate shape.

2. **`stack-alloc-advances` / `validityWF-frontier-advance` family.** These currently model alloc.next-slot bumping. They need full restructuring to operate on the new shape (likely: explicit `start-slot-advance` lemmas).

3. **`continuation-alloc` in `result-place`.** Currently `record alloc { next-slot = next-slot final-alloc; next-heap-ref = next-heap-ref final-alloc }`. After: the start-slot becomes a separate threading — either a field on ResultPlace or split into stack and heap pieces.

4. **Stack-mode producers reference `alloc.current-frame` plus a slot index.** Should remain unaffected (current-frame stays in AllocState), but worth verifying when migrating the `validityWF-write-at-frontier`-family lemmas.

## Why the hybrid (Plan 0.14 Phase 2A) is preferred first

Plan 0.14 Phase 2A's hybrid (η + trace-state-alloc-coherent lemma) closes Bridge A's outcome — all `trace-is-ir-to-trace` become refl, no postulates — in 7-10 sessions instead of 12-18, with much smaller surgery on `AllocState`. The conceptual debt (alloc.next-slot still does two jobs, just via convention) is real but bounded; future work can resolve it via Plan 0.15.

If at any point the hybrid's `alloc-after-scratch` bookkeeping starts to leak into new producers in surprising ways, Plan 0.15 escalates to the structural fix.
