# Plan 0.32 — Flatten the abstract machine (align with the target, reverse M1)

## Diagnosis (the root of every correspondence headache)

The abstract machine models control flow at a **different level** than the
target, so abstract↔target is NOT 1-to-1:

| | abstract machine | target (`Semantics.exec`) |
|---|---|---|
| straight-line | `exec-trace` (list fold) | pc walks the program |
| **loop** | `exec-loop` — **structured fuel recursion** | `label`/`cmp`/`je`/`jmp` + pc + `find-label` + fuel |
| **branch** | `exec-case-dispatch` — **structured** | `cmp`/`je` |

Straight-line instructions correspond 1-to-1 and are trivial. **Only the
structured control-flow constructs are hard** — precisely because the
abstract machine invented its own control model no target shares. That is
the "fighting the abstraction" the difficulty was pointing at.

This traces to **Plan 0.29 M1**, which chose the structured `exec-loop`
specifically to avoid making `exec-trace` pc-based ("43 consumers"). That
trade bought a small blast radius and paid for it in correspondence
complexity (the `instr-sim` `!!` holes, the `CataDescendCompiledInduction`
fuel gymnastics, the 3 parallel Cata structures). **Reverse it.**

## Target design — a generic flat-fuel CPU

The abstract machine becomes a **target-independent `Semantics.exec`**:
**flat control flow** (pc + `label`/`je`/`jmp` + `find-label` + fuel),
**typed values** (`StoredValue` stays — keeps the codegen-correctness
proofs clean; values are where the abstract machine *should* stay richer
than the untyped-`ℕ` target).

- `AbstractInstr` gains flat control: `a-label`/`a-cmp`/`a-je`/`a-jmp`
  (over abstract registers/conditions). `instr-loop` / `instr-case-on-tag`
  are **removed** — the codegen lowers structured recursion to these flat
  jumps directly (it already does for the target in `compile-trace-cnt`;
  now it does so one level earlier, into the abstract ISA).
- Execution becomes `exec-abstract : ℕ → AbstractProgram → MachineState →
  Maybe MachineState` (fuel, pc, `find-label`) — structurally identical to
  `Semantics.exec`, just over `AbstractInstr`/`StoredValue`.

**Correspondence then = 1-to-1 instruction relabel + a uniform
`StoredValue → Word` value encoding.** No structured↔flat bridge. Adding an
architecture = define its instruction relabel + reuse the value encoding.

## How this unifies with the SigOp-trace fuel

The SigOp-trace proofs already run over `Semantics.exec` — flat, pc, fuel.
Today the abstract machine's `exec-loop` fuel is a **second, parallel**
fuel in a structured model. Flattening makes the abstract machine share
the **one** flat-fuel model: straight-line codegen, recursion-scheme
loops, and SigOp effect traces all bound by the same fuel and proved by
the same induction principle. Fuel becomes the single universal currency,
which is the coherence the SigOp pivot was reaching for.

## Blast radius — the 43 `exec-trace` consumers

Categories (to confirm during M0 audit):
- **WF proof layer** (~20: `PairStackWF/*`, `ComposeWF`, `ApplyWF`,
  `CataLayer`, `RecTrace`, `Sum*WF`, `Curry*WF`, `ClosureWellFormed`, …)
  — prove an IR's trace yields `ValidAtWF`. These reason about
  `exec-trace`'s *reduction*; the deepest migration.
- **SigOp** (`Helper`, `Faithful`, `Proofs`, `RelaxedContract`, …) — these
  are ALREADY fuel/`Semantics.exec`-aligned; should get *simpler*.
- **Correctness/DirectSimulation** (×3 targets) — the correspondence;
  becomes the 1-to-1 relabel.
- **Examples** — collapse (`AbstractCataFoldInduction` +
  `CataDescendCompiledInduction` → one proof over the flat abstract CPU).

## M0 AUDIT RESULT (de-risks the cascade)

The structured control execs `exec-loop`/`exec-case-dispatch` appear in
only **8 files**: `SMCore`, `SMPrimitives`, the 3 `DirectSimulation`, and
our 3 Examples — **NOT the WF proof layer**. The 43 `exec-trace` consumers
use the **sequential interface** + reduction lemmas (`exec-trace-cons` ×11,
`exec-trace-append` ×7) — left-to-right list composition, independent of
how a single control-flow instruction executes internally.

Consequence: the deep "structured → flat control" change is contained to
~8 files. The WF layer keeps working through a **preserved sequential
`exec-trace`** whose `cons`/`append` lemmas hold for non-jump instructions.
`exec-trace` survives as the straight-line composition view; the flat
`exec` (pc/fuel/`find-label`) is the real model and the correspondence
target. Migration is far smaller than "43 sites".

## M3/M4 DECISIONS (2026-06-05 — the DirectSimulation→FlatSimulation swap)

Ground-truth audit corrected the plan's "DirectSimulation is dead" framing:

- `CompileCorrect.compile-correct` (the REAL top-level theorem, over the live
  `ir-to-trace`/`compile-trace`) **consumes `DirectSimulation.trace-sim`** — so
  DirectSimulation is *connected*, not dead. BUT it is **loop-blind and holed**:
  `exec-abstract (instr-ctrl _) = identity`, `exec-prog` is a straight-line
  walk, and `instr-sim (instr-ctrl _) = !!` / `instr-sim (instr-loop _) = !!`.
  The live cata emits exactly those `instr-ctrl` jumps, so DirectSimulation
  **never proved the cata loop** — its correspondence is vacuous there.
- `FlatSimulation` relates the real flat machine (`exec-flat`, pc/jump/fuel) to
  the real x86 CPU (`Semantics.exec`) — the only correspondence that runs the
  loop. Currently standalone (imported by nothing) and clean (0 postulates).

**Principle (user):** don't judge by "connected?" but by "*should* it be
connected?". FlatSimulation should be (→ connect it); the old `compile-ir`
second codegen should not (→ deleted, 0.31-0b, this session); DirectSimulation
should stay only until FlatSimulation takes its bridge.

**DECISION — wholesale flat, ONE execution view** (user, 2026-06-05): no two
execution models. `exec-flat` becomes *the* abstract semantics end-to-end;
`exec-trace` is removed or reduced to a straight-line specialization of
`exec-flat`. Cleaner end state is worth more than fewer edits. Sound proof
obligations (postulates/`!!`) are acceptable as the bridge **only if clearly
provable from context**.

**Minimal swap path:**
1. `FlatSimulation` top-level `flat-sim` = per-instruction block-step lifted
   over the whole flat program by fuel-induction. Remaining inputs as
   clearly-provable postulates: alloc-heap block-step (0.35 M6, contract
   designed), stack-ops block-step (deferred, mechanical), fuel-induction lift
   (mechanical once block-step total).

   **MACHINE-SIDE LIFT DONE (2026-06-06).** Two new postulate-free modules:
   - `Target/X86-64/ExecCompose.agda` — `exec-just-compose : exec a P s ≡
     just s' → halted s' ≡ false → exec (a + b) P s ≡ exec b P s'` (the
     `exec≡just` counterpart of `StepLemmas.exec-steps`, chains x86 blocks).
     Proof: match the `State` as `mkstate _ _ _ _ h` to expose `halted` as a
     literal (else `exec (suc n)` eta-expands `s` inside `just s` and defeats
     subst/cong); the `with…in` then reduces `eq`+goal, collapsing the
     non-halting case to the IH.
   - `Target/X86-64/FlatSim.agda` — `flat-sim`: the fuel induction lifting
     `block-step` over a whole program → `∃ m s'. X.exec m (compile-trace
     prog) s ≡ just s' × CompiledCorr prog (exec-flat fuel prog fs) s'`. Uses
     the flat machine's `exec-flat-halted/step/offend` so each branch's
     CompiledCorr index lands definitionally (no transport); x86 fuel chained
     by `exec-just-compose`. Takes 3 clearly-provable inputs as HYPOTHESES
     (not postulates): `block-step-all` (per-instr dispatcher — block-steps
     done for cata instrs; alloc-heap/stack-ops deferred), `flat-no-halt`
     (a fetched compiled instr never halts the flat machine), `end-corr`
     (x86 halts in correspondence at `fetch ≡ nothing`). DISCHARGE next.
2. Migrate the WF layer (`CataLayer`, `RecTrace`, `Sum*WF`, `Curry*WF`,
   `ComposeWF`, …) + `CompileCorrect` off `exec-trace` onto `exec-flat`
   (`exec-flat` ↔ `Semantics.exec` via `flat-sim`).

   **CHOICE (a) — one model + a proven specialization** (user, 2026-06-05).
   `exec-flat` is *the* abstract semantics. `exec-trace` does NOT remain a
   parallel definition; it survives only as a **theorem about `exec-flat`**:

   > `exec-trace-is-flat : (trace jump-free) → exec-flat … ≡ exec-trace …`

   This is a *provable* bridge lemma, NOT definitional — `exec-flat` walks a
   pc via `fetch`/`find-label` while `exec-trace` folds the list, so they
   differ in recursion shape but agree in result on jump-free traces (both
   thread `exec-abstract` per instruction; cf. `flat-step-straight`). KEY
   FACT: **only `Cata` has a loop** — every other WF proof (`Pair`/`Sum`/
   `Curry`/`Compose`/`Simple`) is straight-line, so those reuse the bridge
   unchanged; only `Cata`'s WF + the arch correspondence go fully flat.
   So (a) is genuinely ONE execution model (`exec-flat`) with a derived
   theorem — it does NOT reintroduce the two-views trap. Rewriting the ~43
   consumers directly onto `exec-flat` (option b) is cosmetic and can fall
   out opportunistically later.

   First concrete step: prove `exec-trace-is-flat` (the straight-line bridge).

   **STEP 2 SEMANTIC-SIDE LIFT DONE (2026-06-06, user: semantic-side first).**
   Three new postulate-free modules build the reusable transport from an
   `exec-trace`-stated `ValidAtWF` onto the flat final state:
   - `Codegen/StraightTrace.agda` — `StraightIR` (Cata-free predicate) +
     `straight-ir-to-trace : StraightIR ir → Straight (ir-to-trace ir)`.
     Only `Cata` emits `instr-ctrl` into the main trace (case→case-on-tag
     arg, curry→bodies list), so the predicate excludes exactly `Cata` and
     recurses only into `_∘_`/`⟨_,_⟩`.
   - `Machine/ValidAtWFHalted.agda` — `validAtWF-set-halted : ValidAtWF … s
     → ValidAtWF … (record s {halted = b})`. Premises pass through via
     `readLoc-stack-heap-eq` (readLoc ignores halted); companion module,
     `ClosureWellFormed` untouched.
   - `Codegen/FlatSemanticLift.agda` — `lift-validAtWF-flat`: the capstone,
     two substs over the `exec-trace-is-flat` equalities (alloc + forced
     state) after `validAtWF-set-halted true`.
   Remaining semantic-side: APPLY `lift-validAtWF-flat` in the grand theorem
   (restate `compile-correct`'s semantic conjunct over `exec-flat`) — this
   couples with the machine-side rethread below.
3. Re-thread `compile-correct`/`EndToEnd`; delete `DirectSimulation` +
   `AbstractSimulation`.

Sequencing reality (a real cycle the original order missed): full
DirectSimulation retirement ⊃ FlatSimulation complete ⊃ alloc-heap block-step ⊃
**0.35 M6**. So 0.35 M6 (allocator call-boundary contract) is on this critical
path; the alloc-heap obligation is the one postulate that 0.35 M6 discharges.

## Key risks / decisions

- **Does `exec-trace` survive?** If many WF proofs only need
  "trace → final state" (interface), keep a total straight-line
  `exec-trace` wrapper to shrink the cascade; the *correspondence* still
  uses the flat `exec`. Decide in M0 — but beware re-creating two models;
  the end-state is ONE flat `exec`.
- **Shared core vs mirror?** M1 mirrors `Semantics.exec`'s shape in a
  separate module (less coupling, correspondence still 1-to-1). A later
  refactor could parameterize a single core instantiated for abstract +
  each target (true CompCert/CakeML shared framework) — out of scope for
  0.32, revisit after M3.
- **Heap-only value model** stays; the `StoredValue→Word`/`HeapLocation→ℕ`
  encoding is the value-correspondence (simple, uniform, proven once).

**DESIGN RULE — `with`-free `exec`.** The flat machine's `step` /
`execInstr` / jump resolution must NOT use `with`/`case`-on-scrutinee:
each routes through a top-level helper taking the decision value (fetched
instr, `find-label` result, `zf`, encoded read) as an explicit argument —
the SMCore `exec-load-via-resolved`/`-with-value` pattern (Plan 0.27).
`with` freezes reduction behind a case tree, which is exactly the friction
the 1-to-1 correspondence proofs must avoid (they reduce under the
value-encoding hypotheses). ([[feedback_with_clauses_painful]],
[[feedback_with_abstraction]], [[catchall_preserves_reductions]].)
