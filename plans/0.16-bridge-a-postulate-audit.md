## Once Compiler Formal Verification

## Executive Summary

**Total obligations:** 116 `SMP.!!` postulates across 11 producer modules. Bridge A consists of:
1. **Core abstraction** (`ClosureWellFormed.agda`): `IRResultBase` (14 fields) + `IRStackBudget` (11 fields) + `IRHeapBudget` (6 fields) + `ResultPlace` data + extraction helpers with 4 unit-result postulates.
2. **Per-IR producers**: Translate IR semantics to `IRResultAWF` witnesses.
3. **Bridge theorem** (`IRTraceCorrect.agda`): Closes the gap between codegen trace shape (`IRToTrace`) and producer trace shape (`run-X`).

**Key finding:** The 116 obligations cluster into **4 archetypal patterns**, of which **2 are fighting abstractions** (should be refactored) and **2 are fighting proofs** (real work). Most obligations are consequences of architectural mismatch, not genuine semantic gaps.

## B. Pattern Recognition

### Pattern 1: instr-alloc-stack structural mismatch (14 SMP.!!)

**Manifestation:**
- SumRecWF, PairHeapWF, ApplyWF emit `instr-alloc-stack n ∷ ...` at the start of their traces.
- IRToTrace doesn't (function prologue handles slot allocation globally).
- `trace-is-ir-to-trace` fails to unify; producers post `SMP.!!` placeholder.

**Files affected:**
- SumRecWF.agda lines 379, 535, 685, 806, 974, 1098, 1186, 1271 (8 producers × 1–2 occurrences each)
- PairHeapWF.agda line 112
- ApplyWF.agda line 205

**Verdict:** **FIGHTING ABSTRACTION**. The IRToTrace and producer trace shapes are architecturally divergent by design. Solutions:
1. Drop `instr-alloc-stack` from producers (requires redefining prologue in producers; ripples to alloc-final).
2. Add it back to IRToTrace (changes runtime codegen; small but visible change).

### Pattern 2: alloc-correct heap-mode scaffold (13 SMP.!!)

**Manifestation:**
- Heap-mode producers (SumInlHeapWF, SumInrHeapWF, PairHeapWF, CurryHeapWF) post `alloc-correct = SMP.!!`.
- Phase A marked as "scaffold"; Phase C discharges require per-producer trace-execution verification.
- Stack-mode SimpleWF discharges trivially (`trace-correct = refl` + `alloc-correct = refl`).

**Files affected:**
- SumInlHeapWF.agda line 88
- SumInrHeapWF.agda line 88
- PairHeapWF.agda line 114
- CurryHeapWF.agda line 128
- PairWF2.agda line 101 (1 postulate)

**Verdict:** **FIGHTING PROOF** (in principle). The obligation is real: the trace execution must produce the intended alloc-final state. However, the per-producer discharge is independent. These are Phase C discharges—legitimate proof work required for each heap-mode IR.

### Pattern 3: trace-twf + mem-preserved-before composite (17 + 16 = 33 SMP.!!)

**Manifestation:**
- SumRecWF case-dispatch producers (lines 700, 821) chain per-instruction `TraceWF` via `twf-∷ (SMP.!!) twf-[]`.
- These are load-indirect/load-indirect-suc instruction witnesses.
- ApplyWF has 13 such per-instruction witnesses (lines 358, 452, 454, 457, 500, 535, 553, 556, 597, 599, 602, 625, 627, 630, 702).
- mem-preserved-before (16 total) captures the consequence: "caller's BeforeFrontier locations read the same after the trace."

**Key entanglement (SumInlHeapWF 88–94 pattern):**
```agda
alloc-correct = SMP.!!            -- [1] Trace exec produces alloc-final
trace-twf = SMP.!!                -- [2] Per-step instruction validity
mem-preserved-before = λ _ _ → SMP.!!  -- [3] Caller memory unchanged
not-halted-final : exec-trace-preserves-halted-WF ... SMP.!!  -- [4] Halted preserved
```
All four share the same per-step state evolution. If we factor that evolution once, three of them derive for free.

**Files affected:**
- SumRecWF: per-instr witnesses at 700, 821 + mem-preserved-before at 386, 542, 701, 822, 985, 1105, 1193, 1282
- ApplyWF: per-instr at 358, 452–457, 500, 535, 553, 556, 597–602, 625–630, 702 + mem-preserved-before at 212
- PairHeapWF: mem-preserved-before at 120
- CurryHeapWF: mem-preserved-before at 134
- SumInlHeapWF, SumInrHeapWF: per-instr `exec-trace-preserves-halted-WF` at 177 (each)

**Verdict:** **FIGHTING ABSTRACTION**. The 33 obligations exist because the per-trace state evolution is tracked in isolation for each purpose. A single `TraceEvaluator` record (described below) would consolidate this.

### Pattern 4: Slot-frontier alignment (12 SMP.!!)

**Manifestation:**
- Compose, Pair, Curry, Apply all must align their static `next-slot alloc` in the run-X spec with the dynamic frontier counter in IRToTrace.
- IRTraceCorrect tries to bridge via `ir-to-trace-at-frontier (next-slot alloc) ir`, but sub-IRs' final frontiers must match parent's static offsets.
- Slot-frontier alignment postulates in IRTraceCorrect (3) + producer-side mismatches contribute to trace-is-ir-to-trace failures.

**Files affected:**
- IRTraceCorrect.agda lines 362–366 (inl-stack, inr-stack), 412+ (pair, curry, apply catchall)
- SumRecWF.agda lines 379, 535, 685, 806, 974, 1098, 1186, 1271 (cascading from frame dispatch)

**Verdict:** **FIGHTING ABSTRACTION**. The frontier alignment is architectural. Plan 0.14 refactored to `ir-to-trace-at-frontier`, but producers and IRToTrace still disagree on when slots are allocated (prologue vs. inline).

**Manifestation:**
- `ResultPlace` has constructors `at-loc` (6 fields: loc, valid, before, rax-eq, cont-valid, cont-before) and `unit-result` (0 fields).

## C. Abstraction Recommendations

### Recommendation 1: TraceEvaluator Record (eliminates 33 SMP.!!)

**Problem:** Obligations `alloc-correct`, `trace-twf`, `mem-preserved-before`, `not-halted` all depend on the same per-instruction state trajectory. Each is proven in isolation, leading to 33 postulates.

**Solution:** Introduce a `TraceEvaluator` record bundling the per-step state evolution:

```agda
record TraceEvaluator {FS} (trace : AbstractTrace) (s : LocState FS) 
                      (alloc : AllocState {FS}) : Set where
  field
    final-state : LocState FS
    final-alloc : AllocState {FS}
    -- Per-instruction execution faithfulness
    trace-wf : TraceWF s alloc trace
    -- Exec result matches stored final state
    exec-state-eq : proj₁ (exec-trace trace s alloc) ≡ final-state
    exec-alloc-eq : proj₂ (exec-trace trace s alloc) ≡ final-alloc
    -- Consequences derived from trace-wf
    mem-preserved : ∀ (loc : ValueLocation FS) → BeforeFrontier alloc loc →
                    readLoc final-state loc ≡ readLoc s loc
    halted-preserved : halted final-state ≡ false → halted s ≡ false
```

**Blast radius:**
- SumRecWF: case-dispatch producers (inl, inr, case-inl, case-inr, in) replace 3 postulates each with a single `TraceEvaluator` witness.
- ApplyWF: replace 13 per-instr witnesses + mem-preserved-before + not-halted + alloc-correct (15 total) with 1 composite.
- PairHeapWF: replace alloc-correct + trace-twf + mem-preserved-before + not-halted (4 postulates) with 1.
- CurryHeapWF: same (4 → 1).

**Estimated reduction:** 33 → ~10 postulates (TraceEvaluator constructor discharges per-producer, amortizing the per-instr burden).

**New obligations introduced:** Per-producer must discharge `TraceEvaluator` instead of 3+ separate fields. But the structure is a single coherent proof object, not scattered pieces.

**Files modified:**
- New: `Once/CCC/Machine/TraceEvaluator.agda`
- Modified: SumRecWF, ApplyWF, PairHeapWF, CurryHeapWF (update producer traces to return TraceEvaluator)
- Modified: ClosureWellFormed (import TraceEvaluator, add smart constructors to IRResultBase from TraceEvaluator)

**Requires changes:**
- IRResultBase fields: `trace-twf`, `mem-preserved-before` could be marked `@erased` after extraction from TraceEvaluator (they're proofs of properties already captured).
- IRTraceCorrect: bridge discharges now destructure TraceEvaluator and rewrite through its fields (no new postulates).

**Load-bearing lemma:** 
```agda
trace-evaluator-from-trace-wf : ∀ trace s alloc → TraceWF s alloc trace →
  ∃ (te : TraceEvaluator trace s alloc), …
```

This lemma IS the per-instruction chaining and will still need SMP.!! for per-instr load-indirect/store-indirect witnesses until those instructions' semantics are defined. But it centralizes the dependency.

### Recommendation 2: instr-alloc-stack alignment resolution (eliminates 14 SMP.!!)

**Problem:** Producers emit `instr-alloc-stack`, IRToTrace doesn't. trace-is-ir-to-trace fails.

**Option A (recommended): Drop from producers**
- Refactor SumRecWF, PairHeapWF, ApplyWF, CurryWF traces to NOT emit instr-alloc-stack.
- Update alloc-final definitions to track slot frontier separately (don't bump next-slot in trace).
- Prologue remains; trace execution doesn't bump.
- **Impact:** ~8 files, ~20 lines changed per file. High confidence (architectural intent is clear).
- **Postulate reduction:** 14 SMP.!! → 0 (trace-is-ir-to-trace discharges via `refl`).

**Option B: Add to IRToTrace**
- Emit instr-alloc-stack in IRToTrace for non-trivial IRs.
- Update compile-trace to handle it (already does; it's a no-op in runtime x86).
- **Impact:** Changes runtime codegen slightly; lower risk than Option A if codegen is already tested.
- **Postulate reduction:** Same 14 → 0.

**Recommendation:** Option A (keep producer-side consistent, avoid runtime codegen change).

**Files modified:**
- SumRecWF.agda (6 producers, lines 379, 535, 685, 806, 974, 1098, 1186, 1271)
- PairHeapWF.agda (1 producer, line 112)
- ApplyWF.agda (1 producer, line 205)
- Correlate with alloc-final definitions in each.

### Recommendation 3: Consequence-form mem-preserved-before derivations (14 SMP.!! → 5)

**Problem:** mem-preserved-before is stated as a consequence-form (good), but producers still post postulates because the connection to trace shape isn't explicit.

**Solution:** Provide per-producer derivation helpers:

```agda
-- SumRecWF case-dispatch shape: load-indirect ∷ result-f.trace ∷ result-g.trace ∷ [...]
mem-preserved-compose-case : ∀ f g s alloc result-f result-g →
  mem-preserved-before (result-f.trace ++ result-g.trace) →
  mem-preserved-before-combined

-- ApplyWF frame-preservation: setup-trace ++ body-trace
mem-preserved-apply-compose : ∀ setup-trace body-trace →
  TraceWF s alloc (setup-trace ++ body-trace) →
  frame-preserved setup-trace →
  mem-preserved-before (setup-trace ++ body-trace)
```

**Blast radius:**
- SumRecWF: 8 mem-preserved-before postulates → 3 (one helper per producer family: inl, inr, case).
- ApplyWF: 1 mem-preserved-before postulate → 0 (derive from frame-preserved + setup-trace properties).
- PairHeapWF, CurryHeapWF: 2 postulates → 2 (heap-mode mem-preservation is harder; may need heap footprint lemmas).

**New obligations introduced:** Per-helper requires load-bearing lemma about heap/stack isolation and trace composition. These are real proof work but localized.

**Files modified:**
- New: `Once/CCC/Machine/TracePrimitives/MemPreserved.agda` (5 derivation helpers)
- Modified: SumRecWF, ApplyWF (use helpers instead of postulating mem-preserved-before)

### Recommendation 4: Unit-result type-aware refactor (eliminates 4 SMP.!!)

**Problem:** `ResultPlace` forces all consumers to carry `place-*` extraction logic for Unit results, which is vacuous.

**Solution:** Two parallel tracks:
1. **Short-term:** Keep postulates but add a remark that they're transitional (done; ClosureWellFormed already documents this).
2. **Long-term:** Refactor `rec-wf` preconditions to be type-aware:
   ```agda
   rec-wf : ∀ {A B} → IR A B → RecDispatcherWF ...
   -- For Unit-typed IRs (A ≡ Unit), preconditions on input-loc are omitted.
   ```
   This makes the 4 postulates unreachable code (Agda would error if you tried to use them).

**Blast radius:** Medium (affects rec-wf, all consumers of result-place: Compose, Pair, RecTrace, Dispatcher).

**Estimated Phase:** Post Phase C (lower priority; doesn't block any ongoing discharge work).

### Recommendation 5: Consolidate per-instr load-indirect witnesses (13 SMP.!! → 3)

**Problem:** ApplyWF has 13 `SMP.!!` for per-instruction `load-indirect` and `load-indirect-suc` TraceWF witnesses.

**Solution:** Factor `load-indirect-witness` and `load-indirect-suc-witness` helpers:

```agda
load-indirect-twf : ∀ {FS} (s : LocState FS) (input-loc : ValueLocation FS) →
  readReg (regs s) Input1 ≡ SV-Ptr input-loc →
  readLoc s input-loc ≡ just (SV-Ptr result-loc) →
  InstrWF (load-indirect) s
```

Then in ApplyWF:
```agda

step1-tph = twf-∷ (load-indirect-twf s1 closure-loc closure-readable) twf-[]
```

**Blast radius:** ApplyWF (13 → 3), possibly ComposeWF (load-indirect composition).

**Estimated reduction:** 13 → 1 helper + 2–3 per-producer applications.

**Files modified:**
- Modified: SMPrimitives.agda (add load-indirect-twf, load-indirect-suc-twf helpers)
- Modified: ApplyWF (use helpers)

### Summary Table

### Key insight

**Fighting Proof** work (alloc-correct, halted-preservation, load-indirect semantics, ValidAtWF result-loc):
- These require genuine proof labor—step through the trace, verify invariants hold at each step.
- Consolidating them into a single `TraceEvaluator` structure doesn't reduce the work, but it makes the coupling explicit and prevents re-proving the same per-step facts 4+ times.

**Fighting Abstraction** work (trace-is-ir-to-trace, mem-preserved-before, unit-result postulates, place-* extraction):
- These exist because the types don't align or the specification is mis-shaped.
- Fixing them requires design change (drop instr-alloc-stack, make rec-wf type-aware), not more proof tactics.
- Attempting to "just prove" these by layering more Agda tactics will fail.

## E. Hidden Coupling Analysis

### SumInlHeapWF alloc-correct entanglement (10-instr trace)

The user observed that `alloc-correct` on SumInlHeapWF's trace cannot be proven in isolation—it depends on:
1. **Halted preservation** through the trace (lines 137–146: mov-to-output, store-at-slot, instr-alloc-heap, store-indirect, etc.)
2. **Register values at key steps** (e.g., Output = SV-Ptr sum-loc at step 10 for store-indirect-suc)
3. **Heap write tracking** (instr-alloc-heap + store-indirect don't corrupt Input1)

**Per-step state evolution:**
```
s0 → s1 (mov-to-output)
s1 → s2 (store-at-slot)
s2 → s3 (instr-alloc-heap) ← heap frontier bumps here
s3 → s4 (store-indirect)
...
s9 → s10 (load-from-slot) ← Output becomes SV-Ptr sum-loc
s10 (ready for store-indirect-suc)
```

**Coupled obligations that need this evolution:**
1. `alloc-correct` — proof final-alloc matches exec-trace's alloc (requires tracing next-heap-ref through each instr)
2. `sum-rax-eq` (line 164) — proof Output = SV-Ptr sum-loc at final state (requires step 10 state)
3. `sum-valid-final` (line 158) — proof sum-loc satisfies ValidAtWF (requires knowing heap allocation was successful)
4. `mem-preserved-before` (line 94) — proof caller's BeforeFrontier locs read the same (requires tracing read paths)
5. `not-halted-final` (line 177) — proof halted s-final ≡ false (requires halted preservation through trace)

**Verdict:** **STRUCTURAL COUPLING (real), but resolvable via TraceEvaluator.**

The coupling is real—you cannot discharge any one of these without understanding the entire per-step state evolution. But the solution is not to "work harder" at proving them separately; it's to **factor the state evolution once** and have all five obligations *consume* it.

This is exactly what `TraceEvaluator` achieves: the record captures the per-step trajectory, and the obligations are consequences (sometimes trivial, sometimes requiring load-bearing lemmas) derived from it.
