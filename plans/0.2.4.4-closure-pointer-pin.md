# Plan 0.2.4.4: Closure pointer pin (closure[1])

## Context

A 2026-05-05 audit started from what looked like a cosmetic issue:
`CurryStackWF.curry-trace` stores `lea-slot (suc closure-slot)` (a self-
pointer to the closure's own second slot) into `closure[1]`, while
`IRToTrace.curry` correctly stores `instr-load-code-addr label` (the
body's actual code address). Two different abstract traces, two
different runtime values, bridged by the postulate
`ir-to-trace-correct-curry`.

The audit found this isn't cosmetic — it's the load-bearing structural
disconnect that lets a buggy codegen put **anything** at `closure[1]`
without the typechecker noticing. Three independent mechanisms compose
to create the hiding place:

1. **`exec-abstract instr-call-closure s alloc = s , alloc`** in
   `Once.CCC.Machine.SMCore`. The slot-machine semantics treats the
   indirect call as a no-op. Whatever is at `closure[1]` is irrelevant
   — execution never *follows* the pointer abstractly.

2. **`exec-x86 (call _) xs _ = xs`** in
   `Once.CCC.Target.X86-64.DirectSimulation`. The simulation model
   says calls don't change state. Equivalent to a postulate "calls
   are identity" at the simulation level — false at real runtime
   (where `call` pushes return address and jumps), but the model
   pretends otherwise.

3. **Type-driven body dispatch.** `ApplyWF.run-apply` extracts the
   body IR from `decomposeClosureWF`'s witness (a *type-level*
   value), not by reading `closure[1]` from runtime memory. So the
   spec runs the right body even if `closure[1]` holds garbage.

These together decouple runtime control flow from abstract control
flow. The bridges that connect runtime to spec
(`ir-to-trace-correct-{curry,apply}` in `IRTraceCorrect.agda`) are
**postulates** — visible to `make postulates-grep` but unverified.

The (1) and (2) modeling-by-omission entries are not literally
`postulate`s, but they're the structural reason the postulates can
absorb the gap: with calls as no-ops everywhere abstract, `closure[1]`
can hold any value and the proofs go through.

## Goal

Pin `closure[1]`'s value at the spec level: a closure-validity witness
must name a body label `n` and prove `closure[1] ≡ encode-code-addr n`.
A buggy codegen that stores anything else cannot construct the witness,
so apply-correctness refuses to typecheck.

This closes the pointer-corruption hiding place at the spec layer.
Wiring abstract `instr-call-closure` to actually follow `closure[1]`
(the deeper fix) is staged as a follow-on.

## Approach

### Stage 1 — Spec-level pin (the closeable gap)

Already started; in progress. Adds the structural witness that codegen
must satisfy.

1. **`Once.CCC.Machine.SMCore`** — add a sibling postulate to
   `encode-code-addr`:
   ```agda
   decode-code-addr : ValueLocation FS → ℕ
   encode-decode-code-addr : ∀ (n : ℕ) →
     decode-code-addr (encode-code-addr n) ≡ n
   ```
   These are small, named, removable when a real label model lands.
   Status: ✓ landed (uncommitted).

2. **`Once.CCC.Machine.ClosureWellFormed`** — strengthen
   `valid-closure-wf` and `ClosureValidWF`:
   - Add `body-label : ℕ` field.
   - Replace `code-loc : ValueLocation FS` arbitrary field with
     `code-ptr : readLoc s (sucLoc closure-loc) ≡ just (encode-code-addr body-label)`.
   - Replace `code-before : BeforeFrontier alloc code-loc` with
     `code-before : BeforeFrontier alloc (encode-code-addr body-label)`.
   Status: ✓ constructor + record updated; ~7 downstream pattern
   sites in `ClosureWellFormed.agda` still need arity update.

3. **`CurryStackWF.curry-trace`** — take a `body-label : ℕ` parameter
   (threaded from the dispatcher) and emit `instr-load-code-addr
   body-label` instead of the `lea-slot` placeholder. Establish
   `code-ptr` and `code-before` from the trace's post-state.
   Status: pending.

4. **`Dispatcher`** — thread the label counter (already used by
   `IRToTrace`) into `CurryStackWF.run-curry`. The Dispatcher and
   IRToTrace then agree on labels.
   Status: pending.

### Stage 2 — Couple `instr-call-closure` to `closure[1]` (the deeper fix)

Beyond the spec pin: change `exec-abstract instr-call-closure` from
no-op to "read `closure[1]`, decode to a label, dispatch the matching
trace from a label-keyed dictionary." This makes runtime control flow
*model-visible* and the simulation proof for `instr-call-closure`
non-trivial.

Requires:
- A label-to-trace dictionary in `AbstractExec` (or threaded as a
  parameter).
- `Simulation.trace-sim` for `instr-call-closure` to discharge that
  the x86 `call *0x8(%r12)` lands at the right label given
  `code-ptr ≡ encode-code-addr label`.
- `BodyCorrect` adjusted (or replaced) so body dispatch can flow
  through `closure[1]` rather than the type-level witness.

This is substantive; left for after Stage 1 + 0.2.4.3 land.

## Compose-test as live regression

Same as 0.2.4.3 — `(id . id . id) 42` exits 42 once Stage 1 lands.
The 3-id segfault we currently see manifests only when 3+ closures
chain because the temp-frame escape compounds; Stage 1's pin makes
the typechecker reject any codegen that doesn't store the right code
address, which is the type-level analogue of catching the runtime
bug.

## Out of scope

- Stage 2 (`instr-call-closure` runtime coupling) — separate plan
  follow-on once Stage 1 + 0.2.4.3 land cleanly.
- Layer 5+ recursive closures.
- Reflection of `body-label` into the surface IR — labels stay
  inside `IRToTrace`/Dispatcher; the surface IR doesn't see them.
