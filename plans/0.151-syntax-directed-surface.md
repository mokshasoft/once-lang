# Plan 0.151 — The surface typing has one rule per form, and the generators are a table

## Summary

The language definition says which programs are accepted with a list of typing rules. Today most of
that list repeats one pattern: each of the language's dozen building blocks (`id`, `fst`, `inl`, `compose`,
`cata`, …) has its own rule, often three times over, once per way of checking. Some programs also match
more than one rule. This plan rewrites the list so that each kind of expression has exactly one rule, and
the building blocks are described once, in a table, instead of rule by rule. The accepted programs and
their meaning do not change. When it is done, the definition is shorter and reads as mathematics, and a
rejected program fails exactly one identifiable rule. That last property is what plan 0.149 needs in order
to explain every rejection with a proved reason.

## 1. Why

A category theorist reading `Spec/Surface/Typing.agda` would recognise the core (D231: the typed λ-calculus
as the internal language, the generators defined in it, `Core/Derived`) and be puzzled by the surface:

- **The generators are rules, not data.** 38 of the 65 rules are about one named generator in one mode
  (`c-fst`, `d-fst`, `s-fst-app`, …). A generator is a morphism with a type schema. Its typing should be one
  rule ("instantiate the schema") over a table, as plan 0.150 does for the numeric operators.
- **Some expressions have more than one rule.** The mode switches (`c-sub`, `d-infer`) apply wherever a more
  specific rule also applies (`c-pair-lit`, `d-lam`, `d-compose`, …), and some forms have alternative routes
  (`c-compose-g` / `c-compose-f`, D230; `s-app` / `s-app-spine`). A program that is rejected then has no
  single rule it breaks, so an error message cannot be a proved fact about the Spec (plan 0.149).

D316's amendment already asked for "generic rules where the per-generator ones only repeat them". This plan
carries that out and adds the second half: rule choice determined by the expression and the mode.

## 3. Decisions

- **E1, modes.** (a) Keep the three modes (D316's amendment); the cleanup is inside the bidirectional
  judgment. (b) Mode-free: a language change with full inference. Recommended: (a). Open.
- **E2, the generator table.** Each generator gets one entry: its type schema, the types of its arms if it
  takes any (`compose`, `case`, `pair`, `curry`, `cata`, `ana`), which of its type variables the expected
  type or domain determines (what decides the mode it can be used in), and its `Core/Derived` definition.
  The per-generator rules become one rule per mode over the table. Open points: the generators whose rule
  depends on the grade or the type, not just the schema (`apply` / `apply-eff`, `Out` / `Out-act`,
  `ana` / the loop, D317), and whether they are separate table entries or one entry with a type-directed
  case. Open.
- **E3, one rule per form and mode.** For each overlap, either (a) the Spec rule is restricted so that only
  one applies (a mode switch only for forms with no rule of their own in that mode; one route for
  `compose`), or (b) the Spec keeps the overlap where it reads as a definition, and the implementation's
  algorithmic judgment is syntax-directed, proved equivalent. Recommended: (a) wherever the restricted
  rule still reads as a definition, decided per overlap from the inventory; (b) only when (a) needs an
  algorithmic side condition. The property itself is stated as a metatheory claim (rule choice is a
  function of the form, the mode and the head of the given type), so a later rule cannot reintroduce an
  overlap unnoticed. Open.
- **E4, what must not change.** The same texts are accepted, and each elaborates to the same core term, so
  `Core`, `Meaning` and everything after elaboration are untouched. Proved as an equivalence between the
  old and new judgments during the branch; the old one is then deleted. Open, recommended.
- **E5, scope.** Surface typing first. Resolution, `Surface.Program` and the grammar (unambiguous by
  construction, the parse-error counterpart of one rule per form) are reviewed in the same step 1, and the
  user decides whether they join this plan or get their own. Open.

## 4. Steps

   `Surface.Program` and the grammar, for E5. No code.
2. **Decisions E1–E5 with the user**, from the table.
3. **The Spec patch**, drafted in a scratch worktree and approved as one patch (`make spec-approve`): the
   generator table, the new rules, the restated metatheory claims and the one-rule-per-form claim. Gate:
   `Once/Spec.agda` type-checks and the spec gates pass.
4. **Equivalence** (E4): old and new judgments accept the same expressions with the same core terms, in an
   implementation-side module, with the old rules copied there for the duration of the branch. Gate: the
   module alone, inside the per-module budget (D373).
5. **Follow the red**: `Elaborate` reads the table, `ElaborateSound`, `Completeness` (`Rules`, `Routes`), the
   usage modules, `Witness`, `SpecFront`, `Metatheory.Surface`, `Adequacy`, `RealizeS`. Then the
   equivalence module and the old rules are deleted (no legacy copies). Gate: `make certified`,
   `cabal test` (texts unchanged).
6. **Records and gates**: a decision entry (amends D316's amendment, relates D230), MAlonzo re-extraction,
   the exit tests on all arches, `make merge-gate`, the AST dumps.

## 5. Done when

The surface typing has one rule per expression form and mode. The generators are a table, each described
once. The Spec claims, and the metatheory proves, that the rule for an expression is determined by its
form, mode and given type. The same programs are accepted with the same core terms. No per-generator rule
remains.
