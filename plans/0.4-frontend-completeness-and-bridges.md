# Plan 0.4: Frontend Completeness & Semantic Bridges

## Context

Plan 0.3 closed the bulk of the frontend verification gaps. The
pipeline is now extensionally correct *in one direction*:

- Parser is total, sound against the parsing relation, and
  pretty→parse round-trips (`round-trip-concrete-expr`).
- Typechecker is intrinsically typed (`inferElab` produces
  `Expr Γ Ψ A`; linearity-by-construction).
- Zero postulates / zero `TERMINATING` pragmas across parser →
  typechecker → surface elaboration.

What remains unproved falls into three buckets, ranked by size and
value:

1. **G2 completeness** — every well-typed program is *accepted* (not
   just: every accepted program is well-typed).
2. **G1 parse→pretty direction + grammar conformance** — the parser
   extensionally agrees with the grammar spec in *both* directions.
3. **Surface-semantics bridges** — three small `postulate`s in
   `Surface/Correct.agda` (`intLit-correct`, `effApp-correct`,
   `prim-correct`) plus `extensionality` in `Postulates.agda`.

Plan 0.4 closes items 1-3. After 0.4, the frontend is "fully
verified" modulo `extensionality` (a standard Agda axiom we keep).

## Scope

In scope:
- `formal/Once/Parser/`
- `formal/Once/TypeCheck/`
- `formal/Once/Surface/` (including `Surface/Correct.agda`)
- `formal/Once/Grammar/` (including grammar conformance predicate)

Out of scope (has its own track):
- CCC / IR backend (`formal/Once/CCC/`, `formal/Once/Escape`,
  `formal/Once/Fusion`) — covered by 0.2.x plans.
- G8 performance bounds — deferred indefinitely.

## The Gaps (prioritized)

### T1 — G2 typechecker completeness (LARGEST)

**Goal**: state and prove
```agda
complete-type :
  ∀ {ctx e T} → Judgment ctx e T
  → ∃ λ (d : InferResult ctx) → extract d ≡ just (T, -)
```
(and the check-mode variant) — where `Judgment` is the declarative
typing relation defined in `Once.Judgment`.

**What could fail without this**: a case in `checkElab` falls through
to `failure` for some well-typed shape the author didn't consider.
After the 0.2.6 linearity refactor, polymorphic-builtin specialization
happens only at pattern-matched shapes (e.g., `RVar "compose"` fully
applied); a slightly-different shape — `compose` split across a
`let`-binding — can fall through to the generic path and fail.

**Strategy**:
1. Audit `Once.Judgment`: confirm all typing rules landed in plan
   0.3's G2(a) split (`Judgment` → mutual `Infers` / `Checks`). Any
   missing rule is a hole in the completeness statement.
2. Walk each `Judgment`/`Checks` constructor and prove the
   corresponding `inferElab`/`checkElab` path succeeds. Expected
   structure mirrors `Surface.Correct.elaborate-correct`.
3. **Polymorphic-builtin completeness** is the sharp edge. Two
   sub-options:
   - (a) Prove a "shape-normalization" lemma: every judgment of the
     form `Γ ⊢ app (app compose f) g : T` can be rewritten to match
     the elaborator's expected n-ary shape.
   - (b) Generalize the elaborator to accept partial applications
     (restructure rather than prove). Likely cleaner; would close
     related latent bugs.
   Decision point before starting.

**Entry cost**: ~400-800 lines. Bigger if option (a), smaller if
option (b) (which shifts work to implementation).

**Wiring**: add a `tc-complete-*` field per rule to
`VerifiedTypeChecker` (structural enforcement via record).

### T2 — G1 parse→pretty direction

**Goal**:
```agda
parse-pretty-roundtrip :
  ∀ {toks g rest} → parseGExpr toks ≡ just (g , rest)
  → ∃ λ toks' → toks ≡ printGExpr g ++ toks' ∧ rest ≡ toks'
```
(and the type-side variant) — saying parser output, when pretty-
printed, reconstructs the token stream it was parsed from.

**What could fail without this**: the parser accepts `toks`, produces
`g`, but `printGExpr g` tokenizes to something *different* from
`toks`. Current proofs would not catch that.

**Strategy**:
1. **Induction on the parsing relation** (`ParsesExpr toks e rest`),
   not on the WF parser. Each relational constructor corresponds to a
   printer production; structural induction mirrors the printer's
   case analysis.
2. The critical premise per case: inner derivations already satisfy
   `printGExpr g_inner ++ r_inner ≡ toks_inner`.
3. Leaf cases (pae-unit, pae-int, pae-str, pae-var, pae-qual) are
   direct — one token becomes one printer call.
4. Compound cases compose via `++-assoc`.

**Entry cost**: ~300-500 lines. Less than `complete-expr` because
there's no parser-level `with`-dispatch to mirror — the relation is
fully abstract.

### T3 — G1 grammar conformance (`WellFormed ⟺ ∃ g. parse`)

**Goal**:
```agda
-- Formal grammar predicate (inductive)
data WellFormed : List Token → Set where ...

-- Soundness
parse-well-formed :
  ∀ {toks g rest} → parseGExpr toks ≡ just (g, rest)
  → WellFormed (take (length toks - length rest) toks)

-- Completeness
well-formed-parses :
  ∀ {toks} → WellFormed toks
  → ∃ λ g → parseGExpr toks ≡ just (g, [])
```

**What could fail**: a token stream the grammar says is valid fails
to parse (completeness), or the parser accepts something the grammar
rejects (soundness).

**Strategy**:
1. Define `WellFormed` as an inductive predicate mirroring
   `Once.Grammar`'s productions.
2. Soundness: induct on `ParsesExpr`. Each constructor produces a
   `WellFormed` witness for its token span. Mechanical after T2.
3. Completeness: induct on `WellFormed`. Invoke the `complete-expr`
   bridge per production to get a parser equation. Mechanical.

**Entry cost**: ~400-600 lines. Largest item is the `WellFormed`
datatype definition — expected to have 30+ constructors for
expression productions and 10+ for types.

**Dependency**: T2 should precede T3 (parse-pretty is reused).

### T4 — Surface-semantics bridge postulates

**Goal**: eliminate three postulates in `Surface/Correct.agda`:
```agda
postulate
  intLit-correct   : ∀ {Γ} (n : ℤ) (γ : ⟦ Γ ⟧)
                   → eval′ (intLit n) γ ≡ n
  effApp-correct   : ...
  prim-correct     : ∀ (n : String) → evalSurface ρ (prim n)
                                    ≡ eval′ (elaborate (prim n)) (interpEnv ρ)
```

**What could fail**: elaborated-form semantics and surface semantics
disagree on a literal leaf. A semantic mismatch slips through.

**Strategy**:
1. `intLit-correct`: unfold `intLit`, `eval′`, `evalPrim "lit.int.N"`.
   Should reduce to definitional equality. If it doesn't, identify
   the blocker — likely a case where `evalPrim`'s string-dispatch
   isn't definitionally unfolded.
2. `effApp-correct`: structural induction on the `effApp` constructor.
   Similar to `eval′ (f x)` unfolding; one lemma per IR primitive
   reached via `effApp`.
3. `prim-correct`: per-primitive case — one clause per builtin string
   name. Essentially a lookup-table correspondence between
   `evalSurface`'s primitive table and `elaborate`'s elaboration.

**Entry cost**: ~100-300 lines total; each postulate is small.

**Note**: `extensionality` in `Postulates.agda` stays as a postulate.
It's Agda's standard function-extensionality axiom; eliminating it
would require moving the whole proof tree to an extensional setoid
model, which is out of scope.

## Phase Ordering

Suggested:

1. **T4** first (smallest, independent) — closes the last three
   frontend postulates. A quick win establishes momentum.
2. **T2** (parse-pretty direction) — builds on existing parsing
   relation machinery; no new datatypes.
3. **T3** (grammar conformance) — reuses T2's structural lemma; adds
   `WellFormed` datatype.
4. **T1** (G2 completeness) — largest; benefits from being last
   because option-(b) of the polymorphic-builtin strategy may suggest
   elaborator restructuring that could ripple into other proofs.

Alternative ordering: T1 first if option-(b) restructures the
elaborator substantially — better to do structural changes before
piling proofs on top.

## Build & Test Strategy

```
timeout 300 make frontend
```
Must remain green at every commit. No new postulates. No
`TERMINATING` pragmas. Additions only — never weaken existing proofs.

Every theorem added is wired into `VerifiedTypeChecker` so a broken
proof fails the module graph, not just its own file.

## Verification

- `make frontend` green after each phase.
- `grep -c "postulate" Once/Surface/Correct.agda` goes from 3 to 0
  after T4.
- `grep "postulate\|TERMINATING" Once/Parser/ Once/TypeCheck/
   Once/Surface/ Once/Grammar/` returns only `extensionality` in
  `Postulates.agda` after T4.
- Each task adds a named theorem / datatype; no task deletes or
  weakens an existing proof.

## Expected Outcome

After 0.4:

- Frontend "fully verified" modulo `extensionality`:
  * Parser sound ⟺ grammar-well-formed.
  * Pretty → parse ⟺ parse → pretty round-trips in both directions.
  * Elaborator accepts ⟺ declarative judgment holds (G2 complete +
    the existing soundness).
  * Surface semantics = elaborated semantics (three postulates gone).
- The remaining three postulates are:
  * `extensionality` in `Postulates.agda` (kept; standard axiom).
- `VerifiedTypeChecker` record now mechanically enforces every proved
  property — a broken proof fails the build graph.

## Deferred Items

- **G5 integration at stage boundaries** — `parse ∘ elaborate ∘
  desugar` as a composed theorem. Individual stages are proved; the
  compositional statement is informal. Low value: a compositional
  bug would have to survive being invisible to all three individual
  soundness proofs. Could be added later if desired.
- **G6 typechecker determinism** as a stated theorem. Trivially
  holds because Agda functions are deterministic; stating it adds
  future-refactor guardrails but no immediate value. Low priority.
- **G8 performance bounds** — out of formal scope; belongs with CI
  benchmarks.

## Risks & Open Questions

1. **Polymorphic-builtin completeness (T1)** — option (a) vs (b).
   Option (b) (generalize elaborator) may be a large implementation
   refactor with its own proof re-work. Decision needed before T1
   starts.
2. **`WellFormed` datatype size (T3)** — 40+ constructors expected.
   Management via mutual blocks is routine but verbose. No
   fundamental risk.
3. **`prim-correct` per-primitive work (T4)** — depends on how many
   primitives the surface exposes. Scales linearly; no algorithmic
   risk.

## Non-Goals

- Adding new language features (graded types, refinement types,
  dependent types) — those belong in separate plans.
- Proving anything about MAlonzo-extracted code — outside the formal
  scope.
- QuickCheck-style randomized testing — see plan 0.3's "Why Not
  QuickCheck" section. Superseded by these proofs.
