# Plan 0.4: Frontend Completeness & Semantic Bridges

## Context

Plan 0.3 closed the bulk of the frontend verification gaps. The
pipeline is now extensionally correct *in one direction*:

- Parser is total, sound against the parsing relation, and
  pretty→parse round-trips (`round-trip-concrete-expr`).
- Typechecker is intrinsically typed (`inferElab` produces
  `Expr Γ Ψ A`; linearity-by-construction).
- Zero postulates / zero `TERMINATING` pragmas across parser →
  typechecker → surface elaboration.

What remains unproved falls into three buckets, ranked by size and
value:

1. **G2 completeness** — every well-typed program is *accepted* (not
   just: every accepted program is well-typed).
2. **G1 parse→pretty direction + grammar conformance** — the parser
   extensionally agrees with the grammar spec in *both* directions.
3. **Surface-semantics bridges** — three small `postulate`s in
   `Surface/Correct.agda` (`intLit-correct`, `effApp-correct`,
   `prim-correct`) plus `extensionality` in `Postulates.agda`.

Plan 0.4 closes items 1-3. After 0.4, the frontend is "fully
verified" modulo `extensionality` (a standard Agda axiom we keep).

## Scope

In scope:
- `formal/Once/Parser/`
- `formal/Once/TypeCheck/`
- `formal/Once/Surface/` (including `Surface/Correct.agda`)
- `formal/Once/Grammar/` (including grammar conformance predicate)

Out of scope (has its own track):
- CCC / IR backend (`formal/Once/CCC/`, `formal/Once/Escape`,
  `formal/Once/Fusion`) — covered by 0.2.x plans.
- G8 performance bounds — deferred indefinitely.

## The Gaps (prioritized)

### T0 — Globalize soundness (PREREQUISITE for T1)

**Discovered 2026-04-30 mid-T1.** The current verification framework
has only *per-shape* soundness lemmas (`tcInfer-sound-RInt`,
`tcInfer-sound-RApp-generic`, …, all collected as fields of
`VerifiedTypeChecker`). There is **no top-level theorem** of the
form

```agda
infer-sound : ∀ ctx e {A Ψ eE d f}
  → tcInfer ctx e ≡ success A Ψ eE d f
  → ctx ⊢ e ∶ A ⨾ Ψ
```

**Why this matters for T1.** Without a global theorem, adding a new
elaborator code path (CHANGE 2's argument-driven application is the
canonical example) can pass type-checking *without* a corresponding
judgment rule, because no per-shape lemma covers the new behavior.
The verification silently misses the gap. With a global theorem,
any new clause either matches a judgment rule (proof goes through)
or breaks soundness (forcing us to update the spec or revert the
clause). T1's whole point — adding new elaborator behavior safely —
requires this guarantee first.

**Methodology — top-down.** State the global theorem first, let
Agda's type-checker enumerate every missing case as a precise
compile error, fill them one at a time. Each gap becomes a hole
the proof must close, not an "did we cover everything?" question.
The structure of the proof is dictated by the elaborator's case
dispatch, which Agda walks for us.

**Audit findings (from initial scaffolding attempt, 2026-04-30).**

   RInt, RStringLit, RUnit, RVar, RQualified, RPair, RLet,

   `t-embed (IH refl)` to bridge to `⊢ᶜ`, but no real caller

   2026-04-30 (commit precursor): IH now returns `⊢ᶜ` directly,

   shapes (inl/inr/initial/pair-applied/compose-applied/curry)
   needs an absurd pattern after a `with eq` reduces the elaborator
   to `failure ...`. Tedious but mechanical.

5. *Real spec gaps — judgment rules missing for the elaborator's
   success cases.*
   - `arr f` in infer mode: elaborator succeeds when `f : A → B`,
     producing `Eff A B`. No `t-arr-app-infer` rule exists.
   - `apply p` in infer mode: elaborator succeeds when `p :
     (A → B) * A`, producing `B`. No `t-apply-app-infer` rule.
   - Each gap requires a new judgment rule + a soundness proof for
     it. These are the *real* spec/impl-divergence findings.

6. *Check-mode soundness coverage is essentially zero.* Only
   `sound-check-RLam` exists. All other check-mode dispatches need
   new `sound-check-*` lemmas:
   - `checkPair`/`checkCompose`/`checkCurry`/`checkApply` — each
     has its own success path in checkElab.
   - `checkElab-RVar`'s 7+ bare-builtin specialised clauses
     (id/fst/snd/terminal/initial/inl/inr/arr).
   - The ahv-other inferElab fallback in checkElab.
   This is the single largest chunk of T0 work.

### T1 — G2 typechecker completeness (LARGEST)

**Goal**: state and prove
```agda
complete-type :
  ∀ {ctx e T} → Judgment ctx e T
  → ∃ λ (d : InferResult ctx) → extract d ≡ just (T, -)
```
(and the check-mode variant) — where `Judgment` is the declarative
typing relation defined in `Once.Judgment`.

**What could fail without this**: a case in `checkElab` falls through
to `failure` for some well-typed shape the author didn't consider.
After the 0.2.6 linearity refactor, polymorphic-builtin specialization
happens only at pattern-matched shapes (e.g., `RVar "compose"` fully
applied); a slightly-different shape — `compose` split across a
`let`-binding — can fall through to the generic path and fail.

**Concrete evidence (added 2026-04-30).** `compiler/test/layer0-compose.once`
exhibits the predicted shape from a different angle:

```once
main = exit ((id . id . id) 42)
```

The saturated 2-ary `compose id (compose id id)` appears in *function
position* of an outer application. `checkElab` for `RApp f arg`
classifies `f` as `ahv-other` (because the head is `RApp _ _`, not
`RVar "compose"`), falls back to `inferElab`, which then trips on the
inner partial compose at the bottom of the chain (`inferElab` on
`ahv-compose-applied` returns `failure (BuiltinTypeMismatch
"compose")`, `Elaborate.agda:1145`). Rejected with a "type error"
despite being well-typed by the language definition (D007: every term
has a unique inferable type; no specialization needed).

This is exactly the case T1 is meant to surface, and it confirms
option (b) is the right call (see below).

**Strategy — option (b) locked.** Rather than prove a
shape-normalization bridge (option (a)), generalize the elaborator
so the bidirectional rules are *complete for the polymorphic
schemas Once supports*. The principled fix is to add **argument-
driven application** as a check-mode rule, alongside the existing
function-driven rule:

```
-- Function-driven (existing):
Γ ⊢ f ⇒ A → B    Γ ⊢ x ⇐ A    B <: T
-----------------------------------------
            Γ ⊢ f x ⇐ T

-- Argument-driven (new):
Γ ⊢ x ⇒ A    Γ ⊢ f ⇐ A → T
-----------------------------------------
            Γ ⊢ f x ⇐ T
```

The argument-driven rule lets check mode propagate *through* an
application into the function position. Combined with the existing
`checkCompose`, `checkPair`, `checkCurry`, `composeArgB`, and the
poly-schema instantiation for bare builtins (`id`, `fst`, `snd`,
`terminal`), every saturated polymorphic-builtin chain whose
intended IR types are inferable becomes elaborable.

Expected to also unstick latent variants:
- saturated `pair`/`curry` in function position
- compose-of-compose nested arbitrarily deep
- mixed chains like `(curry f) ((compose g h) x)`

**Why the rule is sound.** Standard bidirectional metatheory:
adding the argument-driven rule preserves soundness because both
premises are themselves sound, and the conclusion's expected type
`T` is unchanged. Determinism is preserved if the elaborator picks
*exactly one* of the two rules per RApp shape — proposed
discipline: try function-driven first (current behavior); only fall
to argument-driven when function-driven fails *because the head
isn't synthesizable* (specifically, an `ahv-{compose,pair,curry}`
classifier on the head).

**Strategy steps**:
1. Audit `Once.Judgment`: confirm all typing rules landed in plan
   0.3's G2(a) split (`Judgment` → mutual `Infers` / `Checks`). Any
   missing rule is a hole in the completeness statement.
2. Add the argument-driven application rule to `Judgment` (as a
   `Checks` constructor) and to `checkElab` (as a fallback when
   function-driven would fail because of an unsynth-able poly-builtin
   head). Verify determinism: the new rule fires only on shapes the
   old rule rejected.
3. Walk each `Judgment`/`Checks` constructor and prove the
   corresponding `inferElab`/`checkElab` path succeeds. Expected
   structure mirrors `Surface.Correct.elaborate-correct`.
4. The new argument-driven rule's completeness obligation is the
   easy direction: pattern-match on the new `Checks` constructor,
   invoke `inferElab` on the arg, then recurse with `checkElab` on
   the head at the synthesized arrow type.
5. Land `compiler/test/layer0-compose.once` in `Layer0Spec` (it's
   currently expected-fail) as the executable regression.

**Entry cost**: ~600-1000 lines (option (b) plus completeness
proofs). Larger than option (a)'s 400-800 because the elaborator
restructure is non-trivial, but option (b) closes a class of latent
bugs that option (a) would have left as future work.

**Wiring**: add a `tc-complete-*` field per rule to
`VerifiedTypeChecker` (structural enforcement via record).

### T2 — G1 parse→pretty direction

**Goal**:
```agda
parse-pretty-roundtrip :
  ∀ {toks g rest} → parseGExpr toks ≡ just (g , rest)
  → ∃ λ toks' → toks ≡ printGExpr g ++ toks' ∧ rest ≡ toks'
```
(and the type-side variant) — saying parser output, when pretty-
printed, reconstructs the token stream it was parsed from.

**What could fail without this**: the parser accepts `toks`, produces
`g`, but `printGExpr g` tokenizes to something *different* from
`toks`. Current proofs would not catch that.

**Strategy**:
1. **Induction on the parsing relation** (`ParsesExpr toks e rest`),
   not on the WF parser. Each relational constructor corresponds to a
   printer production; structural induction mirrors the printer's
   case analysis.
2. The critical premise per case: inner derivations already satisfy
   `printGExpr g_inner ++ r_inner ≡ toks_inner`.
3. Leaf cases (pae-unit, pae-int, pae-str, pae-var, pae-qual) are
   direct — one token becomes one printer call.
4. Compound cases compose via `++-assoc`.

**Entry cost**: ~300-500 lines. Less than `complete-expr` because
there's no parser-level `with`-dispatch to mirror — the relation is
fully abstract.

### T3 — G1 grammar conformance (`WellFormed ⟺ ∃ g. parse`)

**Goal**:
```agda
-- Formal grammar predicate (inductive)
data WellFormed : List Token → Set where ...

-- Soundness
parse-well-formed :
  ∀ {toks g rest} → parseGExpr toks ≡ just (g, rest)
  → WellFormed (take (length toks - length rest) toks)

-- Completeness
well-formed-parses :
  ∀ {toks} → WellFormed toks
  → ∃ λ g → parseGExpr toks ≡ just (g, [])
```

**What could fail**: a token stream the grammar says is valid fails
to parse (completeness), or the parser accepts something the grammar
rejects (soundness).

**Strategy**:
1. Define `WellFormed` as an inductive predicate mirroring
   `Once.Grammar`'s productions.
2. Soundness: induct on `ParsesExpr`. Each constructor produces a
   `WellFormed` witness for its token span. Mechanical after T2.
3. Completeness: induct on `WellFormed`. Invoke the `complete-expr`
   bridge per production to get a parser equation. Mechanical.

**Entry cost**: ~400-600 lines. Largest item is the `WellFormed`
datatype definition — expected to have 30+ constructors for
expression productions and 10+ for types.

**Dependency**: T2 should precede T3 (parse-pretty is reused).

### T4 — Surface-semantics bridge postulates

**Goal**: eliminate three postulates in `Surface/Correct.agda`:
```agda
postulate
  intLit-correct   : ∀ {Γ} (n : ℤ) (γ : ⟦ Γ ⟧)
                   → eval′ (intLit n) γ ≡ n
  effApp-correct   : ...
  prim-correct     : ∀ (n : String) → evalSurface ρ (prim n)
                                    ≡ eval′ (elaborate (prim n)) (interpEnv ρ)
```

**What could fail**: elaborated-form semantics and surface semantics
disagree on a literal leaf. A semantic mismatch slips through.

**Strategy**:
1. `intLit-correct`: unfold `intLit`, `eval′`, `evalPrim "lit.int.N"`.
   Should reduce to definitional equality. If it doesn't, identify
   the blocker — likely a case where `evalPrim`'s string-dispatch
   isn't definitionally unfolded.
2. `effApp-correct`: structural induction on the `effApp` constructor.
   Similar to `eval′ (f x)` unfolding; one lemma per IR primitive
   reached via `effApp`.
3. `prim-correct`: per-primitive case — one clause per builtin string
   name. Essentially a lookup-table correspondence between
   `evalSurface`'s primitive table and `elaborate`'s elaboration.

**Entry cost**: ~100-300 lines total; each postulate is small.

**Note**: `extensionality` in `Postulates.agda` stays as a postulate.
It's Agda's standard function-extensionality axiom; eliminating it
would require moving the whole proof tree to an extensional setoid
model, which is out of scope.

## Phase Ordering

**Updated 2026-04-30** — T0 prerequisite added after discovering
mid-T1 that the verification framework lacks a global soundness
theorem. T0 first guarantees that subsequent T1 elaborator
changes are forced to either match a judgment rule or break
soundness; without it, the new elaborator paths slip through.

1. **T0** (globalize soundness) — prerequisite. Compose
   per-shape lemmas into top-level `infer-sound` / `check-sound`.
   Fill coverage gaps so every elaborator code path is covered.
2. **T1** (G2 completeness, option (b)) — argument-driven
   application restructure plus the completeness theorem itself.
   T1's CHANGE 1 (function-driven inferElab swaps to check on
   the arg) is already done in branch `plan-0.4-T1`; CHANGES 2–4
   are blocked on T0.
3. **T4** (surface-semantics bridges) — smallest, independent;
   closes the last three frontend postulates.
4. **T2** (parse-pretty direction) — builds on existing parsing
   relation machinery; no new datatypes.
5. **T3** (grammar conformance) — reuses T2's structural lemma;
   adds `WellFormed` datatype.

## Deferred Items

- **G3 crash freedom as a named theorem.** The property holds
  structurally today — every parser / typechecker / elaborator
  entry point is total (no `TERMINATING`, structural recursion on
  `List Token` / `RawExpr`), so Agda's totality checker is the
  proof. What's missing is a *named* lemma like
  `parser-total : ∀ toks → parseExpr toks ≡ just _ ∨ parseExpr toks ≡ nothing`
  wired into `VerifiedTypeChecker` as a guard against future
  refactors that reintroduce a `TERMINATING` pragma or an escape
  hatch. Trivial one-liner per entry point, but adds no new
  information beyond what the totality checker already guarantees.
  Add if/when a refactor threatens the structural-totality
  discipline.
- **G5 integration at stage boundaries** — `parse ∘ elaborate ∘
  desugar` as a composed theorem. Individual stages are proved; the
  compositional statement is informal. Low value: a compositional
  bug would have to survive being invisible to all three individual
  soundness proofs. Could be added later if desired.
- **G6 typechecker determinism** as a stated theorem. Trivially
  holds because Agda functions are deterministic; stating it adds
  future-refactor guardrails but no immediate value. Low priority.
- **G8 performance bounds** — out of formal scope; belongs with CI
  benchmarks.
- **`extensionality`** in `Postulates.agda` — kept. Eliminating it
  would require an extensional setoid model; out of scope.

## Risks & Open Questions

1. **Polymorphic-builtin completeness (T1)** — option (b) locked
   2026-04-30 (argument-driven application as a check-mode rule).
   Risk: the new `Checks` constructor expands the case split in
   `Surface.Correct.elaborate-correct` and any future proof that
   inducts on `Checks`. Mitigation: each existing case is unaffected

   one new completeness obligation is mechanical (recurse through
   inferElab + checkElab).
2. **`WellFormed` datatype size (T3)** — 40+ constructors expected.
   Management via mutual blocks is routine but verbose. No
   fundamental risk.
3. **`prim-correct` per-primitive work (T4)** — depends on how many
   primitives the surface exposes. Scales linearly; no algorithmic
   risk.
