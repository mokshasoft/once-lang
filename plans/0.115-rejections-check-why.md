# Plan 0.115 — A rejecting test checks why it rejects

## Why

`PuritySpec`, `TelescopeSpec`, `QttSpec`, `TypeErrorSpec` (and others) assert only `isLeft`: ANY
rejection passes. So a test can keep passing after the feature it pinned changed — D258 turned the
String tests into tests that pass for a different reason (unknown type instead of the old error),
and nobody noticed. A rejection test is evidence about the Spec only if it names the rule that
rejects.

## Steps

1. Inventory: every rejecting assertion in `compiler/test/*.hs` (`isLeft`, `assertParseError`,
   `shouldSatisfy … isLeft`) with the program and the intended reason.
2. One small helper per stage (parse / resolve / type check) that matches the error CONSTRUCTOR (and
   where useful its key field), e.g. `assertTypeError (QuantityExceeded …)`.
3. Convert each test; where the actual error differs from the intended one, that is a finding —
   record it (the test was passing for the wrong reason) and fix the test or the program.
4. Rule for new tests (MERGE.md / test README): a rejection names its reason.
