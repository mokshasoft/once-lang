# Plan 0.8: `.` as Sugar for `compose`

## Motivation

Function composition is the everyday glue of a categorical language.
Point-free definitions like

```once
firstSwapped : Int * Int -> Int
firstSwapped = compose fst swap
```

read fine with one composition but pile up quickly:

```once
rotatedHead = compose fst (compose swap (compose shiftLeft dup))
```

The universally-understood infix form is `f . g`, denoting "apply `g`
first, then `f`" — the Hask convention, matching the mathematical
meaning. Once already treats `compose` as a first-class builtin with
its own `spec*` helper and (post-Phase-C.3) classifier; adding `.` as
sugar is a pure parser/desugar change.

```once
-- after this plan
rotatedHead = fst . swap . shiftLeft . dup
```

## Constraints

1. **Surface-only.** No new IR, no new judgment rules, no new
   classifier entries. Desugar at parse time to
   `RApp (RApp (RVar "compose") f) g`.
2. **TDot is already a token.** The lexer emits `TDot`; several
   submodules use it as a boundary marker (e.g. `parseAtomicWF`
   stops on `TDot`). Changing its role means auditing those boundary
   stops.
3. **Dotted names.** Qualified primitives use `.` in their surface
   form (`exit@E`, `alias.name`). Those go through a different path —
   `TAt`-prefixed or appear inside import decls. Normal expression
   contexts should never see both meanings simultaneously, but any
   new infix `.` handling must keep dotted primitives working.
4. **Associativity.** Function composition is associative; the natural
   convention is right-associative so `f . g . h` parses as
   `f . (g . h)`, matching mathematical reading order.
5. **Precedence.** Should sit lower than function application (so
   `f x . g y` means `(f x) . (g y)`) and likely above the arithmetic
   operators (Hask puts `.` at fixity 9, tighter than `+`/`*`). Once's
   current operator table has arithmetic at a single precedence tier;
   `.` slots in tighter than arithmetic.

## Surface desugaring

In the parser:

```
parseCompExprWF :
  ... → f . g → RApp (RApp (RVar "compose") f) g
```

Equivalent to:

```
f . g  ↦  compose f g
```

Right-associative: `f . g . h ↦ compose f (compose g h)`.

## Implementation phases

### D.0 — Audit TDot usage

Walk every `TDot ∷` pattern in the parser and classify:

- **Boundary usage** — parser currently stops on `TDot` (e.g.
  `parseAtomicWF`). These will need to *recurse* into the compose
  parser instead of stopping, at the correct precedence tier.
- **Dotted-name usage** — qualified imports. These must keep their
  meaning; `.` between an alias and a name is not composition.
  Typically distinguished by token context (alias followed by `.` is
  in a qualified-name position, not an expression position).

### D.1 — Add composition-precedence parse level

Slot a new `parseCompExprWF` into the expression grammar at tighter
fixity than arithmetic, looser than application. Right-associative.
Walk the `TDot`-terminated list and left-fold into
`RApp (RApp (RVar "compose") f) g` with right-fold layout.

### D.2 — Printer round-trip

Extend `Once.Grammar.ExprPrinter` to emit `.` for the
`compose`-as-head two-arg shape, and extend the printer/parser
round-trip tests.

Edge case: `compose` used in a non-infix position (e.g. passed as a
higher-order argument) should still print as `compose`, not `.`.

### D.3 — Update parser relation + bridge

Plan 0.3 Task #38's `Once.Parser.ExprRelation` needs a constructor
for compose-infix; `Once.Grammar.ExprBridge`'s soundness /
completeness covers the new rule. Mechanical extension of the
existing binop pattern.

### D.4 — Proof-side updates

Only if any frontend proof pattern-matches on `TDot` boundaries. A
grep pass will find these; each one needs either to extend its
alternation (accept `TDot` as a continuing-token for expression
contexts) or to stay unchanged (for contexts where `TDot` still ends
the phrase, e.g. qualified-name context).

### D.5 — Stdlib migration

Rewrite point-free stdlib entries (Canonical.once, etc.) to use `.`
where it reads better than `compose`. Not required for correctness —
purely ergonomic.

## Dependencies

- **Plan 0.6 Phase C.3** (compose classifier). `.` desugaring yields
  `compose f g`; without the classifier, this still fails to
  typecheck at ground expected types. D.0–D.4 can land before C.3,
  but D.5 and user ergonomics require both.

## Non-goals

- **Partial application of `.`**. `(. g)` / `(f .)` sections are not
  in scope; Once has no sections in general today.
- **Dot as record/field access.** Not introducing field-access
  semantics; `.` stays a binary expression operator.
- **Generalizing `.` to other 2-arg NTs.** This plan is specifically
  about `compose`.

## Acceptance tests

1. `f . g` parses equivalently to `compose f g`.
2. `f . g . h` parses as `compose f (compose g h)` (right-assoc).
3. Qualified primitives (`exit@E`, `alias.name`) still parse.
4. Printer round-trip: parse → print → parse yields the same AST for
   composed expressions.
5. Post-C.3: `fst . swap` at ground type typechecks end-to-end with
   `swap` a polymorphic user def.

## Open questions

- Exact precedence: tighter than arithmetic, looser than application.
  Is there a conflict with any other operator in the current table?
  (Grep pass required.)
- Do we want `$` (low-precedence apply) in the same pass, to match
  Hask's `.`/`$` duo for point-free writing? Probably a separate plan.
