# Plan 0.66 — the x86-32 correspondence: the third instance, and the width axis

**Status**: OPEN, written 2026-08-06. Its other gate (`events-running-{ret,call}`)
LIFTED 2026-08-06 — both are theorems (D095/D098). NB this arch's `Semantics`
carries the same `rip+label` defect D096 fixed for x86-64; repair it here too,
as part of the port. **Depends on plan 0.65** (the generic
`FlatCore`). Do not start until 0.65's G1 gate has passed.

## The goal

Same as 0.65's, one arch over: replace `x86-32-conc-flat-sim` — a whole-cloth
postulate asserting the entire simulation — with a proof, plus retire
`entry-frame-x86-32` and turn x86-32's resource bounds into parameters.

If 0.65 did its job this is mostly an INSTANCE, not a development. The plan
exists because there is exactly one thing 0.65 could not have validated, and
it is load-bearing.

## THE PREMISE OF THIS PLAN IS FALSE UNTIL 0.69 LANDS (2026-08-11)

This plan says width is "the one new axis". It is currently **two**: x86-32's
emitter addresses slots off `%ebp` (anchored once, at function entry) while its
own `FrameInstantiation` says `frame-base = sp-addr` and
`slot-addr f k = sp-addr f + k * word-size`. The emitter is outside the model —
invisible only because `x86-32-conc-flat-sim` assumes the whole simulation. X2
below (`block-step-c-thunk` in particular) is the proof that would be FALSE:
an inlined body's slots alias its caller's.

Plan 0.69 fixes that by moving x86-32 to `%esp`-relative slots — after which
this plan's premise is TRUE and width really is the single new variable.

## The one new axis: **`slot-size` is 4, not 8**

    Once/CCC/Target/X86-64/Syntax.agda   slot-size = 8
    Once/CCC/Target/RiscV64/Syntax.agda  slot-size = 8
    Once/CCC/Target/X86-32/Syntax.agda   slot-size = 4

0.65 generalises over the ISA with the width held FIXED at 8 — deliberately, to
isolate one variable. x86-32 is where the width assumption gets tested, and it
is the reason this is the third instance rather than the second.

### Where the width can hide

A core extracted against two 8-byte arches can contain a `slot-size ≡ 8`
assumption in four ways, none of which the x86-64/riscv64 pair would catch:

1. **A literal `8`** anywhere a `slot-size` belongs — in `slot-to-disp`, in an
   offset, in a `sndOffset` / `valueOffset` (`X86-64/Syntax.agda` defines both
   as `slot-size`, so they follow automatically IF the core says `slot-size`
   and not `8`).
2. **`slots n = n * slot-size` reasoning done by `refl`** where it should be by
   the multiplication lemma. Anything that computes `slots 2 ≡ 16` numerically
   is width-locked, and it typechecks silently at both 8-byte arches.
3. **`word-eq : frame-word FS ≡ slot-size`** — the frame instantiation's tie
   between the machine word and the slot. All three arches set
   `frame-word = word-size`, so this holds per arch; the risk is core code that
   USES it via a computed value rather than via the equation.
4. **Address arithmetic in `Window` / `StackWindows`** — `frame-base f +
   slot-to-disp k`, and the `slot-addr-inj` injectivity that the store lemmas
   rest on. Injectivity of `base + slot-to-disp k` in `k` needs `slot-size > 0`,
   nothing more; check the proof actually says that rather than dividing by 8.

**Task before anything else** (cheap, do it first, it re-scopes the whole plan):

    grep -n '\b8\b' formal/Once/Adequacy/ArchCorrectness/FlatCore/*.agda

Every hit is either a width leak or needs a comment saying why it is not. If
this returns nothing and every offset goes through `slot-size` / `slots` /
`slot-to-disp`, x86-32 is a genuine instance and the rest of this plan is short.

### The second, smaller x86-32 difference

`updateFlags` takes ONE argument on x86-32 (`Word → Flags`) and TWO on x86-64
(`Word → Word → Flags`). This is harmless **if** 0.65's rule was obeyed —
that the core takes the branch OUTCOME in read-back form and never mentions
`Flags` or `updateFlags` at all (RISC-V has no flags register, which is what
forced the rule). If it was not obeyed, x86-32 is where the second bill for it
arrives. Treat a `Flags` parameter in the core as a 0.65 defect and fix it
there, not here.

## X0 — the two gates 0.65 handed this plan (BOTH CLOSED, 2026-08-17)

**X0.1 — x86-32's `initState` handed `main` `esp ≡ 0`.** The same defect D107
found on riscv64, still present here because `x86-32-conc-flat-sim` still
assumes the whole simulation. FIXED FIRST, before the correspondence exists —
`stack-top` is postulated in `X86-32/Semantics.agda` and `initState` sets `esp`
to it, exactly as the other two arches state it.

**X0.2 — the `Input2` decision: RETIRE** (D108). The role had no producer on any
arch, so x86-32's non-injective role map was reporting dead state rather than a
register shortage. `Input2`, `role-in2`, `e-in2`, the `input2` register field and
`mov-{output-to-input2,input2-to-output}` are all gone; x86-32's seven realised
roles fit its seven available registers with `ebp` reserved as the frame anchor.
SPILL was rejected: `reg-of` is register-valued, so a spilled role widens the
interface for all three arches to keep an instruction nothing emits.

**X1 is also already CLOSED** — see below; the audit found no width leak.

## The exit-test signal, which matters more here than elsewhere

**PREREQUISITE, added 2026-08-11: plan 0.69 comes FIRST.** x86-32's 20 failures
are all SIGSEGV and the cause is now CONFIRMED — the post-0.63-flip inline body
bracket re-anchors nothing, so a body's slots alias its caller's `%ebp` frame
and run off the end of it. That is an emitter defect, and proving a
correspondence about an emitter that segfaults is the wrong order. See
`plans/0.69-arch-runtime-regression.md`, which also decides whether x86-32
moves to `%esp`-relative slots — a decision this plan's `FlatCore` instance
depends on.

x86-32's exit tests currently sit at **35 passing / 20 failing** — the weakest
of the three (x86-64 is 55/0 since C1/D101, riscv64 18/37). A correspondence
proof does not fix a failing test, and must not be expected to.

But the reverse is a real signal: **if landing X2 changes any exit-test count,
something in the emitter moved that should not have.** Record the counts before
and after. That is the same discipline the rung-D branch used, and it is how a
"pure proof" commit that quietly edited codegen gets caught.

If the correspondence proof turns out to be UNPROVABLE at some instruction
because the x86-32 emitter is wrong there, that is a genuine find — those 20
failures have to live somewhere. Write it up as a defect, do not weaken the
statement to accommodate it.

## Done means

`x86-32-conc-flat-sim` and `entry-frame-x86-32` are gone; x86-32 carries a
loader axiom and two resource parameters, the same shape as x86-64 and riscv64.
All three arches then share one proof, and a change to the abstract machine
costs one core edit instead of three.
