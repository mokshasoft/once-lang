# Plan 0.39 — Every producer provides its own `ClaimedProvider`; `rest-claims = []`

## Goal

The compiler/CCC names **no** producer. The apex SigOp provider is a
composition of **producer-owned** `ClaimedProvider`s, each PROVEN by its
producer. The residual `rest-claimed` **postulate** and its `rest-claims`
string list (which still names `arith.<op>.int` and `lit.*`) are **deleted**.

This is the same move as removing `"linux."` from `rest-claims`, finished:
internal producers (arith, lit) each land a proven provider, so the apex
needs no name list and no postulate.

## Why this is principled (the model, settled in discussion)

- CCC only ever sees a SigOp's **type + `PreservesCCC`** (`Once.CCC.SigOp.Helper`,
  6 state-only fields — value-agnostic). The dependency-breaker.
- A SigOp's contract is its **producer's** job. Arith already proves its
  *value* (`Once/Arith/Backend/X86/Correct.agda`) and its *block* provider
  (`ArithBlockProvider.blockProvider`, via the polymorphic `block-int-proof`,
  which discharges the `Contract` for ANY `Int`-returning SigOp through
  `fits-int` + `arith-trace-correct` — it does NOT read the body).
- The per-op arith SigOps (`arith.add.int` …) and the literals (`lit.int.`,
  `lit.str.`) currently fall into the **postulated** `rest-claimed` instead of
  a proven provider. That is the leak. They are dischargeable by the SAME
  template, generalised to their return shapes.

## The correct abstraction (top-down)

```
sigOp-proof = provider (blockClaimed <|>' arithOpClaimed <|>' litClaimed)
```
- `arithOpClaimed` (arith module) — covers `arith.<op>.int`. Int-returning
  ops via `block-int-proof`; Bool-returning comparisons (`Unit + Unit`) via a
  new `block-bool-proof` (same `fits-in-reg?` machinery for the sum-return).
- `litClaimed` (lit/IntLit module) — covers `lit.int.` (Int, via the int
  template) and `lit.str.` (Str, via a `fits-str` template).
- `blockClaimed` — unchanged (`arith.block.`).
- **DELETED:** `rest-claims`, `rest-claimed` (all 3 targets x86-64/x86-32/riscv64).

Each provider's discharge is producer-owned and value-correct via the
existing `Contract` (`IRResultAWF`, i.e. output = `eval (SigOp si) x`), proven
generically through `fits-in-reg?` per return shape — never by naming the op
in CCC.

## Method (per the user: top-down, delete, let the checker fill)

1. Fix the **prerequisite blocker** (see below) so the apex typechecks.
2. In the apex, write the correct `sigOp-proof` composition and **delete**
   `rest-claims` + `rest-claimed`. The checker now demands `arithOpClaimed` /
   `litClaimed`.
3. Fill them in the **producer** modules: generalise `block-int-proof` to the
   Bool (`block-bool-proof`) and Str (`lit-str-proof`) return shapes; assemble
   `arithOpClaimed` / `litClaimed` via `mk-claimed`.
4. Verify the apex is green with `rest-claims = []` and zero new postulates.

Do NOT incrementally migrate — write the correct apex, delete the old list +
postulate, and discharge what the checker then demands.

## Prerequisite blocker (decision needed)

The apex (`EntryPointCCC`) is **pre-existing-RED** and **not in the live
extraction closure**:
- `RecCoreWF.run-fuse-core` (`Once/CCC/Machine/IR/RecCoreWF.agda:~345`) declares
  `transform : IR (⟦G⟧T (μ-type G)) (⟦F⟧T (μ-type G))` but `Fuse` now expects
  `NatTr G F` — the clean-semantics NatTr migration (≈`e72b2003`) never updated
  this module. Fixing it = applying that migration here (size unknown; these WF
  modules are OOM-heavy).
- The **live** grand theorem (`CompileCorrectFlat`) is already parametric over
  `sigOp-proof`, so it names no producer today.

⟹ This plan cleans the **orphan apex**; the live correctness is already clean.
Doing it top-down requires fixing `RecCoreWF` first. Alternatively, the
producer `ClaimedProvider`s (arith/lit) can be built **green in their own
modules** independently, with the apex wiring deferred until `RecCoreWF` is
addressed.
