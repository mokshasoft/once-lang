# Plan 0.139 — A type error names the rule that was broken

## Summary

When the compiler refuses a program, its message should say which rule the program broke. In a few
common cases it doesn't. For example, it calls a well-known built-in such as `id` or `inl` an "unbound
variable" when the real problem is a type that doesn't fit. One message even suggests a fix that
doesn't work. This plan makes those messages name the real problem. When it is done, the tests that
pin today's poor messages (D368) check the right ones.

## 1. Why

D368 made every rejecting test name its reason. Five tests could only pin a poor diagnostic, because
the elaborator reports a different rule than the one the program breaks. A diagnostic that names the
wrong rule sends the programmer to the wrong fix, and it is the Spec's rule, not the elaborator's
shortcut, that the message should report.

## 2. Where we are

Measured 2026-11-02 with `once check` and `once build --lib` (the tests are in `compiler/test`):

| Program | Message today | The rule |
|---|---|---|
| `x : Int; x = id` (TypeErrorSpec "function for Int type") | `Unbound or unspecialized variable: id` | a function where `Int` is expected |
| `swap 5` at `Int * Int` (SpecMatrixSpec d-poly) | `Unbound or unspecialized variable: swap` | `Int` is no instance of `a * b` |
| `g = inl` / `inr` / `initial` (TypeErrorSpec, D323) | `The body has no type of its own (Unbound or unspecialized variable: inl …)` | the outer reason is right; the inner one should be `inl requires check mode` (`InlInInferMode`, …) |
| `f : Unit -> Int; f x = -x` | `Type mismatch: expected Int but got Unit` | right, but `NegationNotInt` is never produced: it is defined in `Once.TypeCheck.Error` and used nowhere in `Elaborate` |
| `ana (compose (\_ -> 7) (emit@E : Act Int Unit))` at `Int -> Nu (K Int)` | `compose: cannot determine the middle type … annotate one of them` | annotating the SECOND argument does not help; annotating the first does (PuritySpec's coalgebra test now annotates the first) |

Where the "unbound" text comes from: `formal/Once/TypeCheck/Elaborate.agda`,
`inferElabV-RResolved-dispatch` (`failure (UnboundVariable "id")`, … for each generator, about line
1585) and the poly lookups (`inferElabV-RVar-poly-lookup-aux`, about line 864). Each `failure` is pinned
to its variant by `TypeCheck.ErrorProofs`, and `ElaborateSound`/`Verified` mention the variants.

## 3. Decisions

- **D1, a new variant or the existing ones.** For a generator or a polymorphic definition seen in infer
  mode: add a variant (e.g. `GeneratorNeedsTarget name`, "`id` needs a known type here; annotate it or
  give the definition a signature"), or reuse `BuiltinTypeMismatch`. Recommended: a new variant, since
  the case is common and has its own fix. Open.
- **D2, instance failure.** `swap 5` should say "`Int` is not an instance of `a * b`". That needs the
  failed unification's two types in the error. Recommended: `NoInstance (schema actual)`. Open.
- **D3, `NegationNotInt`.** Delete the unused variant, or have the negation rule produce it. Recommended:
  delete it, since the operand check at `Int` already says the right thing. Open.

## 4. Steps

1. Dispatch for generators in infer mode: report D1's variant instead of `UnboundVariable`; update
   `ErrorProofs`, `ElaborateSound`, `Verified`. Check: `agda-safe.sh certified`.
2. Instance failure (D2) in the poly lookup.
3. `inl`/`inr`/`initial` without a target: route them to `InlInInferMode`/`InrInInferMode`/
   `InitialInInferMode` (they exist and have proofs; the dispatch never reaches them).
4. `compose`'s middle type: make an annotated second argument determine it, or change the advice to

5. D3.
6. Re-extract MAlonzo (`make malonzo`), `cabal test`, and update the five pinned tests' reasons (remove
   their "Pinned" notes).
