**AND 0.69 CHANGED THIS PLAN'S GROUND, in this plan's favour (D102).** All three
arches now address slots off the STACK POINTER, re-anchored by the body bracket
itself — x86-32 moved to `%esp` and riscv64 was already there. So `FlatCore` is

## The goal

`riscv64-conc-flat-sim` is a whole-cloth postulate: "the concrete riscv64
`run-events` equals the abstract `flat-events`", the entire simulation assumed
in one line (`ArchCorrectness/RiscV64.agda`). x86-64 has a real proof of the
same statement. This plan replaces riscv64's postulate with a proof, and does it
by EXTRACTING an arch-generic core from x86-64's rather than copying 6,800 lines.

    x86-64 correspondence cone, today
      ConcFlatSim.agda          2387   the CCC engine, FlatInv, the dispatch
      FlatCorrespondence.agda   1833   HeapView, Window, StackWindows, FlatCorr
      FlatSimulation.agda       1567   block-step-* — one per abstract instr
      FlatComposition.agda       555
      StepLemmas.agda            265
      RunContext.agda            122
      ResourceBounds.agda         99
                                ────
                                6828

Copying that per arch is not a plan, it is a promise to maintain three divergent
copies of a proof we have already changed twice this month.

## Why riscv64 FIRST, and not x86-32

`slot-size` is **8** on both x86-64 and riscv64, and **4** on x86-32. Doing
riscv64 first isolates one variable: the generalisation is over the INSTRUCTION
SET only, with the word width held fixed. x86-32 (plan 0.66) then adds width as
the single new axis, against a core that is already known to work at two ISAs.

Rule of three, the same discipline that produced `ArithSimCore`: generalise on
the second instance, validate on the third.

## The precedent to copy exactly: `ArithSimCore`

`Once/Adequacy/ArchCorrectness/ArithSimCore.agda` already solved this problem
for the arith slice, and its design note records the failure that taught it:

> The core makes NO assumption about the concrete write shape (how many io
> registers `i` clobbers, or which). … That difference — which broke a
> writeReg-shape parameterisation — lives entirely in the arch instances.

So the core takes the concrete machine as opaque parameters (`St`, `rr`, `mem`,
`e1`, `eb`) plus **read-back laws** (`rt-*`: after this instruction, reading its
target yields this value; `rf-other`: reading a non-target is unchanged). Each
arch discharges the laws from its own frame lemmas.

**Apply the same rule here, and expect the same trap.** Do not parameterise over
how a block is BUILT. Parameterise over what holds AFTER it runs.

## The two structural differences that must not be papered over

These are the reason this is a design task and not a `sed` script.

### 1. RISC-V HAS NO FLAGS REGISTER

`Once/CCC/Target/RiscV64/Semantics.agda` says so in the source: its `State` is
`regs / memory / pc / halted` — four fields. x86-64's is five, with `flags`, and
`updateFlags : Word → Word → Flags`. (x86-32 has flags too, but its
`updateFlags : Word → Flags` takes one argument — even the two x86es differ.)

The lowering differs structurally, not cosmetically:

    riscv64:  c-branch-scratch-zero n  ↦  beq s3 zero (once n)        -- ONE instr
    x86-64:   c-branch-scratch-zero n  ↦  test/cmp … ; je (once n)    -- more

**Therefore**: the core must NOT take `Flags` as a parameter, and must not
mention `updateFlags`. It takes the branch OUTCOME in read-back form:

> for the compiled block of `c-branch-*`, running it from a state corresponding
> to `fs` lands at `find-label`'s target exactly when the abstract scrutinee is
> zero, and preserves `FlatCorr`.

x86-64 discharges that from `test`+`je` and its flags lemma; riscv64 from `beq`
directly. Neither shape leaks into the core. A `Flags` parameter would force
riscv64 to invent a fictional flags register — the exact mistake `ArithSimCore`
records having made once already.

### 2. BLOCK LENGTH IS PER-ARCH

`x86-len : AbstractInstr → ℕ` and its companions (`x86-off`, `x86-off-suc`,
`fetch-block-head`, `fetch-block-2nd` … `fetch-block-6th`) are the interface
between the abstract pc and the concrete one. riscv64's lengths differ
instruction by instruction (the branch above is 1 where x86-64's is 2).

These become parameters with their laws, renamed off `x86-`: `blk-len`,
`blk-off`, `blk-off-suc`, `fetch-block-nth`.

## The layer split — what is generic, what is per-arch

| module | verdict | why |
|---|---|---|
| `FlatCorrespondence` | **GENERIC**, with parameters | `HeapView`, `AddrMap`, `enc-sv`, `Window`, `StackWindows`, `FlatCorr`, `windows-{forget,lower,leave,above,reanchor}` are all about the LAYOUT, not the ISA. It touches the machine only through `readMem` / `readReg` / the stack-pointer register / `slot-to-disp`. Its `sim-*` lemmas (`sim-thunk`, `sim-alloc-stack`, …) are stated over abstract effects, so they generalise with it. |
| `ConcFlatSim` | **GENERIC** | The CCC engine (`ccc-step-bs`, `events-agree`, `events-running-fetch`) dispatches on `AbstractInstr` and calls a block-step. Give it a per-instruction block-step supply and the entire event/trace layer — the largest single file — is written once. `FlatInv`, `RunAt`, `Reachable` are abstract-side only. |
| `FlatSimulation` | **PER-ARCH** | This is where the ISA lives: `block-step-mov-rr`, `block-step-c-thunk`, `block-step-alloc-heap` … one per abstract instruction, each assembling concrete steps. Its SHAPE is generic (`BlockStepAt`), its CONTENT is not. |
| `StepLemmas` | **PER-ARCH** | `step-mov-rr`, `step-sub-ri`, `step-label` — literally the ISA semantics. |
| `FlatComposition` | **GENERIC** | label/thunk scanning over `AbstractTrace`; `HeadView` induction. Already abstract-side. |
| `RunContext` | **GENERIC** | `RunAt`, `Reachable` — abstract-side only. |
| `ResourceBounds` | **PER-ARCH shell** | `HeapRoom`/`StackRoom` statements name the arch's `X.State` and stack-pointer register. The *shape* is generic; give riscv64 its own 100-line file. |

Rough split: **~4,900 lines generic, ~1,900 per-arch.** riscv64's cost becomes
the per-arch 1,900 plus its resource shell, not 6,800.

#### The first move, concretely (added 2026-08-11 when the plan was opened)

G1 is a big edit and the temptation is to start by writing the parameter record.
Don't — start by MEASURING which of the four modules actually mention the
machine, because the layer split above is a claim this step should verify:

    grep -n "X\.\|x86-\|rax\|rsp\|rdi\|Flags\|updateFlags" \
      formal/Once/Adequacy/ArchCorrectness/X86-64/{FlatCorrespondence,ConcFlatSim,FlatComposition,RunContext}.agda

Every hit is either (a) a genuine machine dependency that becomes a parameter,
or (b) a leak the split says should not be there. Classify all of them before
moving a single line. Two specific things to check while doing it, because they
are the traps this plan already knows about:

- **`Flags` must not appear in the classification at all.** If it does, the
  branch-outcome law (difference 1) has not been factored out yet, and that is
  the first thing to fix — RISC-V has no flags register, and plan 0.66 will send
  the bill a second time if this is fudged.
- **`slot-size` must appear only as `slot-size`**, never as a literal `8`. The
  x86-64/riscv64 pair cannot catch a width leak (both are 8); 0.66 is where it
  would surface, and 0.66's own X1 phase is a re-audit of exactly this. Getting
  it right here makes X1 a formality.

Then extract in the order `RunContext` → `FlatComposition` → `FlatCorrespondence`
→ `ConcFlatSim` (increasing machine-dependence), running the four clusters after
each. The ledger diff is the gate on every one of those commits, not just the
last.

#### THE MEASUREMENT RESULT (2026-08-11) — and it moves the parameter list

Run, classified. Distinct machine tokens per module:

    RunContext         122 lines   1 hit, and it is inside a COMMENT.
                                   Genuinely generic as-is.
    FlatComposition    555 lines   7 distinct tokens: x86-{len,off,off-suc,eq}
                                   + X.{fetch,find-label,find-label-go}.
                                   Exactly the block-length interface this plan
                                   predicted. NO Flags.
    FlatCorrespondence 2117 lines  X.{State,readReg,readMem,Memory,Word} plus
                                   CONCRETE REGISTERS: rsp 212, rax 109,
                                   rdi 86, r15 84. And 29 Flags mentions.
    ConcFlatSim        2832 lines  X.{State,readReg,fetch,exec,execInstr,
                                   readMem,effectiveAddr,mkflags} + rsp/rdi/rax.

**Two corrections to the parameter list above, both found by measuring rather
than by writing the record first.**

1. **`Reg, sp-reg` is not enough — the core needs a ROLE MAP.** The two big
   modules name x86-64's registers directly, and every one of those names is a
   ROLE the abstract machine already has:

       role         x86-64   riscv64   x86-32
       stack ptr    rsp      sp        esp
       Output       rax      a0        eax
       Input1       rdi      t0        ecx
       heap top     r15      s2        esi
       closure      r12      s1        ebx
       Scratch      rbx      s3        edx

   So the parameter is `Reg` plus a record of named roles, and each arch
   supplies its own. A `sp-reg`-only parameterisation would leave 279 concrete
   register mentions behind, which is most of `FlatCorrespondence`.

2. **The `Flags` problem is SMALLER than feared, and its fix is structural.**
   All 29 mentions are the same shape: `sim-*` takes `newFlags : X.Flags` as an
   OPAQUE parameter and passes it straight into a reconstructed state record.
   Flags are never inspected and `updateFlags` never appears. So the
   correspondence genuinely does not care about flags — it only has to REBUILD
   A STATE, and x86-64's state is a 5-field record literal.

   **Therefore: the core must not build states at all.** Give it a per-arch
   state-update interface (`with-mem`, `with-pc`, `with-reg`, …) and the flags
   field vanishes from the core along with the record literal — riscv64's
   4-field state and x86-32's 1-argument `updateFlags` then need no special
   case. This is the same move `ArithSimCore` made and this plan already quotes:
   parameterise over what holds AFTER the block, not over how the state is
   built.

With those two, the layer split at the top of this plan stands: `RunContext`
and `FlatComposition` are generic today, and the two big modules are generic
ONCE the role map and the state-update interface replace their concrete
register names and record literals.

#### G1b, `FlatComposition` — the design, measured 2026-08-11

25 definitions, 555 lines. The machine surface is small (`X.fetch`,
`X.find-label`, `X.find-label-go`, plus `compile-abstract` for `x86-len`), but
the CONSTRUCTOR surface looked enormous: `label` appears 167 times, and 20 more
constructors a few times each.

**It is one lemma, and it should be one law.** `find-label-go-skip` (and its
sibling `-skip-other`) prove

    has-label block ≡ false
    ⇒ find-label-go t (block ++ rest) xi ≡ find-label-go t rest (xi + length block)

by ENUMERATING every `Instr` constructor — 22 near-identical clauses — because
`find-label-go`'s catch-all (`X86-64/Semantics.agda:236`) does not reduce on a
variable instruction. That enumeration is why the module looks arch-locked.

So the core takes, instead of the constructors:

    Instr, Program = List Instr, compile-abstract     -- for blk-len
    fetch, find-label, find-label-go                  -- the machine's scans
    is-label? : Instr → Bool                          -- the ONE view needed
    skip-law  : ∀ t i rest xi → is-label? i ≡ false
              → find-label-go t (i ∷ rest) xi ≡ find-label-go t rest (suc xi)

and `find-label-go-skip` becomes a three-line induction over the block. The
22-clause enumeration does not disappear — it CANNOT, it is a fact about that
ISA's instruction set — but it moves to the arch layer as the discharge of
`skip-law`, written once per arch instead of embedded in the correspondence.
That is `ArithSimCore`'s rule again, and the third time this plan has landed on
it: parameterise over what holds AFTER the step, never over how the step is
built.

Same treatment for `reg-op-no-label` / `const-no-label` (two more enumerations
of the same shape) and for `headView` / `all-headView`, whose `HeadView` is
about BLOCK STRUCTURE, not about x86.

`fetch-block-{head,2nd,…,6th}` are the block-offset interface the top of this
plan already named (`blk-off`, `blk-off-suc`, `fetch-block-nth`); they follow
from `x86-off-suc` + `drop-compile` and carry no constructor at all.

#### G1b-2 DONE: the scan-preservation half — and the law that made it cheap

`FlatCore/HeadView.agda` (new) holds `has-label` + the `HeadView` datatype;
`FlatCore/FlatComposition.agda` holds `find-{label,thunk}-{pres,corr}`,
`all-headView`, `find-label-none-{go,corr}` and `fetch-block-nth` with its six
named offsets. x86-64 is **490 → 188 lines** and supplies exactly six things:
`is-label?`, `skip-law`, `label-hit`, `label-miss`, `headView`, and its
emitter/fetch equations — every one of the latter `refl`.

**The warning below was right about the cause and wrong about the cost.** The
`rewrite ca-eq | meq` steps do stop working, but they do not have to become
~200 lines of `trans`: all four proofs use the same three transports, so they
factor into three BLOCK-GRANULARITY laws proved once —

    skip-plain    a label-free block is stepped over, costing `blk-len i`
    skip-labelled a block OPENING with a non-matching label, same cost
    hit-labelled  a block opening with a MATCHING label: the scan stops

plus `cons-step` (one skipped block, then the IH, re-associated). Every clause
of every scan theorem is then one law + `cons-step`, and the four proofs got
SHORTER than the x86-64 originals. `hv-clabel` is just `skip-labelled` at
`tail ≡ []`, which is why the two label cases stopped needing separate
arithmetic. That is the plan's own rule once more: state the consequence at
the granularity the induction actually steps at (a BLOCK), not the granularity
the machine reduces at (an instruction).

Two parameters beyond the three predicted, both `refl` at every arch and both
forced by the same thing — with the scan opaque, its behaviour on the EMPTY
program is no longer free: `ct-nil : compile-trace [] ≡ []` and
`find-label-nil`. They are the siblings of the already-present `mfetch-nil`.

`find-label-go-skip-other` is GONE, subsumed by `label-miss` as predicted.
`find-label-none-corr` is now stated with `find-label-go … 0` rather than the
arch's `find-label` wrapper, which is definitionally the same term — so no
`find-label` parameter was needed and `ConcFlatSim` consumed it unchanged.
`fetch-block-{head,2nd,…,6th}` collapsed into `fetch-block-nth` + six
one-liners.

Gate met: four clusters green, ledger byte-identical, no downstream edit.

#### G1b-2, the scan-preservation half — the original spec, kept for its warning

Remaining in x86-64's module: `HeadView`, `headView` (39 clauses),
`reg-op-no-label`, `const-no-label`, `find-{label,thunk}-pres`,
`find-{label,thunk}-corr`, `all-headView`, `find-label-none-{go,corr}`, and the
`fetch-block-*` family.

SPLIT: `HeadView` (the datatype) and all four preservation theorems are
GENERIC — they induct over `All HeadView prog` and never touch a constructor.
`headView` itself is PER-ARCH: its clauses are equations about *this* emitter
(`compile-abstract (instr-ctrl (c-thunk m b)) ≡ label (thunk m) ∷ sub (reg rsp)
(imm (slots b)) ∷ []`). So the arch supplies `headView : ∀ i → HeadView i` and
the core does the rest — the same shape as `skip-law`.

TWO MORE PARAMETERS, and one honest warning:

    mk-label   : Label → Instr        -- the arch's `label` instruction
    label-hit  : (ℓ ≡ᵇᴸ t) ≡ true
               → find-label-go t (mk-label ℓ ∷ rest) xi ≡ just xi
    label-miss : (ℓ ≡ᵇᴸ t) ≡ false
               → find-label-go t (mk-label ℓ ∷ rest) xi ≡ find-label-go t rest (suc xi)

(`label-miss` subsumes today's `find-label-go-skip-other`, which is exactly it
with `ℓ = thunk m`.)

**THE WARNING.** Unlike G1b-1, this is not a lift-and-shift. The four
preservation proofs lean on DEFINITIONAL reduction: `rewrite ca-eq | meq`
followed by terms whose types only line up because `X.find-label-go` reduces on
a literal `label _ ∷ _` and `_≡ᵇᴸ_` reduces on a literal provenance. With
`find-label-go` a parameter none of that reduces, so each of those steps becomes
an explicit `trans` through `label-hit` / `label-miss`. Budget for that — it is
proof surgery on ~200 lines, not a move. Do it as its own commit, and if a
clause fights for more than a few minutes, check whether the fight is telling
you a law is missing rather than that the transport is hard (that is how
`skip-law` was found).

#### G1c, `FlatCorrespondence` — measured 2026-08-11, and the table above is WRONG

2,117 lines, 33 `sim-*` lemmas, 44 `mkstate` literals. Both of G1's findings
survive the closer look; one of them gets bigger, and the role table gets a
correction that is not cosmetic.

**CORRECTION 1 — eight roles, not six, and 799 mentions, not 279.** The G1
measurement counted `rsp/rax/rdi/r15` and stopped. The real per-register counts
are rsp 212, rax 109, rdi 86, r15 84, **r14 80, rbx 77, rsi 76, r12 75** — the
four the table omitted are Count, Scratch, Input2 and the closure register.
Measured from the three emitters themselves, not from the table:

    role         x86-64   riscv64   x86-32
    stack ptr    rsp      sp        esp
    frame ptr    rbp      fp        ebp    ← NINE roles, and see below
    Output       rax      a0        eax
    Input1       rdi      t0        ecx
    Input2       rsi      a1        edx  ←┐
    Scratch      rbx      s3        edx  ←┘ SAME REGISTER
    Count        r14      s4        edi
    closure      r12      s1        ebx
    heap top     r15      s2        esi

There are NINE roles, not eight: `instr-push-frame` / `instr-pop-frame` lower
to `push ebp; mov ebp, esp; …` on all three arches. x86-32 has exactly eight
GPRs, so on that arch the collision is FORCED by counting — it is not an
oversight in the emitter.

**CORRECTION 2 — x86-32's role map is NOT INJECTIVE, and that is a defect the
extraction found.** `mov-output-to-input2` emits `mov edx, eax` and
`scratch-one` emits `mov edx, 1`: Input2 and Scratch are one physical register.
The abstract machine has eight independent registers, so a trace holding a
value in Input2 across any `scratch-*` poke loses it. The emitter's own comment
(`AbstractToX86-32.agda:249`) says "Scratch = edx, Input2 = edi" — but `edi` is
where `count-*` writes, so the comment is wrong about which collision exists,
which is why review never caught it.

Stated honestly: **not a live miscompile today.** `mov-output-to-input2` /
`mov-input2-to-output` have NO producer — `IRToTrace` never emits them (they
appear only in proof enumerations), so Input2 is a dead role in every emitted
trace. It is a latent defect and a hard blocker for the role map, which must be
injective or `FlatCorr` claims `Input2 ≡ Scratch` at every step.

**THERE IS NO FREE REGISTER, AND THE OBVIOUS FIX IS A SIGSEGV.** Written down
because it was attempted and backed out on 2026-08-11, and the false trail is
short and inviting:

- `AbstractToX86-32.agda:22` says "ebp: unused by the slot machine (slots are
  esp-relative)". FALSE — lines 183–191 of that same file read
  `push ebp; mov ebp, esp`.
- Those two clauses are `instr-push-frame` / `instr-pop-frame`, and
  `FrameFree.agda` does set `EmittableI` for BOTH to `⊥`, so they cannot occur
  in an emitted trace. At that point "ebp is free within the emittable
  fragment, assign Scratch → ebp" looks proved.
- **It is not, and the disproof is one layer up.** `Once/Target/X86-32.agda`
  emits a real i386 frame prologue in the TEXT — per compiled function and per
  thunk body: `pushl %ebp; subl $N, %esp; movl %esp, %ebp; … leal N(%ebp),
  %esp; popl %ebp; ret`. `%ebp` is the live anchor every epilogue restores
  `%esp` from. Clobbering it does not corrupt a value, it returns to a garbage
  stack — the 35/20 SIGSEGV class D102 spent a plan fixing.

The lesson generalises past this register: `EmittableI` fences the ABSTRACT
TRACE, and the text emitter writes instructions that no abstract trace contains.
A register is free only if BOTH layers agree, and only the second one is
authoritative about the binary.

Corroboration that `edx` really is Scratch, from a fourth file:
`Arith/Backend/X86-32/Emit.agda:215` push/pops `%edx` around every arith block
because it is "live across a cata loop" — and its comment calls `%edi` "Input2"
while `count-*` writes `%edi`. Three files now carry a wrong Input2 labelling;
none carries a right one.

**So the collision has no local fix, and G1c must not pretend otherwise.** What
is true is narrower and still enough: the role map is injective on the roles an
arch actually REALISES. Input2 is dead (no producer), so x86-32 realises seven
roles injectively — esp, eax, ecx, edx (Scratch), edi (Count), ebx (closure),
esi (heap) — with ebp reserved as the frame anchor. Build the role map for the
eight roles x86-64 realises and let 0.66 answer this, where its two real
options are:

    RETIRE Input2 from the abstract machine. Nothing emits it on any arch;
      `mov-{output-to-input2,input2-to-output}` survive only in proof
      enumerations. Widest blast radius (SMCore, three emitters, FrameFree,
      every enumeration), smallest remaining state.
    SPILL. Give x86-32 Input2 a stack slot when it gains a producer. Local, but
      it puts a memory access where the other two arches have a register, which
      the correspondence must then see.

Do NOT re-attempt a register reassignment without first checking
`Once/Target/X86-32.agda`.

**FINDING 2 CONFIRMED, and its fix is stronger than "a state-update
interface".** All 44 `mkstate` literals are 5-field; `flags` occurs only as
`(flags s)` (37×) or as an opaque `newFlags` parameter (7× — `alloc-stack`,
`dealloc-stack`, `thunk`, `ret`, the four that really do clobber flags). Flags
are never read. So do not give the core an updater — give it **the post-state
itself, plus the laws it must satisfy**:

    sim-X : ∀ (s' : State) → readReg s' Output ≡ v
          → (∀ r → r ≢ Output → readReg s' r ≡ readReg s r)
          → memory s' ≡ memory s → halted s' ≡ halted s → pc s' ≡ pc s + 1
          → FlatCorr hv (flat-exec-instr X [] fs) s'

That is `ArithSimCore`'s rule applied literally — parameterise over what holds
AFTER the step, never over how the step is built — and it is what makes the
core state-shape-agnostic rather than state-shape-parametric: flags, CSRs and
any other component simply never appear, and `newFlags` stops being a
parameter of anything. The arch discharges every law by `refl` against its own
record literal.

COST — and **the wrapper plan was wrong, corrected by counting the call sites
rather than the lines.** The fear was a ripple into the 2,832-line
`ConcFlatSim`, so ~33 thin wrappers per arch looked like the cheaper trade. In
fact the `sim-*` family is called **37 times in total**, 31 of them in
`FlatSimulation` and only 6 in `ConcFlatSim`, each one line. Updating a call
site costs `_ … (sets-role-x86 s role-out _ _)` — cheaper than a permanent
wrapper, and it leaves no shim behind for the arch layer to carry forever.
So: no wrappers; update the call sites.

WHAT THE ARCH PAYS INSTEAD, and it is the real cost: `sets-role-x86`, the proof
that x86-64's `mkstate` literal satisfies `SetsRole`. Its `off-role` field is a
**64-clause** case split (8 diagonal absurdities, 56 `refl`s) — because "writing
rax leaves rdi alone" was FREE while the post-state was concrete, and making it
abstract is exactly what withdraws that. Written once, next to the register
file, it is the same shape as `FlatComposition.skip-law`: an ISA fact that
cannot be generalised away, only relocated out of the correspondence.

A SECOND FINDING FROM THE FIRST FAMILY: the post-state laws need no `pc`
clause, because `FlatCorr` HAS NO PC FIELD. The 44 literals all wrote
`pc s + 1`, but the pc discipline lives one layer up in the block-steps, so a
register write's correspondence genuinely does not constrain it. The `SetsRole`
record is therefore four fields, not five.

REJECTED ALTERNATIVE: a `with-reg : State → Reg → Word → ℕ → Extra → State`
updater with `Extra` opaque (`Flags` at x86-64, `⊤` at riscv64). It needs no
wrappers, but it still parameterises over HOW the state is built, and it pushes
one extra argument into all 44 downstream call sites. The whole reason finding 2
exists is that building states is what makes a correspondence arch-locked.

**STEP 2 IS DONE (2026-08-12): all 33 lemmas, 44 `mkstate` literals → 0.** The
only state literals left in the module are the FOUR ARCH REALISERS, which is
where a state literal belongs — the arch exhibits its own state and proves it
satisfies the laws.

FOUR RECORDS, not one, and the reason is the ISA rather than the interface:

    SetsRole     one register role written          22 lemmas
    SetsMem      one address written                 5 lemmas
    SetsRoleMem  both — `call` lowers %rsp AND stores the return address
    Sets2Roles   two roles — `alloc-heap`'s two-instruction block

`call` and `alloc-heap` do not decompose into two single-writes, because the
INTERMEDIATE state is not something either lemma is given. A single record
indexed by "which roles and which address were written" would subsume all four
and is worth doing WHEN THE MODULE MOVES INTO `FlatCore` — not speculatively
now, where four concrete shapes cover 33 lemmas and each says exactly what its
instruction does.

WHAT THE ARCH PAYS, all of it in four realisers: `sets-role-x86`'s 64-clause
`off-role`; `sets-mem-x86`'s TWO clauses (addresses have a decidable equality —
it was registers, an eight-way enum, that forced the enumeration); and the two
combined ones, which reuse the 64 rather than repeating it. `sets-2roles-x86`
takes `ρ₁ ≢ ρ₂` as a real premise — the first write's value must survive the
second, which is false if they name one register — discharged `λ ()` at the one
call site.

THREE THINGS THE CONVERSION DELETED, each one finding 2 paying out:

    `newFlags` as a parameter of five lemmas. There is no field to fill.
    `sim-ret`'s DOUBLE `%rsp` write (nested `xwriteReg`, once for the `add` and
      once for the `ret`'s pop). As a claim about the state AFTER the pair it
      is one write, and the nesting disappears with the literal.
    every `rewrite ≡ᵇ-refl` / `≢→≡ᵇfalse` in the store chain — the alias
      proofs now case-split on the ABSTRACT decision and apply the two laws.

#### G1d, `ConcFlatSim` — measured 2026-08-12, and "most machine-dependent" is BACKWARDS

The plan has said since G1 that `ConcFlatSim` is "the most machine-dependent,
last". Measuring it says the opposite, and by a wide margin.

    module              lines   concrete-register mentions   state literals
    FlatCorrespondence  2,117   799                          44
    ConcFlatSim         2,832    92                           0

**115 machine-mentioning CODE lines out of 2,833 — four percent.** And they are
not spread, they are in two clumps with 1,400 consecutive machine-free lines
between them:

    lines     1– 600   imports, the resource-bound parameters (`%rsp`), helpers
    lines   601–2000   ZERO machine mentions
    lines  2001–2600   the block-step dispatch — peak at 2201–2400
    lines  2601–2833   ZERO machine mentions

**THE 1,400-LINE MIDDLE IS THE BIGGEST GENERIC BLOCK IN THE PLAN** — larger
than everything G1a+G1b+G1c moved put together (~730 lines). It is the flat
machine's WELL-FORMEDNESS layer, driven by `RunAt`: `RetMatch`, `SegWF`,
`SegCur`, `JumpPost`, `PcView`/`pcView`, `run-seg-wf`, `stack-ptr-*`,
`ptr-bounds-*`, `run-shape-check`, `slot-read-*`, the four
`{load,store}-indirect{,-suc}-target-*` disciplines, `branch-tag-scrutinee-wf`.
Not one of them mentions x86. G1d step 1 is a MOVE, the same shape as G1b-1,
and it is where most of the module's line count goes.

**AND SEVERAL OF THE RESIDUALS ARE ARCH-GENERIC TOO** — the postulate block
says so itself: `call-site-shape` carries the comment "No `X.State` in the
type: this is a fact about the ABSTRACT machine", and the same holds for
`ret-site-owes`, `ret-budget-matches`, `emitted-thunk-guarded`,
`emitted-code-addr-has-body`, `emitted-shape-check`, `run-meets`. Today they sit
in an arch module, so riscv64 and x86-32 would each acquire their own copy of
each. Moving them into the core is the plan's second payoff made concrete: **a
residual that lives in the core is discharged once for all three arches**, and
the ledger stops growing per-arch.

**WHAT IS ACTUALLY ARCH-SPECIFIC is the two-instruction BRANCH lowering**, and
it is the clump at 2201–2400. x86-64 lowers `c-branch-*` to `cmp; je`, so the
proof hand-runs both instructions and builds the intermediate flags state
(`X.mkflags`, the only 3 uses in the file). riscv64 does it with a single
`beq` and has no flags at all, which is why this cannot be shared as-is.

The fix is the move this plan has now landed on FIVE times — parameterise over
what holds AFTER the block, never over how the block is built:

    branch-block-law : the emitted block for `c-branch-* m`, run from a state
      whose guard register holds `v`, reaches (a) the resolved target when
      `v ≡ 0` and the label is present, (b) the fall-through when `v ≢ 0`,
      (c) HALTED when the label is absent — in each case emitting no events.

x86-64 discharges it with its `cmp; je` pair and its flags; riscv64 with one
`beq`; and the core's dispatch stops knowing there is such a thing as a flag.
That is `skip-law`, `label-hit`/`label-miss`, the role map, the post-state laws,
and now this — the same rule five times, which is enough to call it the plan's
actual result rather than a recurring coincidence.

ORDER: (1) move the 1,400-line WF layer into `FlatCore` — a relocation, no
proof surgery, four clusters green; (2) move the arch-generic residuals with
it, which is a LEDGER-VISIBLE change (the rows move module, and the gate's
"ledger diff empty" needs re-reading as "no row added or weakened"); (3) the
branch-block law; (4) what is left is the dispatch, which is small.
