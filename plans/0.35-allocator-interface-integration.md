# Plan 0.35 — Allocator interface integration (malloc-like alloc/free wired into the live codegen)

## Why

Heap allocation in the live compiler is currently **inlined and allocator-agnostic-by-accident**, and there is **no `free`**:

- `CCC.Target.X86-64.AbstractToX86` lowers `instr-alloc-heap n` to a hard-coded
  bump: `mov rax r15 ∷ add r15 (slots n)`. The bump pointer `r15` is baked
  straight into codegen.
- The abstract machine's `instr-alloc-heap` (`SMCore`/`SMPrimitives.Heap`) routes
  through `Once.Allocator.AbstractInstance`, whose State is a **bump-by-1 ref
  counter**. It only ever grows; nothing is ever freed → the heap leaks.
- A well-designed allocator subsystem **already exists but is a parallel,
  partially-dead structure** (same shape as the historical compile-ir vs
  ir-to-trace split):
  - `Once.Allocator.Interface.AllocatorInterface` — `State / init / Allocated /
    alloc / block-in-region / blocks-disjoint`. **alloc-only, no `free`.**
  - Implementations: `BumpAllocator`, `Malloc`, `Mempool`, `Slab`,
    `AbstractInstance`. Only `Malloc` declares its *own* `free : Addr → State →
    State`, in a separate `record Malloc` — not in the shared interface.
  - `Once.Allocator.Target.X86` — an x86 refinement of the bump allocator
    (`alloc-instrs n = mov rax r15 ∷ add r15 (n*8)`) **plus** a correspondence
    proof. But it targets `Once.Target.X86`, **not** the live
    `Once.CCC.Target.X86-64`, and **no live codegen module imports it.**

So we have most of the pieces — an interface, four implementations, an x86
refinement — wired to nothing. ARCHITECTURE.md (§AllocMode, §Allocator usage)
mandates a malloc-like interface where **Place** picks the concrete allocator per
use-site and emits `free` for (a) escaping outputs at their last consumer and (b)
transient / locally-consumed allocations inside an IR. This plan connects the
subsystem to the live path and adds `free`.

This also **supersedes** the dead-end from the 0.32 block-step work where
`alloc-heap` was going to get an `alloc-eq : r15 ≡ enc(next-ref)` field in the
abstract↔x86 simulation. That drags allocator-private state into the simulation
relation and forces an unsatisfiable bump-law (abstract bumps the ref counter by
1, x86 bumps `r15` by `slots n`). The correct design hides allocator state behind
a contract; see M5.

## Design decisions (settled in discussion)

### D1 — Calling convention: `call`/`ret`, leaf, frameless

`instr-alloc-heap` / `instr-free-heap` lower to `call <allocator-label>` where
Place supplies the label.

- **Frames: no.** A leaf allocator (calls nothing, no locals) needs no
  prologue/epilogue — it works out of scratch registers + its global state.
- **Plain jump: no.** alloc is called from many sites; returning needs a return
  address. x86-64 has no link register, so "just jump" forces the return address
  into a GP register (`jmp reg` back) — that *is* call/ret but burns a register
  the hot cata loop wants. Strictly worse.
- **`call`/`ret`: yes.** Its decisive virtue: **net-zero on `rsp`** (call pushes
  the return address, ret pops it; the IR never observes the mid-call state). So
  from the simulation's view the call is **atomic** — registers in, `rax` out,
  `rsp` unchanged, allocator-private state advanced — which is exactly the
  abstract `instr-alloc-heap` semantics. The return-address slot is transient and
  invisible to the IR's slot frontier.
- **No inline.** Inlining only ever makes sense for the bump allocator — the
  *uninteresting* one. The allocators that matter (`Mempool`/`Slab`/`Malloc`)
  carry free-list logic that must not be duplicated per call site; they have to
  be called. So `call`/`ret` is the universal mechanism, not a fallback.

### D2 — Place stamps the allocator + emits free

- Each Allocator-mode use-site carries *which* concrete allocator backs it
  (label/address), per ARCHITECTURE.md §AllocMode ("which concrete allocator …
  is a separate choice made by Place").
- Place emits `free` for: **escaping** outputs (at the last consumer) and
  **transient / locally-consumed** sub-IR outputs (inside the IR's own trace).
  There is no `free` IR *constructor* — frees are trace-level instructions
  (ARCHITECTURE.md §Codegen / §Allocator usage).

### D3 — Two contract levels; **`PreservesCCC` stays untouched**

`PreservesCCC` (in `CCC.SigOp.Helper`) is a **SigOp-only, abstract-machine,
grow-only frontier-monotone** contract: `frame-eq`, `prior-preserved`
(`BeforeFrontier` locations unchanged), `heap-monotone`, `slot-monotone`,
`not-halted`. We do **not** generalize it.

- `alloc` *would* fit `PreservesCCC` (monotone, writes no existing memory) — but
  reusing it conflates levels; alloc/free are trace-level memory ops with **no
  CCC-morphism denotation** (no IR constructor), invoked **mid-IR**, so they get
  a **separate, lighter boundary contract**:
  - **abstract level:** a liveness-preservation property (alloc: live set grows
    by a fresh disjoint block; free: a now-dead block leaves the live set; all
    *live* blocks preserved).
  - **x86 level:** preserve the encoding relation (`enc-hl`/registers) + the
    calling convention (preserve IR-live regs `rdi/rsi/rbx`, output in `rax`,
    `rsp` net-zero, allocator-private state hidden).
- `free` **cannot** fit `PreservesCCC`: it reclaims a `BeforeFrontier` block,
  violating `prior-preserved` and `heap-monotone`. The obstacle is
  **non-monotonicity**, not the inside-IR position. This is *the* reason the
  separate contract is required.

### D4 — Free **with reuse**, in lockstep through the interface (no live-set)

Reuse of a freed block is **not** a problem, because abstract allocation routes
through the *same* interface (`instr-alloc-heap` → `AI.alloc-impl`) as the
concrete target. So abstract and concrete reuse **the same ref in lockstep**.
Checked against `heap-eq : ∀ hl → x86mem@(enc-hl hl) ≡ enc-maybe (heapMem … hl)`:

- alloc ref r, write v1 → abstract `just v1` / x86 `just (enc-sv v1)`. ✓
- free(r) (memory-non-destructive — updates only allocator State) → both still
  hold v1, stale-but-consistent. ✓
- realloc **reuses ref r**, write v2 → both hold v2. ✓

`heap-eq@r` holds throughout, and `enc-hl` stays injective because a reused ref
is the **same** ref — never two distinct refs colliding on one address.
Disjointness-among-live is exactly the interface's existing `blocks-disjoint` (a
freed block is re-handed-out only after its occupant is dead). **No live-set, no
injective-on-live, no staging.**

The one residual constraint: `enc-hl` must be a pure function, so each ref maps to
a **fixed** address. That holds for **fixed-size-slot allocators (`Mempool` /
`Slab`)** — ref = slot, address = base + slot·size, reuse returns the same slot.
The **only** deferred case is variable-size **`Malloc` with coalescing/splitting**
(ref↔address not a fixed function), which only matters for heterogeneous block
sizes — cata's uniform size-2 containers don't need it. So the deferral is a
specific allocator, not "reuse."

The previous worry (a live-set / `enc-hl`-injective-on-live) was an artifact of a
non-design: abstract minting fresh refs while concrete reuses addresses. We never
do that — both go through the interface.

**Disjointness is a contract field, never a postulate.** The interface already
declares `blocks-disjoint` as a *field* (a proof obligation every implementation
discharges — `AbstractInstance` proves it from distinct ref-ids). The free+reuse
extension keeps it that way: `blocks-disjoint` is strengthened to its
liveness-aware form ("any two *currently-allocated* blocks have disjoint address
ranges, even after intervening frees/reuse"), and **each implementation
(`Mempool`/`Slab`/…) must prove it** — no postulate is introduced anywhere. The
simulation then *consumes* that proof; it does not re-derive or assume
disjointness.

### D5 — Orthogonal (out of scope, tracked)

Allow `PreservesCCC`-bearing **SigOps to free** data. A SigOp can currently
return heap-allocated data but cannot free it. Letting SigOps participate in the
free protocol interacts with Stage B's live-set work — note and defer.

## Milestones

- **M1 — `free` + liveness-aware disjointness in the shared interface.** Add
  `free : Addr → State → State` to `AllocatorInterface`, and strengthen
  `blocks-disjoint` to its liveness-aware form (any two *currently-allocated*
  blocks are disjoint, across intervening frees/reuse) — **as a field each
  implementation proves, no postulate.** Update `BumpAllocator`, `Mempool`,
  `Slab`, `AbstractInstance`, and fold `Malloc`'s standalone `free` into the
  interface. `Mempool`/`Slab` (fixed-size slots) are the reusing allocators that
  discharge it cleanly; `Malloc` (coalescing) is the deferred hard case.

- **M2 — live abstract free + lighter contract.** Add `instr-free-heap`
  AbstractInstr (returns a block to the allocator State, memory-non-destructive)
  in `SMPrimitives.Heap` / `SMCore.exec-abstract`. Define the alloc/free boundary
  contract record (separate from `PreservesCCC`) capturing the abstract
  liveness-preservation property (all *live* blocks preserved across the op).

- **M3 — wire codegen through the interface, one allocator target per arch.**
  `instr-alloc-heap` / `instr-free-heap` lower to `call alloc-label` /
  `call free-label` in `CCC.Target.X86-64.AbstractToX86`. **Retarget**
  `Once.Allocator.Target.X86` (written against the old `Once.Target.X86`, from
  when x86-64 was just "X86") onto the live `Once.CCC.Target.X86-64`, structured
  as **one allocator implementation per target, mirroring the CCC target tree**
  (portable; x86-64 is the current focus). The existing alloc correspondence
  proof is reused, not duplicated.

- **M4 — Place: escape/liveness analysis + free emission.** The substantive
  step. A static analysis over the IR DAG classifies each value-producing
  Allocator-mode output into the three ARCHITECTURE.md flavours — **transient**
  (freed inside the producing IR), **locally-consumed** (freed by the consuming
  compositional IR — `compose`/`pair`/`case` — right after the last read), and
  **escaping** (not freed here; the obligation passes to a later consumer or the
  program output). Place then (a) stamps each use-site with its concrete
  allocator label and (b) emits the `free` instructions at the computed
  last-consumer points. Liveness = "is this block read again after this point";
  for the heap-only cata path the IR DAG is small and acyclic, so the analysis is
  a straightforward last-use computation. Its **correctness is pinned by M7**, not
  asserted.

- **M5 — abstract free-correctness contract.** Each compositional IR's WF proof
  gains an obligation that the frees it emits target blocks it (or its sub-IRs)
  produced and that are dead at the free point — the per-IR half of M7.

- **M6 — x86 call-boundary simulation contract.** Prove once per concrete
  allocator: `call alloc-label` preserves `CompiledCorr` with `rsp` net-zero,
  `rdi/rsi/rbx`/heap preserved, and `rax`/Output a fresh `enc-hl`-corresponding
  disjoint pointer; same for free. The cata `block-step-alloc-heap` (0.32 M2)
  then **consumes this contract** instead of tracking `r15` — closing that hole
  the principled way and unblocking 0.32 M2.

- **M7 — leak-freedom: every alloc has a matching free (the crown).** The heap
  analog of the existing stack reclamation theorem (`alloc-correct`,
  ARCHITECTURE.md:189). State, over the abstract trace, a **live-set conservation
  law**:

  ```
  heap-conservation : ∀ (ir : IR A B) s alloc →
    live-set (exec-trace (compile ir) s alloc)
      ≡ live-set-before  ⊎  escaping-footprint ir
  ```

  i.e. an IR's trace grows the live-set by **exactly** its escaping output; every
  transient/locally-consumed block is matched by a `free`. Proved by structural
  induction on the IR (leaf allocator: `live += {output}`; `compose g∘f`: emits
  `f`-output's free, net `live += {g-output}`).

  **Whole-program corollary — net-zero, not "output remains."** A Once program
  is `main : Eff Unit Unit`; it **returns no value** — the only observable
  behaviour is the SigOp trace (and the "exit code" is `linux.exit`'s *argument*,
  not a return). Heap blocks are never themselves observable; they only ever flow
  *into* SigOp invocations as arguments (e.g. a buffer to `linux.write`, which the
  kernel copies), which is a **locally-consumed** use — Place frees it right after
  the call. So `escaping-footprint main ≡ ∅`, and the corollary is:
  **`live-set at program exit ≡ ∅`** — every block is freed; full reclamation.
  (The `escaping-footprint ir` term still matters for *intermediate* IRs, where a
  sub-IR's output escapes to its parent; only the top level bottoms out at ∅.)
  See [[feedback-programs-dont-return]].

  This **subsumes** no-leak (conservation to ∅), no-double-free
  (multiset/ownership accounting), and no-use-after-free (pointer discipline: heap
  rooted in stack, frees only at last consumer). It is also what forces Place's M4
  analysis and the spec to stay in sync — a global theorem, not per-shape
  witnesses. Net-zero-at-exit is exactly what makes valgrind report zero *still
  reachable*, not merely zero *definitely lost*.

- **M8 — deferred: variable-size `Malloc` (coalescing).** The only allocator
  whose ref↔address map isn't fixed (free splits/merges regions). Needs the
  heavier address model; only required once programs allocate heterogeneous heap
  block sizes. Fixed-size `Mempool`/`Slab` reuse (M1–M5) cover cata.
  SigOp-free (D5) rides along here.

## Success criteria

1. **Primary (∀-inputs proof):** `heap-conservation` (M7) holds, postulate-free —
   every allocation is matched by a free, no leak / double-free / use-after-free.
2. **Empirical (runtime):** the extracted binary runs **valgrind-clean** on the
   layer5 cata test. For our own allocators (bump/mempool/slab), emit valgrind
   mempool client-requests (`VALGRIND_MEMPOOL_ALLOC` / `MEMPOOL_FREE`) so valgrind
   tracks blocks it otherwise can't see. Belt-and-suspenders to the proof.
3. **No regression:** layer5 cata still exits 42; full x86-64 build green.

## Interplay with in-flight plans

- **0.32 M2** (`block-step-alloc-heap`): do **not** add an `alloc-eq`/`r15` field
  to the simulation. The alloc case waits on **M6** and consumes the call-boundary
  contract. The other 0.32 block-step cases are unaffected.
- **0.31 0b** (delete compile-ir): unchanged; this is orthogonal heap plumbing.
