# Plan 0.144 — No module needs more memory than the machine has to spare

## Summary

Checking the proofs takes more memory than this machine can comfortably give. Every few days a check
runs out of memory, and the work stops while we raise limits and retry. We now have a measurement of
every proof file: how long it takes and how much memory it needs, each on its own. A small group of
files causes almost all of the trouble. This plan rewrites those files, using a few techniques that have
already worked in this project, until each one fits with room to spare. When it is done, a full check
runs at the default limits, and a new file that is too heavy is noticed when it is added, not weeks
later.

## 1. Why

On 2026-11-05/06 the merge gates of plan 0.143 ran out of memory four times: the backstop needed its cap
raised to 6G, and the AST dump needed 12G, after `Resusp.Id`, `Laws.Combinators` and `Laws.Categorical`
each exhausted the heap in turn. None of these modules was changed by 0.143. The same has happened on
earlier merges (`ConcFlatSim` in `run-ast-dumps.sh`'s header). Each time the limit was raised and the
cause left in place, so the margin shrinks with every new module. Running out of memory also costs
time far beyond the module: a kill means hours of rechecking, and a night lost when it happens unattended.

**Why the gates still run out although every module fits alone:** `make certified`, the backstop and the
AST dump check many modules in ONE process, which keeps what it has checked. The heaviest modules then
run on top of an already large heap. Making group A light helps every gate; checking bottom-up in
separate processes (as the profiler does) is the other lever, for the gates themselves (step 5).

### Known patterns (read before probing)

Most causes are already measured and recorded as session memories in the other checkouts
(`~/.claude/projects/-home-whatever-Repo-mokshasoft-Once-once-lang{2,5}/memory/`), not in the tree. For
each module: run `--profile=internal` first (phases: Typing, Positivity, Termination, (De)serialization),
then `--profile=definitions`, and match to one of these before experimenting.

| symptom in the profile | known cause | fix | measured |
|---|---|---|---|

| nested `where` helpers `goA : … → _` with `with … \| refl` chains | the result type is a meta, solved from the goal while the `with`s abstract over it (`meta-standing-for-a-computation`) | name the goal once (`GOAL = SameM π₀ (T ⟨ σ ⟩) (⟦ d ⟧ …) (⟦ d′ ⟧ …)`) and write `→ GOAL` | Categorical 2026-11-06: 242 s → 57 s, 4.3 → 2.9 GB |

## 3. Decisions

- **B1, the target — DECIDED 2026-11-06:** every module at most **3 GB peak RSS** and **50 s** alone
  (about 1.5 GB live), so two Agda sessions can run side by side and a recheck stays short. Exempt from
  the time limit for now: the apex modules `Once.Certified` (51 s) and `Once.Compiler`, whose time is
  loading the 560–760 modules they must import.
- **B2, the ratchet — DECIDED 2026-11-06:** NO profile data is committed. `make profile-gate` profiles only
  the modules a branch changes (against the merge base) and fails when one exceeds the B1 target. A merge
  gate (MERGE.md §5) only with the user's approval of the wording.
- **B3, the order — DECIDED 2026-11-06:** every module above the target is fixed, worst offender first
  (by time, then peak RSS), working up the list in §4. A fix that teaches a pattern is applied to the
  family it belongs to when that family comes up.

## 4. Steps

Each fix is measured the same way: `agda-profile.py --root <module> --work ~/.cache/once-profile/master
--ref <commit>` (the master work tree keeps every import built), before and after, numbers in the commit
message. Proofs do not change meaning: no postulate, no pragma, no weakened statement; the module's
exported types stay as they are (its consumers do not change). Patterns: `abstract` around lemmas whose
users need only the type (`Pair/Pres`, 2026-09-29); typed pieces instead of one long chain
(`Resusp.Id`'s `srC`/`srB`/`sr`); sharing a construction through its module (`NineStepPres`) instead of
unfolding it by hand; splitting a module whose parts do not depend on each other.
