## 0. The defect

A call enters a frame `enter-call` makes by `shift-frame (current-frame pre) 1`; `do-thunk` then grows it
by `b` and CLEARS that region. Every call proof needs the callee frame to be fresh: strictly below the
caller's in `≺`, so the caller's live slots become `stack-ancestor`s (`Allocation.parent-before-child`) and
`clear-frame` misses them. `FrameSemantics` has no law relating `shift-frame` to `≺`, and none is true:

* x86-64's `Frame` is a `StackPointer`, an address with an `InStack` bound
  (`CCC/Target/X86-64/FrameInstantiation.agda`), and `x86-shift-frame f n = sp-addr f ∸ n·word`. At the
  stack bottom the subtraction stops at zero, so the callee frame IS the caller's (`StackMem` is keyed by
  `Frame`, so they are the same cells), and `do-thunk` wipes the caller's live data.
* x86-32 and riscv64 are the same.

So the abstract obligation cannot prove a call correct, and an assumed run of a called block cannot be
satisfied at the stack bottom. That is what blocks plan 0.88's M0, plan 0.93's `curry` case, and any
honest replacement for `BlockRuns`.

The concrete machines already know about room: `StackRoom`/`CallRoom` (`<arch>/ResourceBounds.agda`) hold
at every reachable state and say the reservation fits above the heap. The fact exists; it lives at the
wrong level.

## 1. The idea

Separate WHICH frame from WHERE it sits in memory:

* **Abstract:** a call always gets a fresh frame strictly below its caller. `shift-frame f (suc n) ≺ f`
  holds outright, for every frame. The abstract stack is unbounded, as the abstract heap already is.
* **Concrete:** each arch maps an abstract frame to an address, and its simulation shows the address is
  the real `%rsp`/`sp` value while the run has room. Running out of stack is the concrete machine's
  outcome, exactly as running out of heap is (`HeapRoom` today, the `exhausted` end after plan 0.123 A, with Part C's coarse checks).

Nothing in `Flat.agda`'s machine changes: `enter-call`, `do-thunk`, `clear-frame` and `leave-frame` keep
their definitions. Only the frame type and its laws do.

## 2. The new law

One field in `FrameSemantics` (`CCC/FrameSemantics.agda`), beside `≺-trans`/`≺-irrefl`/`≺-compare`:

    shift-≺ : ∀ f n → 0 < n → shift-frame f n ≺ f

and whatever `shift-base`/`frame-disjoint-bounded` turn into. Those are the address laws, and they become
conditional on room, since an abstract frame below the floor has no address.

From it, in the machine layer: `current-frame (grow-frame b (enter-call pre)) ≺ current-frame pre`, then
`BeforeFrontier pre loc → BeforeFrontier callee loc` for every caller-live `loc`, then the input transport
plan 0.88 worked out (`validityWF-with-bf-transfer` + `validityWF-mem-preserved`).

## 3. The representation (settle in S0)

Two candidates for the abstract `Frame` of each arch:

* **(a) An unbounded address.** `Frame` is an address with no floor (an integer, or a ℕ offset from a
  virtual top), `shift-frame` subtracts exactly, and `≺` stays "address `<`". `frame-base` agrees with the
  real stack pointer only under room. Smallest change: `≺` and the correspondences keep addressing by
  `frame-base`.
* **(b) A depth.** `Frame = ℕ` (call depth, plus a sub-index for `grow-frame`), `≺` is `>`. Cleanest laws,
  but every correspondence needs a depth→address map built from the frame sizes above it.

Recommendation: (a), unless S0 shows the `InStack` bound is load-bearing in many abstract proofs.

## 4. Steps

### S0 — Spike: add the law and measure
Add `shift-≺` to `FrameSemantics` with the three instances as holes. Record which modules break and why:
expected to be the three `FrameInstantiation`s and their `Layout`s, plus what reads `InStack`/`in-stack`
directly (about 16 files touch `shift-frame`, 16 `InStack`). Decide (a) or (b). Also write the
**stack-bottom probe** (§6) against today's code. If it does not refute, this plan's motivation is weaker
than stated and must be re-argued.

### S1 — x86-64 frames
New `Frame` and `shift-frame`, `≺` laws, `shift-≺` proved, address laws made conditional.
`FrameInstantiation` + `Layout`. Then the abstract consumers that used the bound (`FlatPtrBounds`,
`FlatStoreWF`, `FlatStackPtr`, `SMCore`), each against the new laws rather than the arithmetic.

### S2 — x86-64 correspondence
`FlatCore/FlatCorrespondence` and `X86-64/FlatSimulation`: the abstract frame's address is `%rsp`, under
room. Room comes from `StackRoom`/`CallRoom`, which are already conditioned on reachable states, so no new
hypothesis appears. After plan 0.123 A it comes from the emitted room check instead (§5).

### S3 — x86-32 and riscv64
The same as S1+S2, twice. `Once/Certified.agda` green on all three.

### Hand-over to plan 0.125
The block-call lemma (the generalised M0) and its consumers (`cata-correct`, `curry`'s arrow clause, `Out`,
`Call`) are plan 0.125 S2/S3 (D341). This plan ends when `shift-≺` holds on all three arches and
`Once/Certified.agda` is green.

## 5. Relation to plan 0.123 (memory runs out observably)

* **Not the same bug.** The six failing Layer5Spec tests ("a server never ends") are HEAP exhaustion: each
  round bump-allocates and nothing reclaims. Only plan 0.123 Part B (reclaiming allocators) turns them
  green. This plan does not touch them, and neither waits for the other.
* **Same shape.** 0.123 Part A makes running out an observable `exhausted` end and REMOVES `HeapRoom`,
  `StackRoom` and `CallRoom` from the apex, with a room check emitted at every frame reservation and call.
  That is exactly the concrete half of this plan: the abstract stack never runs out, and the concrete
  machine either has room (S2's proof) or reaches `once_exhausted`.
* **Order.** S0 and S1 are independent of 0.123. S2/S3 use whichever room fact exists when they run:
  the `StackRoom`/`CallRoom` parameters before 0.123 A, the room check after it. If 0.123 A is close to
  landing, do S2 after it so the correspondence is written once.
