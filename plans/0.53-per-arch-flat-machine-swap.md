# Plan 0.53 — Bring X86-32 / RiscV64 to X86-64's Level in the Adequacy Apex (and retire the legacy backend island)

## Correction (2026-07-01) — the premise changed after investigation

This plan was first written to "mirror the X86-64 Plan 0.32 flat stack
(`FlatSimulation`/`CompileCorrectFlat`) to the other two arches and delete
`DirectSimulation`." **That target turned out to be legacy.** Ground-truth
investigation established:

- The live top-level theorem is `Once/Compiler.agda` → `Once.Adequacy` →
  `Once.Adequacy.ArchCorrectness.arch-correctness`. Its checked closure is 162
  modules. It is **green** (post-0.36, confirmed by the standing MAlonzo
  re-extraction that is downstream of the 0.36 `lea-indexed` commit).
- x86-64's witness `x86-64-correct` is discharged through the **`IRObsCorrectFlat`
  observable-trace theorem** (`ir-obs-correct → cata-correct`, Plan 0.36/0.44) —
  **not** the Plan 0.32 flat stack.
- The old backend correctness formulation — `EntryPointCCC`, per-arch
  `CCC.Target.*.Correct` / `.CompileCorrect`, the entire Plan 0.32 flat stack
  (`CompileCorrectFlat`/`FlatSimulation`/`FlatComposition`/`FlatSim`/`ExecCompose`/
  `FlatCorrespondence`/`StepLemmas`), and `DirectSimulation` (x86-32 + riscv64) —
  is an **orphaned island**, reached by **none** of the 162 live modules. It had
  drifted **red** (0.36's `lea-indexed` broke `FlatComposition.headView`; a
  `NatTr`/`Fuse` refactor broke `RecCoreWF`) with no gate catching it, because
  the Makefile's `compiler-x86-64` target still pointed at a renamed-away file
  (`Once/Compile/EndToEnd.agda`, gone in the 0.47/0.48 restructure).

So "retire DirectSimulation" needs **no porting**: the whole legacy island is
dead code relative to the apex. And "bring the other arches to x86-64's level"
means discharging their **Adequacy postulates through `IRObsCorrectFlat`**, not
building a per-arch flat stack.

## The real structure (`Once/Adequacy/ArchCorrectness.agda`)

```
postulate
  x86-32-correct  : ArchCorrect x86-32  (arch-semantics x86-32)   -- whole-record postulate
  riscv64-correct : ArchCorrect riscv64 (arch-semantics riscv64)  -- whole-record postulate

arch-correctness x86-64  = x86-64-correct    -- = x86-flat-from-obs ir-obs-correct  (DISCHARGED via IRObsCorrectFlat)
arch-correctness x86-32  = x86-32-correct     -- postulate
arch-correctness riscv64 = riscv64-correct    -- postulate
```

x86-64's `ArchCorrectness.X86-64` builds `x86-64-correct` from the FS-generic
`IRObsCorrectFlatness {x86v3-frame-semantics}` module via a single **named**
bridge postulate `x86-flat-from-obs` (+ `program-bound`). That is "x86-64's
level": the record is *constructed* from `ir-obs-correct`, with a named,
explicit residual postulate — not a whole-record black box.

## Phase 4 — runtime parity check under QEMU (riscv64 chosen)

Confirm the *emitted* binaries run under user-mode emulation. Findings 2026-07-01:

**Toolchain wiring — SOLVED.** `once build --exe --target riscv64` +
`AS/LD/OBJCOPY = riscv64-unknown-linux-gnu-*` produces a valid **static riscv64
ELF**, and `qemu-riscv64` executes it. (Fixed en route: the 5 `Linux/*.riscv64`
Strata impls used `//` comments that GNU `as` rejects — converted to `#`,
committed `bc922984`.)

**Blocker — the riscv64 runtime backend is incomplete (never executed).**
`exit 42` SIGSEGVs immediately (`si_addr=NULL`, zero syscalls). Root cause:
`Once/Target/RiscV64.agda` is an **83-line stub** emitting only the function
symbol; it lacks the `_start` runtime harness that `Once/Target/X86-64.agda`
(183 lines) emits:
- `.section .bss` + `once_heap_pos` (heap bump-pointer storage);
- `.globl _start` / `_start:` that inits the heap register, calls `once_main`,
  and falls through to `sys_exit(0)`.
So the riscv64 binary has an **undefined `_start`** (entry fell back to
`once_4main`), the heap register and frame pointer `s0` are never initialized,
and main's first `sd a0,0(s0)` writes to null.

**Phase 4a — implement the riscv64 Layer-0 runtime (IN PROGRESS).** Matching
x86-64's frameless `sp`-relative model. Changes:
- `RiscV64/Syntax.agda`: add `lla` (load code-label address) + its
  `instr-consumed-slots` case.
- `RiscV64/Emit.agda`: `lla rd, .L_thunk_n` display.
- `RiscV64/Semantics.agda`: `execInstr … (lla …)` case.
- `RiscV64/AbstractToRiscV.agda`: slot addressing `fp`→`sp` (frameless);
  `instr-load-const fits-int v → li a0, v`; `instr-alloc-heap n → mv a0,s2;
  addi s2,s2,n*8` (s2 = heap bump pointer); `instr-load-code-addr n → lla a0,n`;
  **`instr-call-closure` loads the code ptr into `t1` not `t0`** — `t0` carries
  the Input1/arg pointer the callee reads via `ld a0,8(t0)` and must survive the
  call (mirrors x86-64's non-clobbering `call *0x8(%r12)`).
- `Once/Target/RiscV64.agda`: `_start` runtime stub (`.bss once_heap_base`,
  `.data once_heap_pos`, init `s2`, `call once_main`, `sys_exit` via `ecall`);
  `irToAsm` brackets the trace with `addi sp,sp,∓budget*8`; `irToBodies` emits
  `.L_thunk_<n>` bodies with their own `sp` frame + `ret`.

Three runtime bugs found & fixed (none catchable by the value-level proofs):
1. no `_start`/frame → SIGSEGV at entry (implemented `_start` + frameless).
2. `instr-call-closure` clobbered `t0` (the arg pointer the callee reads via
   `ld a0,8(t0)`) with the code ptr → `exit(<code word>)`; fixed via `t1`.
3. nested closure calls clobbered `ra` (RISC-V keeps the return address in a
   register, not on the stack like x86-64 `call`) → `layer0-terminal`/
   `layer1-swap` looped forever; fixed by saving/restoring `ra` in the frame.

**Result (qemu-riscv64 exit-test suite): 27 passed / 17 failed / 2 skipped**,
up from **0 runnable** (the backend never executed). All Layer 0/1 + the
closure/heap/const/apply machinery works. The 17 failures are cleanly the
stubbed higher-layer ops:
- Layer 2–4 (7): `instr-case-on-tag` / `instr-load-tag-lit` are `unimp` →
  `SIGILL` (132) on sum/case tests.
- Layer 5 cata (10): build-fails — `lea-indexed`/`instr-loop`/`instr-reg-op`/
  `instr-ctrl` stubbed (x86-64 builds 8/10; riscv64 0/10).

**Phase 4c (follow-on, not done): riscv64 Layer 2–5 codegen.** Port the x86-64
sum (`instr-case-on-tag`, `instr-load-tag-lit`) and cata (`lea-indexed`,
`instr-loop`, `instr-reg-op`, `instr-ctrl`) lowering to `AbstractToRiscV`. Each
is its own piece; closes the 27→~42 gap to the x86-64 ceiling (42/44; the 2
`layer5-cata-*-emit` fail on x86-64 too).

**Phase 4b — harness.** `tests/run-exit-tests-riscv64.sh` (added): mirrors
`run-exit-tests.sh` but `--target riscv64`, links `.riscv64` impls, sets
`AS/LD/OBJCOPY` to the `riscv64-unknown-linux-gnu` cross tools, runs each binary
under `qemu-riscv64`, checks exit-code parity.

The proof-side apex is unaffected (value-level); this is target-emission work.

## x86_32 arith-lambda-2 residual — precise diagnosis (2026-07-01)

The single remaining suite failure (`arith-lambda-2` on x86_32: `g x y = x + 2*y`,
`g 4 19` → 110 not 42). Root-caused via gdb under qemu-i386:

- **Not** the arith emitter's per-arch offset, and **not** env construction in
  general: non-arith 2-level curry is correct on x86_32 (`k x y = x` → 4,
  `k x y = y` → 19). Only the **arith block's direct 2-hop env read** is wrong.
- The arith block reads the outer capture `x` via InputPath `[Fst,Snd]` →
  `[[ecx]+4]`. gdb shows `[ecx]=inner` (a stack cell), `[ecx+4]=y=19` ✓, but
  `[inner+4]` is a heap pointer (`0x804a048`), not `x`. The value `x=4` is
  physically at **`inner-8`** on the stack.
- Contrast x86_64 (works): `x=[[rdi]+8]` lands on `x=4`; its `inner` holds `x` at
  `+8`. So on x86_32 the nested arith-env slot for `x` sits ~3 slots the *wrong
  side* of `inner` — a stack-slot layout/direction mismatch specific to the
  2-level arith env hand-off (the closure-apply that sets Input1 for the arith
  SigOp), in `Once/CCC/Target/X86-32/AbstractToX86-32.agda` (lea-slot /
  lea-indexed / restore-input slot arithmetic), NOT the arith emitter.

1-level curried arith (`arith-lambda-1`) and non-arith 2-level both pass, so the
bug is the interaction of ≥2-level currying with a direct-env arith block. Fix
needs iterative re-extraction cycles against that slot arithmetic; deferred as
the lone known x86_32 backend residual (suite is 265/266).

## arith-lambda-2 — RESOLVED (2026-07-02): it was a stack-vs-heap mode leak

The earlier gdb diagnosis (blaming AbstractToX86-32 slot arithmetic / a per-arch
frame bug) was **wrong**. Root cause: `--alloc heap` is threaded through
`elaborate`/`pipeline`, but three sites built closure/entry environments on the
**stack unconditionally**, ignoring heap-mode:

- `Once/Compile.agda` `wrapMainAsEntry` — main-entry apply pair hardcoded `Stack`.
- `Once/Compile.agda` `directCallIR` — every direct-call fn wrapper apply pair `Stack`.
- `Once/CCC/Codegen/IRToTrace.agda` `apply` — the closure-call `(env,arg)` buffer
  built at stack slots (`store-at-slot`/`lea-slot`), not mode-controlled.

A curried application (`g 4`) returns a closure that captures its environment and
ESCAPES; with that env on the stack the capture pointed into a transient stack
cell reused after the frame popped. x86-64/riscv64 survived by luck (the slot
wasn't reused before the read); x86-32's frame reuse clobbered it → wrong result.

Fix: `Stack → Heap` at all three (AllocMode is semantically transparent → apex
re-typechecks green; no per-arch emit change). The `apply` buffer now
heap-allocates (mirrors the `⟨ f , g ⟩ Heap` clause). Hardens x86-64/riscv64 too.
**once-test: 266/266 on x86_64 + x86_32 + riscv64.**

Latent (not reached with `--no-optimize`): `Once/Optimize.agda` `optimize-pair-aux`
still rewrites pairs to `⟨ f , g ⟩ Stack` unconditionally — a mode leak on the
optimized path; fix by threading/keeping the mode when the optimized use escapes.
