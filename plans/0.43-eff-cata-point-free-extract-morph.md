# Plan 0.43 — Eff cata point-free form (the `extract-morph-eff` blocker)

## The problem

The eff cata's **fold runs** today via application:

```once
main = emitAll xs    -- runs the fold; emit fires in fold order; exit 0
```

That is the Plan 0.36 milestone (emit-order, verified at the trace level). What
does **not** work is the *point-free* form (composing the cata with `exit`/a
value so the program has an explicit exit code and is a single morphism):

```once
main = compose exit@S (compose (arr 7) (compose emitAll (arr xs)))
```

This fails with `compose: expected type mismatch`. Plan 0.41's `⊢ᵍ` value-lift
fixed the **value** side (`xs` as an inline `In(inr(3, …))` coerces and extracts
via `lift-morphism`). The remaining blocker is **`emitAll` (the cata morphism)**.

## Root cause (diagnosed 2026-06-09)

The eff `compose` clause requires **both** factors to be *extractable* point-free
morphisms — `extract-morph-eff` handles only `lift-morphism` / `arr'` / `cata`
(inline), and there is **no closure-realm fallback** (that would need eff
*application* `f (g x)`, the open action-composition area). Then:

- **Named `emitAll`** → elaborates to `sigOp "emitAll"`. `extract-morph-eff`
  cannot extract a named ref (no resolver pre-resolve) → fails. (`composeMid`
  *does* recover `B` here, via `domainOfHead`'s lookup — that part is fine.)
- **Inline `cata …`** → `extract-morph-eff` succeeds (it handles `cata`), but now
  `composeMid` **cannot recover the middle type `μF`**: it's functor-dependent,
  and `composeArgB`/`domainOfHead` are structural (can't infer `F` from the
  `cata`/`In`-construction).

So neither shape works: named cata fails extraction; inline cata fails B-recovery.
This is the known open `extract-morph` area (`project_effectful_cata_blocker`,
`effect-composition.md`).

## Candidate approaches (pick after spike)

1. **`extract-morph-eff` resolves named refs.** Teach extraction to look a named
   def up and extract its (already-elaborated) morphism — so `compose emitAll …`
   works with the named cata (whose `B` `composeMid` already recovers). Needs the
   named-def's IR available at extraction time (resolver ordering — the hard
   part; extraction currently runs pre-resolve).

2. **Functor-aware B-recovery for the inline cata.** Extend `composeMid`/
   `domainOfHead` to recover `μF` from an inline `cata alg` (read `F` from the
   algebra's type) and/or from an `In`-construction arm. Then inline `cata …`
   composes (extraction already handles `cata`). Requires (bounded) inference in
   what is currently a structural decision procedure — tension with D045.

3. **A point-free eff-compose that doesn't extract.** Emit the eff `compose` as a
   closure-realm form (`app (app specCompose) f g`) — but the grade-poly
   `specCompose` body is `λf λg λx. f (g x)`, whose eff `f (g x)` is the
   action-composition usage obstacle. Would need that resolved first.

## Notes / constraints

- The **completeness** of the eff `compose` already has a postulate
  (`checkComposeWithB-just-success`) that is **false for named args** (dormant
  because this test is PENDING). Whatever approach is chosen should let that
  postulate be retired (or replaced by an honest one) — it's the same root cause.
- Do **not** weaken `lift-morphism`'s `zeroUsage` (the soundness guard) or the
  D044/D045 structural-`composeArgB` decision without recording why.
- Keep `main = emitAll xs` working (the fold milestone) regardless.

## Acceptance

`layer5-cata-list-emit` (un-PENDed, point-free form) compiles, runs, emits `[3,5]`
in fold order, and exits `7`; the eff-compose completeness is postulate-free (or
its postulate honestly justified).
