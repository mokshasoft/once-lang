# Plan 0.7: Parser Strictness + Relational Module Parser

## Context

Plan 0.6 Phase A (commit `01b447be`) added strict-error mode to the
parser: non-trivial residual tokens after the last parsed decl now
produce `Parse error: unexpected tokens remaining …` instead of a
silent drop. The operational behaviour is correct.

But the property is **not formally proven.** A question came up in
the same session — "shouldn't the completeness proofs have caught
silent drops?" — and the honest answer is no: the existing
completeness proofs are about the *typechecker* (well-typed expression
↔ `inferElab` succeeds), not the *parser*. Silent drops happen
before typechecking runs, and the parser's module-level layer has no
relational specification at all.

At the same time, the *expression*-level parser (`parseExprWF`) is
proven complete relative to a `ParsesExpr` inductive relation (see
`Once.Parser.ExprRelation`). That machinery exists; it just stops at
expressions and doesn't lift to the decl / module level.

This plan closes both gaps:

1. **A lightweight strictness theorem** for `parseStrict`, stating
   that an `inj₂ m` result implies the residual is trivial. Proof is
   almost definitional given `allTrailing`'s shape; stating it
   turns an operational invariant into a CI-enforced proof.

2. **A relational specification for the module parser** — a
   `ParsesDecls toks ds rest` inductive relation paralleling
   `ParsesExpr`, plus soundness/completeness theorems. Lifts the
   "parser is correct by relation" discipline from expressions up
   to the decl / module level.

## Why this matters

The compiler's trust story has two pillars:
* **Typechecker proofs** (plan 0.3 / 0.4): accept-iff-well-typed.
* **Codegen proofs** (plan 0.4.2 and target-specific): eval-equiv
  between source and target.

Connecting them requires **parser proofs** — accept-iff-valid-source.
Without this link, a buggy parser can silently produce an accepted
Module that semantically mismatches the user's source, and nothing
downstream can tell.

## Goals

* `parseStrict` has a formal strictness theorem: any `inj₂ m` result
  comes from a fully-consumed input.
* The module-level parser has a `ParsesDecls` relation and soundness
  (`parseDeclsWF` returns `just … ⇒ ParsesDecls` holds) + completeness
  (`ParsesDecls` holds ⇒ `parseDeclsWF` finds it).
* A single composition theorem joins the expression-level parser
  proofs, the decl-level proofs, and the module-level parser so the
  user can state *"this source parses to this module"* as a single
  proposition.

## Non-goals

* Parser error *recovery* — the strictness theorem says the parser
  commits to either full consumption or an error, not that it offers
  graceful mid-file recovery. Separate concern.
* A concrete-syntax round-trip proof (parser ∘ printer ≡ id). That's
  related work in `Once.Grammar.*` / Task #38 but not in this plan's
  scope.

## Phases

### Phase 1: `parseStrict` strictness theorem (small)

A direct proof that `parseStrict source ≡ inj₂ m` implies all input
tokens were consumed or are trivially trailing. Shape:

```agda
parseStrict-consumes-all : ∀ source m →
  parseStrict source ≡ inj₂ m →
  ∃[ r ] (parseModule (tokenizeString source) ≡ just (m , r)
        × allTrailing r ≡ true)
```

Proof is almost definitional — `parseStrict` case-splits on
`allTrailing r` and only returns `inj₂` when it's `true`. Stating
the theorem makes this dependency first-class.

Estimate: 1 commit, <50 lines. Small closing task for plan 0.6
Phase A, but breaks out into its own phase here because the
next step needs relational infrastructure.

### Phase 2: `ParsesDecl` relation (medium)

An inductive relation `ParsesDecl : List Token → Decl → List Token
→ Set` paralleling `ParsesExpr`. Constructors correspond to
`parseDeclB`'s clauses (import, type, primitive, typeSig, funDef,
opDecl). Proved sound + complete relative to `parseDeclB`:

```agda
parseDeclB-sound : ∀ toks →
  parseDeclB toks ≡ just (d , rest , _) →
  ParsesDecl toks d rest

parseDeclB-complete : ∀ toks d rest →
  ParsesDecl toks d rest →
  ∃[ bnd ] parseDeclB toks ≡ just (d , rest , bnd)
```

The existing expression-level (`parseExprWF` + `ParsesExpr`) and
type-level (`parseTypeWF` + `ParsesType`) relations are the template.
Each clause of `parseDeclB` gets a corresponding `ParsesDecl`
constructor.

Estimate: 1–2 commits. Moderate line count (one constructor per
decl kind + soundness/completeness per clause), but follows the
existing expression-level pattern closely.

### Phase 3: `ParsesDecls` / `ParsesModule` relations (medium)

Lift Phase 2 to the decl list (which `parseDeclsWF` produces) and
the module level (`parseModule`). The decls-list relation is a
standard list-valued parsing relation:

```agda
data ParsesDecls : List Token → List Decl → List Token → Set where
  pd-nil  : ∀ {toks rest} → …skipNewlines leaves no more decls… → ParsesDecls toks [] rest
  pd-cons : ∀ {toks d rest₁ ds rest₂} →
              ParsesDecl toks d rest₁ →
              ParsesDecls rest₁ ds rest₂ →
              ParsesDecls toks (d ∷ ds) rest₂
```

Soundness + completeness by induction, with the well-founded measure
matching `parseDeclsWF`'s termination argument.

Module-level `ParsesModule source m`: tokenise source, apply
`ParsesDecls`, assert residual is trivial.

Estimate: 1 commit. Mostly boilerplate once Phase 2 is in place.

### Phase 4: Strict-parse completeness (small, closing)

Tie everything together:

```agda
parseStrict-complete : ∀ source m →
  ParsesModule source m →
  parseStrict source ≡ inj₂ m
```

And its mirror image (soundness, already implied by Phases 1 + 3
chained). This is the theorem a downstream compilation-correctness
proof wants to *use*: "if the source is grammatically valid, the
strict parser accepts it."

Estimate: 1 commit, short.

## Interaction with other plans

* **Plan 0.6 Phase B** (TVar parsing): changes `Once.Parser.Type`'s
  grammar. The type-level relational parser `ParsesType` needs
  updating to carry `PolyType` with TVar constructors. Partial
  re-proving. Do plan 0.6 Phase B *first*, then this plan, so the
  relational specs are built against the final grammar.

* **Plan 0.4.2 (end-to-end connector)**: this plan's Phase 4
  theorem feeds directly into 0.4.2's composition. The signature
  `parseStrict source ≡ inj₂ m` is what 0.4.2 wants on the "source
  loaded successfully" side of the pipeline.

* **Plan 0.5 (IR extension hygiene)**: orthogonal; no interaction.

## Risk / watch-outs

* **Parser churn during plan 0.6**: if 0.6's strict-error fixes
  evolve past Phase A (e.g. richer error messages, multi-error
  batching), the strictness theorem statement needs updates to
  match. Prefer to stabilise plan 0.6 first.

* **`parseDeclB`'s catch-all pattern**: the current implementation
  uses a variable catch-all at the end to collapse dozens of
  "return nothing" cases (see memory
  `feedback_malonzo_catchall_patterns.md`). The corresponding
  "no ParsesDecl derivation" case in the relational spec may need
  an "absurd cases" helper. The parser-expr layer solved this with
  `parseOpExprWF`-style explicit rejection relations (`PET_X ∷ _`
  → `nothing`). Mirror that pattern for decls.

## Success criteria

* Phase 1: `parseStrict-consumes-all` in
  `Once/Parser/StrictStrictness.agda` (or similar), exports clean.
* Phase 2: `ParsesDecl` + sound/complete lemmas; `parseDeclB`'s
  behaviour is now specified by a relation, not just an
  implementation.
* Phase 3: `ParsesDecls` + `ParsesModule` relations; module-level
  parsing is specified.
* Phase 4: `parseStrict-complete`; closed loop from grammar to
  acceptance. Zero postulates added (goal), existing postulates
  not removed (scope).

## Starting point

The expression-layer templates to follow:
* `Once.Parser.ExprRelation` — `ParsesExpr` inductive relation.
* `Once.Parser.Expr` — `parseExprWF` implementation.
* `Once.Parser.ExprRelation.ParsesExpr-shrinks` — length-decrease
  lemma used by completeness.
* `Once.Grammar.ExprBridge` — relates `parseExpr` and `ParsesExpr`
  at the surface level. Analogous module for decls is what Phase 3
  produces.
