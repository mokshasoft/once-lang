# Plan 0.5: IR Extension Hygiene

## Context

Plan 0.2.4 picked back up on 2026-04-20 and — in the course of adding
the `applyEff` IR constructor to unblock the `effApp` surface
elaboration (replacing the `unsafeCoerce` postulate in
`Once.Surface.Elaborate`, commit `2f83cb61`) — surfaced three
proof-engineering patterns that scale poorly with the number of IR
constructors. The change was principled and structurally simple (one
new constructor, mechanical boilerplate for the downstream walkers),
but ~90% of the line count was repetitive.

This plan captures what to improve so the **next** IR extension is
cheaper. It's not layer-specific — it applies to any addition to
`Once.CCC.IR` (Layer-N operators, new recursion schemes, future
effect primitives).

## Findings from the applyEff change

One new constructor (`applyEff : IR ((Eff A B) * A) B`) touched 14
files. The bulk of the cost was concentrated in three places:

### 1. `≟IRH` decidable-equality enumeration (Once.Optimize)

`≟IRH` enumerates every pair of IR constructors as an explicit clause:
one `yes refl` on the diagonal, `no (cross-no (λ ()) eqA eqB)`
off-diagonal. Currently 23 constructors ⇒ 23 + 23×22 = 529 clauses.
Adding one constructor adds `~2n` lines of pure boilerplate. Scales
`O(n²)` in total, `O(n)` per addition.

### 2. View functions (Once.Optimize: pairView, coprodView, composeFirstView, composeSecondView, fstSndView, inlInrView)

Each view enumerates all constructors and returns either a specific
view (for the cases of interest) or `is-other-*` / `-other` (catch-all).
Six such views today, each ~23 lines. Each new constructor adds one
line to each view = +6 lines per constructor.

### 3. IRResultAWF record-rebuild (Once.CCC.Machine.Dispatcher)

`IRResultAWF m ir x s alloc` is parameterized by the IR term. Delegating
`run-applyEff` to `run-apply` requires re-tagging the index from
`apply` to `applyEff`; Agda has no direct way to do this since record
parameters aren't up to semantic equality. The fix requires either a
field-by-field copy (~30 fields) or a dedicated `apply→applyEff`
conversion lemma. This session took a scoped postulate to defer the
work (commit `2f83cb61`, the `applyEff-placeholder`).

## Scope

In scope:

- **F1. Factor `≟IRH` through `IRHead`.** Replace the 23×23 enumeration
  with a two-phase check: compare `ir-head f ≡ ir-head g` (one-shot,
  using derived decidable equality on `IRHead` which is a simple
  enum); on the diagonal, dispatch via pattern-match on the shared
  tag. Eliminates the 46-lines-per-constructor tax and makes the
  algorithm's cost visible (compare tag, then compare sub-structure)
  instead of hidden in boilerplate.

- **F2. Collapse view-function catch-alls.** Agda accepts catch-all
  variable patterns after specific clauses (used elsewhere in the
  codebase, e.g. parser catch-alls — see memory
  `feedback_malonzo_catchall_patterns.md`). Each view keeps its
  specific clauses, then ends with one catch-all. +1 line per view
  per new constructor → 0 lines per view per new constructor.

- **F3. Add `apply→applyEff` (and `arr→apply-like`) conversion
  lemma** to unblock the Dispatcher postulate from commit `2f83cb61`.
  The lemma takes an `IRResultAWF m (apply {q = Many}) x s alloc` and
  produces `IRResultAWF m (applyEff {A} {B}) x s alloc` by field-
  rebuild. Also re-examine `IRResultAWF`'s parameterization: would
  indexing by `IRHead` (tag) instead of the full IR term, with the
  term recoverable from context, eliminate the whole class of
  "same fields, different index" rebuilds? This may touch the
  ClosureWellFormed module non-trivially — evaluate first.

Out of scope:

- The `Eff` semantic design (whether `effApp f x : B` vs `Eff Unit B`).
  That's a language-design question, tracked separately (possibly as
  a follow-up around the effect composition doc).
- Adding new IR constructors. This plan makes future additions cheaper
  but doesn't introduce any itself.
- Replacing `run-apply`'s implementation. F3 only changes the
  `applyEff` delegation; `run-apply` is unchanged.

## Load-bearing criterion

We only pay to fix these if they're on the critical path. A rough
cost model: current extension tax is ~120 lines of boilerplate per new
constructor (46 `≟IRH` + 6 views + 60 Dispatcher). With 23
constructors today and Layer 0–3 likely to add 5–10 more, that's
600–1200 lines of mechanical noise pending. F1+F2 would reduce this
to ~30 lines per new constructor (semantic cases only).

**Trigger for starting this plan:** a new IR-constructor PR that would
otherwise need the 120-line boilerplate. F1+F2 pay for themselves by
the third such PR.

## Phases

### Phase A: F2 (view-function catch-alls) — **small, quick win**

Estimated: one commit, <50 lines removed.

Replace each view's `| <ctor> = is-other-* ...` enumeration with a
variable catch-all. Verify coverage. This is the cheapest fix and
unblocks the pattern for future additions. Do this first to validate
the approach.

### Phase B: F1 (`≟IRH` via `IRHead`) — **medium, high-leverage**

Estimated: one commit, ~400 lines removed (the 46×n ≟IRH body) and
replaced with a 23-case tag-dispatch (~50 lines) plus a derived
`_≟IRHead_` (~23 lines). Net save: ~330 lines.

Algorithm:

1. Derive `_≟IRHead_ : (h₁ h₂ : IRHead) → Dec (h₁ ≡ h₂)`.
   `IRHead` is a flat enum; this is trivial.
2. Prove an injection lemma: `ir-head f ≡ ir-head g → ∃ eq. f ≡
   subst₂-IR eq g` for matching heads (one clause per head, inductive
   on sub-structure for constructors with arguments).
3. Refactor `≟IRH f g eqA eqB`:
   - Compare `ir-head f` vs `ir-head g`. If differ, use
     `head-mismatch-abs` (already exists).
   - If same, pattern-match on the head and invoke the structural
     compare (existing diagonal clauses).

The ~460 existing cross-case one-liners collapse into a single
`head-mismatch-abs` application.

### Phase C: F3 (Dispatcher conversion / IRResultAWF reparameterization) — **large, discharges postulate**

Estimated: one commit, ~100 lines added (either the conversion
lemma with field copy, or the record reparameterization).

Two sub-options to evaluate first:

- **C1. Field-copy conversion**: write `apply→applyEff-result :
  IRResultAWF m (apply {q = Many}) x s alloc → IRResultAWF m
  (applyEff {A} {B}) x s alloc` explicitly. ~30 field copies, closes
  the postulate. Narrow scope, predictable.

- **C2. Reparameterize IRResultAWF by IRHead**: change the record's
  `ir` parameter to `ir-tag : IRHead` and add a field `ir-witness :
  IR A B` with `ir-head ir-witness ≡ ir-tag`. Delegations become
  trivial when two IR constructors share a head category. Broader
  benefit, higher risk — ClosureWellFormed has extensive machinery
  keyed on `ir`, and the refactor may cascade.

Recommendation: do C1 first (closes the known postulate), evaluate
whether C2 is worth it once we see how many more such conversions
arise as Layer 1–3 add effect-related constructors.

## Success criteria

- F1: removing constructor from `IR` + removing its corresponding
  `IRHead` clause + removing its diagonal `≟IRH` clause should be
  the only changes needed in `Optimize.agda`. Adding a constructor
  is symmetrical: 2 lines instead of 48.
- F2: each view has ≤1 new line per new constructor (the specific
  case, if any).
- F3/C1: `applyEff-placeholder` postulate removed from
  `Once.CCC.Machine.Dispatcher`.
- Regressions: zero. `make compiler` + `make malonzo` continue to
  pass. No new postulates anywhere.
