# Plan 0.14: AtDynamic-mode end-to-end proof for compound values (Layer 0/1/2)

## Scope

Both `Stack` and `Heap` AllocMode tags **stay** in the IR — programs continue to pick Stack vs Heap per allocation site. This plan delivers a **proven `compile-correct` end-to-end path for the `Heap` (= AtDynamic) variants** of Layer 0/1/2 compound IRs. Stack-mode `run-pair`/`run-inl`/`run-inr` and their existing postulates are untouched.

After this plan, a user can write:

- `⟨ f , g ⟩ Heap`, `inl Heap`, `inr Heap` — fully proven end-to-end via the new heap-allocating handlers.
- `⟨ f , g ⟩ Stack`, `inl Stack`, `inr Stack` — still works at the codegen level under their existing postulates; not part of this plan.

## Why this path first

The `layer2` branch has spent most of its time rebuilding stack-allocation infrastructure (Plans 0.13.2 StoredValue, 0.13.3 TraceWF / option U, PairStackWF Stages A/B/C). The structural complexity that keeps Layer 1 and Layer 2 proofs hard isn't allocation per se — it's the **stack gap problem**:

- `pair`'s setup writes `backup-slot` *before* `f`'s trace runs, so memory state at `[backup-slot, f-start)` differs between proof states.
- ValidAtWF carries `BeforeFrontier`, which doesn't prove sub-locations avoid the gap.
- Discharging `validityWF-mem-preserved-in-regions` requires a parallel `LocsInRegions` predicate (see `feedback_agda_typecheck_oom_abstract` and the CWF strong proof).

Heap allocation eliminates the gap. Each compound value gets a **fresh heap-ref**, disjoint from everything else by construction. Sub-locations are at `sucLoc (AtDynamic hl)`, also fresh. No frontier, no reclaim, no gap.

User constraints (2026-05-12):

- *"don't pivot to only heap in the sense that we should remove stack"* — keep both Stack and Heap modes in the IR. The user gets to choose per-allocation what works best. This plan **doesn't deprecate Stack mode** — it just adds a working *proven* Heap-mode path.
- *"it is ok to use the scratch still as long as the proofs are simple."* Stack slots can still hold scratch (Input1 register backups, intermediate values inside a single IR's trace) — only *compound values that flow between IRs* go on heap in the Heap-mode handlers.

## Target scope: Layer 0/1/2 IRs

| IR | Allocates? | Heap-pivot impact |
|---|---|---|
| `id` | No | None — mode-agnostic |
| `_∘_` | No (composes sub-IRs) | None — threads input/output through registers |
| `terminal` | No (Unit erased) | None |
| `initial` | No (Void absurd) | None |
| `arr` | No (identity coercion) | None |
| `fst`, `snd` | No (reads pair) | Pair input is on heap → `load-indirect` reads from `*Input1` (already polymorphic over stack/heap) |
| `⟨f,g⟩` | **Yes** (pair cell) | Allocate 2-cell heap block; store fst-ptr and snd-ptr there |
| `inl`, `inr` | **Yes** (sum cell) | Allocate 2-cell heap block; store tag and payload-ptr there |
| `case` | No (reads sum) | Tag read from heap (`load-tag-from-indirect`?); dispatch on tag |
| `SigOp` | (host) | None — already opaque |
| `free-heap` | No (already heap-aware) | None |

Layer 0 (`id`, `_∘_`): no allocation, untouched.
Layer 1 (`⟨,⟩`, `fst`, `snd`): only `⟨,⟩` allocates — single new instruction needed.
Layer 2 (`inl`, `inr`, `case`): `inl`/`inr` allocate; `case` reads via existing indirect-load.

Out of scope: `curry`/`apply` (Layer 4 closures), recursion schemes (Layer 5/6). Closures already require `Heap` mode by typing (`valid-closure-wf` returns `Heap`); leave them for after Layer 0/1/2 is solid.

## What changes

### 1. New AbstractInstr: `instr-alloc-heap`

```agda
instr-alloc-heap : ℕ → AbstractInstr  -- alloc N heap cells; Output := SV-Ptr (AtDynamic <fresh>)
```

Semantics (in `SMCore.exec-abstract`):

```agda
exec-abstract (instr-alloc-heap n) s alloc =
  let (loc , alloc') = heap-alloc alloc n
  in record s { regs = writeReg (regs s) Output (SV-Ptr loc) }
   , alloc'
```

`heap-alloc` already exists in `Allocation.agda` (lines 81-87); the new instruction just wires it into the abstract semantics.

Already-existing infrastructure that needs no change:
- `readLoc (AtDynamic hl)` — works (line 455 of SMCore)
- `writeLoc (AtDynamic hl) (SV-Ptr (AtDynamic v))` — works (line 503)
- `sucLoc (AtDynamic hl)` — works (line 241)
- `BeforeFrontier alloc (AtDynamic hl)` via `heap-before` — works

### 2. Codegen lowering for `instr-alloc-heap`

Two options:

**(a) Inline sigop call** — `compile-abstract (instr-alloc-heap n) = call alloc; mov rax, output`. Routes through the existing `SigOp` framework (`Dynamic-allocator` in `IR.agda` line 69). Pro: zero abstract-layer change beyond the new instruction; con: requires a `alloc-N` named sigop in `SigOpInfo`.

**(b) Inline bump allocator** — emit a few instructions reading a bump pointer in `.bss` and incrementing it. Pro: no sigop; con: target-specific (need entry per arch).

Recommend **(a)** — sigops are already the mechanism for "external runtime call." Adds one named sigop (`alloc-cells`) with `semM (alloc-cells n) tt = ⟦ A * B ⟧` or similar parameterised by N. Match the existing pattern for `linux.exit`.

### 3. Rewrite Heap-mode run-X handlers

**run-pair Heap mode** (currently shares `run-pair` with Stack via mode param):

```agda
run-pair-heap : ∀ {A B C} (f g : IR ...) ... →
  IRResultAWF Heap ⟨f,g⟩Heap x s alloc

-- trace skeleton:
--   1. mov-to-output Input1            -- save input-loc (so f can use it)
--   2. push input-loc to backup-slot  -- scratch use (stack OK)
--   3. f-trace                          -- f's IR runs; Output := fst-loc
--   4. push Output to fst-stash        -- scratch (stack OK)
--   5. restore-input from backup-slot  -- Input1 := input-loc again
--   6. g-trace                          -- g's IR runs; Output := snd-loc
--   7. push Output to snd-stash        -- scratch (stack OK)
--   8. instr-alloc-heap 2              -- Output := SV-Ptr (AtDynamic <fresh>)
--   9. push Output to pair-stash       -- save pair-loc
--  10. mov-to-input pair-loc           -- Input1 := pair-loc
--  11. restore-input from fst-stash    -- Output := fst-loc
--  12. store-indirect                  -- *pair-loc := fst-loc
--  13. restore-input from snd-stash    -- Output := snd-loc
--  14. store-indirect-suc              -- *(sucLoc pair-loc) := snd-loc
--  15. restore-input from pair-stash   -- Output := pair-loc
```

Or simpler ordering if `instr-alloc-heap` is run first (the pair-loc is then available for the whole sequence).

Critically: the *result* `pair-loc` is `AtDynamic <fresh-heap-ref>`. The validity is `valid-pair-wf` (already mode-agnostic) at that heap-loc. **No `BeforeFrontier alloc` issues with stack-frontier** — heap-before is the only relevant case.

**run-inl / run-inr Heap mode**: same skeleton, smaller:

```agda
--   1. mov-to-output (Input1)             -- save payload-ptr in scratch
--   2. push Output to scratch
--   3. instr-alloc-heap 2                 -- Output := SV-Ptr (AtDynamic <fresh>)
--   4. push Output to sum-stash
--   5. mov-to-input (Output)              -- Input1 := sum-loc
--   6. instr-load-tag-lit t               -- Output := SV-Tag t
--   7. store-indirect                     -- *sum-loc := SV-Tag t
--   8. restore-input from scratch         -- Output := payload-ptr
--   9. store-indirect-suc                 -- *(sucLoc sum-loc) := payload-ptr
--  10. restore-input from sum-stash       -- Output := sum-loc
```

### 4. Proof obligations (and what's simpler)

For each heap-allocating run-X, the validity proof obligations are:

| Obligation | Stack model (current) | Heap model (proposed) |
|---|---|---|
| `readLoc s pair-loc ≡ just (SV-Ptr fst-loc)` | gap-aware, needs `LocsInRegions` to transfer through stack writes elsewhere | trivial: pair-loc is fresh AtDynamic; `store-indirect` to it then `readLoc`-of-write |
| `BeforeFrontier alloc pair-loc` | `stack-before` (k < next-slot) | `heap-before` (ref-id < next-heap-ref) — trivially holds after `heap-alloc` bumps |
| Sub-loc validity (`fst-loc`, `snd-loc`) | transferred through f-trace + middle-trace gap | inherited from f's / g's IRResultAWF directly; heap doesn't interfere |
| `frontier-slot-stable` | nontrivial — depends on stack-write pattern | trivially `inj₂ (inj₂ tt)` (allocation moves heap-frontier, not stack) |
| `mem-preserved-inl loc bf` for input-loc | guaranteed only via `write-at-frontier-preserves-before` chains | heap-write doesn't touch stack at all; `readLoc-stackMem-eq` does the work |

Heap doesn't have a frontier-overwrite problem — every allocation is at a new ref-id, disjoint from anything readable through prior valid pointers.

**Open obligation we still need**: `validityWF-mem-preserved` (the simple version) for heap writes. The mem-eq is "stack memory unchanged" (heap write doesn't touch stackMem) plus "heap memory preserved at all old refs (we only wrote to the freshly-allocated ones)." Both are direct consequences of `heap-alloc`'s definition.

### 5. Scratch (stack slots) still allowed

Inside a single run-X handler's trace, stack slots can be used for:
- Saving `Input1` so it survives sub-IR execution (the existing `backup-slot` pattern).
- Stashing `Output` between operations (sub-IR result before stitching).

These scratch writes are local: they live and die within the run-X's trace, never observed across IRs. Reclaim them by resetting `next-slot` at the end of the run-X (which `instr-reclaim-to` already supports).

This is the "ok to use scratch" point — scratch's BeforeFrontier domain is the slot range strictly within `[old-next-slot, new-next-slot)`, which is FRESH and thus disjoint from any sub-IR's reads. No gap, no preservation worries.

## What's already in place

- `heap-alloc : AllocState → ℕ → ValueLocation × AllocState` (Allocation.agda:83)
- `AtDynamic`, `sucLoc (AtDynamic ...)`, `readLoc`/`writeLoc` for heap (SMCore)
- `store-indirect`, `store-indirect-suc` (heap writes via pointer) (SMCore:859-860)
- `load-indirect`, `load-indirect-suc` (heap reads via pointer)
- `heap-before` BeforeFrontier constructor (Allocation.agda:277-278)
- `valid-pair-wf`, `valid-inl-wf`, `valid-inr-wf` are mode-agnostic — work for AtDynamic locations as-is

## What's new

- `instr-alloc-heap : ℕ → AbstractInstr` (SMCore)
- `exec-abstract` clause for it (SMCore)
- Sigop or arch lowering for it (per-arch CompileCorrect or Simulation)
- `run-pair` Heap mode rewritten to allocate on heap (PairStackWF — likely a *replacement* of the unified `run-pair`, with a separate Stack-mode handler kept only if needed)
- `run-inl` / `run-inr` Heap mode rewritten (SumRecWF)
- `ir-to-trace'` clauses for `⟨f,g⟩ Heap`, `inl Heap`, `inr Heap` emit the new trace shape (Stack-mode clauses untouched)
- `ir-to-trace-correct-pair` / `-inl` / `-inr` / `-case` discharged **for the Heap-mode variants only**. The current catchall postulate `ir-to-trace-correct-non-layer0` is replaced with mode-aware dispatch: Heap mode → proven, Stack mode → still postulated.

## What is *not* dropped

(Reflecting the user's "keep both modes" constraint.)

- The Stack-mode `run-pair` / `run-inl` / `run-inr` handlers in `PairStackWF.agda` / `SumRecWF.agda` remain. Their existing postulates (`validityWF-mem-preserved-in-regions`, `LocsInRegions`, `inl-inr-trace-state-correct`, etc.) are untouched.
- The CWF infrastructure committed in `a88712ae` (`LocInRegions`, `LocsInRegions`, `validityWF-mem-preserved-in-regions-strong`) stays — it serves the Stack-mode path and Layer 4 closures.
- PairStackWF Stages A/B/C (commits `0b245e63` / `ca22cd43` / `57411355`) stay — they're Stack-mode infrastructure that will eventually get used if a user picks Stack mode.

## What's *new and proven* (heap path only)

- `run-pair` Heap mode body: simpler proof, no `LocsInRegions` reliance.
- `run-inl` / `run-inr` Heap mode bodies: simpler proof, no gap dispatch.
- Heap-mode arms of `ir-to-trace'` and `ir-to-trace-correct`.

## Migration plan

**Phase A — instruction + semantics** (~1 session)

1. Add `instr-alloc-heap` to AbstractInstr.
2. Add exec-abstract clause.
3. Add `instr-alloc-heap` no-write/no-stack-read predicates (it's a heap-only op).
4. Verify SMPrimitives still typechecks.

**Phase B — pair on heap** (~1-2 sessions)

1. Replace `run-pair`'s Heap mode body with heap-alloc-based trace.
2. Update `ir-to-trace'` for `⟨ f , g ⟩ Heap` to emit the matching trace.
3. Prove `ir-to-trace-correct-pair` (Heap mode). Discharge `LocsInRegions` reliance via heap-disjointness.
4. Layer 1 with `⟨ f , g ⟩ Heap` is then end-to-end verified.

**Phase C — sums on heap** (~1-2 sessions)

1. Replace `run-inl` / `run-inr` Heap mode bodies with heap-alloc + tag-write traces.
2. Update `ir-to-trace'` for `inl Heap` / `inr Heap`.
3. Discharge `ir-to-trace-correct-inl` / `-inr`.
4. `case` doesn't allocate — its codegen already reads the tag via `load-indirect`; verify the proof for `ir-to-trace-correct-case` follows from the inl/inr witnesses + existing dispatch infrastructure.

**Phase D — leave Stack mode alone**

Explicit non-goal: this plan does not touch Stack-mode handlers or Stack-mode IR clauses. They keep working under their current postulates. A future plan can return to Stack mode (or its closure / recursion-scheme cousins) once the Heap path is shipped and the actual ergonomics of mixed Stack/Heap programs are clear.

## Risks

- **Heap pool exhaustion**: at the abstract level, `next-heap-ref` is unbounded. At runtime, the heap-alloc sigop could fail. Soundness story: the abstract model assumes infinite heap; runtime exhaustion lives in the sigop's halt path. Same trust point as `linux.exit`.
- **Sigop framework dependency**: if Phase A goes the sigop route, the `alloc-cells` semantics need to be defined; this connects to Plan 0.11 trusted-base.
- **Codegen for `instr-alloc-heap`**: per-arch — x86-64 calls a runtime allocator (could be `malloc` or a stack-grown bump pool). RISC-V and X86-32 need parallel work.
- **Closures (Layer 4) and recursion schemes (Layer 5/6) still use stack**: their proof debt isn't paid by this plan. They'd need a similar pivot or a separate model.

## Success criteria

- `ir-to-trace-correct` discharged for `⟨,⟩ Heap`, `inl Heap`, `inr Heap`, and `case` — i.e., **for IR programs whose compound allocations all use Heap mode**, the catchall `ir-to-trace-correct-non-layer0` no longer applies.
- `compile-correct` works end-to-end on a Layer-0/1/2 example program that uses `⟨_,_⟩ Heap` / `inl Heap` / `inr Heap` throughout.
- Stack-mode programs still build (Stack mode is unchanged); their proofs still go through the existing postulates as before.
- The net postulate count does **not** decrease at this stage — Stack-mode handlers keep their postulates, and the new Heap handlers replace zero postulates (since Heap mode was previously covered by the same catchall). The win is *paths*, not *counts*: a sound end-to-end path exists for Heap-allocated L0/1/2 programs.
