# Compose runtime bug: investigation handoff

## State
- HEAD: `0fe77380` (Plan 0.2.4.5 D1: thread slot frontier into curry's body, frameless thunks)
- `exit (id 42)` ✅ exits 42
- `exit ((id . id) 42)` ❌ segfault
- `exit ((id . id . id) 42)` ❌ segfault

## Crash
RIP = `0x2a` = **42**. The integer constant is being called as a code pointer.

Backtrace at crash (from layer0_id_id):
```
0x000000000000002a in ??         ← jumped to address 42
0x000000000040130c in once_main  ← outer apply's call site
0x00000000004011fa in once_main
0x0000000000401083 in once_main
0x000000000040101d in _start
```

At 4013d5 `call *0x8(%r12)`:
- `r12 = stack-slot-address`
- `*(r12+8) = 42` (the integer literal stored at adjacent slot)

The closure record at `r12` has env at `[0]` and "code" at `[8]`. The "code" field has 42 instead of a thunk address.

## Hypothesized cause
Surface elaborator emits double-apply chains for `exit ((id . id) 42)`:
```
apply ∘ ⟨ exit , apply ∘ ⟨ (id . id) , 42 ⟩ ⟩
```

The inner apply returns 42 (the int). The outer apply's pair-trace stores this as snd. Then OUTER apply tries to dispatch using slot[1] (fst, should be exit closure ptr), and somewhere a slot is written that should hold the code-ptr but gets the int 42 instead.

Specifically, look at IR-to-trace for compose `apply ∘ ⟨ exit , inner ⟩`:
- pair-trace: backup, f-trace (exit), store-at-slot 1, restore, g-trace (inner apply), store-at-slot 2, lea-slot 1
- g-trace's last instruction puts inner-result (42) in rax
- store-at-slot 2 stores rax=42 into slot 2 (snd of outer pair)
- lea-slot 1 puts &slot 1 into rax

So slot 1 SHOULD be exit's closure pointer (from f-trace), slot 2 SHOULD be 42 (from g-trace).

The outer apply then:
- load *(rdi+8) → arg = slot 2 = 42 ✓
- load *(rdi) → closure-ptr = slot 1 = exit's closure ✓ (if f-trace was exit)
- *(closure+0) = env, *(closure+8) = code

If exit is a curry-built closure, [0]=env, [8]=L_thunk for exit body. Should work.

## Where the divergence happens
Slot 1 isn't getting exit's closure. Trace through which thunk-store actually writes slot 1.

The hand-decoded `0x2a = 42` strongly suggests it's the const 42 from somewhere. Probably a slot reuse: slot 1 was used by an inner construction that wrote 42 there, then never properly overwritten with exit's closure ptr.

The slot-frontier threading I added should have prevented this, but:
- For OUTERMOST `apply ∘ ⟨ exit, inner ⟩` at frontier 0: slot 1 = fst slot.
- exit's f-trace runs at frontier 3 (= n+3 from pair). exit elaborates to a curry that builds a closure at slots 3-4. Last instr: lea-slot 3 → rax = &slot 3.
- store-at-slot 1: slot 1 := &slot 3 (a closure pointer pointing into the same frame).
- Then restore-input 0.
- Then inner = apply ∘ ⟨ (id . id), 42 ⟩ at frontier... let me check.

Wait, (id . id) elaborates to the specCompose lambda chain → curry+curry. These curries are at frontiers 5, 7. Their bodies need slots starting at 7, 9 (with my threading fix).

But (id . id)'s IR ends with returning a closure pointer (from the outermost specCompose curry). Then 42 is fed as arg to inner apply.

Actually wait — looking at `(id . id) 42` IR: it's a function-application. Surface: `app (id . id) 42`. (id . id) is the head. CCC IR:
- `app (id . id) 42` → `apply ∘ ⟨ id . id , const 42 ⟩` (per Surface.elaborate `app`)
- where `(id . id)` is itself a Surface app: `app specCompose id . id` → `apply ∘ ⟨ apply ∘ ⟨ specCompose , id ⟩ , id ⟩`

So `(id . id) 42` = `apply ∘ ⟨ apply ∘ ⟨ apply ∘ ⟨ specCompose , id ⟩ , id ⟩ , const 42 ⟩`. Triple apply chain.

This gives lots of intermediate closures. Slot conflicts likely.
