# Plan 0.81 — Put name resolution under specification

## The claim

`src ⊢R tp` should mean *"the text parses, by the grammar, to a module that
resolves, by the resolution rule, to `tp`"* — and `tp` should be the RESOLVED
module. Today it means "the text parses to `tp`", with `tp` un-resolved.

That single change puts the resolver's actual behaviour under the correctness
criterion for the first time, and deletes the ~4.5k-line machinery that exists
only to carry typing derivations back and forth across resolution.

## Why now: plan 0.50 is blocked on it

D136 made a bare `fst` mean the generator, so the resolver maps `RVar "fst" ↦
RResolved (gen "fst")` and stage A deleted every bare-`RVar` generator rule.
Consequences, both already visible on `plan-0.76-context-indexed-composition`:

  1. `resolver-reflects-typing` is **false**. Its var case rebuilds
     `⊢ᵢ RVar x` from `⊢ᵢ RResolved (canonical [x])`; the generator arm would
     need `⊢ᵢ RResolved (gen "fst") → ⊢ᵢ RVar "fst"`, and no such rule exists
     BY CONSTRUCTION. Unlike preservation, no side condition on the source
     rescues it — the source genuinely writes `fst`.
  2. `ModuleTyped mU` over the UN-resolved module is now underivable for any
     program that names a generator. So today's criterion is already **silent
     about essentially every real Once program**: completeness's antecedent is
     unsatisfiable for them and soundness cannot build the `tp` it must return.

So this is not a tightening we could postpone — the current shape has gone
vacuous where it matters, and (1) has no repair inside the current shape.

## Reconciliation with the 2026-06-26 decision (IMPORTANT — read before objecting)

`0.51-resolver-into-verified-apex.md` closed with an explicit directive:

> **Route `moduleToIR` through `resolveImports`, and KEEP `ModuleTyped` over the
> UN-RESOLVED source.** … (If `ModuleTyped` is instead moved to the RESOLVED
> form, it goes vacuous again — so DON'T.)

**That warning was correct, and this plan does not contradict it.** Moving
`Typed` to `mR` *while leaving `⊢R` parse-only* makes `src ⊢R tp` read
`ParsesText text mR` — which is false for every `tp`, because the text parses to
`mU`, not `mR`. Genuinely vacuous, exactly as the note says.

The note's implicit assumption is that typing-transport is the ONLY way to keep
the resolver inside the theorem. This plan breaks that assumption: the resolver
is instead pinned by an INDEPENDENT resolution relation in `⊢R`. The old
directive rules out "move `Typed`"; it does not rule out "move `Typed` AND
extend `⊢R`", which is what follows.

## What today's criterion actually constrains about the resolver

Three obligations (`Once.Adequacy.ResolverBridge`):
`resolver-preserves-typing`, `resolver-reflects-typing`,
`resolver-preserves-trace`. All three say only *"something survives resolution"*
— typing, typing backwards, traces. **A resolver that resolved `foo` to the
wrong module, while keeping the program well-typed and behaviour-preserving,
satisfies all three.** The name → `CanonicalName` map itself is unconstrained.

`Resolves` constrains it.

## The change

```agda
-- Once/Adequacy/Compile.agda
Typed : Set
Typed = Σ[ mR ∈ P.Module ] Σ[ mt ∈ ModuleTyped mR ] MC.HasValidMain-decl mR mt

_⊢R_ : Source → Typed → Set
src ⊢R (mR , _ , _) =
  Σ[ mU ∈ P.Module ] (FB.ParsesText (Source.srcText src) mU × RB.Resolves mU mR)
```

`⟦_⟧ˢ` and `Admissible` follow `Typed` onto `mR`.

### `Resolves` — the new spec module

An INDEPENDENT declarative relation: the three arms of `canonVar` as inference
rules over the AST, with the scope set explicit, lifted structurally to decls
and modules.

```
    x ∈ binders                    ⊢ RVar x        ↝ RVar x
    x ∉ binders, GenWord x         ⊢ RVar x        ↝ RResolved (gen x)
    x ∉ binders, ¬ GenWord x, …    ⊢ RVar x        ↝ RResolved (canonical …)
```

**It must be WRITTEN INDEPENDENTLY**, as rules, the way `ParsesModule` is
written against the grammar rather than read off the parser. Transliterating
`canonExpr` makes it independent in name only and turns the bridges into
tautologies. This is the one place this plan can go wrong quietly.

Two bridges replace the three ResolverBridge obligations:

```agda
resolves-sound    : Resolves mU mR → resolveImports mm mU ≡ inj₂ mR
resolves-complete : resolveImports mm mU ≡ inj₂ mR → Resolves mU mR
```

Both are structural inductions over a TOTAL, DETERMINISTIC function — far more
tractable than transporting derivations. An import-shaped residual may reappear
inside them, but as "a function matches a relation", not "derivations
transport".

## Steps

0. **Tighten the `Once/Spec/**` re-exports FIRST.** `Spec/Correct.agda` and
   `Spec/Typing.agda` use `open import … public`, so the trust boundary is
   whatever happens to be in those modules — it widens silently when anyone
   adds a definition. The audited transitive re-export closure is **16
   modules**. Replace each blanket `public` with an explicit `using (…)` so the
   boundary is a decision and shows up in review when it changes. Do this
   BEFORE adding `Resolves`: adding to an implicit boundary is how boundaries
   rot. (`formal/scripts/spec-closure.py` regenerates the closure.)

1. **Write `Once.Spec.Resolution`** — the `Resolves` relation, as rules. Spec,
   trusted-by-reading, ~40–60 lines.

2. **Prove `resolves-sound` / `resolves-complete`** against `resolveImports` in
   a new `Once.Adequacy.ResolveBridge`. Import-free fragment first; the import
   case may stay a named residual, as today.

3. **Flip `Typed` / `_⊢R_` / `⟦_⟧ˢ` / `Admissible` onto `mR`** in
   `Once/Adequacy/Compile.agda`, and re-prove `correctR-sound` /
   `correctR-complete`. Both get SHORTER:
   * soundness: `accept-sound` already yields `ModuleTyped mR`; `⊢R` comes from
     `srcToModule-inv` + `resolves-complete`. No reflection.
   * completeness: `parseStrict-complete`, then `resolves-sound`, then
     `moduleToIR-complete mR`. No preservation.
   * `resolver-preserves-trace` and `admissible-{un,}resolve` disappear —
     meaning and admissibility are already over `mR`.

4. **Delete** the canon/resolver family (inventory below) and `ResolverBridge`.

5. **Unblock plan 0.50**: with reflection gone, the resolver flip finishes.
   0.50's own remaining steps (stage C `named-morph-strong`, stage D dead-path
   deletion, `@this` in the parser, the gate) resume unchanged.

6. **Gate** (MERGE.md): the Spec CHANGED, so the gate runs against the new
   statement — re-read `Once/Spec/**` as a whole, re-extract MAlonzo,
   `cabal build`/`test`, exit tests ×3.

  * `resolver-reflects-typing-imports` (CanonReflectModule)
  * `resolved-main-agrees` (ResolverTrace)

`inferType-transport` (CanonAllFuns / CanonReflectAllFuns),

`DohOK`, `head-unclaimed*`, `cabOK-*`, `dohOK-of`, `classify-canon`'s and
`composeArgB-canon`'s premises.

## Rejected alternative

Keep `⊢R` parse-only and let `Typed` carry both modules plus
`canonModule mU ≡ mR`. Cheaper, deletes the same machinery — but it puts the
EXECUTABLE resolver into the specification, so "correct" degenerates to "agrees
with `canonExpr`" and no resolver bug can fail the criterion. That is strictly
weaker than the status quo, which at least requires typing to survive. It is
the defect D134 removed one level down, re-introduced one level up.
