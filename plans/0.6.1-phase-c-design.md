# Plan 0.6.1: Phase C Design — What does `swap = pair snd fst` mean?

## Context

Plan 0.6 Phase B (landed in commit `3dca8aad`) revived `PolyType` at
the parser/signature boundary so user-declared polymorphic signatures
like `swap : a * b → b * a` survive parsing. Currently Phase B
**rejects** such signatures at `extractFunctions` with a targeted
error pointing to Phase C:

```
Type signature for `swap` contains type variables (not yet supported):
((a * b) ω→ (b * a)) — plan 0.6 Phase C will add bidirectional
specialization for user-polymorphic signatures
```

Before writing code for Phase C, we need to settle what user
polymorphism actually means in Once.

## Re-reading D007

**D007 (2025-12-08)** — *Structural Type Matching for Signatures*:

> *"The expression alone determines the type. The signature is the
> programmer saying 'I believe this has type X' and the compiler
> verifying that belief."*
>
> *"`foo : Unit -> Unit` with `foo = id` is rejected (signature doesn't
> match `A -> A`)."*

**What D007 prohibits**: signature-guided *specialization*. A signature
can't tighten an expression's inferred schema into something stricter.
`foo : Unit → Unit; foo = id` is rejected because `id`'s schema is
`A → A` and `Unit → Unit` is strictly more specific than the schema —
the signature is trying to force an instantiation on the definition.

**What D007 does not prohibit**: polymorphic schemas on user
expressions. The whole IR is built on natural transformations — `id`,
`fst`, `snd`, `pair`, `compose` — each with a polymorphic schema. A
user expression combining these inherits a polymorphic schema
naturally. `pair snd fst` has schema `(A × B) → (B × A)` by
composition, not by fiat.

**The correct reading of `swap : a * b → b * a; swap = pair snd fst`**:
the signature states the expression's *natural* schema, not a tighter
one. The expression determines the type (D007); the signature verifies
the stated schema matches it. This is D007-compatible.

## D021

**D021 (2025-12-10)** names a stdlib `Canonical.once` with entries
like `swap`, `diagonal`, `bimap`, `first`, `second` — polymorphic
morphisms derived from universal properties. The intent is user-level
polymorphic combinators.

With the corrected reading of D007, there is no tension between D007
and D021: D021's entries are polymorphic schemas expressed via NT
combinators, exactly what D007 allows.

## The question that is actually open

User polymorphism is legitimate. The open question is purely one of
**implementation**:

### Position P-schema — First-class polymorphic definitions

User polymorphic defs carry their schema through the pipeline as
`PolyType`. At each call site, the bidirectional typechecker
instantiates the schema against the expected type — the same
mechanism that handles every builtin today via per-builtin `spec*`
helpers.

- `FunInfo` is extended (or a sibling record is introduced) so
  `funType` may be a `PolyType` instead of a `Type`.
- `extractFunctions` no longer forces projection to ground at the
  definition site for polymorphic sigs — it keeps the `PolyType`.
- The typechecker gains a generic specialization path: given a
  polymorphic `FunInfo` and an expected ground `Type`, unify the
  schema's TVars against the expected shape and produce a ground
  instantiation. This is structural matching, not HM: no
  meta-variables, no constraints across expressions, just per-call
  schema-to-expected unification.
- Instantiation is local to the call site. No cross-expression
  inference. D007 preserved: the expression (at the call site) still
  determines the type, and instantiation flows *from* the expected
  type into the schema, not into the expression.

**Pros**: user polymorphic functions are compiled once, reused. No
body duplication. The mental model matches builtins — polymorphic
schemas instantiated at use. Canonical.once becomes a proper library.

**Cons**: implementation is heavier than P2 — the typechecker needs
a generic schema-instantiation pass, and IR codegen needs to know
what ground instantiation to emit for each call site.

### Position P2 — Macro extension

User polymorphic defs are accepted but implemented by substituting
the raw body at each call site. The inlined body then gets typed
in context as any expression would.

- `extractFunctions` produces functions *and* a macro table
  (`List (String × RawExpr)`) for names with polymorphic sigs.
- `inlineAll` substitutes macro bodies into call sites.
- Typechecker unchanged — it sees the inlined expression and types
  it at the use site's expected type via existing mechanisms.
- Polymorphic signatures are documentation-only; the compiler does
  no direct verification they describe the macro's schema (any
  mismatch would surface as a use-site type error).

**Pros**: minimal new machinery. Canonical.once works.

**Cons**: body duplication at each call site (inlining anyway,
but conceptually different). Signatures on poly names are
decorative — weaker story than builtins which have explicit
specialization logic. Larger IR.

### Position P1 — Strict rejection (deprecated)

Reject all user polymorphism. Rewrite Canonical.once at concrete
types per use. **No longer on the table** now that the D007/D021
reading is clarified — there is no semantic reason to reject
polymorphic user defs.

## Recommendation

**P-schema**.

Reasons:

1. **Categorical foundation**: Once is built on natural
   transformations, which are polymorphic by nature. User combinators
   built from NTs inherit polymorphic schemas. First-class handling of
   those schemas is the semantically honest implementation.

2. **Symmetry with builtins**: every builtin already has a polymorphic
   schema and per-call instantiation. User polymorphic defs should
   work the same way. P2's asymmetry (builtins specialized, user defs
   inlined) is a smell.

3. **D007-compatible**: instantiation at a call site flows from the
   expected type into the schema. The expression still determines the
   type. The signature doesn't *change* what the expression is; it
   states the schema that the expression has naturally.

4. **Canonical.once as a real library**: entries compile once, link
   against use sites via instantiation. Not repeatedly inlined.

5. **No HM, no meta-variables**: P-schema is structural unification at
   each call site — same shape as existing `spec*` helpers, just
   generalized to user-declared schemas. Local, decidable, no
   cross-expression constraints.

## Implementation path (P-schema, delegated specialization)

A key observation during C.1 implementation: a dedicated
schema-instantiation primitive (a-priori option (i) below) is not
actually needed, because specialization can be delegated to the
existing per-builtin `spec*` family.

- **(i) Direct:** carry `PolyType` through the typechecker's context;
  add `instantiate : PolyType → Type → Maybe Subst` and `applySubst`;
  at each call site, instantiate the schema and emit a specialized IR
  node referencing the user def.
- **(ii) Delegated (adopted):** inline the user's polymorphic body at
  each call site *before* typechecking. The inlined body is a
  composition of NT combinators (builtins) plus, recursively, other
  user poly names. Each constituent builtin gets specialized at the
  call site's expected type via the existing AppHeadView classifier
  and `spec*` helpers. No new machinery.

(ii) is what the code actually does. (i) would duplicate
specialization logic.

### C.0 — Data-shape split (landed `a582aa0f`)

- New `PolyFunInfo` record beside `FunInfo`.
- `extractFunctions : ... → String ⊎ (List FunInfo × List PolyFunInfo)`.
- Ground and polymorphic defs flow in separate lists; primitives stay
  ground-only.
- `Parsed` stage surfaces both lists; `Check`/`Build` stages temporarily
  errored on non-empty poly lists with a pending-message pointing at
  C.1.

### C.1 — Pipeline inlining with poly seed (in flight)

- `inlineAllWithPoly : ℕ → List FunInfo → List PolyFunInfo → List FunInfo`
  in `Once.Parser`. Seeds the substitution table with every polymorphic
  body up-front; scans ground functions in source order as before.
- `Once.Compile.compileModule` / `compileResolvedModule` / `compile` /
  `compileFromModule` now pre-inline ground bodies via
  `inlineAllWithPoly inlineFuel funs polys` before `compileAllFuns`.
- `requireNoPoly` helper removed. Unused poly defs pass through
  silently; used ones expand at the call site.

After C.1: a call site `swap (1, 2)` becomes `(pair snd fst) (1, 2)`
which the existing typechecker evaluates at the expected type. This
hits the applied-form classifier on `pair` — still missing, the
subject of C.2.

### C.2 — Applied-pair desugaring via universal property

Pivot from the originally-sketched classifier-extension approach to
**surface-level RawExpr desugaring**, motivated by the proof-weight
savings:

- `pair f g  ↦  λ x → (f x, g x)` — the universal property of the
  categorical pair morphism, which is *literally* the body that
  `specPair` emits at the classifier route.
- Rewrite fires on every `RApp (RApp (RVar "pair") _) _` in
  `Once.Parser.Inline.expandPairs`, invoked immediately after
  `inlineReferences` in `inlineAllWithPoly`.
- The fresh bound variable `$pair_x` uses `$` (illegal in user
  identifier syntax — see `Once.Parser.Lexer.isIdentContinue`) so
  capture with user code is impossible by construction.
- No new `AppHeadView` constructor, no `t-pair-app` judgment, no
  Soundness / Completeness / ErrorProofs delta. The existing RLam +
  RPair + RApp paths handle the desugared form.
- The optimizer's beta/eta laws fuse the lambda + pair + app shape
  back into `IR.pair` post-typecheck, so runtime output matches the
  classifier route.

Trade-off accepted: the desugared body flows through the typechecker
as a lambda rather than as a direct `IR.pair` node, which slightly
enlarges the intermediate SExpr. Post-optimization this is invisible.
No proof churn in exchange.

### C.3 — Applied-form classifier for `compose` (3-arg)

Same pattern as C.2 but for `compose : (B ⇒ C) ⇒ (A ⇒ B) ⇒ (A ⇒ C)`.
Expected type `A ⇒ C` drives extraction of `A`, `C`; intermediate `B`
is inferred from the second argument.

### C.4 — Applied-form classifier for `curry` (2-arg)

For `curry : (A * B ⇒ C) ⇒ A ⇒ B ⇒ C`. Drives specialization from the
final result type.

### C.5 — Applied-form classifier for `apply` and `arr` (1-arg each)

Both are simple arity-1 builtins following the existing `ahv-fst` /
`ahv-snd` pattern. `apply : (A ⇒ B) * A ⇒ B`, `arr : (A ⇒ B) ⇒ Eff A B`.

### C.6 — Exercise `Canonical.once`

Make `swap`, `diagonal`, `bimap`, `first`, `second` end-to-end
usable. At least one call site per entry in a test fixture. This
confirms the full P-schema path works without any per-user-def
specialization logic — the existing builtin `spec*` family handles it
through inlining.

## Scope and non-goals

- **In**: local schema instantiation at call sites for user defs.
- **Out**: Hindley-Milner, meta-variables, constraint solving across
  expressions, let-generalization with inference (users write the
  schema explicitly).
- **Out**: ad-hoc polymorphism, type classes (separate feature).
- **Out**: revisiting builtin specialization paths — P-schema
  generalizes them but we don't need to unify the implementations in
  Phase C.

## Decision needed

Confirmation on **P-schema** vs P2.

If P-schema: proceed with C.0 (FunInfo carries PolyType, projectSig
becomes validator).

If P2: revert to the macro-table approach in the previous draft of
this doc.
