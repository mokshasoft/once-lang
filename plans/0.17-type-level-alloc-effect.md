# Plan 0.17 — Type-level Alloc Effect in IRResultBase

## Once Compiler Formal Verification

**Status:** Open — depends on Plan 0.16. Recommended before Plan 0.16's Pattern 1.

**Date:** 2026-05-20

---

## Motivation

Plan 0.16's Pattern 1 (drop `instr-alloc-stack` from producers) POC'd
on `CurryWF` today and failed Gate 1: dropping the instruction creates
a contradiction between `alloc-correct` and `BeforeFrontier` unless we
relax one of them.

Investigating the contradiction surfaced the actual root cause: **the
alloc effect of each IR producer (its delta on `next-slot` and
`next-heap-ref`) is a convention baked into each producer, not a
type-level contract.**

Empirical evidence of the resulting drift:

| Producer | Result location | Has `instr-alloc-stack` in trace? | Has `trace-is-ir-to-trace` SMP.!!? |
|---|---|---|---|
| `CurryHeapWF` | Heap (`AtDynamic`) | No | No |
| `PairHeapWF`  | Heap (`AtDynamic`) | **Yes**       | **Yes** |
| `SumInlHeapWF`| Heap (`AtDynamic`) | No | No |
| `SumInrHeapWF`| Heap (`AtDynamic`) | No | No |

Both `CurryHeapWF` and `PairHeapWF` are heap-result producers — their
result `BeforeFrontier` reduces to `next-heap-ref` comparisons. Neither
**needs** to bump `next-slot` in its alloc-final. Yet they were written
in opposite styles. The inconsistency is invisible to Agda.

## Goal

Make the alloc effect a **first-class typed contract** of every
`IRResultBase`. Each producer declares its `next-slot` delta and
`next-heap-ref` delta; `final-alloc` is derived from `alloc + bumps`,
not a free field. Any inconsistency between the declared bumps, the
trace, and the result-place's `BeforeFrontier` becomes a type error.

## Design (Option B from the 2026-05-20 discussion)

### Core change — `ClosureWellFormed.agda`

```agda
-- Before
record IRResultBase (m : AllocMode) {A B : Type} (ir : IR A B) ... where
  field
    final-state : LocState FS
    final-alloc : AllocState {FS}                              -- free field
    trace       : AbstractTrace
    alloc-correct : proj₂ (exec-trace trace s alloc) ≡ final-alloc
    ...

-- After
record IRResultBase (m : AllocMode) {A B : Type} (ir : IR A B) ... where
  field
    final-state : LocState FS
    trace       : AbstractTrace
    -- Declared alloc effect: producer's contract with the caller.
    next-slot-bump     : ℕ
    next-heap-ref-bump : ℕ
    -- `final-alloc` is derived (see `final-alloc` projection below).
    -- alloc-correct's RHS uses the derived value.
    alloc-correct :
      proj₂ (exec-trace trace s alloc) ≡
      record alloc { next-slot     = next-slot alloc +ℕ next-slot-bump
                   ; next-heap-ref = next-heap-ref alloc +ℕ next-heap-ref-bump }
    ...

-- Derived projection for backward-compat with consumers:
final-alloc : IRResultBase m ir x s alloc → AllocState {FS}
final-alloc {alloc = alloc} r =
  record alloc
    { next-slot     = next-slot alloc +ℕ IRResultBase.next-slot-bump r
    ; next-heap-ref = next-heap-ref alloc +ℕ IRResultBase.next-heap-ref-bump r }
```

`current-frame` is omitted from the bump because every instruction
preserves it (already proved by `exec-abstract-preserves-frame`).

### What this enforces

- **Heap-result producers** (CurryHeap, PairHeap, SumInl/InrHeap)
  declare `next-slot-bump = 0`. If their trace contains
  `instr-alloc-stack n`, `alloc-correct` can't hold — Agda rejects.
  Pattern 1's trace-is-ir-to-trace SMP.!!s for heap producers vanish
  as a side effect.

- **Stack-result producers** (CurryWF Stack, SumRecWF run-inl Stack,
  ...) declare `next-slot-bump = N` matching their stack scratch.
  Their trace MUST include the matching `instr-alloc-stack n` (or
  equivalent next-slot-bumping instructions). Inconsistency caught.

- **Compositional producers** (ComposeWF) declare bumps as the SUM of
  sub-IR bumps. Algebraic composition. Today's exec-trace state
  threading in `alloc-correct-compose` collapses to bump-additivity.

- **Dispatching producers** (ApplyWF, SumRecWF case dispatch) declare
  bumps inherited from the dispatched sub-IR. Type-checks that the
  inheritance is faithful.

### `BeforeFrontier` interaction

For a heap-mode result `loc = AtDynamic (heap-loc hr 0)`:
`BeforeFrontier (final-alloc-of alloc bumps) loc` reduces to
`hr < next-heap-ref alloc +ℕ next-heap-ref-bump`. If `bumps.next-heap-ref-bump = N > 0`
and `hr = next-heap-ref alloc`, this is `≤-refl`. Mechanical.

For a stack-mode result `loc = AtStack frame k`:
`BeforeFrontier (final-alloc-of alloc bumps) loc` reduces to
`k < next-slot alloc +ℕ next-slot-bump`. Same shape.

The discipline ("heap-result doesn't bump next-slot; stack-result
doesn't bump next-heap-ref") becomes self-evident from the types.

## Refactor Steps

### Phase 1 — Foundation (single commit)

1. Add `AllocBump : Set` (or just two `ℕ` fields) in
   `Allocation.agda`, with the `apply-bump : AllocBump → AllocState → AllocState`
   transform.
2. Define `final-alloc-of : AllocState → AllocBump → AllocState`.
3. Lemmas: `bump-0-is-id`, `bump-add`, `current-frame-preserved-by-bump`.

### Phase 2 — IRResultBase refactor (single commit)

1. Replace `final-alloc` field with `next-slot-bump` + `next-heap-ref-bump`.
2. Update `alloc-correct`'s type.
3. Add `final-alloc` as a derived projection (so consumers reading
   `IRResultBase.final-alloc r` keep working).
4. Update `IRResultAWF` re-export of `final-alloc`.
5. Expect this commit to break every producer's record construction
   — they all need updating. That's Phase 3.

### Phase 3 — Producer migration (one commit per producer family)

For each producer, declare its bumps explicitly and prove
`alloc-correct` against the derived form.

**Heap-result producers (Pattern 1 side effect):**

- `SumInlHeapWF`, `SumInrHeapWF` — `(0, 1)`. Already follow Model A; no trace changes.
- `CurryHeapWF` — `(0, 1)`. Already follows Model A; no trace changes.
- `PairHeapWF` — `(0, 1)`. **Must drop `instr-alloc-stack pair-heap-overhead`** from setup-trace. Closes its trace-is-ir-to-trace SMP.!! as side effect.

**Stack-result producers (defer or do later):**

- `SumRecWF` run-inl / run-inr Stack — `(sum-slots, 0)`. Trace keeps `instr-alloc-stack sum-slots`.
- `CurryWF` Stack — `(closure-slots, 0)`. Trace keeps `instr-alloc-stack closure-slots`.
- `PairWF2` (stack pair) — `(pair-slots, 0)`.

**Compositional / dispatching:**

- `SimpleWF` — `(0, 0)`. id, fst, snd, const are pure.
- `ComposeWF` — `(rf-slot-bump + rg-slot-bump, rf-heap-bump + rg-heap-bump)`. Bump-additivity replaces exec-trace state threading in `alloc-correct-compose`.
- `SumRecWF` case-dispatch — bumps inherited from dispatched sub-IR (case-inl ⇒ f's bumps; case-inr ⇒ g's bumps).
- `ApplyWF` — bumps inherited from body's bumps (+ apply's own scratch budget?).
- `RecCoreWF`, `ParaWF`, `AnaWF` — depend on recursion-scheme semantics.

### Phase 4 — Consumer migration (single commit)

- `Dispatcher.agda` — likely minimal change (it just routes).
- `IRTraceCorrect.agda` — `alloc-correct`'s shape changed; may need to update its bridge proofs.
- Any other file reading `IRResultBase.final-alloc r` directly — works unchanged because `final-alloc` is now a derived projection.

### Phase 5 — Verify SMP.!! reduction

After all producers migrated:

- All `trace-is-ir-to-trace` SMP.!!s for heap-result producers should be discharged via `refl` or `cong`.
- All `alloc-correct` SMP.!!s for heap-result producers should simplify (PairHeapWF's `alloc-correct-pair-heap` becomes much simpler).
- Stack-result producers' `instr-alloc-stack` stays in-trace; their `alloc-correct` discharges via current chain-form proofs but now structured around bumps.

## Risks & Mitigations

- **Risk:** consumers reading `IRResultBase.final-alloc r` directly.
  **Mitigation:** keep `final-alloc` as a derived projection; consumers
  see no change.

- **Risk:** Compose's `alloc-correct-compose` proof rewires.
  **Mitigation:** bump-additivity (f's bumps + g's bumps) is a cleaner
  formulation than today's exec-trace state threading. Likely shorter.

- **Risk:** IRTraceCorrect.agda's bridge proofs assume specific
  `final-alloc` shape.
  **Mitigation:** `final-alloc = final-alloc-of alloc bumps` is fully
  determined; bridge proofs use the explicit form.

- **Risk:** PairWF2 has 133 references to `alloc-after-pair-slots`/
  `pair-overhead`/`instr-alloc-stack` (per memory
  [[project_bridge_a_audit]]). The stack-result tier (Phase 3
  stack-result) is the biggest single-file refactor.
  **Mitigation:** defer to a follow-up session. Phase 3 heap-result
  producers are the load-bearing demonstration; PairWF2 follows the
  same template once validated.

## Acceptance Criteria

- IRResultBase has `next-slot-bump` and `next-heap-ref-bump` fields.
- `final-alloc` is a derived projection, not a free field.
- All producers compile.
- Layer 0/1/2 tests pass (`cabal test -p /Layer/ -j1`).
- `make compiler-x86-64` clean.
- Heap-result producers' `trace-is-ir-to-trace` SMP.!!s are discharged
  (or removed) as a side effect.
- No regression in existing SMP.!! count outside the heap-result
  producers (stack-result tier is its own follow-up).

## Why this is principled

The "single source of truth" argument: today, the alloc effect of an
IR is implicitly expressed in three places — the trace's instructions,
the `final-alloc` field, and the `alloc-correct` proof. Producers can
silently disagree across these three (PairHeapWF vs CurryHeapWF).
After Plan 0.17, the alloc effect is one typed quantity declared by the
producer, and `alloc-correct` is the consistency check. Inconsistency
becomes a type error, not a runtime postulate.

The "BeforeFrontier mechanical derivability" argument: today consumers
have to look at how `final-alloc` was constructed to know whether
`BeforeFrontier final-alloc loc` reduces to a stack or heap check.
After Plan 0.17, the structural shape (`final-alloc-of alloc (s, h)`)
makes this derivation automatic.

The "Compose-as-monoidal-composition" argument: bump-additivity is a
clean algebraic statement. Today's Compose proof threads exec-trace
state through `result-f.alloc-correct` and `result-g.alloc-correct`.
After Plan 0.17, Compose's bumps are literally `f.bumps + g.bumps`.
