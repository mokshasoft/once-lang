# Plan 0.50 — Canonicalize the generators (finish the CanonicalName migration)

## CORROBORATED 2026-09-01 — and it now blocks plan 0.80 too

Hit from the other end while removing algorithmic premises from the typing
rules (plan 0.80 / D134). `t-app`/`t-effApp`/`t-arg-driven-app-check` carry
`classifyAppHead f ≡ nothing`; that premise was classified as DISAMBIGUATION
and slated for removal. Removing it typechecks `Judgment` and all 59 call
sites — and then `check-complete` fails, on exactly this shadowing case:

    fst : Int -> Int
    fst x = x
    test = fst 5        -- elaborator REJECTS ("fst requires a pair argument")

`classifyAppHead` is ctx-free and bare-string, so it calls that head the
BUILTIN whatever the user wrote; without the premise `t-app` derives the
program with the user's `fst`, and the judgment accepts what the elaborator
rejects.

**So `classifyAppHead f ≡ nothing` is load-bearing TODAY only because this
plan is unstarted.** It is not intrinsically semantics — it is a bare-string
COLLISION GUARD. Once generators are `Generators.fst` and a user's is
`User.Module.fst`, there is no collision, the guard has nothing to guard, and
plan 0.80's `classifyAppHead` item becomes the free removal it was thought to
be. Add that to this plan's payoff list.

**Two documentation facts found at the same time:**

  * **D001 has NOT been superseded in the decision log.** It still reads
    "Generators as Reserved Words / Accepted — Users cannot define variables
    named `fst` … The parser can assume these names always refer to
    generators." This plan's 2026-06-26 decision reverses that, and there is
    NO `D0xx` entry recording it. Per MERGE.md step 2 the reversal owes one
    before it lands.
  * **A test PINS the bug.** `compiler/test/TypeCheckSpec.hs`'s

## The finding

The CanonicalName migration is NOT done: the CCC generators (id, fst, snd, inl,
inr, terminal, initial, compose, pair, case, curry, apply, cata, ana, arr, In,
Out) are the holdout — `classifyBareBuiltin : String → …` dispatches on the BARE
string `"fst"`. So `User.Defined.Module.fst` and the generator `fst` share one
identity space. Consequences (all the same root cause):
- **Shadowing bug** (confirmed): `fst = id; … fst 7` → "fst requires a pair
  argument" — the builtin wins, the user's def is silently unreachable.
- `checkElabV (RVar x)` dispatches `classifyBareBuiltin x` BEFORE scope lookup
  (Elaborate:1581), so a builtin-named import elaborates as the builtin.
- `named-morph-strong` is un-dischargeable: it's only true for `bbc-other` names,
  and the judgment doesn't track that.

## Decision (2026-06-26): reserved compiler namespace

Generators get a canonical path the compiler owns, e.g. `canonical ["Generators", g]`.
Then `User.Module.fst ≠ Generators.fst` BY CanonicalName — collision, ambiguity,
and the discharge gap all dissolve. (Not "reserve builtin names" — that was a
band-aid guard. Canonicalizing is the principled completion.)

## The change (top-down: change the classification spec, follow the red)

1. **`Generators` namespace + `classifyByCanonical : CanonicalName → BareBuiltinClass`**
   matching `canonical ["Generators", g]`; replaces bare-string `classifyBareBuiltin`.
2. **Resolver** (`Once/Parser/Module/Resolve.agda`, `canonVar`/`isBuiltinName`):
   a bare generator reference NOT shadowed by a user def → `RResolved (canonical
   ["Generators", g])`; a user-defined name → its own module path. Normal scoping
   then lets a user define `fst` (their `User.Module.fst`) and reference it — no
   reservation needed, no shadowing.
3. **Elaborator** (`checkElabV`/`inferElabV`): dispatch on the resolved
   `CanonicalName` (RResolved), `classifyByCanonical cn` — `Generators.*` → builtin
   IR; else the import/morphism path. Replaces the bare-string `RVar` dispatch (1581).
4. **Discharge `named-morph-strong` (+ `-resolved`)**: a user `RResolved cn` has
   `cn ≠ Generators.*` ⇒ provably not a builtin ⇒ the morphism path ⇒ the postulate
   discharges by construction. The implicit `bbc-other` assumption becomes
   type-enforced (the [[feedback_runtime_failure_find_hiding_postulate]] principle).

## Why the apex is GREEN today even though this isn't done

Two reasons, only one a postulate (the diagnostic, 2026-06-26):
1. **The spec agrees with the impl on bare strings.** The judgments identify a
   generator by bare-string `RVar` + scope-absence (`m-id`'s `lookupLocal ≡
   nothing`, `lookupImport ≡ nothing`) — the SAME rule as `classifyBareBuiltin`.
   Spec ↔ impl match ⇒ green. The bare-string-ness is in the SPEC, not hidden;
   the top was simply never written to demand canonical generators.
2. **The `StrongElab` postulates hide the COLLISION cases.** `named-morph-strong`
   / `const-morph-strong` / `cata-morph-strong` assert elaboration-completeness
   without proving it against the real elaborator; `named-morph-strong` papers
   over the `bbc-other` shadowing. Discharging them surfaces the gap (needs
   `bbc-other`). Canonicalizing makes them dischargeable (canonical names can't
   collide), so they stop hiding anything.
