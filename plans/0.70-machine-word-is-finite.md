# Plan 0.70 — The Machine Word Is Finite

**Status**: not started. Written 2026-08-13, out of plan 0.65's G2 port.
**Blocks**: nothing. **Blocked by**: nothing. Resume 0.65 G2 after this.

## Why

All three target semantics say

    Word   = ℕ
    Memory = Word → Maybe Word
    add    = _+_          sub = _∸_        (truncated)

Real registers are fixed-width and modular. So the models are not a coarser
view of the machine, they are a DIFFERENT machine — D103's phrase, and this is
the same class of defect one layer down.

`add` diverges only past 2^64. **`sub` diverges at small values**: `3 ∸ 5 = 0`
in the model, `2^64 − 2` on hardware. Truncated subtraction is not modular
subtraction, and the gap opens at the first subtraction that would go negative.

D054 ALREADY DECIDED AGAINST THIS for the language: Once's `Int` denotes a
modular `Once.Word` (carrier `ℕ` in `[0, modulus)`, ops `⊕ ⊖ ⊗ ⊝` via `norm`,
width-parameterised). The tree therefore carries both notions, meeting at
`FlatCore.FlatCorrespondence.lit-word : Carrier → Word` — a modular value
injected into an unbounded one, with nothing checking the seam.

### Why nothing has caught it

The ABSTRACT flat machine uses the same arithmetic — `sv-pred (SV-Tag 0) =
SV-Tag 0` clamps exactly as `∸` does — so both sides diverge from hardware
TOGETHER and agree with each other. The correspondence is TRUE.

**AND THE DIVERGENCE IS NOT POSTULATED ANYWHERE — corrected 2026-08-13.** An
earlier draft said it lands in `<arch>-loader-faithful`. It does not:
`asm-sem = exec-bytes ∘ assemble`, `exec-bytes = run-trace ∘ decode`, and
`conc-trace` is `run-trace` on the compiled program — so both sides of that
axiom use OUR `run-trace`, the arithmetic cancels, and the axiom's comment
("NOT the CPU, NOT the arith logic") is correct. `run-trace` is DERIVED from
`execInstr` on all three arches, so real hardware appears nowhere in the
development.

No postulate says our `execInstr` matches a CPU. The grand theorem is
conditional on a model whose fidelity is not assumed, not proved, and not
stated — which is why counting postulates would never have surfaced this, and
why the repair is to make the model right rather than to narrow an axiom.

## THE DECISION THAT COMES FIRST — addresses are not values

Do not start by replacing `ℕ` with `Once.Word` everywhere. Measure first (this
was measured 2026-08-13, numbers below), because the correspondence uses the
machine word for TWO different jobs and they want different treatments.

**As a VALUE** (register contents, what `Int` computes) the word is modular.
That is D054, and it is not in dispute.

**As an ADDRESS** the model relies on ORDER and CANCELLATION, and modular
arithmetic supplies neither:

    lemma            uses   survives modularly?
    m≤m+n             17     NO   — `x ⊕ 1` can be BELOW `x`
    <-transˡ          14     the transitivity survives; the ORDER does not
    m∸n+n≡m            4     YES, and improves: `(x ⊖ y) ⊕ y ≡ x` always
    +-monoʳ-<          4     NO
    +-cancelˡ-≡        3     YES — `⊕` is cancellative in ℤ/nℤ
    *-cancelʳ-≡        3     **NO, and this one is load-bearing**

`slot-addr-inj` is `*-cancelʳ-≡ k slot slot-size (+-cancelˡ-≡ …)`: distinct
slots get distinct addresses by cancelling `* slot-size`. Modularly that is
FALSE — `slot-size` is 8, not a unit mod 2^64, and `8 * 0 ≡ 8 * 2^61`, so slot
`0` and slot `2^61` would share an address. Every stack window argument rests
on this.

And the layout separation (`hfront ≤ lo ≤ %rsp`, the virgin region
`[hfront, lo)`, `dom-below`) is an ORDER-THEORETIC argument. There is no total
order on `ℤ/2^64ℤ` compatible with `⊕`.

**So the answer is not "make addresses modular".** It is the one CompCert
reaches for: addresses stay ORDERED and BOUNDED, and the boundedness becomes an
explicit carried invariant — the program's memory lives in a region that does
not wrap. That is TRUE of every real program (the loader hands you a contiguous
region well inside the space) and it is exactly what today's proofs assume
silently.

    VALUES    modular `Once.Word`   — wrapping is the semantics
    ADDRESSES ordered ℕ + a NO-WRAP invariant — wrapping is a precondition
                                       violation the invariant excludes

Today one type does both jobs, which is why the question looks harder than it
is.

## Phases

### A — SPLIT THE TWO JOBS, no semantics change yet

Give the target semantics two names: `Word` (register/memory CONTENT) and
`Addr` (what `Memory` is indexed by, what `effectiveAddr` returns, what the
layout is ordered by). Both `= ℕ`, so definitionally a no-op.

**CORRECTED 2026-08-13, BY DOING IT.** The text that stood here said the value
of this phase is "the TYPE ERROR it creates later". **That is false and the
phase must not be sold on it.** `Addr = ℕ` is a TRANSPARENT alias, so
`Word ≡ Addr` is provable by `refl` and a value passes where an address is
expected with nothing to say about it — probed directly, not assumed. What
phase A actually buys is NAMING: the signatures now say which role each
position plays (`Memory = Addr → Maybe Word`,
`effectiveAddr : State → Mem → Addr`). Documentation and a prerequisite, not a
check.

BUYING THE CHECK IS A SEPARATE, EXPENSIVE PHASE. Making `Addr` opaque (a record
wrapper, or `abstract`) is the only thing that turns misuse into a type error,
and it is emphatically not a no-op: address ARITHMETIC is everywhere — **263
sites in `FlatCore.FlatCorrespondence` alone, 100 in `X86-64.FlatSimulation`,
33 in `ConcFlatSim`** — and `abstract` additionally blocks the reductions the
proofs run on. It breaks the "no proof changes" gate by construction.

DECIDE EXPLICITLY, do not drift: either

  (A1) accept naming-only, and let phases B/C expose the confusions through
       their arithmetic obligations — the confusions still surface, just later
       and as proof failures rather than type errors; or
  (A2) pay for the wrapper as its own phase with its own gate, BEFORE B, so
       B's obligations land in a type system that can tell the two apart.

Recommendation: **A1**. Those ~400 arithmetic sites are the same ones phase B
must revisit anyway, and doing the wrapper first means touching them twice.

GATE: four clusters green, ledger untouched, and NO proof edited. That gate is
still right — it tests that the naming is definitionally inert, not that it is
protective.

### B — THE ℕ↔MODULAR BRIDGE, AND THE AUDIT — done 2026-08-13

**CORRECTED BY DOING IT, like phase A.** B was written as "carry a
`region-fits` invariant". That is wrong on its own terms: nothing would CONSUME
such an invariant until phase C, and an invariant with no consumer is the thing
this repo calls a stub. Worse, it is not even needed for the ORDER — addresses
stay `ℕ`, and `ℕ`'s order works unconditionally. The invariant is born in C, at
the value→address boundary, not before.

What B is instead: **state exactly when the ℕ model agrees with the machine,
and audit which sites already satisfy it.** Both lemmas are now in
`Once.Word.Width`:

    ⊕≡+ : x + y < modulus  →  x ⊕ y ≡ x + y
    ⊖≡∸ : y ≤ x → x < modulus  →  x ⊖ y ≡ x ∸ y

THE ASYMMETRY IS THE POINT. Addition's condition is about the RESULT and no
current proof carries it. Subtraction's is about the ARGUMENTS — no borrow —
and truncated `∸` has been FORCING the proofs to carry it all along.

THE AUDIT, over every `∸` on a machine value in the correspondence:

    sim-alloc-stack       `slots n ≤ rreg s sp-reg`     ✓ carries it
    sim-thunk             `slots b ≤ rreg s sp-reg`     ✓ carries it
    sim-call              `slot-size ≤ rreg s sp-reg`   ✓ carries it
    sim-reg-scratch-dec   —                             ✗ NO premise

So three of the four are already faithfulness-ready: their `fits` premises,
which read as ℕ bookkeeping, ARE the no-borrow conditions, and under C they
become the reason `⊖` may replace `∸`.

THE FOURTH IS THE INTERESTING ONE. `sim-reg-scratch-dec` takes
`rreg s scratch-reg ∸ 1` unconditionally, and the abstract side clamps to match
(`sv-pred (SV-Tag 0) = SV-Tag 0`, `dec-enc`'s zero clause). At scratch ≡ 0 the
model gives 0 and hardware gives all-ones — a real divergence, currently
invisible because BOTH sides clamp.

But the EMITTED CODE already guards it. `cata-nat-I₂`/`I₃` emit

    L4: c-branch-scratch-zero → L5 ; <body> ; scratch-dec ; c-jmp L4 ; L5:

so `scratch-dec` is reached only when the branch was NOT taken, i.e. scratch
≢ 0. The guard exists in the program and is simply not recorded in the proof —
which makes `dec-enc`'s clamping clause reachable only in states the emitter
cannot produce. Same shape as this plan's other findings: the condition is
true in the code and absent from the statement.

C's work at `scratch-dec` is therefore to CARRY that guard as a premise (and
discharge it from the branch), not to invent a bound.

GATE: `Once.Word` gains two lemmas; nothing else changes; four clusters green.

### C — VALUES BECOME MODULAR

`Word = Once.Word.Width bits .Word`, `add = _⊕_`, `sub = _⊖_`, and `∸`
disappears from the three semantics.

**SUBTRACTION, x86-64 — done 2026-08-13.** `execInstr`'s `sub` computes `⊖`,
`step-sub-ri` says so, and all four `sub` block-steps bridge back with `⊖≡∸`.
Three needed no new premise: `fits` was already there. The fourth,
`scratch-dec`, needed its guard written down — and that guard is the branch
sitting immediately above the instruction in the emitted code.

**ADDITION, x86-64 — done 2026-08-13, after one wrong turn worth recording.**

THE WRONG TURN. Addition was first attempted, backed out, and written up here
as "different in kind", on the grounds that its sites need `%rsp + slots n <
2^64` and `%r14 + 1 < 2^64`, that nothing in the program guarantees them, and
that assuming them would be "assuming the machine does not overflow in order to
prove the machine is modelled correctly".

THAT REASONING IS WRONG, and D054 says so directly: wraparound is *correct,
defined* Once semantics, "not a bug, not undefined behaviour, and not something
the programmer or the compiler must prove absent". A no-overflow precondition
is "exactly the narrow regime where the impossible accidentally holds". We do
not model `+` as something that overflows or not — the emitted `add` MEANS `⊕`,
and a program whose arithmetic wraps is a program with a defined result, which
the correctness theorem must cover rather than exclude. Putting a premise on
the INSTRUCTION would have excluded it.

WHAT WAS ACTUALLY TRUE, and what the wrong turn misread: every `add` the
compiler emits computes an ADDRESS or the OBSERVABLE COUNTER —

    c-ret                   add rsp, slots b    frame release        LIVE
    alloc-heap              add r15, slots n    heap bump            LIVE
    count-inc               add r14, 1          observable counter   LIVE
    dealloc-stack           add rsp, slots n    frame release        unemittable
    lea-indexed             add rcx,rcx ×3      slot-index → byte    unemittable
                            add rdi, rcx        offset

(The last two are killed by `frame-op-absurd` in ConcFlatSim's routing — the
heap-linked-stack rework of 2026-08-01 retired them — so only THREE sites are
live, which is exactly the three fields `AddrNoWrap` ended up with.)

— and NOT ONE is a user `Int` addition. User arithmetic goes through the Arith
backend over `Once.Word`, where it already wraps by design. So the range facts
these sites need are LAYOUT facts ("the compiled image fits in the address
space"), of exactly the `HeapRoom`/`StackRoom`/`CallRoom` family, with the same
D087 discharge route — a linker sizing pass. They are not claims about what user
values do, and a wrapping user program stays fully covered.

That also corrects the ordering conclusion the wrong turn drew. "Fix the
abstract side first so `⊕` faces `⊕`" does NOT apply here: for these sites the
abstract side is ADDRESSES, which phase A deliberately kept at `Addr = ℕ`. There
is no modular abstract side to line them up with, and the bridge is the layout
bound — which is where it belongs.

WHAT LANDED, and what it cost. Five D087-class parameters, threaded
`Certified → Compiler → ArchCorrectness → X86-64 → ConcFlatSim`:

    RegRange           a register holds a value below the modulus. True of any
                       real state; not derivable because `mov reg, imm n` and
                       `lea` write unbounded values. Becomes a theorem when the
                       register file carries its range.
    ScratchDecGuarded  a reachable `scratch-dec` finds a non-zero Scratch.
                       Route: the `emitted-thunk-guarded` induction.
    AddrNoWrap         a record of three (`ret-no-wrap`, `count-no-wrap`,
                       `lo-fits`) — bundled so the four-module thread is written
                       once and does not change as fields move.

THE HEAP BUMP COST NOTHING: `HeapRoom` already bounds the bumped frontier by
`lo`, so `lo-fits` — "the stack's high-water mark is representable", the layout
bound in its most basic form — discharges it outright. `dealloc-no-wrap` was
written and then DELETED: `instr-dealloc-stack` is unemittable, so ConcFlatSim
kills that route with `frame-op-absurd` and the bound is never consumed. Assume
nothing that is never used.

DIVISION NEEDED NOTHING. D055 already made `/` and `%` total, on RISC-V's
semantics (`a / 0 = -1`, `a % 0 = a`, `INT_MIN / -1 = INT_MIN`) — the one op
where the silicon disagrees, aligned on the total variant. It lives in
`Once.Word` as `_/ˢ_`/`_%ˢ_`, one definition all three arches share, so the
"align where arches differ" work is already done and this phase does not touch
it.

STILL OPEN IN C: riscv64 and x86-32. riscv64's `step-add`/`step-sub` still say
`+`/`∸` (see its `StepLemmas`), and its block-steps do not exist yet — G2 owns
them, and they should be WRITTEN modular rather than written in ℕ and converted.

GATE: four clusters green. C CANNOT CHANGE WHAT A COMPILED PROGRAM DOES — the
emitter is untouched, the same bytes come out. The exit tests are a regression
check on the proofs' consumers, not evidence about behaviour.

### D — CLOSE THE SEAM

`lit-word : Carrier → Word` becomes the identity (both sides modular at the
same width), and `word-eq`-style equations tie the target's `bits` to the
frame semantics' word size. The residual ledger's "THE UNBOUNDED-REGISTER
MODEL" section is deleted, not reworded.

## What this will break, stated up front

Phase B and C will break proofs, and that is the content rather than the cost:
**every break marks a place the current proof quietly assumes an infinite
register file.** Expect them concentrated in

- the window/frame arithmetic (`win-at`, `windows-*`, `StackWindows`),
- `slot-addr-inj` and everything downstream of it,
- `descend-view` / `untouched` (the virgin region is an interval),
- `sim-alloc-stack` / `sim-thunk` / `sim-call`, whose `fits` premises are the
  ∸-taming ones.

If a break cannot be repaired by the region invariant, that is a REAL
divergence and belongs in the ledger, not in a workaround.

## Order and scope

A is safe and mechanical. B is the substantial one and can land alone. C
changes the machine and should not be attempted until B is green, because
without the region invariant the ordering proofs have nothing to stand on.

**Do NOT do this inside plan 0.65.** 0.65 is extracting an arch-generic core
and its gate is "the ledger diff is empty"; this plan changes what the machine
IS and will move the ledger. Finish 0.65's G2/G3 first — the extraction makes
this plan cheaper anyway, since after it there is ONE correspondence to change
instead of three.

## Relationship to D054 and D103

- **D054** decided values are modular and moved the LANGUAGE off `ℤ`. This is
  the same decision applied one layer down, to the MACHINE MODEL, which D054
  did not touch.
- **D103** found a model that was a different machine and repaired it. This is
  the same shape at a different scale: there the value was a code address, here
  it is every arithmetic result.
- Neither was shielded by an axiom, which is the uncomfortable part. D103's
  `lla` defect and this one both sat in the MODEL, and the development contains
  no statement that the model is faithful — so no postulate had to be weakened
  to accommodate them and no postulate count moved when D103 was fixed. The
  worthwhile side effect of this plan is therefore not a narrower axiom but a
  MODEL that earns the theorem already proved about it.
