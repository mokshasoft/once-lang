## 0. Where this starts

- The inline fold `exit@S (snd (cata (case start step) fifteen))` is rejected with
  "case: expected type mismatch". The same fold named with a signature
  (`count : Mu (K Unit + Id) -> Int * Int; count = cata (case start step)`) checks, and so does the inline
  one with an annotation, `(case start step : Unit + Int * Int -> Int * Int)` (`s-annot`); it exits 7.
- The checker is right: it follows the Spec. `d-cata` (`Spec/Surface/Typing.agda`, ~l. 309) types
  `cata alg` from its domain `μ F` and needs the algebra to SYNTHESIZE (`alg ⇒ ⟦F⟧ A ⇒⟨π⟩ A`); the checker's
  `given-cata` (`TypeCheck/Elaborate.agda` ~l. 285) calls `inferElab` on it. No postulate is involved.
- `d-cata` is categorically right. By initiality the domain `μ F` fixes `F` and nothing about the carrier
  `A`; the carrier is the algebra's. Handing the algebra the domain `⟦F⟧ A` would be circular.
- What is not right: the morphism combinators have checking rules (`c-case`, `c-pair`, `c-compose`,
  `c-compose-f`) and domain-given rules (`d-case`, `d-pair`), but no synthesis rule, and `sh-case`,
  `sh-pair`, `sh-compose` (`SpecialHead`) keep them out of `s-app`/`s-app-spine`. Yet by the universal
  properties a copairing `[f, g]` is determined by `f` and `g`, a pairing `⟨f, g⟩` likewise, and
  `g ∘ f` by `g` and `f`. In fizzbuzz `start` and `step` have signatures, so the algebra's type is fully
  known, and the Spec still has no derivation.
- The error message names `case` and says nothing useful.

## 1. The goal

When the parts synthesize, the combinator synthesizes:

```
s-case-fun    : f ⇒ A ⇒⟨π⟩ Cf → g ⇒ B ⇒⟨π⟩ Cg → Cf ⊔ Cg ≔ C
              → case f g ⇒ (A + B) ⇒⟨π⟩ C            -- each branch coerced to C, as in d-case
s-pair-fun    : f ⇒ A ⇒⟨π⟩ B → g ⇒ A ⇒⟨π⟩ C
              → pair f g ⇒ A ⇒⟨π⟩ (B * C)
s-compose-fun : g ⇒ B ⇒⟨π⟩ C → f ⇒ A ⇒⟨π⟩ B′ → B′ <: B
              → compose g f ⇒ A ⇒⟨π⟩ C
```

Then `cata (case start step) n` types through `d-cata` with no annotation. A branch written as a lambda
still does not synthesize, so an inline algebra with a lambda branch still needs its annotation; there the
carrier is genuinely not written down.

## 2. Open questions (decide in the decision entry)

1. **Grades.** The rules above ask both parts for the same `π`. Taking the join of the parts' grades (and
   coercing) is more general; is it wanted, and does `domain-agrees-synth` (`π′ ⊑π π`) still hold?
2. **Quantities.** `domain-agrees-synth` says a synthesized arrow is `mk-kind Many π′`. A part with a
   linear arrow type: reject in synthesis (use checking), or synthesize the meet?
3. **Domains of `pair`.** Equal domains, or the meet of `f`'s and `g`'s domains when one exists?
4. **`compose` direction.** `compose g f` synthesizes from both; with `c-compose-f` already reading `f`
   first, is a version where only one part synthesizes (and the other is checked) wanted too?
5. **The fallback.** Should `d-cata` keep requiring synthesis (recommended: yes, it is the categorical
   reading), with only the message improved when the algebra cannot synthesize?
