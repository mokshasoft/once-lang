# Plan 0.2.4.5 D2: Surface morphism/closure realm split

## Goal

Distinguish CCC morphisms (arrows in the category — `IR A B`) from
closure values (exponential objects — `IR Γ (A ⇒ B)`) at the Surface
language level. The morphism realm covers most categorical-style code
(point-free composition, primitives, projections, identity); the
closure realm is reserved for genuine first-class function-value use.

## Why principled (not just a workaround)

1. **Categorical structure.** CCCs have two function-like things;
   morphisms are the arrows, closure values are inhabitants of
   exponential objects. They're related by curry/apply but distinct.
   Once's IR already distinguishes; Surface should match.
2. **Performance.** Morphism realm has zero closure-record overhead.
3. **Verification surface.** The verified `ApplyWF` machinery is
   complex (closure-decomp eval bridge, alloc-state threading);
   compose's correctness is structurally trivial. Pushing programs
   to the morphism realm shrinks proof obligations.
4. **Surface honesty.** `f . g` should mean "compose these two
   functions", not "construct a closure value representing the
   composition that I'll then invoke via apply".
5. **FFI / SigOps** have no environment — they're morphisms by
   nature. Surface should reflect that.

## What this fixes

`exit ((id . id . id) 42)` (and any genuine compose chain like
`exit (((+1) . (*2) . (+3)) 42)`) currently segfaults due to
**dangling closures** in nested apply chains: each apply's body
allocates the returned closure in its own %rsp-relative frame, which
is gone after the body's `addq %rsp; ret`. Middle-apply receives
a dangling pointer.

After the realm split, these compose chains lower to pure CCC compose
(no apply, no intermediate closures, no dangling). The closure realm
keeps the existing (buggy) ABI for genuine higher-order use, which
no current test exercises.

When closure-realm tests arrive later, separate ABI work is needed:
either heap-allocated returned closures (.bss pool, Plan 0.2.4.2 D7
direction) or out-parameter pattern (caller pre-allocates closure
result slot).

## Implementation

### Step 1: Add `lift-morphism` Surface IR constructor

In `Once/Surface/Syntax.agda`'s `Expr` data type:

```agda
lift-morphism : ∀ {n} {Γ : Ctx n} {A B}
              → IR A B
              → Expr Γ zeroUsage (A ⇒ B)
```

Wraps a CCC morphism `m : IR A B` as a Surface function value.
Usage is zero (morphism doesn't consume context variables).

### Step 2: Surface elaboration

In `Once/Surface/Elaborate.agda`, add a dispatch for app-of-morphism:

```agda
elaborate (app (lift-morphism m) x) = m ∘ elaborate x  -- compose realm
elaborate (app f x) = apply ∘ ⟨ elaborate f , elaborate x ⟩ Heap  -- closure realm (current)
```

The first pattern is more specific so it fires when the head is a
lifted morphism.

### Step 3: Replace `specId` / `specCompose` / `specFst` / `specSnd` /
        `specTerminal` / `specInitial`

Currently in `Once/TypeCheck/Elaborate.agda` these are Surface
lambdas. Replace with `lift-morphism` over the corresponding CCC IR
primitive:

```agda
specId : (A : Type) → SExpr S∅ Surface.zeroUsage (A ⇒ A)
specId A = lift-morphism id

specCompose : (A B C : Type) → SExpr S∅ Surface.zeroUsage ((B ⇒ C) ⇒ (A ⇒ B) ⇒ A ⇒ C)
specCompose A B C = ???  -- The composition combinator is itself
                          -- a higher-order function. Genuine
                          -- closure use? Or rewrite checkCompose
                          -- to emit lift-morphism (compose-CCC f g)
                          -- directly without going through specCompose?
```

Subtlety: `specCompose` is only used by `checkComposeWithBg` to build
the application `app (app specCompose f) g`. We can bypass specCompose
entirely by having `checkComposeWithBg` emit:

```agda
lift-morphism (elaborate-as-morphism f ∘ elaborate-as-morphism g)
```

— directly producing a CCC compose IR wrapped as a value.

This requires `elaborate-as-morphism : SExpr Γ Ψ (A ⇒ B) → IR A B` for
the cases we recognize as morphisms. Implementable as:

```agda
elaborate-as-morphism (lift-morphism m) = m
elaborate-as-morphism (lam q _ e) = curry (elaborate-as-morphism' e) Stack  -- closure case
                                                                              -- (still falls through to apply)
... (other cases)
```

Recursive structure mirrors CCC IR shape.

### Step 5: Thinning, Semantics, etc.

`Once/Surface/Thinning.agda`'s `rename`: pass `lift-morphism m` through
unchanged (morphism doesn't bind context).

`Once/Surface/Semantics.agda`'s `evalSurface`: lift-morphism evaluates

### Step 6: Wire bbc paths in TypeCheck/Elaborate

The `bbc-id`/`bbc-fst`/`bbc-snd`/`bbc-terminal` etc. paths currently
emit `specId`/`specFst`/etc. which were Surface lambdas. With the new
spec helpers (which now use lift-morphism), these paths automatically
use the morphism realm.

Compose head case (`checkComposeWithBg`) emits the bypass:

```agda
checkComposeWithBg ctx f_inner arg A B C eqArgB
  (success Ψg gE dg frg , wG) _ (success Ψf fE df frf , wF) _ =
    -- Replace:
    --   Surface.app (Surface.app (weakenFromEmpty (specCompose A B C)) fE) gE
    -- with direct morphism construction:
    let m_f = elaborate-as-morphism fE
        m_g = elaborate-as-morphism gE
    in success _
      (Surface.lift-morphism (m_f ∘ m_g))
      (suc (df Data.Nat.⊔ dg)) frf , t-compose-check eqArgB wF wG
```

Same pattern for other application sites that build morphism-style
expressions.

## Why direct `app f x` dispatch was abandoned

Original Step 2 design proposed a more-specific `elaborate (app
(lift-morphism m) x) = m ∘ elaborate x` clause before the generic
`app f x`. This hits a `SplitError.UnificationStuck` in Agda 2.8: the
pattern compiler can't decide whether `var i`'s opaque index `lookup
Γ i` could equal `A ⇒ B`, blocking case enumeration. Both nested
patterns and `with f` rewrites of the same dispatch fail identically.

The workaround: introduce `morph-app` as a distinct constructor and
have the typechecker emit it directly at known-morphism call sites.
This dodges the dependent-pattern issue (see memory
`feedback_generic_codomain_trick`).

## Open (historical, kept for reference): compose chain

`(id . id . id) 42` still segfaults — checkComposeWithBg still
emits `Surface.app (Surface.app (weakenFromEmpty (specCompose …))
fE) gE`, which goes through closure realm and triggers the apply-
chain dangling-pointer bug.

To fix: write `extract-morph : SExpr Γ Ψ (A ⇒ B) → Maybe (IR A B)`
via the codomain trick:

```agda
extract-aux : ∀ {n} {Γ Ψ T A B} → SExpr Γ Ψ T → T ≡ (A ⇒ B) → Maybe (IR A B)
extract-aux (lift-morphism m) refl = just m
extract-aux _ _ = nothing
extract-morph e = extract-aux e refl
```

(Direct `extract-morph (lift-morphism m) = just m` hits the same
SplitError as the original `app` dispatch.)

Then `checkComposeWithBg`:

```agda
... with extract-morph fE | extract-morph gE
... | just m_f | just m_g = ... lift-morphism (m_f IR.∘ m_g) ...
... | _ | _              = -- existing app-of-specCompose path
```

Caveat: when both extract, `Ψ₁ = Ψ₂ = zeroUsage`, so the judgment's
usage `zeroUsage +ᵘ (Many *ᵘ Ψ₁) +ᵘ (Many *ᵘ Ψ₂)` should reduce to
`zeroUsage` definitionally — but Agda may need explicit subst with
`Many *ᵘ zeroUsage ≡ zeroUsage` and `_+ᵘ zeroUsage ≡ id`. Budget a
small lemma module.

A similar dispatch is needed at `inferElabV-RApp-other` /
`checkElabV` outermost-app sites: when fE is a `lift-morphism m`,
emit `morph-app m argE` instead of `Surface.app fE argE`. Without
this, even after compose-bypass produces `lift-morphism (m₁ ∘ m₂)`,
applying it to `42` re-enters closure realm.

## SUPERSEDED (2026-05-23): see Plan 0.19

The "outermost-app `lift-morphism` dispatch" open item above is
**superseded by `plans/0.19-sigop-closure-split.md`**. Reason:
extending the dispatch only patches the morphism-realm subset (fns
like `myid = id`) while leaving the deeper conflation in place —
user-defined fns continue to route through `sigOp` with a Surface
type that doesn't match their asm signature, and `sigOp-arrow-eta`
(an undocumented inline postulate in `Once.Surface.Correct`) keeps
silently bridging the mismatch.

Plan 0.19 takes the principled path: split the Surface constructor
so `sigOp` carries only external primitives (asm-direct arrow) and
introduce `closure` for user-defined entries whose asm signature is
`Unit → Closure(A → B)`. The resolver (Phase 3 of 0.19) handles the
morphism-alias substitution that this open item would have done,
plus generalises to non-app contexts; the closure constructor
(Phases 1/4) handles genuine captures that the open item never
addressed.

The "closure-realm ABI fix" mentioned elsewhere in this file (heap-
pool returned closures, out-param pre-allocation) is now reframed:
the user-fn-invocation half of that work is subsumed by 0.19; what
remains is the *branch-returned-closure dangling pointer* problem,
which is a separate codegen issue not addressed here.
