# Plan 0.124 — `once fmt`: one canonical layout, proved not to change the program

status: STARTED 2026-10-26 on branch `once-fmt` (written 2026-10-23, at the user's request). Starts after plan 0.122 (one surface syntax: the
formatter reads `Spec.Surface.Syntax.Module`, which 0.122 makes the parser's only output). No Spec change.

relates: plan 0.122 (one syntax; deleting the parallel trees), plan 0.71 (`RFloat` keeps the fraction's
length "for the printer round-trip"), plan 0.74 (positions only on literal tokens), D325 (the lexing
behaviours the Spec fixes), plan 0.3 task #38 (`Grammar.Printer`/`ExprRoundtrip`: an earlier printer over
the parallel `Grammar` syntax).

## 0. Where this starts

- No formatter exists. Layout is by hand; nothing checks it.
- The lexer drops comments (`--` to end of line, nested `{- -}`, `Spec.Surface.Lexing` `lex-comment`) and
  whitespace; the parser sees tokens only, so the module it returns carries no comments, blank lines or
  layout.
- Positions: only literal tokens carry a source offset (`TInt`, `TFloat`, plan 0.74). Putting one on every
  token was measured then at 6,738 pattern sites through the verified parser.
- Literals: a float keeps its digits and the fraction's length (`1.50` ≠ `1.5`, plan 0.71); an integer is a
  `ℤ` (`007` reads as `7`).
- An earlier printer exists over the PARALLEL syntax `Once.Grammar` (`Grammar.Printer` with a type
  round-trip, `Grammar.ExprRoundtrip` smoke tests for expressions). It prints a second tree.

## 1. The goal

`once fmt FILE` rewrites a module in the one canonical layout; `once fmt --check FILE` fails if it is not.
Formatting never changes what a program means, and that is a theorem, not a test:
1. **Round-trip** — parsing the formatted text gives the same `Module` as parsing the input.
2. **Idempotence** — formatting formatted text changes nothing.
3. **Comments survive** — the comments come out in the same order, with the same text.

## 2. Design (and the pitfalls each choice avoids)

1. **No second syntax tree.** The formatter reads the Spec's `Module` (the parser's output) plus what the
   lexer kept on the side. A concrete syntax tree of its own would be one more syntax to keep in step with
   the Spec — the duplication plan 0.122 removes. The `Grammar` printer is not extended; it goes (§3, step 6).
2. **Trivia on a side channel.** The lexer also returns the comments and blank lines, each anchored to the
   token it precedes (by index in the token list, not by offset — no position on every token). The parser
   and the Spec's grammar do not change. Attachment rules, fixed: a comment on its own line belongs to the
   next token; an end-of-line comment to the token before it; blank lines are kept between declarations (at
   most one) and inside bodies (at most one in a row).
3. **One style, no options.** A Wadler/Leijen document algebra (`text`, `line`, `nest`, `group`) at one
   width (100). No vertical alignment (aligned columns turn one-line edits into multi-line diffs). Rules per
   construct: declarations, signatures, `let`/`destruct` chains, application spines, lambdas, binary
   operators by precedence.
4. **Parentheses from the grammar.** The printer emits a parenthesis only where the grammar's precedence and
   associativity would otherwise parse differently; the round-trip theorem checks the table. Anchoring trivia
   to tokens counts only non-parenthesis tokens, so a parenthesis the printer adds or drops moves no comment.
5. **Literals as written.** Floats print their digits as lexed. Integers print in their canonical decimal
   form (`007` → `7`): the `Module` holds a `ℤ`, so round-trip holds; recorded as a style rule, not a loss.
6. **Unresolved, untyped input.** The formatter runs on the parser's output — before the resolver and the
   checker — so it formats code that does not typecheck yet. Nothing in the surface syntax may need names or
   types to lay out (no user-defined fixity, no layout rule that depends on resolution).

## 3. Steps (each green: backstop, extraction + cabal + tests when the compiler changes)

1. **Lexer trivia.** `tokenizeWithTrivia : String → List Token × Trivia` (compiler code): the token list is
   exactly `tokenize`'s (a theorem: the first component equals today's lexer), and `Trivia` anchors each
   comment and blank-line run to a non-parenthesis token index.
2. **Document algebra.** `Once.Format.Doc` (`text`/`line`/`nest`/`group`, `render width`), with its laws
   (rendering a document is a string whose tokens are the document's texts, in order).
3. **Printer.** `print : Module → Trivia → Doc`, one function per syntactic category (declarations, types,
   schemas, expressions), parentheses from the precedence table.
4. **Theorems.** (a) round-trip: `parseStrict (render (print m t)) ≡ inj₂ m` for every `m` the parser
   produces — stated against the Spec's grammar (`ParsesModule`), using `parseStrict`'s soundness and
   completeness as they stand; (b) idempotence; (c) the comments of the output are the input's.
5. **CLI.** `once fmt FILE` (in place), `once fmt --check FILE...` (exit code), and a `--stdout` mode for
   editors. CI runs `--check` over `examples/`, the stdlib and the tests.
6. **Delete the parallel printer.** `Grammar.Printer`, `Grammar.ExprRoundtrip` and what only they use go
   (plan 0.122 removes the rest of `Grammar` with the surface bridges).
7. **Format the tree once.** One commit formats every `.once` file; the style is versioned (a style change is
   one reformat commit, never drift).

## 4. Risks

- **Comments inside expressions.** Anchoring to tokens handles them, but a comment between a function and its
  argument forces a line break in the output; the printer must treat a trivia anchor as a forced break.
- **Width-sensitive layout and the theorem.** The round-trip theorem does not depend on the width (layout is
  whitespace to the grammar); only the token sequence matters. State it at the token level first (the
  printed tokens are the module's tokens up to parentheses), then lift through `parseStrict`.
- **The verified parser's cost.** The round-trip proof runs through the WF parser; plan 0.3 task #38 hit the
  opaque `Acc` argument. The relational parser (`ParsesModule`, sound and complete) is the route: prove the
  printed tokens are related to `m`, then use completeness, never reduce the WF parser.

## 5. Decisions (2026-10-26; the user delegated them: constants in code, nothing configurable)

- **No configuration.** No options, no config file, no per-project style: the style is constants in
  `Once.Format` (`width = 100`, `indent = 2`). A style change is a code change plus one reformat commit.
- **Width 100, indent 2.** Measured: 21 of the tree's lines exceed 100 columns (the longest 149).
- **`--check`** also requires LF line ends, exactly one trailing newline, no tabs and no trailing whitespace —
  all of them are what `fmt` writes.
- **Canonical spellings** (each pair parses to the same `Module`, so the round-trip is unaffected):
  - a definition whose body starts with lambdas is written with parameters, `f x y = e` (the tree: 85 to 10);
  - `compose f g` (the grammar's `RApp (RApp (RVar "compose") f) g`) is written `f . g` — the grammar's
    designated syntax for composition; `compose` with fewer arguments stays a word;
  - integers in decimal (`007` → `7`), floats as lexed (§2.5);
  - a lambda, `let` or `destruct` is parenthesized unless it is a whole expression (a right-hand side, a
    lambda/`let` body, a parenthesis, a pair component, a `destruct` arm): it extends as far as it can, so
    elsewhere a parenthesis keeps it from swallowing what follows.
- **Lexical hazards the printer avoids:** `-` before `-` gets a space (`--` starts a comment); a line break
  inside a declaration is always indented (an unindented line is a new declaration: `lex-nl`), and so is a
  comment inside one; there is no blank line inside a declaration (a blank line is a newline token).

## 6. Refinements found when starting (2026-10-26)

- **Anchors** (§2.2 corrected). Anchoring to "the token index" breaks under the canonical spellings above:
  `f = \x -> e` and `f x = e` differ in `\`, `->` and the place of `=`; `f . g` and `compose f g` in `.`
  and `compose`. A comment is therefore anchored to the index of a WORD OR LITERAL token (`TWord`, `TInt`,
  `TFloat`), not counting the word `compose`: that sequence is the same in the input and in every canonical
  spelling of its module (parameters vs lambdas keep the words in order; parentheses, operators, `\`, `->`,
  `=` are not counted). An own-line comment belongs to the next anchor, an end-of-line comment to the
  previous one; a comment after the last token belongs to the end.
- **Blank lines only between declarations** (§2.2 corrected). Inside a declaration a blank line is a newline
  token (`lex-nl`), which ends the declaration, so none can occur there; between declarations, and between
  the comments before one, at most one is kept.
- **Measured** (2026-10-26, the tree's 146 `.once` files): 2,528 comment lines at column 0, 39 indented
  comment lines and 30 end-of-line comments inside declarations (8 files), no block comments.
- **Progress (2026-10-26).** Steps 1–3 and 5 landed, the theorems (step 4) not yet:
  `Format.Lex` (`lexItems`, with `tokens-lexItems : tokensOf (lexItems cs) ≡ tokenize cs`, proved),
  `Format.Doc` (text/line/newline/blank/eol/nest/group; indentation written at the line break, so `nest`
  indents only the lines it breaks; no line ends in blanks), `Format.Print` (trivia, printer),
  `Format.formatSource`, `once fmt [--check | --stdout]`. Checked by test on the tree's 126 parseable `.once`
  files: idempotent, every comment kept in order with its text, no line over 100 outside comments, no tab
  or trailing blank, and the formatted file compiles to the SAME assembly with the same result. The layout
  choices found on the way: a `let` chain is one group (each `in` on its line when broken, each value kept
  after its `=` when it fits); a left-nested chain of one operator or of `.` is one group, broken before
  each operator; a `Mu`/`Nu` functor is parenthesized unless it is `Id`, and the whole `Mu` only where a
  `*` or `+` follows it.
- **Steps 6 and 7 landed (2026-10-26).** Step 6: the parallel printer (`Grammar.Printer`, `ExprPrinter`, the
  round-trip smoke tests and the converters/relations/invariants only they used, 11 modules) is deleted;
  `Once.Parser` no longer imports modules only to force a check (the backstop checks every module), so the
  whole `Grammar` family and `Parser.Tests` leave the extraction. Step 7: the tree is formatted (67 of the
  126 parseable files changed; the 18 files that do not parse are left as they are) and compiles to
  exactly master's assembly; `FmtSpec` keeps it so (a parseable file not in the layout fails `cabal test`).
  Left: step 4, the theorems.

## 7. Step 4, the theorems: the route (2026-10-26, the user: "finalize the theorems too before merging")

Available: `FrontEndBridge.parseStrict-complete : ParsesText text m → parseStrict text ≡ inj₂ m`, its
soundness, and `SpecGrammar`'s `parses→`/`parses←` between the compiler's `ParsesText` and the Spec's `Parses`.
So round-trip is a Spec derivation `Parses (render …) m`, built in two halves that meet at a token list:
- 4.0 **Tokens in the document.** `Doc`'s atoms become Spec tokens (`tk`), a space (`sp`) and comments, not
  free text; `spell : Token → String`. The printer's output does not change (`FmtSpec` and the tree test).
- 4.1 **Well-formedness of a parsed module** (`Format.WF`): its names are identifiers, not reserved, its
  operator names operator characters, its literals non-negative… — a property of `Parses text m`, proved
  by induction on the derivation.
- 4.2 **Grammar** (`Format.Grammar`): for a well-formed module the document's tokens parse to it,
  `ParsesDecls (toksOf (print m tv)) (decls m) r` with `Trailing r` — per category, the parentheses and the
  follow conditions (`¬ ArgStart`, `¬ Starts …`) from the printing contexts; independent of trivia.
- 4.3 **Lexing** (`Format.Layout`): the rendered text lexes to the document's tokens with a newline token
  between declarations — every line break inside a declaration is indented (`nest ≥ indent`), every token
  pair that would lex as one is separated (`sp`), comments sit before line ends. Stated over a separation
  invariant of the document, proved on `layout`'s output.
- 4.4 **Round-trip**: `parseStrict text ≡ inj₂ m → parseStrict (formatSource text) ≡ inj₂ m`.
- 4.5 **Comments survive and idempotence**: the items of the output (4.3 at item level) are the input's
  comments in order; their trivia is the input's normalized, and `format m` reads trivia only through the
  normal form, so formatting the output gives the output.

## 8. Nothing left to the writer (2026-10-26, the user: "even blank lines and comments should not be left
for the user … like elm that always formats everything for you")

- **Blank lines come from the code**: one between declarations, none between a type signature and its
  definition, none between consecutive imports; a comment run stands directly above what follows it,
  except the file's leading comments, which a blank line separates from the first declaration. The
  input's blank lines are read only inside a run of comments, where they separate its paragraphs.
- **Comments are formatted**: `--x` is `-- x`; a prose line longer than the width is wrapped at its words,
  at its indentation; lines are never joined (tried first: joining merged the license header's two lines
  and every short line meant to stand alone — whether a short line ends a thought is not readable); kept as
  written: banners (only dashes), lines indented past `-- ` (code, tables), list items, block comments; a
  word longer than the width is not broken.
- **Canonicity**: the output is a function of the module and of the comments' words and paragraph
  structure, nothing else of the input. The theorem 4.5 is about the comments' words, in order.
