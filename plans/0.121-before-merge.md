## 3. Scoping the bridges (items 1–3), 2026-10-20

Two read-only passes (no build). Both bridges are **false today**, for reasons that are fixed before any

### 3.1 Why `complete` is false: signature-less definitions
`w-nosig` (`Spec/Surface/Program.agda:208`) lets a definition without a signature take ANY schema that is
principal over its own domains, i.e. its domains may be chosen to suit later uses. `twice = \f -> f (f 3)`
is principal at both `(Int -> Int) -> Int` and `(Int -> Void) -> Void` (incomparable, D322 §5), so
`h : (Int -> Void) -> Void; h = \k -> twice k` is a Spec program the compiler (one schema per definition,
by unification) rejects. No compiler that fixes one schema can match it, and an oracle hypothesis is
refutable (it would make the apex vacuous). Options:
- **(c1) without a signature, a definition has the type its body SYNTHESIZES** (`L ⊢ e ⇒ A`, still
  `Principal`). Synthesis is deterministic (`synth-unique`); the compiler uses `inferElab` only, the D072
  oracle leaves the trust boundary (it may stay as a suggested-signature hint), plan 0.59's "scope grew"
  hole closes. Cost: a body that only checks (a lambda, `f x = …`, or a bare polymorphic reference) needs a
  signature; ~4 of 153 test programs. Amends D007/D072. Binder annotations (D322's future extension) bring
  signature-less lambdas back deterministically later.
- **(c2) Hindley–Milner most-general schema** under equality typing at domains: keeps signature-less
  functions, but needs a declarative HM layer in the Spec and verified unification (plan 0.59 P1–P3), roughly
  +3,000–6,000 lines.
- Rejected: verified inference for the Spec as it stands (the property is false); a conditional apex.

### 3.2 Why `sound` is false: compiler divergences (all compiler-side fixes)
- **R1** `extractFunctions` silently drops a definition whose name differs from the pending signature, and
  ignores dangling/duplicate signatures (`Parser.agda:330,334,369`); the Spec's `Walk` rejects them.
- **R2** `main` is put in scope at `Eff Unit Unit` (`Lang/Module.agda:113`); the Spec gives it its own type
  and converts only at the entry. Keep `main` at its type, convert at the entry (also closes S10).
- **R3** the program's own polymorphic names are resolved bare and BEFORE generators and imports
  (`Resolve.agda:224`); the Spec resolves generators, then imports, then definitions, to `canonical [x]`.
- **R4** imported signatures sit at the import's position; the Spec's signature is `Σ₀ ++ Σᵢ` (own first),
  and `sound` asks for `exec … ≡ …`. The compiler adopts the Spec's order.
- **R5** imported modules are only parsed, and the compiler's grammar still accepts string literals, which
  the Spec's grammar does not (string support went with plan 0.106). The parser rejects them.
- **R7** (found 2026-10-21, building the front-end bridge) `main`'s body is checked only at `Eff Unit Unit`
  (`entryType`), never at `main`'s own type: `main : Unit -> Unit; main = tick` with `tick : Act Unit Unit`
  is accepted (`once check`: OK) though the Spec rejects it (the body does not check at the pure type). Fix,
  compiler-side, the Spec's shape (D315): `main` is checked and compiled at its own type `A <: Eff Unit Unit`
  like every definition; the core program's entry converts (`runEntry` along `A <: IOUnit`), and the
  binary's entry calls `main` (`initial ∘ Call main` when `A`'s codomain is `Void`).
- **R6** (to confirm) `Lang.Principal` assumes checking is closed upward along `<:`, unproved; the
  exact-shape generator rules (`c-id`, `c-poly`) are suspects. POC first.
- **R8** (found 2026-10-21, F6) a definition without a signature is compiled from its body CHECKED at the
  type it synthesizes (`ce-mono` → `checkElabV`, `Lang.Module.mono`'s `⊢ᶜ`); the Spec's `w-nosig` takes the
  SYNTHESIZED term. The two differ (a pair literal checks component-wise, a synthesized subterm checked at
  its own type gains `coerce A A`), so the Spec program is not the compiler's translated one and no
  surface-coherence theorem relates them. Fix, compiler-side: a signature-less definition is typed by its
  synthesis derivation (`ModTele.mono-syn`, `⊢ᵢ`) and compiled from it (`realize-infer`). (The other option,
  a Spec `w-nosig` whose term is the body checked at its synthesized type, would be a Spec change.)
- **R10** (found and fixed 2026-10-21, F6) `sigsAdjacent` runs on the RESOLVED declarations, where an import is
  already replaced by its module's signatures: `f : T` / `import M` / `f = …` with `M` exporting no
  `signature` passes (the import vanishes), while the Spec's `Walk` (`w-sig`: the type signature immediately
  followed by its definition) rejects it. Fixed: the resolver keeps the `DImport` where it was written,
  followed by the signatures (`resolveDecls`, `rds-import`). Test: `TypeErrorSpec`.
- **R11** (found 2026-10-21, F2; the `sound` side FIXED) `name@this`: the compiler resolves it for every
  name (`re-this`), the Spec only for `name ≢ main` (`r-this`); and for an own POLYMORPHIC name the
  compiler's `canonical [name]` has no typing rule (its own polymorphic references are bare), while the
  Spec types it (`c-poly`/`d-poly`). Acceptance agrees for `main@this` (both reject), not for `poly@this`
  (Spec accepts — a `complete` gap). For `sound`, F2 must show a TYPED body has neither; either a lemma over
  the typing ("a typed body's references are generators, Σ's, or definitions in scope"), or the resolver
  made to follow `r-this` exactly plus a typing rule for a resolved own polymorphic reference (which
  `complete` needs anyway). Fixed for `sound`: the resolver rejects a body naming `main` or an own
  polymorphic definition by its canonical name (`Lang.ResolvedRefs.GoodRefs`, `rd-fundef`'s premise,
  `Resolve.consDecl`) — acceptance unchanged (the typing rejected both). Open for `complete`: `poly@this`,
  which the Spec accepts (a typing rule for a resolved own polymorphic reference).
- **R12** (found and fixed 2026-10-21, F6) an imported operation's key was built as a STRING,
  `showPath path ++ "." ++ name`, while the Spec's name renders as `showCanonical (canonical (path ++
  [name]))` (and the compiler's own references resolve to that canonical name). The two strings agree when
  run, but Agda proves no associativity of string append, so `toISig Σ ≡ moduleSig` was unprovable. Fixed:
  the owner tag is the imported module's expanded PATH (`DSignature`'s `Maybe (List String)`, `ownerOf`),
  and the key is `showCanonical (canonical (path ++ [name]))` — the same function the Spec and the typing's
  lookup use. Same strings at run time.
- **R13** (found 2026-10-21, F6; OPEN — needs the user's decision) a generator is found by its RENDERED
  name: the compiler types `RResolved c` by `lookupImport sig (showCanonical c)` (`t-var-resolved`) and its
  core `⊢sigop c` by `(showCanonical c , A) ∈ Fs`; the Spec by `(c ∶ t) ∈ Σ`. `sound` therefore needs
  `(showCanonical c , A) ∈ toISig Σ → (c ∶ declS A) ∈ Σ` (`SpecApex.R13`, the one hypothesis left of
  `sound-of`), i.e. `showCanonical` injective on the names that occur; `complete` needs the same fact the
  other way (the extractor's `guardDistinct` compares RENDERED names, so a Spec program's distinct canonical
  names must render distinctly). It is true for lexed names (components are lexer words: nonempty, no
  `.`), but Agda cannot prove it: no property of `primStringAppend` is available
  (`Agda.Builtin.String.Properties` has only `toList`/`fromList` injectivity) — the R12 wall. Options:
  (a) RECOMMENDED: a trust-base postulate `toList (a ++ b) ≡ toList a ++ toList b` (a fact about the
  primitive, like P1 about functions) — then `showCanonical` is injective on word names; plus "word names"
  for the names that occur: from the lexer (Spec `isIdentContinue` has no `.`) through parsing and
  resolution, and on the core side a decidable premise `WordName c` on `t-var-resolved`/`⊢sigop` (never
  failing on a parsed program) or the invariant threaded through elaboration; (b) key the generator tables
  by `CanonicalName` in the front end and core, rendering only at run time — but the guard and the
  codegen's symbol table still compare rendered strings, so (b) does not avoid the injectivity for
  `complete`; (c) render `showCanonical` through `fromList` (provably injective with the builtin
  injectivity primitives) — loses `showCanonical (canonical [x]) = x` definitionally, which many proofs use.
- **R9** (found and fixed 2026-10-21, F5; D327) a reference to a definition required a CONCRETE type
  (`t-var-own`'s `IsConcrete`), so a signature-less definition of non-concrete type (`f = cata …`) could not
  be referred to; the Spec's `s-def` can.

  Spec call whose answer is `void`; `eff` the same, coinductively (`T∞` on both sides).

  `sigop` is the declaration's contract on both sides (`pureAt`/`answerAt`), a `ref` the definitions
