# Plan 0.2.4.5: IR destination passing + Allocator sum type

> **Re-scope note (2026-05-05).** Plan started as "AllocMode semantic
> clarification" with three resolution paths (rename / repurpose /
> drop). Discussion converged on a deeper restructure: drop
> `AllocMode` entirely, introduce destination-passing for IRs, and
> rename `ValueLocation` constructors to mirror the new `Allocator`
> sum type. The Place pass that *decides* destinations is a separate
> sibling plan (0.2.4.6).

## Core principle: IRs are allocator-agnostic

The architectural commitment driving this plan: **CCC IRs do not
know or care which allocator placed their values.** Every IR
primitive (`pair`, `curry`, `apply`, `inl`, `inr`, `In`, `in-ν`,
…) takes a *destination* — a pre-computed `ValueLocation` saying
where to write its output. The IR writes there. End of story.

The destination might point to:

- **A stack slot** (`AtStack frame n`) — frontier-bumped at function
  entry, reclaimed at exit. Today's Layer 0 path.
- **A dynamically-allocated cell** (`AtDynamic ref`) — a pointer
  obtained from a runtime allocator. The allocator can be a malloc
  heap, a mempool, an arena, a region, a bump pool — any backend
  with `alloc(size) → ptr` / `free(ptr)` calling shape.
- **A register** — for `FitsInReg` primitives that ride in a
  register and never get a memory home. (Originally targeted as an
  `InReg` constructor of `ValueLocation`; retired 2026-05-07 after
  cascade issues — see D4 below. Lands instead as a separate
  `Place = AtStorage ValueLocation | InReg AbstractReg` sum type
  used only at result-handle handover points.)

The IR doesn't see the difference. It just dereferences the
destination. This means:

- The same IR primitive serves stack, heap, mempool, arena, region
  — every backend.
- New allocator backends become a Place-pass concern, not an IR
  concern.
- Verification proofs of IR correctness apply uniformly across all
  destination kinds.

`Allocator = Stack | Dynamic` is intentionally binary: the
distinction at the IR level is "frontier-bump (stack)" vs "runtime
call (everything else)". Pool / Arena / Heap / Region all collapse
into `Dynamic` — they share the alloc/free SigOp calling shape;
which allocator gets called is a Place-time decision (which
function symbol to emit), not a runtime/link-time concern.

**Concretely, this plan replaces the per-IR `AllocMode` parameter
(which leaks "Stack vs Heap" as a binary choice into IR signatures)
with a per-IR `ValueLocation` *destination*** — the same dependency
moved upstream of CCC. The Place pass (Plan 0.2.4.6) sits between
the optimiser and codegen, walks each IR, decides each output's
destination, and threads the chosen `ValueLocation` into the IR.
The IR receives that location and writes there. It cannot pick.

```agda
-- Today (AllocMode drift — IR makes the Stack/Heap choice):
⟨_,_⟩ : IR A B → IR A C → AllocMode → IR A (B * C)
inl   : AllocMode → IR A (A + B)
curry : IR (A * B) C → AllocMode → IR A (B ⇒ C)
free-heap : HeapRef → IR A A   -- heap-specific!

-- After this plan (destination-passing — Place makes the choice
-- and threads it in via a ValueLocation):
⟨_,_⟩ : IR A B → IR A C → ValueLocation → IR A (B * C)
inl   : ValueLocation → IR A (A + B)
curry : IR (A * B) C → ValueLocation → IR A (B ⇒ C)
-- (no `free-heap`; alloc/free are SigOps invoked by the Place
-- pass around values whose ValueLocation is `AtDynamic _`)
```

`ValueLocation` is the IR's interface to the placement decision:

```agda
data ValueLocation FS : Set where
  InReg     : Reg → ValueLocation FS                 -- register-resident
  AtStack   : Frame FS → Slot → ValueLocation FS     -- placed by Allocator = Stack
  AtDynamic : MemRef → ValueLocation FS              -- placed by Allocator = Dynamic
```

The constructor encodes the allocator decision. `AtStack` →
frontier-bump-allocated, frame-bound lifetime. `AtDynamic` →
runtime-allocator-allocated, lifetime explicit via Place-inserted
alloc/free SigOps. `InReg` → no allocator, register-resident
(only valid for `FitsInReg` types).

The IR primitive sees only the location and writes there. Same IR
primitive lowers identically regardless of which allocator placed
the destination → one proof obligation discharged once, valid
across stack / mempool / arena / heap / region / any future
allocator backend.

## Audit finding (the trigger)

`AllocMode = Stack | Heap` was supposed to classify each IR's output
allocation location. It drifted into a vestigial layout tag
(boxed/inline) with almost no operational consequence — only
`closure-mode-is-heap-proof` is non-vacuous, and there it means
"boxed two-slot record," not "lives in heap memory." `ValueLocation`
already carries actual physical location.

## Three independent axes (untangled)

`AllocMode` conflated:

1. **Where the value's home is** — register, frame slot, dynamic memory.
2. **What shape the value has** — inline vs boxed (a type-level property).
3. **How it's accessed** — direct read vs deref (a consequence of (2)).

## Input vs output asymmetry

- **Input**: allocation question is moot. Reader; data has a home upstream.
- **Output**: the IR creates a persistent home. Real allocation choice.

## Three output cases (not two)

Not Stack vs Heap. **Register / Stack-allocated / Dynamic-allocated**:

- **Register-resident**: only valid for register-fittable primitives;
  lifetime bounded by next register write. No memory home; rides in a
  register, consumed immediately. Codegen does this implicitly today
  (compose chains); spec doesn't model it.
- **Stack-allocated**: in a frame slot. Lifetime governed by frame-pop
  semantics.
- **Dynamic-allocated**: in memory obtained from a runtime allocator.
  Lifetime governed by explicit alloc/free pairs.

## Goal

Drop `AllocMode` entirely from IR signatures. Replace it with a
**destination parameter** every IR receives — the IR is told where
to write its output, doesn't choose. Couple the spec's
`ValueLocation` to the new `Allocator` vocabulary so location,
allocator, and lifetime model all read the same way.

## Locked decisions

### D1: Drop `IsPrimitive`; introduce `FitsInReg`

`IsPrimitive` currently includes Str / Buffer (which are 16-byte
fat 2-slot records — structurally compound). Reclassify:

- **Unit**: erased — no register, no slot, no value tracked anywhere.
- **`FitsInReg`** = {Int, Bool} — register-fittable value types.
- **Str, Buffer**: compound (2-slot, pair-shaped); reclassified out of
  `IsPrimitive`.
- **Pairs, sums, closures**: compound; live in memory.

One predicate (`FitsInReg`), honest meaning. `IsPrimitive` is dropped.

### D2: Two input registers — `Input1`, `Input2`

Today's `apply-setup-trace` packs `(env, arg)` into adjacent slots
before calling body — two stores + a `lea` per apply, purely to
satisfy "body takes one pointer to a pair." Pure copy waste.

Adopt two input registers:

```agda
data Reg : Set where Input1 Input2 Output : Reg
```

Apply doesn't pack — it sets two registers. Compose still uses
single Output → Input1 by convention. Two suffices for all CCC
primitives (no primitive takes 3+ top-level inputs).

### D3: `Allocator` sum type

```agda
data Allocator : Set where
  Stack   : Allocator    -- frontier-bump, no runtime call, frame-bound
  Dynamic : Allocator    -- runtime call to alloc/free SigOps; explicit lifetime
```

Binary at the IR level. Pool / Arena / Heap collapse into `Dynamic` —
same calling shape (`alloc(size) → ptr`, `free(ptr)`); choice between
them is a Place-time decision (which function symbol to call), not a
runtime/link-time concern.

### D4: Rename `ValueLocation` constructors to mirror Allocator

```agda
data ValueLocation FS : Set where
  AtStack   : Frame FS → Slot → ValueLocation FS    -- placed by Allocator = Stack
  AtDynamic : MemRef → ValueLocation FS             -- placed by Allocator = Dynamic
```

`OnStack` → `AtStack`; `OnHeap` → `AtDynamic`. The names now state
*which Allocator placed the value*, which determines lifetime model.

> **Update (2026-05-07).** The originally proposed third constructor
> `InReg : Reg → ValueLocation FS` was added in Stage E
> (`53c0af52`) and **retired the same day**. Its presence broke the
> `preserves-mem` family of lemmas universally because `readLoc s
> (InReg Output)` shifts under `mov-to-output` (register-write
> changes the read). No consumer ever produced an `InReg` witness.
> The lesson: **`ValueLocation` stays memory-addresses-only**.
>
> Register-residency (Plan 0.2.4.5 D4) lands as a separate
> polymorphic *result-place* type:
> ```agda
> data Place = AtStorage ValueLocation | InReg AbstractReg
> ```
> so memory-only operations (`readLoc`, `writeLoc`, `stackMem`,
> `regs`) keep their `ValueLocation`-typed signatures and
> `preserves-mem` retains its universal form. Result handles
> (`IRResultAWF.result-loc`, `ValidAtWF`'s loc parameter) move to
> `Place` only at handover points.
>
> The same lesson applies to any "value-typed thing" we'd be
> tempted to add to `ValueLocation` (e.g., the speculative
> `TagLit : ℕ → ValueLocation` from the original Plan 0.13.1
> Phase 1 sketch — also backed out for the same `readLoc-writeLoc-
> same` cascade). See `formal/Once/CCC/Machine/SMCore.agda:185-200`
> for the canonical comment.

### D5: No `free` IR — alloc/free are SigOps

Memory allocation/deallocation are runtime function calls. The SigOp
framework already handles runtime calls. So:

- `alloc` SigOp — calls `once_alloc(...)`. Place inserts before each
  Dynamic-allocated value's first use.
- `free` SigOp — calls `once_free(...)`. Place inserts after each
  Dynamic-allocated value's last use.

The IR primitives (curry, pair, apply, …) are unchanged — they just
write to whatever destination they're given. Place orchestrates
alloc/free SigOps around them. The "placed IR" is a regular IR with
extra SigOp nodes; codegen lowers them like any other SigOp.

### D6: IRs take destinations, don't choose

Each IR is parameterised by a destination — a `ValueLocation`
saying where to put its output. The IR doesn't see surrounding
context (lifetime, register pressure, escape) and cannot make the
choice. The choice belongs upstream (Place pass — see 0.2.4.6).

Curry's "I picked slot n" disappears. The caller passes n in.

`AllocMode` ceases to exist as an IR-level concept. The destination
parameter replaces it.

## Open question deferred

Whether the size goes in the alloc SigOp's symbol name
(`once_alloc_16`, `once_alloc_var` — enables 16B mempool
specialisation) or as a data argument (`once_alloc(size)` — uniform
but always runtime dispatch). Layer 0 is stack-only so this question
doesn't materialise; defer.

## Scope for this plan

**In scope (Layer 0 push):**

- Drop `IsPrimitive`; introduce `FitsInReg`.
- Reclassify Str / Buffer out of "primitive" into compound 2-slot
  shape; treat Unit as erased.
- Introduce `Allocator = Stack | Dynamic` data type.
- Rename `ValueLocation` constructors: `OnStack` → `AtStack`,
  `OnHeap` → `AtDynamic`. (`InReg` retired — see D4.)
- Add two-input-register convention; refactor `apply-setup-trace` to
  not pack.
- Add destination parameter to every IR's WF run-* function and
  `IRResultAWF`; remove `AllocMode` from IR signatures.
- Define `alloc` / `free` SigOps (signature only — Layer 0 doesn't
  exercise them at runtime).
- Prove all IR specs for **Stack-allocated** values only.
- Wire the Dynamic plumbing (Allocator constructor, alloc/free SigOps,
  destination parameter accepting AtDynamic locations) but leave
  Dynamic-side proofs to a later layer.

**Out of scope:**

- Place pass (separate plan 0.2.4.6).
- Dynamic-allocator runtime implementations (mempool, malloc).
- Specific allocator-symbol naming policy (size in symbol vs data arg).
- Closure[1] code-pointer pinning (separate plan 0.2.4.4).
- No-frame slot-model alignment (separate plan 0.2.4.3).

## Stage C status: apply-side done, body-side deferred to F

The apply-side (`apply-setup-trace`, `IRToTrace.apply`, the new
`mov-output-to-input2` instruction with per-arch lowerings) landed
in commit `69cbd013` — apply now sets Input1 = env-loc, Input2 =
arg-loc directly without the packed-pair record.

The body-side gap remains. A closure body of type `IR (env-type * A) B`
uses `fst` to read env and `snd` to read arg. At the slot-machine
level, `fst`/`snd` lower to `load-indirect` / `load-indirect-suc`
against the input register, which assumes the input is a *single
pointer to a packed (fst, snd) pair*. After Stage C's apply-side
change, the body's pair input has been "unpacked" into Input1/Input2,
but the body still tries to read it as a packed pair.

Three resolution options for the body side:

  - The abstract semantics gains a "split input" mode and `fst`/`snd`
    lower differently per mode.
  - The body's IR is rewritten so it doesn't use `fst`/`snd` at the
    abstract level — it reads directly from Input1 / Input2.
  - A new abstract instruction `read-input2` (and similar) is added,
    used in place of `load-indirect-suc` for the apply-body case.

Each is a calling-convention design decision. Deferred to Stage F
(destination parameter), where the broader question of "how does an
IR get its inputs" can be resolved uniformly.

For Layer 0 specifically: until the body-side closes, Stage C is
infrastructure-only — the runtime would call body with Input1/Input2
populated, but body's fst/snd would dereference Input1 looking for
a pair record that isn't there. So the runtime impact of Stage C
needs Stage F to actually fire.

## Future stage scoping note

Stage F (destination parameter on IRs) is the substantive shift —
likely a multi-session refactor of `Dispatcher`, every `*WF`
module's `run-*` function, and `IRResultAWF`. Stage E (InReg)
becomes more tractable once the destination model is in place;
register-residency is a kind of destination ("output goes to
register `r`, no memory location").

## Relationship to other plans

- **Parent**: 0.2.4 (Categorical Layer 0).
- **Sibling**: 0.2.4.6 (Place pass) — this plan provides the IR-side
  primitives Place uses; 0.2.4.6 provides the analysis that decides
  destinations.
- **Sibling**: 0.2.4.3 (no-frame slot model) — destination passing
  meshes with no-frame: destinations for Layer 0 are slots in the
  caller's frame. The two plans are orthogonal but compose cleanly.
- **Sibling**: 0.2.4.4 (closure pointer pin) — unaffected at the
  spec level; the `closure[1] = encode-code-addr body-label`
  constraint applies regardless of where the closure record lives.
- **Discharges**: 0.2.4.2 B3 ("AllocMode ignored in curry") — by
  removing AllocMode from IRs entirely.
