# Plan 0.2.4.5: AllocMode semantic clarification

## Context

`Once.CCC.IR.AllocMode = Stack | Heap` was originally intended to
classify each IR's *output allocation location* — Stack-mode IRs
allocate their result in a stack frame slot; Heap-mode IRs allocate in
heap memory. Escape analysis (Once.Escape) was the producer; codegen
(`ir-to-trace`) was the consumer.

A 2026-05-05 audit found the implementation drifted: `AllocMode` has
**almost no operational consequence** in the current spec/codegen.
Specifically:

- `valid-pair-wf` accepts any `m` and lays out `(fst-loc, snd-loc)`
  the same way regardless. Component modes `mA, mB` are tracked but
  never restrict layout.
- `valid-int-wf`, `valid-inl-wf`, `valid-inr-wf` are all `m`-polymorphic
  with no operational distinction.
- The single non-vacuous use is `closure-mode-is-heap-proof`: closures
  must be tagged `Heap`. But the layout is the same fixed two-slot
  record regardless, and `closure-loc` itself is always `OnStack
  frame slot` in the current Layer 0 model.

So `Heap` for closures means "boxed two-slot record" (a *layout*
classification) — not "lives in heap memory" (the original *allocation*
classification). The names lie.

`ValueLocation` already distinguishes physical location:

```agda
data ValueLocation FS : Set where
  OnStack : Frame → Slot → ValueLocation FS
  OnHeap  : HeapLocation → ValueLocation FS
```

A closure with mode-tag `Heap` and `closure-loc = OnStack frame slot`
is **stack-allocated, boxed-layout** — fully Layer-0-compatible with
"no heap allocation."

## Goal

Resolve `AllocMode`'s meaning so it's load-bearing again, then make
"Layer 0 = stack-only allocation" a **type-level invariant** rather
than a documented convention.

## Three resolution paths

### (A) Rename to layout

Acknowledge `AllocMode` is currently a layout tag (boxed/inline).
Rename `Stack → Inline`, `Heap → Boxed`. The closure rule
`closure-mode-is-heap-proof` becomes "closures are boxed." Minimal
change. Layer 0 invariant for "no heap allocation" stays a convention
about `ValueLocation`, not the mode tag.

### (B) Repurpose to allocation location

Drop the layout interpretation. `Stack` means "value's primary location
is in a stack frame", `Heap` means "in heap memory." For closures the
constraint becomes `closure-loc ≡ OnStack _ _` (Layer 0) rather than
`m ≡ Heap`. Layer 0 invariant: every IR returns `m ≡ Stack`. Layer 5+
introduces `Heap` allocations for recursive structures.

This is the *original intent*. Cost:
- Drop `closure-mode-is-heap-proof`; add `closure-on-stack` field to
  `ClosureValidWF` (`closure-loc ≡ OnStack _ _`).
- Update `ApplyWF` and `Dispatcher` to expect Layer 0 closures with
  `m ≡ Stack`.
- Update `IRResultAWF`'s mode tracking to reflect Stack/Heap as
  allocation, not layout.

After (B), "Layer 0 doesn't heap-allocate" is enforced at the type
level: any IR returning `m ≡ Heap` would have to witness `closure-loc
≡ OnHeap _`, which the codegen wouldn't construct for stack-resident
values.

### (C) Drop entirely

Vestigial under (A). `ValueLocation` carries everything informative
already. Just remove `AllocMode` throughout. Cleanest but most edits;
Layer 5+ would need a different mechanism for tracking heap vs stack
results.

## Open question

Decision pending. User's stated preference (2026-05-05): **(B)**, on
the principle of "don't have postulates / vestigial tags hiding
structural information." Path (B) makes "Layer 0 = stack-only" a
type-level assertion that codegen bugs cannot violate silently.

If we adopt (B), the locked decision becomes:

> Layer 0 invariant: every IR's result is allocated in a stack
> frame. The mode tag `m` on `IRResultAWF` reflects this directly:
> `m ≡ Stack` ⇒ `result-loc` matches `OnStack _ _`. Any IR returning
> `m ≡ Heap` cannot be used in a Layer 0 program — caught at typecheck
> time, not at runtime.

## Status

Audit done; resolution pending decision.

## Out of scope

- Layer 5+ heap allocation strategy (real allocator, GC, etc.). This
  plan only resolves the *classification* question for Layer 0.
- Region-typed closures (would type-enforce escape rules — separate
  future direction).

## Relationship to other plans

- **Parent**: 0.2.4 (Categorical Layer 0).
- **Discharges**: 0.2.4.2 B3 ("AllocMode ignored in curry") — by
  giving `AllocMode` actual semantic meaning under path (B), curry's
  pattern-wildcard becomes a type error.
- **Sibling**: 0.2.4.3 (slot alignment), 0.2.4.4 (closure pointer pin).
  Both currently assume the (A)-style "AllocMode is a tag, ignore"
  semantics; under (B), 0.2.4.3 and 0.2.4.4 would gain explicit
  Stack-mode constraints.
- **Discharges (partly)**: the bug-hiding pattern in escape analysis
  — Once.Escape's `AllocMode` outputs become observable invariants
  rather than hint annotations.
