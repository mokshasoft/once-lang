## Why this plan exists

Two things happened on `plan-0.54-rung-d` that a green tree could not have told
us:

- `IRObsCorrectFlat` named `CataNat*` as `cata-correct`'s discharge on
  2026-06-13. On 2026-06-17 commit `5088e571` deleted two thirds of `CataNat*`
  as "dead — no live importers". The comment kept pointing at the amputated
  route for seven weeks. **Reachability said "dead"; content said "owed".**
- `StraightTrace.StraightIR` let `case` and `curry` fall into a catch-all
  claiming `⊤`. The flip made both FALSE. The module sat there proving a false
  statement, in no cluster, silently.

Neither is a defect in a proof. Both are defects in the *inventory*. This plan
fixes the inventory.

## The rule (do not relax it)

> **The test for deleting an island is CONTENT — does it prove something the
> apex only postulates? — never reachability.** A green backstop is silent
> about an island you deleted, so "nothing broke" is not evidence.

Corollary, learned the hard way: **before deleting, grep the reachable tree for
the module's name.** A comment naming it is a claim someone is relying on, and
deleting the module turns that claim into a lie rather than an error.

## Group O — the optimizer correctness chain (8). VERDICT: **W**. The prize.

    RED    Optimize/Correct        289   RED  Optimizer/Normal        1263
    RED    Optimize/Shape          326   RED  Optimizer/IRReducible    627
    RED    Optimizer/Depth         125   RED  Optimizer/PairCaseNormal 381
    GREEN  Optimizer/Cost          110   RED  Category/Laws            549

**The content test passes, and this is the strongest pass in the survey.**

    Once/Optimize.agda:8  -- Each rewrite preserves semantics (see Once.Optimize.Correct).

`Once.Optimize` is LIVE — imported by `Once.Compile`, inside the apex cone, it
runs on every optimizing build. `Once.Optimize.Correct` is a RED ISLAND. And
`Once.Adequacy.Compile` postulates

    opt-trace : ... compileFromModule Heap Build true arch m ≡ Built asm
              → moduleToIR m ≡ just ir
              → ∀ n → exec arch (string-to-bytes arch asm) n ≡ ⟦ just ir ⟧IR ... n

i.e. the `doOpt=true` trace. The `doOpt=false` trace is PROVEN from the codegen
chain. So the optimizer runs, its correctness is assumed at the apex, and the
module the source points at for justification does not compile. This is the
"stale pointer from a live postulate" that motivated this plan, in its purest
form.

**Repair order — one root.** `Optimizer/Normal` -> `Optimize/Correct` ->
`Category/Laws`. `Category/Laws:269` named `arr`, RETIRED by plan 0.52 M2
(ungraded `IRTy` makes `A ⇒[pure] B` and `A ⇛ B` the same object, so the lift
IS `id`); that lemma is deleted (D141) as unstatable and subsumed by `eval-id`.
Behind it stands plain M2 rot — `IRTy !=< Type` at `Laws:36`. **Fix M2 in
`Category/Laws` first; it gates the other seven.**

**Wiring plan.** Repair the chain bottom-up, then discharge `opt-trace` by
composing `optimize-correct` with the existing `trace-false` codegen chain —
the doOpt=true trace becomes the doOpt=false trace transported along
optimize's semantics preservation. Size against plan 0.83's step 2 (the same
M2 migration, on ~2,800 lines). Relates: plan 0.39 (trace-correct optimizer).
