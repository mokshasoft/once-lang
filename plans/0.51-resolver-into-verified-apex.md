# Plan 0.51 — Pull the resolver into the verified apex

## Why (the finding, 2026-06-26)

`resolveImports`/`canonExpr` (Once.Parser.Module.Resolve) — the whole import-
resolution / reference-canonicalization phase — is called ONLY from the Haskell
driver (`Bridge.resolveImports`, `CLI.hs`). The verified apex path is
`src → gmoduleToModule → compileResolvedModule → moduleToIR` and never calls it.
So resolution is TRUSTED, outside the correctness theorem; a resolver change can't
red the apex (proven empirically: a generator cut to `canonExpr` left the apex
green). This BLOCKS the generator/CanonicalName migration from being top-down/
red-driven — the resolver edits are simply invisible to the proof. See
[[project_resolver_outside_verified_loop]].

## The crux

`resolveImports : ModuleMap → Module → String ⊎ Module` needs a `ModuleMap` (the
transitive imports, loaded by Haskell I/O). The apex's `compile`/`⟦_⟧⊥`/`correctR`
is over a single `Source` with NO import environment, so the apex currently only
covers import-free programs (import programs fall out vacuously: imported
primitives are never inlined ⇒ `ModuleTyped` unprovable). Pulling the resolver in
requires the apex to MODEL the import environment.

## Top-down cut (one arc, commit when green)

1. **Parameterize the verified `compile`/`⟦_⟧⊥`/`correctR` by a `ModuleMap`** (the
   import environment). The apex proves correctness GIVEN a (well-formed) ModuleMap
   — the I/O that builds it stays the trusted boundary, but resolution itself
   becomes verified.
2. **Route `compile` through `resolveImports`**: `compile mm arch doOpt src =
   compile-gm … (resolveImports mm (gmoduleToModule src))` (resolve, then the
   existing `compileResolvedModule` path). Flip this; follow the typecheck red
   through `compile-gm`/`compile-mir`/`correct`/`correctR` and the
   `⟦_⟧⊥`/`ModuleTyped`/`⊢R` definitions (which must now be over the RESOLVED
   module). The whole point: a resolver bug now reds the apex.
3. Re-prove `correct`/`correctR`/soundness over the resolved module (the resolver
   becomes a verified stage with its own obligation, like `gmoduleToModule-correct`).

## Then (Plan 0.50 continues)

With the resolver in the loop, the generator-canonicalization cut (stashed:
`canonExpr` → `RResolved (canonical ["Generators", g])`) RED-drives the apex, and
the full CanonicalName migration (generators + the elaborator `RResolved`-dispatch
+ judgment leaves + `named-morph-strong` discharge) is genuinely top-down.

## RE-CORRECTED 2026-06-26: resolver-into-apex IS sufficient (the spec is already independent)

An earlier note claimed the independent spec was a deeper prerequisite. That was
WRONG — verified against the code:
- `ModuleTyped` (AcceptSound) is ALREADY independent: `data AllFunsTyped`'s `tcons`
  carries a `⊢ᶜ` derivation, and the header says "ONLY the judgment `_⊢ᶜ_∶_⨾_` —
  no elaborator function appears" (AcceptSound:80). It is `∃ a derivation`, NOT
  "the elaborator accepts." So `correctR-complete : ⊢R tp → compiles` is NOT vacuous.
- `⟦tp⟧ˢ` (the soundness meaning) is `Once.Denotation.SourceDenote.⟦_⟧ˢ` over the
  intrinsically-typed `Expr` — also independent.

The ONLY reason the generator cut stays green is that the resolver isn't in
`moduleToIR`'s path. The fix is JUST this plan, with one constraint:

**Route `moduleToIR` through `resolveImports`, and KEEP `ModuleTyped` over the
UN-RESOLVED source.** Then `moduleToIR-complete : ModuleTyped m (∃ `⊢ᶜ` over the
unresolved `RVar` bodies) → moduleToIR m (= resolve-then-compile) succeeds` becomes
the **resolver-preserves-typing** obligation. The generator cut makes
resolve-then-compile fail while `ModuleTyped` still holds ⇒ `moduleToIR-complete`
unprovable ⇒ RED. (If `ModuleTyped` is instead moved to the RESOLVED form, it goes
vacuous again — so DON'T.)

No separate independent-spec arc is needed; the spec is there.
