# Plan 0.73 — `Float` follows D054, and the observable says what it means

**Status**: OPEN, written 2026-08-19, rescoped 2026-08-20.
On branch `plan-0.72-float-parameter`.
**Implements D113 and D114.** Corrects the instantiation D112 chose.

D114 joined this plan because it was FOUND by it: asking why a float literal's
target format did not seem to reach the apex theorem turned up the reason —
the observable cannot see a float at all, and `print "hello"` and
`print "goodbye"` have the same `Behavior`. The two are one piece of work.
Widening the observable is what makes the float threading load-bearing instead
of precautionary, and both changes want the same edits in the same ~20 files.

## The change in one line

    Once.Semantics.Machine:
      open import Once.Semantics.Value Carrier Dyadic     -- D112
      open import Once.Semantics.Value Carrier Carrier    -- D113

D112's parameterisation was right; only what it was instantiated at was wrong.
`⟦ Float ⟧` is the target's representation, symmetric with `⟦ Int ⟧`, because
IEEE `fadd` rounds and exact dyadic `+` does not — the same straddle D054
removed for `Int`.

`Dyadic` demotes to the role ℤ has for `Int`: the literal payload and the
parked exact spec. It is what the frontend parses digits into, checks
representability against, and encodes at the target's format.

## A REJECTED predecessor, recorded so it is not retried

An earlier draft of this plan went the OTHER way: make `⟦ Int ⟧ = ℤ` and give
`Int` the exact value level `Float` had. It was implemented as far as the arith
`semM` family before being reverted. It contradicts D054 head-on
("representation follows the promise"), and D054's argument is sound. The
work is in `git stash` if the reasoning is ever revisited; the conclusion is
that it should not be.

Two further wrong turns from the same session, also recorded:

- **Folding `- <literal>` in the ELABORATOR.** Blocked on `canon-reflects-ᵢ`:
  the derivation index mentions `canonExpr e₀`, stuck for a variable operand,
  so `t-neg` and `t-neg-float` cannot be told apart. Do not retry.
- **Justifying "fold `-1.5` but not `-5`" by width-freeness.** That reasoned
  from the implementation, not from the promise. Under D113 both types have the
  same kind of denotation, so any literal policy must be the same for both.

## How this plan is sequenced — TOP-DOWN, and why that is not optional

The first half of this plan (F1/F2, landed) was done bottom-up: the threading
started at `Once.CCC.Eval` and worked upward. That is why the cost estimate
was wrong twice — each layer revealed the next only after it was reached, and
the apex shape (`⟦_⟧ˢ` gaining the arch) surfaced last, when it should have
been the FIRST thing decided.

The rest is done the other way, and the rule is mechanical:

1. **Change the top-level STATEMENT first.** Not a helper, not a vocabulary
   module, not a "foundation". The two statements are `SigOpEvent` (what an
   observation IS) and `CorrectCompiler.⟦_⟧ˢ` (what a program MEANS). Edit
   those, then stop.
2. **Let the typechecker produce the work list.** The red from the apex roots
   IS the plan. Any phase list written in advance — including the one below —
   is a guess that the red supersedes.
3. **Follow the red from the APEX ROOTS ONLY**: `Once/Certified.agda` and
   `Once/Target/{X86-64,X86-32,RiscV64}.agda`. NOT `make check-all`. There are
   28 pre-existing red islands (inventory in HANDOFF) and chasing them is
   exactly the island-building this sequencing exists to prevent. A module that
   only the island backstop reaches is not this plan's business.
4. **Never build ahead of the red.** No extending `readTyped` before a
   correspondence demands the shape. No new module that nothing imports yet.
   No POC — the proof lives in the compiler's real path or it does not exist.
5. **When something cannot be proved, name a RESIDUAL AT ITS USE SITE.** Not a
   standalone postulate module — that is an island wearing a different hat.
   `make postulates` must be able to see it, and the obligation must stay in
   the statement that needs it.
6. **Never narrow a claim to make a correspondence go through.** That is D114's
   whole lesson, and it is now a rule rather than a caution: the `isInt?` gate
   existed on BOTH sides for months, with a comment saying it was there "so the
   two sides can be proven equal."

Two mechanical notes that are already validated — do not re-derive them:

- Threading is an explicit ARGUMENT, never a module parameter. `eval`, `evalᴰ`
  and `⟦_⟧ˢ` are recursive, and a recursive function in a parameterised module
  stops reducing downstream at a variable instance.
- A module already parameterised by `{FS : FrameSemantics}` takes a one-line
  ALIAS instead, and its body is untouched:

      eval : ∀ {A B} → IR A B → EvV.⟦ A ⟧ᴵ → EvV.⟦ B ⟧ᴵ
      eval = Ev.eval (FrameSemantics.float-format FS)

  The signature is REQUIRED; without it the implicits stay unsolved.

## Phases — PART ONE: the model (LANDED)

### F1 — the instantiation
Flip `Semantics.Machine` to `Value Carrier Carrier`; follow the red. Expect it
to concentrate where a `Dyadic` is currently treated as a denotation rather
than a payload: `enc-sv`, `SV-Lit fits-float`, `IR.const`.

### F2 — `Dyadic` becomes the literal payload, and the FORMAT enters the machine

A float literal must reach the target un-encoded, because `1.5` is `0x3FC00000`
at 32 bits and `0x3FF8000000000000` at 64 — unlike a non-negative `Int`
literal, whose pattern is width-free. Precedent: a `Str` literal carries a
`String` to the target the same way.

**Attempting F1 corrected this phase — read before starting.** The first
attempt made the payload type dispatch on the type:

    LitPayload : Type → Set
    LitPayload Float = Dyadic
    LitPayload A     = ⟦ A ⟧

and applied it to BOTH `instr-load-const` and `SV-Lit`. That is wrong for
`SV-Lit`, and the typechecker said so at
`Once/CCC/Machine/SMCore.agda:1543` (`pure-sigop-out-val`):

    ⟦ B ⟧ !=< LitPayload B

**`StoredValue` holds COMPUTED values, not just literals.** A SigOp result
`semM si a` is a denotation — bits. So `SV-Lit`'s payload is `⟦ A ⟧`,
uniformly, and only `instr-load-const` — the instruction that MATERIALISES a
literal — carries source syntax.

Which means executing `instr-load-const fits-float d` must encode, and so the
target's `FloatFormat` must be a parameter of the abstract machine.

**That is not a new kind of thing.** `Once/CCC/FrameSemantics.agda:57` is
already a record of target facts (`frame-base`, `slot-addr`, growth direction)
that the abstract machine is parameterised by and each arch instantiates. The
float format joins them. Do NOT invent a second mechanism.

The payoff is deletion, not addition: with the format available at exec time,
`SV-Lit` is uniformly bits, `enc-sv` becomes the identity at both types, and
`fenc` — the per-arch `Dyadic → ℕ` parameter threaded through the whole
`FlatCore` correspondence — disappears.

**Do this FIRST, before popping the stash.** The stashed WIP contains the
wrong `LitPayload` on `SV-Lit`; put the format in `FrameSemantics`, then pop
and follow the red.

**F2a LANDED** (`0abdfe44`): `float-format` is a `FrameSemantics` field;
x86-64/riscv64 take `binary64`, x86-32 `binary32`. `exec-abstract` encodes.

**F2b LANDED IN PART** (`5c9ca971`): `LitPayload` lives next to `⟦_⟧` in
`Semantics.Machine` (codegen needs it, not only the machine) and is indexed by
the `FitsInReg` EVIDENCE, not by `Type` — a payload only exists for a
register-fittable type, so there is no catch-all. `SV-Lit` is uniformly
`⟦ A ⟧`, exactly as the earlier attempt's refutation said.

### F2c — THE COST D113 DID NOT PRICE IN: the denotation is arch-relative

`Once/CCC/Eval.agda:77` was `eval (const fits-float v) _ = v`. Under D113
there is NO target-free machine value for `1.5`, so the IR evaluator — and
every denotation above it, up to the apex `⟦_⟧ˢ` — cannot give a float literal
a meaning without the target's format.

**Every escape route is closed, and this was checked, not assumed:**

- `Once.Compiler` derives ONE denotation for THREE arches (`⟦_⟧ˢ = VC.⟦_⟧ᵈ`,
  `correct` quantified over `Arch`), so the format cannot be baked into the IR
  `const` node — the same IR must serve `binary32` and `binary64`.
- Nor into a `float.lit.<digits>` SigOp's `semM`: that is a closed function
  and would have to bake a format, one level up with the same problem.
- Nor into the elaborator: same shared-IR argument, and `accept?` is
  deliberately target-blind (it demands representability at EVERY supported
  format, which is not the same as one bit pattern).
- Baking `binary64` in `eval` makes x86-32's float obligations unprovable,
  which kills F5.

So `⟦ Float ⟧ = Carrier` FORCES a target-relative machine denotation. That is
the truth — `emitF 1.5` really does write different bytes on x86-32 — but it
changes the shape of the apex theorem, and D113's consequences section did not
say so. **This deserves its own decision-log entry.**

**Threading discipline, non-negotiable:** an explicit ARGUMENT, never a module
parameter. `eval`/`evalᴰ`/`⟦_⟧ˢ` are recursive, and a recursive function in a
parameterised module stops reducing downstream at a variable instance
(see the `feedback_recursive_fn_opaque_under_module_open` trap). Modules
already fixed to a target (anything `{FS : FrameSemantics}`-parameterised) get
a one-line ALIAS instead — `eval = Ev.eval (float-format FS)` — which leaves
their bodies untouched and is what makes `obs-correct-const`'s float case
`refl`: the machine encodes at the format the denotation means.

## Phases — PART TWO: the framework (the top-down spine)

Written as a spine, not a checklist: G0 is an edit, and G1–G4 are named after
the LAYERS the red will land in, so the red can be filed against them. If the
red disagrees with this shape, the red is right.

### G0 — change the two top-level statements. Then STOP and read the red.

Two edits, no others:

**(a) `Once/Denotation/Trace.agda` — what an observation is.**

    record SigOpEvent : Set where
      constructor mk-event
      field
        ev-name  : CanonicalName
        ev-dom   : Type
        .ev-base : IsBaseType ev-dom
        ev-arg   : ⟦ ev-dom ⟧

    mkEvent si arg = mk-event (name si) _ (baseA si) arg

`isInt?` and `mkEvent-name` are DELETED. They exist only to keep the dispatch
reducing on an abstract domain, and there is no dispatch left. `ev-base` is
IRRELEVANT (the dot) or two events with equal name/domain/value but different
witnesses are not `≡`; it is kept because it is what rules out an `ev-dom`
whose `⟦_⟧` is a function type. `SigOpInfo.baseA` already calls itself
proof-irrelevant, so this is the same claim made enforceable.

**(b) `Once/Adequacy.agda` — what a program means.**

    ⟦_⟧ˢ : Arch → Typed → Behavior          -- was: Typed → Behavior

and `correct`'s soundness conjunct becomes `exec arch bytes ≈ ⟦ arch ⟧ˢ tp`.
This is the honest statement, and it is the mirror of `exec : Arch → Bytes →
Behavior`, which has carried the arch all along: a program's machine-level
meaning is target-relative at `Float`, because `1.5` is `0x3FC00000` at 32 bits
and `0x3FF8000000000000` at 64. It is NOT a weakening — it is one claim per
target where there was previously one claim that could not be true at both.

Then: typecheck the four apex roots, and WRITE THE RED LIST INTO HANDOFF. That
list is the plan. Do not fix anything while producing it.

### G2 — the implementation denotation

### G3 — the machine side

`FlatEvents.machine-event` must now decode `⟦ A ⟧` out of `Input1`:

- **scalars** (`FitsInReg`: `Int`, `Float`) — a register read; `decode-ℕ`
  generalises. These are PROVED, and the float case is what finally makes
  `float-format FS` load-bearing end to end.
- **compound base types** (`Str`, `Buffer`, `*`, `+`) — the register holds a
  POINTER, so the decode is a heap walk (`readTyped`, currently Unit/Int/pairs).
  Where it is not proved, a NAMED RESIDUAL per shape, wired at its use site in
  the arch correspondence. Do NOT extend `readTyped` until the red asks.

The three arch correspondences follow. Anything `{FS}`-parameterised takes the
alias, not a thread.

### G4 — the apex closes — **LANDED (2026-08-20)**

`Once/Certified.agda`, `Once/Target/{X86-64,X86-32,RiscV64}.agda`,
`Once/Spec/Correct.agda` and `Once/Compiler.agda` are ALL GREEN with the
widened observable and the arch-indexed meaning.

Two things the red taught that were not in the design:

**`fmt-eq` — the arch's format is a stated obligation, not a coincidence.**
Each arch's `FlatSimulation` is generic in `FS` while its emitter is concrete
(`encode binary32`/`binary64`). While the core took `fenc` as a parameter both
sides were the same hardcoded function and nothing had to be proved. Reading
the format from `FS` exposed the UNDER-CONSTRAINT, so each arch carries
`fmt-eq : float-format FS ≡ binaryNN` beside `word-eq`, discharged by `refl`.

**`fmt-agree` — the two CHANNELS for the format must be shown to agree.** The
machine reads it from `FrameSemantics.float-format FS`; the apex from
`arch-float-format arch`. Nothing made them the same until it was said.
`FlatFromObs` takes `fmt-agree` and spends it in `ir-flat-correct`. Both are
PARAMETERS, so a disagreement is a type error and neither can be forgotten.

Note what happened to the per-arch obligations: `ArchCorrect.ir-flat-correct`
was `flat-trace mir n ≡ ⟦ mir ⟧IR n` and is now
`⟦ mir ⟧IR (arch-float-format arch) n`. The record was ALREADY arch-indexed,
so the claim SHARPENED without changing shape — each target must now match the
denotation that target means.

### G5 — the observable is real, so the tests mean something

`emitF` now records its argument, so `float-emit-{half,eighth,quarters}.once`
stop merely proving the process does not trap. Extend to negative and computed
floats, on all three arches, in `cabal test` and the exit tests. (This absorbs
the old F5.)

## Phases — PART THREE: the remaining float surface

These are ordinary feature work and follow the framework, not the reverse.

### F3 — negative float literals — **LANDED 2026-08-25 (D124)**

`-3.14` is one literal whose payload is `negate (decimalOf i f l)`, by a new
rule `t-neg-float` and D120's three-way dispatch. Ten external pins in
`Once.Float.Decimal`; `FloatEmitSpec` runs `-0.5`/`-2.75`/`-3.14` on all three
arches; `compiler/test/float-emit-neg-half.once` is the exit test.

**The plan text below was wrong on two counts and D124 records both.** It said
fold in the PARSER — D120 rejected that route for `Int` and the same argument
applies here (at the level of grammar `-` really is a prefix operator; what a
negative NUMERAL means is a fact about the language, so it belongs in the
judgment and the front end bridges). And it framed the fold as the better of
two lowerings, as it was for `Int`; for `Float` it is the ONLY one, because
`MArithIR` is Int-only and `Surface.neg` is Int-typed.

Two limitations are stated rather than left to be found: `-0.0` compiles to
`+0.0` (F4 must change this first), and a negative literal in argument position
needs parentheses (a grammar fact `-5` shares).

The historical text follows.

Whether `Int` folds too is now the same
question for both types and should be answered once. **It was: D120.**

**The landmine this phase would have armed is DEFUSED** (`b2908563`). The
literal denotation was the ABSOLUTE VALUE and the elaborator's `intLit` matched
it, so `-5` would have meant `5` the moment this phase folded `- <literal>`.
Both now use `Once.Word.fromℤ`, and `sub-semM`/`neg-semM`/`add-semM`/`mul-semM`
use the modular ops instead of raw ℕ (monus made `3 - 8` mean 0; negation meant
0). `TraceSpec`'s negative-argument cases pin the behaviour. So F3 can fold
freely — but re-read those tests first, because they are what will catch a
regression.

**And the range question it opens.** All ints are SIGNED, so a w-bit target
holds −2^(w−1) … 2^(w−1)−1. A `Float` literal outside its format is REJECTED
(`accept?`); an `Int` literal is not range-checked at all. Same question, two
answers — exactly what D113's lesson says to look for. The recommendation is
to mirror `accept?` and reject an out-of-range `Int` literal: wrapping
ARITHMETIC is the hardware's promise (D054), but wrapping a LITERAL is a
substitution the programmer never asked for. That is the D054/D059 Int-width
bill and is bigger than this plan — it needs its own decision entry.

### F4 — float negation as an operation
`- x` for a float variable is arithmetic, and belongs where `Int`'s negation
is: the arith path. `MArithIR` is currently Int-only and monomorphic, so this
is the largest phase; `NumType` (`NInt | NFloat`, made width-free earlier on
this branch) is what it should be indexed by.

## Done means

**The model (D113).** `⟦ Float ⟧` mentions no exact value; `Dyadic` appears
only in the frontend and in literal payloads; a float can be written, negated
and used on x86-64, x86-32 and riscv64; and no float obligation carries an
exactness precondition.

**The framework (D114).** A `SigOpEvent` records the argument of EVERY SigOp
it observes, at its base type — so `print "hello"` and `print "goodbye"` are
no longer behaviourally equal, and neither are `emitF 0.5` and `emitF 2.75`.
Where the machine side cannot yet decode a shape, that is a named residual
`make postulates` can see, not a gap in the claim.

**The sequencing.** No module was added that the red did not demand, and no
statement was narrowed to make a correspondence go through. If either happened,
this plan failed even if `Once/Certified.agda` is green.
