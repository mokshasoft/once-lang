# Plan 0.73 — `Float` follows D054, and floats work end to end

**Status**: OPEN, written 2026-08-19. On branch `plan-0.72-float-parameter`.
**Implements D113.** Corrects the instantiation D112 chose.

## The change in one line

    Once.Semantics.Machine:
      open import Once.Semantics.Value Carrier Dyadic     -- D112
      open import Once.Semantics.Value Carrier Carrier    -- D113

D112's parameterisation was right; only what it was instantiated at was wrong.
`⟦ Float ⟧` is the target's representation, symmetric with `⟦ Int ⟧`, because
IEEE `fadd` rounds and exact dyadic `+` does not — the same straddle D054
removed for `Int`.

`Dyadic` demotes to the role ℤ has for `Int`: the literal payload and the
parked exact spec. It is what the frontend parses digits into, checks
representability against, and encodes at the target's format.

## A REJECTED predecessor, recorded so it is not retried

An earlier draft of this plan went the OTHER way: make `⟦ Int ⟧ = ℤ` and give
`Int` the exact value level `Float` had. It was implemented as far as the arith
`semM` family before being reverted. It contradicts D054 head-on
("representation follows the promise"), and D054's argument is sound. The
work is in `git stash` if the reasoning is ever revisited; the conclusion is
that it should not be.

Two further wrong turns from the same session, also recorded:

- **Folding `- <literal>` in the ELABORATOR.** Blocked on `canon-reflects-ᵢ`:
  the derivation index mentions `canonExpr e₀`, stuck for a variable operand,
  so `t-neg` and `t-neg-float` cannot be told apart. Do not retry.
- **Justifying "fold `-1.5` but not `-5`" by width-freeness.** That reasoned
  from the implementation, not from the promise. Under D113 both types have the
  same kind of denotation, so any literal policy must be the same for both.

## Phases

### F1 — the instantiation
Flip `Semantics.Machine` to `Value Carrier Carrier`; follow the red. Expect it
to concentrate where a `Dyadic` is currently treated as a denotation rather
than a payload: `enc-sv`, `SV-Lit fits-float`, `IR.const`.

### F2 — `Dyadic` becomes the literal payload
`IR.const fits-float` carries the source-syntax `Dyadic`; codegen encodes it at
the target's format. A float literal must reach the target un-encoded because
`1.5` is `0x3FC00000` at 32 bits and `0x3FF8000000000000` at 64 — unlike a
non-negative `Int` literal, whose pattern is width-free. Precedent: a `Str`
literal carries a `String` to the target the same way.

### F3 — negative float literals
With `Dyadic` a payload rather than a denotation, `-1.5` is a literal whose
payload is `negate d`. Fold in the PARSER (`parseUnaryWF`), not the elaborator
— see the rejected route above. Whether `Int` folds too is now the same
question for both types and should be answered once.

### F4 — float negation as an operation
`- x` for a float variable is arithmetic, and belongs where `Int`'s negation
is: the arith path. `MArithIR` is currently Int-only and monomorphic, so this
is the largest phase; `NumType` (`NInt | NFloat`, made width-free earlier on
this branch) is what it should be indexed by.

### F5 — the tests run end to end
`emitF` with negative and computed floats, on all three arches, in
`cabal test` and the exit tests.

## Done means

`⟦ Float ⟧` mentions no exact value; `Dyadic` appears only in the frontend and
in literal payloads; a float can be written, negated and used on x86-64,
x86-32 and riscv64; and no float obligation carries an exactness precondition.
