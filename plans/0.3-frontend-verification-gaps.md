- **2026-04-19**: **Task #39 CLOSED — OCP-0003 view postulates
  eliminated + downstream correctness proofs.** Committed as
  `eb76fdcd`. 12 of 13 originally-scoped postulates removed; the
  13th (`_≟IR_` in `Once.Optimize`) is orthogonal and tracked as
  task #41.

  Key technique: **generic-codomain + equality-proof trick**.
  ```agda
  pair-split-gen : ∀ {A B'} (f : IR A B') → ∀ {B C} → B' ≡ B * C
                 → Maybe (IR A B × IR A C × AllocMode)
  pair-split-gen (⟨ f , g ⟩ m) refl = just (f , g , m)
  pair-split-gen _ _ = nothing
  ```
  Parameterising over a free `B'` + taking the codomain constraint
  as an explicit equality sidesteps Agda's stuck unification on
  `⟦ F ⟧T (μ-type F) ≟ B * C` for abstract F. Stuck-unification
  constructors (`out-μ`, `Out`, `Cata`, `Para`, `Ana`, `Hylo`,
  `Fuse`, `Prim`, `In`, `in-ν`) are handled via `subst (IR _) eq` in
  the catch-all branch — no `refl` match, no unification obligation.

  Downstream `Correct.agda` proofs (4 in Optimize, 2 in Escape, 1 in
  Fusion) became structural proofs using recursion-scheme congruence
  lemmas: `cong` over `sem-cata` / `sem-para` / `sem-ana` /
  `sem-hylo` / `sem-fuse` with explicit lambda lifting so `cong`
  operates on the function-equality proof.

## Context

The frontend pipeline (parser → typechecker → surface elaboration → IR)
has significant formal verification coverage today, but the coverage is
uneven. Plans 0.2.5 and 0.2.6 landed:

- Intrinsic typing: `inferElab` produces `SExpr Γ Ψ A` — Agda's type
  checker rejects any code path where the output's type index is wrong.
- Linearity-by-construction: `lam q refl body` requires a propositional
  `(q' ≤q q) ≡ true` witness at every lambda site. No term that
  violates its declared arrow grade is constructible.
- Semantics preservation through surface elaboration:
  `Surface.Correct.elaborate-correct : evalSurface ρ e ≡ eval′ (elaborate e) (interpEnv ρ)`.
- Zero postulates, zero `TERMINATING` pragmas in the type-checker
  pipeline (structural termination on `RawExpr` throughout).

That's strong for the properties that are actually proved. But several
important correctness properties of the frontend are **not proved and
not tested**. This plan enumerates those gaps and sketches a proof
strategy for each.

The intent is to close these via formal proof rather than property-based
testing (QuickCheck). The existing verification is strong enough that
adding QuickCheck would mostly duplicate guarantees intrinsic typing
already gives, and the few things QuickCheck would genuinely add are
exactly what these proofs will cover.

## Scope

Everything in `formal/Once/Parser/`, `formal/Once/TypeCheck/`, and
`formal/Once/Surface/`. The IR backend (`formal/Once/CCC/`,
`formal/Once/Escape`, `formal/Once/Fusion`) is out of scope for this
plan — those have their own separate verification tracks.

## The Gaps

### G1: Parser correctness (lexer + parser)

**What's unproved**: the parser is zero-proofs. It's Agda code but it
has no statement of what it's supposed to do, no parse-pretty roundtrip,
no proof that the CFG it implements matches the grammar in
`Once.Grammar`.

**What could go wrong**:
- Silent misparsing (syntactically malformed input accepted as
  something the user didn't intend).
- Ambiguity — the parser accepts a program but elaborates it differently
  than the programmer reads it.
- Missing reject cases — a grammar-invalid token stream parses to a
  `Just` result.
- Drift between `Once.Grammar` (the aspirational spec) and
  `Once.Parser.*` (the implementation).

**Proof strategy**:

1. **Wire `Once.Grammar` to the parser as its output type.** Currently
   `parseType : List Token → Maybe (Type × List Token)`. Change to
   `parseGType : List Token → Maybe (GType × List Token)`. Then add
   `gtype-to-type : GType → Type` conversion (partial, since Grammar
   allows type variables that `Type` rejects after 0.2.5).
2. **Parse-pretty roundtrip**: `parse (pretty g) ≡ just (g , [])` for
   every well-formed `GType`, `GExpr`, `GModule`. Proved by structural
   induction on the grammar types.
3. **Pretty-parse roundtrip**: if `parse toks ≡ just (g, [])` then
   `lex (pretty g) ≡ toks` (modulo whitespace normalization). This
   pins the parser's extensional behavior.
4. **Unique parses**: `parse toks ≡ just (g₁, r₁) ∧ parse toks ≡ just
   (g₂, r₂) ⟹ g₁ ≡ g₂ ∧ r₁ ≡ r₂`. (Trivial since `parse` is a total
   function but stated for clarity — rules out future refactors that
   introduce ambiguity via backtracking choices.)
5. **Grammar conformance**: define `WellFormed : List Token → Set` as
   a grammar predicate, prove `WellFormed toks ⟺ ∃ g. parse toks ≡ just
   (g, [])`. This is the completeness + soundness of the parser
   against the grammar spec.

**Entry cost**: ~600 lines of Agda. `Once.Grammar` needs extending with
pretty-printing; parser-stages need proofs chained through `_>>=_`/`_>>_`.

**Dependencies**: 0.2.6 (surface syntax shapes are finalized).

---

### G2: Typechecker completeness

**What's unproved**: intrinsic typing gives "every accepted program is
well-typed". The converse — "every well-typed program is accepted" —
is unstated. A subtly-wrong typechecker could reject correct programs.

**What could go wrong**:
- A case in `checkElab` falls through to `failure` for some well-typed
  shape the author didn't consider.
- The `_≟T_` decidability is fine, but we pass it the wrong types in
  some code path (e.g., comparing before-substitution and after-
  substitution forms where we should compare matching phases).
- After the 0.2.6 refactor, polymorphic builtins only specialize in
  specific pattern-matched shapes (`checkElab ctx (RVar "compose")
  (...) = ...`). A well-typed but slightly-different shape
  (e.g., `compose` applied fully at surface but split across a let)
  might fall through to the generic path and fail.

**Proof strategy**:

1. **Define the declarative typing judgment**: `Γ ⊢ e : A ; Ψ` as an
   inductive relation on `(Ctx n) × RawExpr × Type × Usage n`. Rules
   mirror the Expr constructors one-for-one (plus substitution and
   signature-specialization rules for polymorphic builtins).
2. **Completeness theorem**:
   `Γ ⊢ e : A ; Ψ → ∃ eE d f. inferElab (ctxOf Γ) e ≡ success A Ψ eE d f`
   (and similarly for `checkElab`).
3. **Soundness theorem** (strengthens what intrinsic typing gives):
   `inferElab ctx e ≡ success A Ψ eE d f → (ctxOf⁻¹ ctx) ⊢ e : A ; Ψ`.
4. **Decidability**: `(Γ, e) → Dec (∃ A Ψ. Γ ⊢ e : A ; Ψ)` — says
   that typeability is decidable, and the typechecker's decision
   matches the judgment.

**Entry cost**: ~800 lines. The declarative judgment is ~20 rules;
completeness proof walks each rule against the `inferElab`/`checkElab`
structure. Builtin-specialization rules are the trickiest part.

**Dependencies**: 0.2.6 (usage-indexed Expr means the judgment is
usage-indexed too).

---

### G3: Robustness / crash freedom

**What's unproved**: there's no statement that `inferElab` is total.
Termination is proved (structural on `RawExpr`). But "total" means
more: no partial patterns, no stuck terms, defined on all inputs.

**What could go wrong**:
- A pattern match we thought was exhaustive isn't (Agda would normally
  reject but some pragmas/underscores can hide this).
- A helper uses `Maybe` in a way where a subtle path reaches an
  unreachable `nothing`.

**Proof strategy**:

1. **Totality is already proved implicitly** — Agda's coverage checker
   demands total pattern matches, no TERMINATING means structural
   recursion. So `inferElab : (ctx : NamedCtx) → RawExpr →
   InferElabResult (NamedCtx.debruijn ctx)` is already a total function
   with no exceptions and no diverging inputs.
2. **What IS missing**: a statement of the form "for every `(ctx, e)`,
   `inferElab ctx e` is either `failure msg` or `success A Ψ eE d f`
   where that `success` is well-typed and respects linearity". This
   is a combined totality + well-formedness theorem.
3. **Strategy**: state and prove
   `(∀ ctx e. Σ err. inferElab ctx e ≡ failure err) ⊎ (∀ ctx e. Σ A Ψ
   eE d f. inferElab ctx e ≡ success A Ψ eE d f)`. Case split on
   RawExpr; structural induction.

**Entry cost**: ~200 lines. Mostly mechanical since totality is
already there implicitly; the proof just makes it explicit and pairs
with well-formedness.

**Dependencies**: G2 (soundness), useful building block for it.

### G4: Error message quality

**What's unproved**: `failure : String → InferElabResult Δ`. The
string can be anything. A regression that replaces
`"Parameter 'x' used with quantity Many but declared with quantity One"`
with `"failure"` would not break any test.

**What could go wrong**:
- Error messages drift into unhelpful "internal error" language.
- Different input shapes produce identical messages, hiding what's
  actually wrong.
- Downstream tools (IDE, LSP) that want to consume structured errors
  have no stable contract.

**Proof strategy**:

1. **Introduce a structured error type**:
   ```
   data TypeError : Set where
     UnboundVariable  : String → TypeError
     ExpectedFunction : Type → TypeError
     ArgumentMismatch : (expected actual : Type) → TypeError
     UsageViolation   : (declared actual : Quantity) (name : String) → TypeError
     ...
   ```
2. Change `failure : String → ...` to `failure : TypeError → ...`.
   Strings become `formatError : TypeError → String`.
3. **Error-preservation theorem**: prove that each failure path of
   `inferElab`/`checkElab` reaches the specific `TypeError` variant
   appropriate to the shape of the rejection. E.g.,
   `inferElab ctx (RVar x) ≡ failure err → lookupLocal ctx x ≡ nothing
   → err ≡ UnboundVariable x`.
4. **Message uniqueness**: `failure err₁ = failure err₂ → err₁ ≡ err₂`
   (trivially refl). Combined with (3), every rejection has a canonical
   structured form.

**Entry cost**: ~400 lines. Larger because every failure site needs
the right constructor; then a theorem per case tying rejection
condition to error shape.

**Dependencies**: none, but G2 makes the rejection side well-specified
via the declarative judgment ("rejects ⟺ no derivation exists"),
which is where the error-shape theorems would live.

### G5: Integration correctness at stage boundaries

**What's unproved**: each stage has (some) local proofs, but
cross-stage invariants aren't stated. E.g., "if the parser returns
`just g`, then the `RawExpr` derived from `g` satisfies the precondition
of `inferElab`".

**What could go wrong**:
- Parser produces a `RawExpr` that the typechecker can't handle due to
  a shape invariant the parser failed to enforce (e.g., empty RLet body
  list, multi-line construct where the typechecker assumes single-line).
- Elaboration assumes the typechecker's output satisfies some
  invariant (e.g., no free TVars) that the typechecker doesn't
  explicitly guarantee.

**Proof strategy**:

1. **Compose soundness/completeness at each boundary**. With G1 and
   G2 in place:
   `parseModule source ≡ just mod → ∀ decl ∈ mod.decls.
    ∃ Γ. Γ ⊢ decl : wellFormed`.
2. **Chain pipeline theorem**:
   `parseModule source ≡ just mod → compileModule source ≠ internalError`.
3. This makes the pipeline guarantees end-to-end for valid source.

**Entry cost**: ~200 lines, assuming G1 and G2 are done. Mostly
stitching existing theorems.

**Dependencies**: G1, G2.

---

### G6: Typechecker determinism

**What's unproved**: nothing says `inferElab ctx e = inferElab ctx e`
(reflexively — but structurally, e.g., the same result constructor with
the same fields).

**What could go wrong**:
- Pure in Agda by construction. Low risk.
- But the `freshCounter` threading could diverge between paths that
  should be equivalent.

**Proof strategy**:

1. `inferElab-deterministic : ∀ ctx e. inferElab ctx e ≡ inferElab ctx e`
   — trivially `refl` in Agda since `inferElab` is total and pure.
2. Stronger: `inferElab-congruence`: if we change context in a way
   that doesn't affect free variables of `e`, the result is isomorphic.
   Stated via a permutation or isomorphism on `InferElabResult`.

**Entry cost**: ~50 lines. Mostly a trivial theorem + a more
interesting congruence statement.

**Dependencies**: none. Cheap to land standalone.

---

### G7: Algebraic identities of frontend operations

**What's unproved**: properties like "re-typechecking an already-elaborated
program is a no-op at the IR level", "`elaborate` commutes with
substitution", etc.

**What could go wrong**: optimization passes or future IR transforms
might assume an algebraic identity that isn't formally guaranteed,
leading to silent correctness bugs.

**Proof strategy**:

Define and prove the identities we rely on:

1. `elaborate` is injective: `elaborate e ≡ elaborate e' → e ≡ e'`.
2. `inferElab`/`checkElab` agree on shared programs:
   `inferElab ctx e ≡ success A Ψ eE d f →
    checkElab ctx e A ≡ success Ψ eE d f`.
   (The reverse isn't quite true because check mode has specialized
   paths; the right statement is that the expressions agree modulo
   specialization.)
3. Elaboration is stable under weakening:
   `elaborate (weaken e) ≡ weakenIR (elaborate e)`.

**Entry cost**: ~400 lines. Each identity is a structural induction
on the relevant datatype.

**Dependencies**: G2 (soundness) useful for stating (2) cleanly.

---

### G8: Performance bounds (NOT IN THIS PLAN)

**What's unproved**: nothing says `inferElab`'s runtime scales
linearly with program size. A performance regression (accidental
exponential) wouldn't break any proof.

**Why not in this plan**: formal proofs of runtime complexity in Agda
are possible but ergonomically painful. Better tracked via
benchmarking (independent of this plan). Mentioned for completeness.

**Strategy if pursued**: instrument `inferElab` with a step counter,
prove the counter is bounded by the structural size of the input.
This changes the function signature and cascades through every
theorem. Not worth it unless we hit a performance regression that
demands it.

## Phase Ordering

Recommended order (by dependency + value):

1. **G6 (Determinism)** — cheap, standalone, low-risk warmup.
2. **G3 (Totality)** — explicit statement of what the coverage checker
   gives us implicitly. Building block for G2.
3. **G2 (Completeness)** — the big one. Declarative judgment + sound/
   complete theorems. Unlocks G4 and G5.
4. **G4 (Error messages)** — structured errors, per-rejection theorems.
5. **G1 (Parser correctness)** — wire Grammar.agda, prove roundtrips.
   Independent of G2–G4; can be done in parallel if we have bandwidth.
6. **G5 (Integration)** — stitches G1 and G2 across the boundary.
7. **G7 (Algebraic identities)** — opportunistic; depends on G2's
   judgment to state cleanly.

## Why Not QuickCheck

A brief defense of the choice to skip property tests in favor of
proofs:

**Bugs QuickCheck could find that these proofs also catch (redundant)**:
- Type-correctness of output → intrinsic typing catches at Agda compile
  time (already does).
- Linearity violations → linearity-by-construction catches at compile
  time (already does).

**Bugs QuickCheck could find that these proofs newly catch (more rigorous)**:
- Parser misparsing → G1 rules out by proof.
- Silent rejection of well-typed programs → G2.
- Degraded error messages → G4.
- Cross-stage integration bugs → G5.

**Bugs QuickCheck catches that these proofs do not**:
- Performance regressions → G8 (deferred).
- Platform-specific behaviors of MAlonzo-compiled code → outside formal
  scope.

Nothing in QuickCheck's value add overlaps with what the planned
proofs cover. Once these are done, QuickCheck would genuinely be
redundant for frontend correctness.

Performance regressions are the one real gap that neither proofs nor
QuickCheck catch. Benchmarking and CI timing checks cover that
dimension and are orthogonal.
