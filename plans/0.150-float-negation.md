# Plan 0.150 — Negation, and the operators of the number types, the same for Int and Float

## Summary

A program can write `-1.5` and `0.0 - x` for a floating-point `x`, but not `-x`, and `<` works on `Int`
only. Negation and comparison of `Int` and `Float` are defined by separate rules that drifted apart. Plan
0.147 has already decided how numbers should look (which laws each operator carries, and separate dotted
operators for IEEE arithmetic). This plan makes negation symmetric for the two types, makes a negated
number a literal for both, and fixes `-0.0`, which today means `+0.0`. §4 lists the decisions, including
how much of 0.147's number design to do now.

## 1. Why

**The drift.** The Spec's typing (`formal/Once/Spec/Surface/Typing.agda`) has one rule per (operator,
type) pair, each written by hand:

| Operator | Int | Float |
|---|---|---|
| `-e` | `s-neg`: any operand, `prim p-neg` | `s-neg-float`: a literal only, folded (D124) |
| `+ - * /` | `s-arith` over `IntArith` | `s-arith-float` over `FloatArith`, plus `-il`/`-ir` for an `Int` operand (D125) |
| `%` | `s-arith` (`ia-mod`) | none (D128: no float meaning) |
| `< <= > >= == /=` | `s-compare` (`Int * Int` only) | **none** |

D124 limited float negation to literals because float arithmetic had no lowering. Float arithmetic got one
(D128) and its rules, but negation and comparison were not revisited, because nothing ties them to the
arithmetic. Seven rules carry the numeric operators, and nothing makes them cover the same types.

**The literal fold is wrong at zero.** `s-neg-float` folds `-i.f` to the literal `negate (decimalOf i f
l)`, a `Decimal` whose significand is `ℤ` (`Spec/Float/Decimal.agda:61`). `ℤ` has no `-0`, so `-0.0`
folds to `0 /10^ 1`, and `round` gives `+0.0` (`Decimal.agda:255`, the sign bit is `signBit (sig d)`).
IEEE 754 says `-0.0` is negative zero. Negation as an operation does not have this problem: the Spec's
`fneg` (`Spec/Float/Arith.agda:372`, a sign-bit flip, "not a decode/round round-trip … would collapse
`−0` to `+0`") is right at zero and on NaN. It is defined and has no caller.

**Int is already the principled shape.** `-5` is `prim p-neg (lit 5)` in the Spec. Only the target-fit
check reads it as the literal `-5` (`negLits`, `Spec/Source.agda:102`, so `-9223372036854775808` fits). The
elaborator's `checkElabV-neg-int-aux` builds exactly `neg (int n)`.

## 3. What plan 0.147 already decided (read 2026-11-12)

Plan 0.147 (data types and lawful structures, decisions by the user 2026-11-03 to 2026-11-06) settles the
frame this plan works in. Its decisions are not yet D-entries, and no Spec patch has been made:

- **Structure belongs to the type** (§3.5.2): a type declares the theories it models; an operator symbol
  resolves through its operand's type to that declaration. No instance search, one candidate per type.
- **A symbol carries its theory's laws** (§3.5.3): `+ - 0` is an abelian group, `< <= > >= compare` a total
  order, `==` is always `χ_Δ` (the classifier of the diagonal).
- **`Int`** (§3.6) is a commutative ring and, separately, a total order (not an ordered ring).
- **`Float`** (§3.6):
  - `==` is identity (`χ_Δ`), with a **warning when `==` is written directly at `Float`**; generic uses do
    not warn.
  - `<` and `compare` are IEEE `totalOrder` (`−0.0 < 0.0`, NaNs at the ends).
  - IEEE comparison and arithmetic have their own symbols: `==. <. <=. >. >=.` and `+. -. *. /.`, plus
    `isNaN`. IEEE `+` is not associative, so it cannot carry `+`'s laws.
  - The theory is RoundedField. NaN results are canonical (one quiet NaN on every target, D113 amended).
- **Step 8** of 0.147 is "Numbers": canonical NaN, the IEEE operator family, Float's `==` and
  `totalOrder`, the direct-`==` warning.

So today's `0.0 - x` at `Float` (undotted `-`) is not the target surface. Under 0.147 it is `0.0 -. x`.
The `Num` table this plan first proposed is the built-in fragment of 0.147's "a type declares the theories
it models".

## 4. Decisions

All decided by the user 2026-11-12 (N6 reopened and re-decided the same day).

- **N1, where this work lives. Decided: plan 0.150 owns the numbers.** 0.147's numbers (its §3.6
  decisions, Spec item §6 (4), step 8, the `Float` done-when) move here; 0.147 keeps §3.6 as the record
  and its step 6 (structure declarations) later expresses this plan's built-in table for `Int` and
  `Float` without changing what the operators mean. Alternatives not taken: a narrow 0.150 that 0.147
  redoes (two designs), or doing nothing until 0.147 step 8.
- **N2, the mechanism for "type → theories". Decided: a closed Spec table** for the built-in types (total
  functions per theory, so a missing operator does not compile), shaped as the instances 0.147 step 6 will
  let a declaration state.
- **N3, which theory owns unary negation. Decided: (b)** (the user, 2026-11-12). 0.147 groups `+ - 0` as
  the abelian group; it does not say where unary `-` sits for a type that is not a group.
  - (a) `-x` belongs to the abelian group: `Float` has none, so Float negation is `-.x`, beside `+. -.`.
  - (b) Unary `-` is its own theory, `Neg`, contained in both richer theories (a theory inclusion, as a
    group's signature contains its inverse). `Neg`'s own law is the involution `-(-x) = x`; each theory
    that contains it adds its own law relating `-` to the rest:
    - AbelianGroup (`Int`): `x + (-x) = 0`, and `x - y = x + (-y)`.
    - RoundedField (`Float`): negation is **exact**: it is the image of real negation (`⟦-x⟧ = -⟦x⟧` on
      finite values, and a sign flip on zeros, infinities and NaN), so it commutes with rounding
      (`round(-r) = -round(r)`, round-to-nearest-even is symmetric); and `x -. y = x +. (-y)` (IEEE
      754 defines subtraction this way; the Spec's `fsub` already is `addV … (negV …)`).
    - Laws that hold exactly at both types and could sit in `Neg` itself: `-(x * y) = (-x) * y` (`*.` at
      `Float`: the sign of a product is the xor of the signs). Laws that fail and must not: order reversal
      (`-minInt = minInt` at `Int`), `-(x + y) = (-x) + (-y)` at `Float` (`x +. (-x)` is `+0`, so
      the zero's sign differs).
  - Why no dot: 0.147 dots an operator because rounding breaks the undotted symbol's laws. Negation does
    not round, so `Neg`'s law holds at `Float` with the plain symbol; a dotted `-.x` would mark a loss
    that does not happen.
  - Decided: (b), with `Neg` = involution plus `-(x * y) = (-x) * y`. It refines 0.147 §3.5.3; recorded
    as a D-entry in step 7. Not taken: (a), `-.x`.
- **N4, a negated literal is a literal, at both types, the same way. Decided: in the grammar** (where a
  literal is a syntactic form). `-` immediately before a numeral, in unary position, parses to a signed
  literal (`RInt (-n)` / `RFloat` negative), so `RNeg` never wraps a literal. The typing has one rule per
  form, and `negLits` and `s-neg-float` go. `x - 5` is binary (the add-tail parses it first). `f -5` is
  also `f - 5` (`ArgStart` has no `-`, OCP-0002 writes `f (-5)`); it is a type error whenever `f` is a
  function, since a function is not a number, and is subtraction when `f` is a number. Not taken: making
  `f -5` an application by whitespace (`x -5` with `x : Int` would then become an application and fail);
  typing rules (two derivations of `-5`); signed numerals in the lexer (`x -1` ambiguous).
- **N5, `-0.0` in source. Decided: rejected** ("no reason to allow `-0.0` in source"). A negative float
  literal whose value is exactly zero (`-0.0`, `-0.00`, `-0e5`) is a type error that names the rule; the
  literal's `Decimal` keeps `sig : ℤ`, which can now represent every literal the source admits. Negative
  zero is still a value: `-x` at `x = 0.0` is `fneg`, a sign flip, and so is `-(0.0)` (a parenthesised
  operand is not a literal under N4 (a)). A literal that is not zero but rounds to zero (`-1e-400`)
  rounds to `-0.0`, as IEEE says, since its `sig` is negative. (Not taken: a sign bit beside an unsigned
  significand.)
- **N6, negation and NaN. Decided: (a), `Float` is IEEE level 2** (the user, 2026-11-12, after step 1
  found the first premise wrong). The Spec already has
  one canonical NaN (D055/D113, `Spec/Float/Arith.agda:141`; x86 canonicalises after every operation),
  and its unused `fneg` flips a NaN's sign on the bit pattern, so as written it would make a second,
  observable NaN. The collision is a confusion of IEEE 754's levels (§3.2): level 2, *floating-point
  data*, has signed zeros, ±∞ and **one** NaN; sign and payload of a NaN exist only at level 3/4
  (representations, bit strings). The Spec mixes them: `FloatVal` (`Arith.agda:123`) is almost level 2
  (one signless `fv-nan`) but has no `-0` (`Bin`'s `sigB : ℤ`), while `Float` values are words and `fneg`
  works on the word.
  - (a) The Spec's `Float` is level 2: `FloatVal` gains signed zero, every operation is defined on it,
    and the word is only the encoding, at the boundary where bits are observed. Negation is then one
    structural rule (flip the sign of whatever has one; NaN has none, as `0` has none in `ℤ`), the
    canonical NaN stops being a rule of arithmetic (it is `encode fv-nan`, the only encoding of the one
    NaN), and signed-zero results (`-1.0 *. 0.0`, `1.0 /. -0.0`) follow IEEE by construction.
  - (b) Keep words as `Float`'s values, give `FloatVal` signed zero, and define `fneg` like every other
    operation, `encode ∘ negV ∘ decode`. One rule too, but the carrier keeps non-canonical NaN words
    that no program can reach.
  - (c) The earlier proposal (sign flip, except NaN ↦ canonical NaN): two rules. Not taken.
  - Decided: (a). Step 1 measures its reach (Core meaning of `Float`, the backends' relation of words
    to values) before the step 2 patch. D113 is restated: one NaN is a fact of the value set, and the
    canonical NaN is its encoding.
- **N7, comparison at `Float`. Decided: in this plan.** By 0.147: `<` and `compare` are `totalOrder`, `==`
  is identity with the direct-use warning, and `==. <. <=. >. >=.` are IEEE.
- **N8, the dotted arithmetic and today's programs. Decided: switch now.** `+ - * /` at `Float` are
  rejected with an error that names the dotted operator; the corpus and tests are rewritten to
  `+. -. *. /.`. No transition period accepting both.
- **N9, `Int` widening into `Float` (D125) under the dotted operators. Decided: kept.** The dotted
  operators widen an `Int` operand, as `+` does today (`1 +. 2.5`).
- **N10, the implementation's front end. Decided (2026-11-13): the table form.** The implementation's
  typed surface syntax (`Once/Surface/Syntax`) carries the Spec's signature: one `num : Has A U → Sym U k
  → …` replaces `add … ne`, `fadd … fdiv`, `neg`, so a numeric term is a symbol interpreted in a model,
  as in the Spec's Core. Elaboration maps `num h o` to `num h o`, and soundness has no per-operator case.
  The lowering to the backend's per-instruction primitives (`Arith.Prim`) is ONE function, the one place
  where the per-model presentation is the truth (`add` and `addsd` are different instructions). Not
  taken: per-operator constructors (the correspondence to `num h o` re-proved per constructor in every
  pass); the table also in the IR and the arith compiler (the largest cascade, into the machine proofs).
  The machine keeps `Float` as words: `Once/Float/Word` gives each operation as `encode ∘ op ∘ decode`
  (negation the sign-bit flip), and the bridges to the Spec read a word by `decode`.

## 6. Done when

- `-x` is one rule over the table, and works at `Int` and `Float`; its laws are proved for both models.
- A negated numeral is a literal at both types, built by the grammar; no rule or function special-cases
  a negated literal; `-0.0` is rejected and negative zero is reachable by `fneg`.
- `Float` has `totalOrder` `<`, identity `==` (with the direct-use warning), the dotted IEEE arithmetic
  and comparison, and one NaN (its value set is IEEE level 2) on every target; undotted `+ - * /` at `Float` are rejected with an
  error naming the dotted operator; `1 +. 2.5` widens.
- Every numeric operator is typed through the table, and a built-in type missing an operator its
  theory requires does not compile.
- The corpus uses the dotted operators; the gates pass; the records of step 7 exist.

Review points (choices made in the draft that the decisions did not fix):
- R1. Subnormals: the value set has them (level 2 of a format does, and every target produces them),
  which supersedes D118's underflow-to-zero, for literals too (`1e-40` at binary32 is now glibc's
  `0x000116c2`).
- R2. A world value (an Interpretation's float) is a `FloatVal` read at the format by `fitV` (rounded,
  like `norm` for `Int`), not a word; its bits exist only in `ABI.Layout`.
- R3. totalOrder puts the one NaN above `+∞` (it is the positive canonical NaN).
- R4. `!=.` is included beside 0.147's `==. <. <=. >. >=.`; `isNaN` is not a primitive (`x !=. x`).
- R5. Widening (D125, N9) applies to every dotted operator, the comparisons included (`1 <. 2.5`); a
  dotted operator with two `Int` operands is rejected.
- R6. Tokens lose whitespace, so `- 5` (with a space) is also the literal `-5`, and `- 0.0` is rejected
  like `-0.0`; `-(0.0)` is the negation.
- R7. 0.147's RoundedField error bound is not stated (it needs the reals). `-(x*y) = (-x)*y` sits in the
  Ring and Rounded laws, not in `Neg`'s, since `Neg` alone has no product.
- R8. Core `prim` now takes a theory symbol (`num h o`): step 3's red reaches every module that matches
  on `p-add` … `p-ne`, not only the float bridges. C's token change reaches the Adequacy lexer and
  grammar bridges (`SpecLexing`, `SpecGrammar/*`), which B's new tokens already break; the
  implementation's own `Parser.Token` is a separate type and is not touched.
- R9. A derived symbol's meaning is its definition: `Int`'s `x - y` means `x ⊕ ⊝y` (not `⊖`), `<=` means
  `not (y <ˢ x)`; the backends keep their instructions and step 3 proves them equal (extensionally,
  on words of the width).
