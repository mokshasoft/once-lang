# Plan 0.56 — register-budget-parameterized arith compiler

## Goal

Let each arch declare *how many* registers it lends the arith block, and make the
arith compiler scale to that budget: the more registers, the fewer stack spills.
Today `compile-go` is a fixed **2-register** stack machine (`n-regs = 2`) that
spills every intermediate to `[sp-…]`, regardless of how many registers the arch
actually has free. 0.55 already produced the declaration this consumes: the
`owner`-partition's `arith` class per arch.

## The budget declaration (builds on 0.55)

Add to each `Once.Target.<arch>.PhysReg`:

```
arith-budget : List Reg          -- the arith-owned registers, in priority order
-- invariant (definitional from 0.55): ∀ r ∈ arith-budget, owner r ≡ arith
```

Then `k = length arith-budget` is the arch's arith register budget:
- x86-64 → `r8 r9 r10 r11`  (k = 4)
- riscv64 → `a3 a4 a5`       (k = 3)
- x86-32 → `[]`              (k = 0 → save/restore fallback, unchanged)

## Plan

### A. Parameterize the abstract compiler by `k`
- `compile-go`/`compile-abs`/`required-scratch` gain a register-budget parameter
  `k` (replacing the hard-coded `n-regs = 2`, regs `0,1`). Values live in abstract
  regs `0 … k-1`; spill only when a subtree needs more than `k` simultaneously.
- The abstract state already has an unbounded register file (`Store`), so this is
  a codegen-strategy change, not a machine change.

### B. Sethi–Ullman allocation
- Label each `MArithIR` node with its register need (`ru`); compile the
  heavier child first so the lighter one reuses registers; spill to scratch only
  when `ru > k`. For `k ≥ tree-depth`, zero spills.
- Keep it a pure refactor of `compile-go`'s RHS (the `Compile.agda` header already
  flags this as the planned "Phase F").

### C. Re-prove correctness generically in `k`
- Generalize `CompileCorrect` (`compile-go-correct`, `CompileGoInv`) and
  `Backend/Correct` (`refine`, `refine-program`, `compile-abs-bound`,
  `block-correct`) with the reg-bound `< k` instead of `< 4`, and the
  Sethi–Ullman spill-placement invariant instead of the fixed depth-spill one.
  `reg-bound` becomes `InBound r = r < k` tied to `abs-reg`.
- `abs-reg`/`xreg-idx` generalize from the fixed 4 to the arch's `arith-budget`
  (a `Fin k`-style index into the list).

### D. Wire `k` per arch
- Each arch instantiates the arith compiler at its `k = length arith-budget`;
  `arith-reg` becomes `lookup arith-budget`. Disjointness stays definitional
  (every emitted register is in `arith-budget`, all `owner ≡ arith`).

### E. x86-32 (k = 0) fallback
- With no arith-owned registers, keep the current borrow-and-save/restore path
  (0.55's `arith-borrows`). Either special-case `k = 0`, or model the borrowed
  set as a "budget with a save/restore obligation" — decide during C.

## Scope / risk

This is a real generalization of the whole CompileCorrect + Backend/Correct
development (every proof re-parameterized by `k` + the Sethi–Ullman invariant).
Bigger than 0.55.

**Empirical finding (2026-07-02): the ROI is currently low.** The arith blocks in
the corpus are tiny — `3 + 5*2`, `x + 3*5 - 2*x`, `x + 2*y` (expression depth 2-3,
`required-scratch` 1-2). The current 2-register machine spills ≤1-2 values on
these; `k>2` would save 1-2 spill/reload pairs on already-tiny blocks. So the
efficiency motivation doesn't justify re-proving the whole compiler generically in
`k` **yet**.

**Decision:** land the cheap, valuable part — the `arith-budget` declaration
(DONE, the `k = length` bridge on all three arches) — and **park steps A-C** until
either (a) larger arith blocks actually occur (measure `required-scratch` in real
programs), or (b) the architectural cleanliness is wanted for its own sake. The
declaration is ready to consume when that day comes.

Higher-value next work: **Phase B** — feed 0.55's `owner`/`arith-disjoint` into an
`asm-trace-correct` decomposition to *retire* the `x86-flat-from-obs` postulate
that still hides PreservesCCC. That reduces real trust and directly consumes what
0.55 built.
