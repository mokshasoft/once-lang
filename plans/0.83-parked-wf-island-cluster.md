# Plan 0.83 — The parked `*WF` island cluster

## What is red, and since when

`make check-all` (the island backstop: `Everything.agda` over every module under
`Once/`) **cannot pass**. Nine modules are red, none of them reachable from
`Once.Certified`:

    Once/CCC/Machine/IR/ApplyWF.agda
    Once/CCC/Machine/IR/ComposeWF.agda
    Once/CCC/Machine/IR/CurryStackWF.agda
    Once/CCC/Machine/IR/LambekValidity.agda
    Once/CCC/Machine/IR/RecSchemeProof.agda
    Once/CCC/Machine/IR/RecSchemePostulates.agda
    Once/CCC/Machine/IR/SimpleWF.agda
    Once/CCC/Machine/IR/SumRecWF.agda
    Once/CCC/SigOp/Helper.agda

This is PRE-EXISTING and orthogonal to plans 0.50/0.76/0.81. Two earlier
migrations passed them by, because an island produces no red on the apex — the
exact failure mode MERGE.md's "no islands" rule exists to prevent, observed
after the fact.

## The two causes, in the order you hit them

**1. The CanonName def-side migration added a parameter.**
`Once.CCC.Machine.ClosureWellFormed` became `(o : CanonicalName)`-parameterised.
All nine still do

    open import Once.CCC.Machine.ClosureWellFormed        -- no `o`
    open ClosureWellFormedDef {FS} program-bound

and fail with `ModuleArityMismatch`. The fix is mechanical and every sibling
already shows it (`ShapeAt.Project`, `ValidAtWFHalted`): take `(o :
CanonicalName)` as a module parameter next to `program-bound`, and pass it at
the import:

    module ComposeWFImpl {FS : FrameSemantics} (o : CanonicalName) (program-bound : ℕ) where
      open import Once.CCC.Machine.ClosureWellFormed o

VERIFIED to clear the arity error on `ApplyWF` and `ComposeWF`. Deliberately NOT
committed: it is a half-migration that cannot be checked green, and an
unverifiable edit to nine parked modules does not belong in a branch about
generators and resolution. Redo it as step 1 here.

**2. Behind it, plan 0.52 M2's IR migration.** With the arity fixed, real type
errors appear — `ComposeWF:172` gives `IRTy !=< Once.Type.Type`, i.e. the
ungraded-`IRTy` IR objects never reached this cluster. `ApplyWF:267` fails
similarly (`⌈ _A ⌉ != A`). This is content work, not plumbing, and it is the
reason the cluster was parked in the first place (see the handoff note "ApplyWF
skipped (bulk = per-instr alloc)", and the 28 remaining holes recorded at the
Recommendation-5 landing).

## Order

1. The `o` parameter, all nine files. Mechanical; gets each module to its REAL
   first error.
2. The `IRTy` migration per module, smallest first (`SimpleWF`, then
   `ComposeWF`, `CurryStackWF`, `SumRecWF`, `LambekValidity`, the RecScheme
   pair, `SigOp/Helper`, `ApplyWF` last — it has the most holes).
3. Only then is `make check-all` a usable gate.

## Also fixed while diagnosing (already committed)

`Once/Allocator/Target/X86.agda` DELETED — a true fossil: it imported
`Once.Target.X86.Syntax`/`.Semantics`, both removed by the "Remove AArch64,
RiscV, and X86 backends; consolidate X86v3" commit, and nothing imported it. It
was the first thing `check-all` tripped on.

## Why this matters beyond the cluster

The backstop is the only check that sees a module no apex reaches. While it is
red for unrelated reasons, it reports nothing about anything else — so a NEW
island would hide behind these nine. That is the argument for fixing it rather
than deleting the cluster: the value is the gate, not the nine modules.

If the cluster turns out to be genuinely abandoned rather than parked, deleting
it is the other honest answer, and it restores the gate just as well. Decide
that deliberately — do not let it rot on by default.
