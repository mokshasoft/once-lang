## 0. Decided (the user, 2026-10-31)

1. **A library build is verified** (plan 0.134 (A)). What `once build` writes for a library is covered by a
   library conjunct on the apex, as a program's is by `CorrectCompiler`.
2. **Exports are explicit**: a declaration `export f` names a definition of the module. Only exported
   definitions are entry points; everything else stays internal (inlinable, droppable, renamable).
3. **Only concrete types cross**: an export's type is a base type, or an arrow between two base types (any
   grade); `IsConcrete`'s boundary (`Once.Type.Concrete`), the same one FFI signatures use. Exporting a
   non-concrete or polymorphic definition is a type error, not a silent omission.
4. **A program cannot export**: a module with `main` and an `export` is a type error. A module is a program
   (`main`, no exports) or a library (exports, no `main`).
5. **Effectful libraries are in scope**: an export may be effectful; the operations it calls are the
   library's signature Σ, provided by whoever links it.

## 1. The property

> For every target, every library source the Spec types, and every Implementation of its signature: calling an
> exported symbol, at the target's external calling convention, with the representation of an argument `a`, in
> a world that has seen `h`, produces the trace of the export's meaning at `a` from `h`, and, if that trace
> returns `b`, returns the representation of `b` with the caller's state preserved as the convention says.

The program conjunct is the special case "one export, `main`, called once from `_start` with `h = []`". The
two should share their statement (§2.4).

## 2. Design

### 2.1 Surface and Spec syntax

- `Spec.Surface.Syntax.Decl` gains `DExport : String → Decl`, written `export f` (one name per declaration,
  like `signature`). It names an OWN definition; not an import, not a `signature`.
- `ModuleDenotes` gains the exports: a list of definition indices, each the definition named by an `export`
  declaration, distinct, each `Exportable`; and `exports ≢ [] → no definition is named main`. (`mains` stays.)
- `Spec.Core.Program`: `Exportable : Schema → Set` (arity 0, the type concrete, over the Spec's `Base ∅ₖ`), and
  `record LibraryBuild` = `library : Library` + `exports : List (Fin size)` + `exportable : All (Exportable ∘
  (sig !!_)) exports` + distinctness. `Program` is unchanged.
- Front end: `export` becomes a keyword; the checker refuses: an unknown name, an import or signature, a
  duplicate, a non-concrete or polymorphic type, an `export` beside `main`. `check-is-typing` (D355) keeps
  its shape over the extended `_⊢ᴹ_`.

### 2.2 Meaning of an export

An export `e` of type `A ⇒[k] B` means, for `a : ⟦A⟧`, the computation `⟦e⟧ a`, observed as
`trace (world ι) h (⟦e⟧ a)` for any history `h` (the host may have made calls before, its own or through other
exports). A pure export's trace is silent; it returns `b` or (under `Many`) may diverge. A constant export
`x : B` is a nullary function (its value may read the model's FFI constants). An operation with an empty answer
halts the trace: the call does not return to the host. All of this is `Spec.Observation` as it stands; nothing
new in the meaning.

### 2.3 The boundary: external representation and convention

- **Representation** (`Spec.ABI`, per target): a concrete type is a C type. `Int` = the target word
  (`int64_t`/`int32_t`), `Float` = the target float, `Unit` = no value, `A * B` = a C struct `{A; B}` BY
  VALUE, `A + B` = a tagged struct `{word tag; union {A; B}}` (tag 1 = `inr`, matching `Bool`, D263),
  `Void` as a result = does not return (`_Noreturn`). No pointer to Once memory crosses the boundary.
- **Convention**: the platform C ABI (SysV x86-64, i386 System V cdecl, RISC-V LP64D), which already says how
  structs by value are passed and returned. The callee clause is plan 0.111's: answer in the return location,
  callee-saved registers and `sp` preserved, memory outside the callee's own regions preserved, caller-saved
  registers unspecified.
- **Runtime state**: an export's stub saves the callee-saved registers, loads Once's heap pointer from the
  library's `.bss`, records it (a MARK), calls the internal code, copies the result out (by value), RESETS the
  heap pointer to the mark, and returns. Since nothing in the heap escapes, each call's heap is released at
  return, with no ownership protocol. Marks nest (LIFO), so an Interpretation operation that calls back into an
  export is fine. Concurrent calls from two threads are NOT: a precondition of the conjunct (§4 Q2).
- **Effectful exports**: the library calls Σ's operation symbols, which stay undefined in the library object.
  The linker resolves them to the host's implementation: an Interpretation's code, or the host's own C. What the
  host owes is exactly an `Implementation Σ` with plan 0.111's ABI half; the library conjunct is `∀ I`, like the
  program one.

### 2.4 One ABI, both directions

An exported Once function is to its caller what an Interpretation operation is to Once: the same callee clause,
with the roles swapped. So `Spec.ABI` is stated ONCE (plan 0.111 S1 and this plan's S2 are one step), and both
directions use the C representation of §2.3. Today Once calls operations with SysV registers but tuples by
POINTER into Once's heap (`Strata/Interpretations/Linux/Syscalls.x86_64` header). Under this design the
compiler marshals at a SigOp call too (structs by value), and the few multi-argument operations in the
Interpretations change with it. Then an effectful library's operations can be written in plain C. §4 Q1.

### 2.5 The output

`once build Lib.once` writes an object (`as` output, D262's one trusted translation) with one `.globl` per
export at its symbol, Σ's operation symbols undefined, and a C header (§4 Q4). A library without exports is
refused ("nothing to export; `once check` checks it"). `--lib`/`--exe` go: `main` or exports decide.

### 2.6 The conjunct

`Spec.Correct` gains `CorrectLibrary` beside `CorrectCompiler` (or one record with both), on the apex. Its
machine side runs from a HOST state (plan 0.110's device: what the host does not promise is opaque), enters the
image at an export (plan 0.89's relocatable units; plan 0.93's `BlockRuns` route), and observes the trace until
the stub returns. Conditional on the same named hypotheses as the program conjunct (`BlockRunsHyp` ×3 until
0.93 discharges them).

## 3. Steps (top-down)

- **S0 — Measure.** Per arch: how the emitter represents each concrete type internally (words, pair cells,
  sum tags); which registers the internal code assumes set up (`r15` heap, others); what `_start` initialises;
  how the heap block is placed; whether the internal code is relocatable as emitted; which Interpretation
  operations take or return a product or sum (the §2.4 change). Record here.
- **S1 — Spec patch (user approval):** §2.1's syntax and `LibraryBuild`, §2.2's meaning (a definition), and the
  `export`-beside-`main` refusal. One patch in a scratchpad worktree.
- **S2 — `Spec.ABI` (with plan 0.111 S1):** §2.3's representation and the callee clause, per target. Spec
  approval.
- **S3 — The statement:** `CorrectLibrary` in `Spec.Correct` and a field on `Certified`, top-down: state it,
  follow the red. Spec approval.
- **S4 — Front end:** lexer/parser `export`, the checker's refusals, `check-is-typing` over the extended
  judgment.
- **S5 — Codegen:** per-arch export stubs (marshal in, mark, call, marshal out, reset, return), `.globl`, the
  library object; SigOp-side marshalling (§2.4); the header.
- **S6 — Proofs:** the stub's correctness per arch; entering the image at an export; the conjunct.
- **S7 — Tests:** a C harness calling a pure library (scalars, products, sums) and an effectful one whose
  operations are implemented in C (history-dependent answers, an operation calling back into an export, a
  halting operation); ×3 arches. `examples/Makefile` and `tests/Makefile` build and link libraries for real.
- **S8 — Docs:** D-entry, `language.md` (§8 libraries and exports), `internal.md` (D008's line rewritten),
  `docs/design/ffi.md` and `libraries.md` brought to the decided design.

## 4. Questions for the user (with recommendations)

- **Q1. One ABI both ways (§2.4)?** Recommended: yes. The alternative keeps tuples-by-pointer for operations
  and needs a second representation in the Spec, and a host could not implement an operation in plain C.
- **Q2. Threads.** Recommended: the conjunct assumes calls into one library are not concurrent (nested calls
  are fine). A per-call context argument (re-entrant, thread-safe) is a later extension.
- **Q3. Symbol names.** Recommended: an export's symbol is its name as written; it must be a C identifier, so an
  operator definition `(<+>)` cannot be exported. Internal labels stay mangled (`once_7firstOf`), so an export
  never clashes with them; clashes with Σ's symbols are already excluded (D249, all names distinct).
- **Q4. The C header.** Recommended: emitted, as a print of the exports' `Spec.ABI` types, and listed beside `as`
  in the trust statement (the C compiler's reading of it is not ours). Alternative: no header; the user writes
  it.
- **Q5. `Void` argument.** `f : Void -> B` is concrete but cannot be called. Recommended: refused as an export.
- **Q6. Erased arguments.** An export at quantity zero (`A ⇒[0, k] B`): recommended, the argument is not passed
  (the C function takes none), as an erased argument has no run-time value.

## 5. Done when

`once build` of a library writes a linkable object whose exports are covered by `CorrectLibrary` on the apex,
for pure and effectful exports, on all three arches; a C program calls them in the tests; plan 0.134 closes with
this plan.

## 6. Not in this plan

- Once-to-Once imports of definitions (separate compilation). With exports and `Spec.ABI` it becomes a matter
  of importing a library's export list as signatures, but it is a language feature.
- Non-concrete exports (closures, callbacks, μ/ν values): need a memory protocol across the boundary.
- Thread-safe, re-entrant libraries (§4 Q2).
