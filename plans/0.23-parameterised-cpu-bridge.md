# Plan 0.23: Parameterised CPU bridge for `--safe` compile

## Goal

Discharge the arith refinement / boundary postulates (X86/Correct.agda,
mkPurePrimResult's two SMP.!!, the unblocked `block-semM` family) by
introducing a **parameterised CPU-axioms record**, instantiated at
exactly one designated top-level entry point. Everything below that
point compiles with `{-# OPTIONS --safe #-}`. This is the first axiom
in the codebase to migrate from "imported postulate" to "wired
parameter," establishing the discipline for the rest of the
formalisation (D054).

The user-observable signals are:

1. `make agda-safe` exists and type-checks a designated subtree of
   the formal codebase without any postulates leaking in via imports.
2. `Once.Arith.Backend.X86.Correct` ships with zero `postulate`
   blocks of its own and zero `SMP.!!` placeholders.
3. `mkPurePrimResult` (Helper.agda) ships with zero `SMP.!!` holes.
4. The arith tests (`arith-simple`, `arith-lambda-1`, `arith-lambda-2`)
   still pass at the executable level.

## Context

Plan 0.20 landed the arith block recogniser + abstract machine +
Validity proof (`compile-go-correct`). The framework now has:

- **Layer 1 (Validity):** `compile-go-correct` ✓ discharged in
  commit 02f321bf.
- **Layer 2 (Refinement):** 9 per-AbstractInstr postulates in
  `Once.Arith.Backend.X86.Correct`. Blocked on "CPU-semantics-
  extraction plan" per Plan 0.20's I-arith-4. THIS plan IS that
  plan.
- **Layer 3 (Boundary):** `mkPurePrimResult` in Helper.agda has two
  `SMP.!!` placeholders (`trace-is-ir-to-trace`, `alloc-correct`).
  These hide a real mismatch between `mov-to-output ∷ []` (what the
  helper claims) and `instr-sigop si ∷ []` (what `ir-to-trace'`
  actually emits for SigOp). Closing them needs the same CPU bridge.
- **block-semM (Block.agda):** 6 per-ctor postulates; technically
  discharable today as ℕ-eval with monus, but spiritually wants
  to align with whatever the machine-int decision settles.

[[arith-open-obligations]] catalogues these and their unblock paths.

The 2026-05-27 design discussion settled three things:

1. **No-overflow as programmer obligation, not type-level encoding.**
   We do *not* encode 64-bit integers as `Fin 2^64`; that's a heavy
   refactor for users who would prove no-overflow at the source
   anyway. Instead the machine-int type stays ℕ (or ℤ — see
   open questions), with a no-overflow side condition attached to
   each arithmetic operation. Programs that obviously don't overflow
   (literal arithmetic, programs with bounded inputs) discharge the
   condition trivially. Programs that need wrap-around live outside
   the safe subset and are explicitly out of scope here.

2. **Wired, not imported.** The CPU bridge enters via an `AxiomsCPU`
   record passed as a parameter to every module that needs it, not
   as a top-level `postulate`. The single `postulate ax-x86 :
   AxiomsCPU.X86` lives at the driver and is the only unsafe surface.
   See D054 for the rationale.

3. **First axiom to migrate.** Other postulates (`extensionality`,
   `funext`, `generic-semI/M`) stay imported for now. This plan
   establishes the pattern; subsequent plans migrate them one at a
   time. The `--safe` boundary creeps outward as each postulate
   moves into a record.

## Locked decisions

### D-cpubridge-1: `AxiomsCPU.X86` is a record bundling per-op correctness

```agda
record AxiomsCPU-X86 : Set where
  field
    -- No-overflow predicates for each binary op.
    add-fits : ℕ → ℕ → Set
    sub-fits : ℕ → ℕ → Set
    mul-fits : ℕ → ℕ → Set
    neg-fits : ℕ → Set

    -- Bridge: register state and decoding to/from abstract values.
    XState     : InputShape → Set
    concretise : ∀ {sh} → ArithAbsState sh → XState sh
    exec-x86   : ∀ {sh} → XProgram → XState sh → XState sh

    -- Per-op correctness: a step on the abstract machine is reflected
    -- by exec-x86 on the corresponding emit, **provided** the
    -- no-overflow witness.
    reg-add-correct :
      ∀ {sh} (d a b : ℕ) (s : ArithAbsState sh) →
      add-fits (regs s [ a ] ↧ 0) (regs s [ b ] ↧ 0) →
      exec-x86 (emit (add-rrr d a b)) (concretise s) ≡
        concretise (step (add-rrr d a b) s)
    -- … reg-sub-correct, reg-mul-correct, reg-neg-correct,
    --     reg-load-imm-correct, reg-load-input-correct, reg-spill-correct,
    --     reg-reload-correct, reg-move-to-out-correct, similarly
```

The predicates `add-fits`/`sub-fits`/… are themselves fields of the
record, so a "permissive" instantiation can take `add-fits _ _ = ⊤`
(no check) while a "strict" one can require `a + b < 2^64`. The
choice is made at the instantiation site, not at the consumer site.

### D-cpubridge-2: `Refinement` module is parameterised

`Once.Arith.Backend.X86.Correct` becomes:

```agda
module Once.Arith.Backend.X86.Correct (ax : AxiomsCPU-X86) where
  open AxiomsCPU-X86 ax

  -- The 9 refinement statements that used to be postulates are
  -- now derived from ax's fields. Each gets an explicit
  -- no-overflow precondition where relevant.

  refine-add-rrr : ∀ {sh} (d a b : ℕ) (s : ArithAbsState sh) →
                   add-fits (regs s [ a ] ↧ 0) (regs s [ b ] ↧ 0) →
                   exec-x86 (emit (add-rrr d a b)) (concretise s) ≡
                     concretise (step (add-rrr d a b) s)
  refine-add-rrr = reg-add-correct
  -- ... and so on for the other 8 cases.
```

No `postulate` block in this file. The dispatcher `refine` similarly
case-splits on the AbstractInstr and dispatches to `ax`'s fields.

### D-cpubridge-3: The boundary's `PreservesCCC` discharge consumes `ax`

`Once.Arith.Boundary` becomes parameterised on the same `ax`:

```agda
module Once.Arith.Boundary (ax : AxiomsCPU-X86) where
  open AxiomsCPU-X86 ax
  open Once.Arith.Backend.X86.Correct ax using (refine)

  -- block-int-proof now demands a no-overflow witness for every
  -- arithmetic op inside the block, harvested from the recogniser.
  -- The witness propagates from the source's compile-time analysis.

  block-int-proof : ∀ {A} (si : SigOpInfo A Int) →
                    BlockNoOverflow si →     -- new precondition
                    Contract Stack (SigOp si)
  ...
```

`BlockNoOverflow` is a structural predicate: for an `arith.block.<d>`
SigOp, walk the IR tree and produce an `add-fits` / `sub-fits` / `mul-fits`
witness at each op. For simple programs (literal arithmetic) the witness
chain reduces to `tt`.

### D-cpubridge-4: One designated `postulate ax-x86 : AxiomsCPU-X86`

The single trusted-surface module:

```agda
module Once.Arith.Backend.X86.AxiomsImpl where
  open import Once.Arith.Backend.X86.Axioms

  -- The only postulate in the safe subtree.
  postulate
    ax-x86 : AxiomsCPU-X86
```

`EntryPointCCC` and downstream consumers instantiate at `ax-x86`.
Nothing else postulates. This module gets a `{-# OPTIONS
--allow-unsafe #-}` or equivalent, and is the only such module in
the safe subtree.

### D-cpubridge-5: `--safe` boundary

A new top-level module `Once.SafeCore` re-exports the parameterised
APIs, instantiated at `ax-x86`:

```agda
{-# OPTIONS --safe #-}
module Once.SafeCore where

open import Once.Arith.Backend.X86.AxiomsImpl using (ax-x86)
open import Once.Arith.Backend.X86.Correct ax-x86 public
open import Once.Arith.Boundary ax-x86 public
-- ...
```

Wait — `--safe` rejects importing modules that use postulates
transitively. So `Once.SafeCore` cannot import `AxiomsImpl` directly.
The correct shape is:

```agda
-- Safe library (everything except the postulate):
{-# OPTIONS --safe #-}
module Once.Arith.Backend.X86.Correct (ax : AxiomsCPU-X86) where ...

-- The driver — NOT --safe — instantiates and links:
module Once.Arith.Backend.X86.Driver where
  open import Once.Arith.Backend.X86.AxiomsImpl using (ax-x86)
  open import Once.Arith.Backend.X86.Correct ax-x86 public
```

So `--safe` covers the parameterised modules; the driver is the only
non-`--safe` boundary. The build verifies by checking
`Once.Arith.Backend.X86.Correct.agda` with `--safe`, which succeeds
iff that module has no transitive postulates.

### D-cpubridge-6: `block-semM` discharged on the side

Independent of the parameterisation work, the 6 `block-semM-*`
postulates in Block.agda can be discharged as ℕ-eval with monus
(see [[arith-open-obligations]] §1). Folded into this plan as
Phase 0 because it's a 30-LOC structural discharge that unblocks
Block.agda completely.

### D-cpubridge-7: `mkPurePrimResult` is reworked to use `instr-sigop`

The two `SMP.!!` holes in Helper.agda hide a real mismatch: the
helper's `trace = mov-to-output ∷ []`, but `ir-to-trace' (SigOp si)
= instr-sigop si ∷ []`. The fix: change `mkPurePrimResult` to use
`instr-sigop si ∷ []` as its trace, and re-derive `trace-correct`
/ `frontier-stable` / `mem-preserved-before` against the per-arch
semantics of `instr-sigop`. This is itself a use of the CPU axioms
— specifically, the bridge needs to know that `instr-sigop si`
emits "exec the SigOp's semantics on Input1, write to Output, leave
stack/heap untouched." That fact is an axiom field
`sigop-instr-pure : ∀ si → IsPure si → exec-pure-semantics …`.

## Implementation phases

Each phase ends with `make agda` green and tests passing. The
`--safe` boundary creeps as phases land.

### Phase 0 — Discharge `block-semM` (warmup)

Independent prerequisite. Discharges Block.agda's 6 postulates.

1. Define `projectM : ∀ sh → InputPath → M.⟦ shape-as-type sh ⟧ → ℕ`
   (machine-shape projection) in Block.agda or a sibling.
2. Replace the 6 `block-semM-*` postulates with definitional bodies:
   - `block-semM-alit z _ = ∣ z ∣` (ℕ abs value, IntLit convention)
   - `block-semM-ainput p inp = projectM _ p inp`
   - `block-semM-aadd a b inp = block-semM a inp +ℕ block-semM b inp`
   - `block-semM-asub a b inp = block-semM a inp ∸ block-semM b inp`
   - `block-semM-amul a b inp = block-semM a inp *ℕ block-semM b inp`
   - `block-semM-aneg _ _ = 0`
3. The dispatcher `block-semM` already case-splits structurally; no
   wiring change needed.

**Estimated cost:** ~30 LOC. `make agda && cabal test -j1` green.

### Phase A — Define the `AxiomsCPU-X86` record

1. New file `formal/Once/Arith/Backend/X86/Axioms.agda` defining
   `AxiomsCPU-X86` with 9 per-instruction correctness fields, 4
   no-overflow predicate fields, and the `XState` / `concretise` /
   `exec-x86` bridge fields. No postulates inside the file — the
   record is a pure interface.
2. The file declares `{-# OPTIONS --safe #-}`.

**Estimated cost:** ~100 LOC of interface + comments.

### Phase B — Parameterise `Once.Arith.Backend.X86.Correct`

1. Convert the module header to `module … (ax : AxiomsCPU-X86)
   where`. Open `ax` at the top.
2. Replace each of the 9 `refine-*` postulates with a definition
   that delegates to the corresponding `ax`-field.
3. The dispatcher `refine : … → …` becomes a real function (it
   already case-splits) that calls the `refine-*` helpers.
4. Add a `{-# OPTIONS --safe #-}` pragma at the top of the file.
5. Adjust every import site to pass the `ax` parameter.

**Estimated cost:** ~80 LOC change in Correct.agda; ~30 LOC
adjusting consumers (which today are zero — the postulates are
imported but never used downstream because the proof chain hasn't
landed; this phase preserves that posture).

### Phase C — Rework `mkPurePrimResult` for `instr-sigop`

1. Change Helper.agda's `mkPurePrimResult.trace` from
   `mov-to-output ∷ []` to `instr-sigop si ∷ []`.
2. Re-derive the four trace-effect arguments
   (`trace-correct-pf`, `frontier-stable-pf`, `mem-preserved-before`,
   `trace-twf`) against `instr-sigop` semantics. This needs a new
   axioms field `sigop-instr-is-pure-copy : ∀ si → exec-trace
   (instr-sigop si ∷ []) s alloc ≡ … (copy Input1 to Output) …`.
3. The two `SMP.!!` holes collapse to `refl` once both sides emit
   `instr-sigop si ∷ []`.
4. Update callers (`add-int-proof`, `block-int-proof`) to no longer
   pass `arith-trace-correct` / `arith-frontier-stable` — instead
   pass the axioms-derived versions.

**Estimated cost:** ~150 LOC. Touches Helper.agda + Proofs.agda
+ Boundary.agda. Most of it is renaming + threading the axioms.

**Risk:** the existing `arith-trace-correct` / `arith-frontier-
stable` proofs in `Once.Arith.SigOp.Proofs.agda` are real proofs
about `mov-to-output ∷ []`. Once we change the trace, those proofs
become dead. They can either move to the `instr-sigop` bridge axiom
(as the "this is what the bridge guarantees" lemma) or be deleted.
Lean toward deletion — they're for a now-obsolete shape.

### Phase D — Parameterise `Once.Arith.Boundary`

1. Convert the module header.
2. `block-int-proof` now takes a `BlockNoOverflow si` precondition
   (a structural witness derived from the IR tree).
3. `blockProvider` propagates the precondition into the `Provider`
   contract. The contract may need a new "no-overflow obligation"
   field, or it can stay implicit (the provider returns `nothing`
   when the precondition fails).
4. Add `{-# OPTIONS --safe #-}`.

**Estimated cost:** ~100 LOC. The structural witness for
`BlockNoOverflow` is the new work; the rest is plumbing.

### Phase E — Single trusted-surface module

1. New file `formal/Once/Arith/Backend/X86/AxiomsImpl.agda`:
   ```agda
   module Once.Arith.Backend.X86.AxiomsImpl where
     open import Once.Arith.Backend.X86.Axioms
     postulate
       ax-x86 : AxiomsCPU-X86
   ```
   This file CANNOT have `--safe`. It is the entire trusted surface
   for x86 arithmetic.
2. Document the postulate's content carefully (what each field
   really claims about x86 behaviour, citing the relevant manual
   sections).

**Estimated cost:** ~50 LOC (mostly documentation).

### Phase F — `--safe` boundary expansion

1. Add `{-# OPTIONS --safe #-}` to every module that no longer
   transitively depends on unwired postulates:
   - `Once.Arith.Machine.{AbsState,AbsInstr,IR,Compile,Recognise,Rewrite}`
   - `Once.Arith.Backend.X86.{Axioms,Correct,CodeGen}`
   - `Once.Arith.Boundary`
   - `Once.Arith.SigOp.{Block, Builders}` (most fields, after
     a future plan migrates `generic-semI/M`)
2. A new make target `agda-safe` type-checks the safe modules with
   `--safe` and fails if any module accidentally imports an unwired
   postulate.
3. Document the boundary in `docs/formal/safe-subset.md`.

**Estimated cost:** ~30 LOC across module headers + ~50 LOC Makefile
+ ~200 LOC documentation.

### Phase G — Driver instantiation + test alignment

1. `Once.Compile` (or `Once.Verified.Compile`) instantiates the
   safe modules at `ax-x86`. This is the single non-`--safe`
   boundary at the top of the pipeline.
2. The arith tests still pass: `arith-simple → exit 13`,
   `arith-lambda-1 → exit 10`, `arith-lambda-2 → exit 42`. The
   no-overflow obligations for these programs are trivially `tt`
   (literal arithmetic; static result fits in any reasonable bound).
3. Bridge.hs (compiler bridge) doesn't change — MAlonzo extraction
   ignores postulates anyway. The user-facing executable is byte-
   for-byte identical.

**Estimated cost:** ~50 LOC.

## Risks / open questions

1. **No-overflow predicate granularity.** Per-op (`add-fits a b`) vs
   global (`fits-in-64 x`)? Per-op gives tighter proofs (you only
   pay where you actually use the op); global is simpler. Recommend
   per-op; revisit if proof obligations balloon.

2. **`M.⟦ Int ⟧` underlying type — ℕ vs ℤ.** Independent decision.
   The plan currently assumes ℕ (status quo). Switching to ℤ would
   give signed arithmetic at the machine layer, with bounds
   `-2^63 ≤ x < 2^63`. Larger refactor; defer to a follow-up plan
   unless the no-overflow side conditions for signed programs prove
   intolerable.

3. **`extensionality` migration.** The longest-standing global
   postulate (`Once.Postulates`). Out of scope here, but the same
   wired-record pattern applies. Follow-up plan.

4. **The single `--allow-unsafe` postulate file.** Agda's `--safe`
   flag works module-by-module. `Once.Arith.Backend.X86.AxiomsImpl`
   is the only non-safe file. The check is "this file has the
   single postulate, no others." Could be enforced by a Makefile
   grep.

5. **MAlonzo extraction.** The compiler binary is produced via
   MAlonzo, which extracts both proofs and definitions. Postulates
   extract to `undefined`. Since `ax-x86`'s correctness fields are
   only used at the proof level (not runtime), the extracted
   compiler is identical before and after this plan.

6. **`BlockNoOverflow` decidability.** For a static program, the
   recogniser should be able to PROVE `BlockNoOverflow` from the IR
   structure (literal arithmetic always fits; inputs from a bounded
   type are constrained). Whether this is decidable in general is
   open. Lean toward "trivial for the current test set; revisit when
   the test set grows."

## Why this is the principled fix

- **Honest trust boundary.** The single `ax-x86` postulate file is
  the entire surface area for x86 arithmetic correctness. A reviewer
  can audit one ~100-line file and know what's assumed.
- **No type-checker tax.** Programs that don't overflow pay nothing.
  The no-overflow predicate is propositional; reduced away at type-
  check time when trivially `tt`.
- **`--safe` as a real invariant.** Once a module says `--safe`, it
  cannot smuggle in a postulate via transitive import. The boundary
  is mechanically enforced.
- **Generalises.** The pattern — `record AxiomsX → postulate axioms-x
  : AxiomsX at one site → everything below is parameterised` — is
  the template for migrating every other postulate. Each future
  migration shrinks the unsafe surface by one record at a time.
- **Closes the arith chain.** With axioms parameterised in, the
  Validity-Refinement-Boundary chain becomes a clean composition:
  the arith pipeline's correctness statement is
  "given `ax-x86`, every arith block discharges PreservesCCC."

## Non-goals

- Encoding 64-bit integers as `Fin 2^64`. Explicitly rejected per
  the design discussion.
- Migrating ALL postulates to wired form. Just the CPU bridge;
  others follow in sibling plans.
- Building a complete x86-64 semantics. Only what the arith bridge
  needs; cmp / shift / control-flow stay out of scope.
- Auto-deriving `BlockNoOverflow` proofs from source-level analysis.
  Trivial-for-now; can be richer later.

## Open questions to resolve in Phase A or B

- Naming: `AxiomsCPU-X86` vs `X86Axioms` vs `CpuBridge.X86`. Pick
  one that mirrors existing module-naming conventions.
- Whether the no-overflow predicates appear in the record at all,
  or whether they live in a separate module that's parameterised
  over the axioms. Cleaner to keep them in-record for proximity;
  revisit if the record gets unwieldy.
- Whether `Once.Verified.Compile` becomes the single instantiation
  site, or whether each backend has its own driver. Lean toward
  per-backend drivers (so `Once.Arith.Backend.X86.Driver` is the
  natural home for `ax-x86`).
