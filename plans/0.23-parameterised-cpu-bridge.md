# Plan 0.23: Wire arith refinement into the existing per-target CPU semantics

## Goal

Discharge the arith refinement / boundary postulates by **wiring** the
arith abstract machine into the **already-existing** per-target CPU
semantics modules (`Once.CCC.Target.{X86-64,X86-32,RiscV64}.Semantics`).
For x86-64, the discharge is structural — real proofs against
`execInstr`, modulo a two's-complement encoding and a no-overflow
side condition the programmer carries. For the other two targets,
the same parameterised interface accepts a *stub* bridge (matching
the existing "notImplemented codegen stubs" posture from Plan 0.20).

The compiler compiles to **all three** targets via the same generic
arith pipeline; this plan establishes a per-target `BackendBridge`
typeclass-style record so the parameterised arith modules can stay
target-agnostic while each backend supplies its own bridge.

Concurrently, this plan introduces the **wired-not-imported**
postulate discipline (D054). For the bridges that *are* postulated
(stub backends, eventually-extensible-axioms), the postulate lives
in a single per-target driver module. The arith pipeline body is
`--safe`.

The user-observable signals:

1. `Once.Arith.Backend.X86.Correct` ships with zero `postulate`
   blocks and zero `SMP.!!` placeholders.
2. `Once.Arith.Backend.RiscV64.Correct` and `Once.Arith.Backend.X86-32.Correct`
   exist with stub bridges (postulated) matching the existing
   "skeleton-only" backend posture.
3. `mkPurePrimResult` (Helper.agda) ships with zero `SMP.!!` holes.
4. `make agda-safe` type-checks a designated subtree without any
   postulates leaking via imports.
5. The arith tests still pass (binary unchanged; MAlonzo ignores
   propositional content).

## Context

Plan 0.20 landed the arith block recogniser + abstract machine +
Validity proof. The remaining gaps:

- **Layer 2 (Refinement):** 9 per-AbstractInstr postulates in
  `Once.Arith.Backend.X86.Correct`. Plan 0.20's I-arith-4 said:
  "reuse + extend `Once.CCC.Target.X86-64.Semantics`." THIS PLAN
  carries that out.
- **Layer 3 (Boundary):** `mkPurePrimResult` has two `SMP.!!`
  placeholders hiding a real `trace = mov-to-output ∷ []` vs
  `ir-to-trace' (SigOp si) = instr-sigop si ∷ []` mismatch.
- **block-semM (Block.agda):** 6 per-ctor postulates dischargeable
  as ℕ-eval; folded in as Phase 0.

### What CPU semantics already exists

```
formal/Once/CCC/Target/X86-64/Semantics.agda    345 LOC
formal/Once/CCC/Target/X86-32/Semantics.agda    real semantics
formal/Once/CCC/Target/RiscV64/Semantics.agda   real semantics
```

Each provides:

```agda
record State : Set where ...      -- arch-specific register file + memory + flags + pc
execInstr : Program → State → Instr → Maybe State    -- per-instr semantics
step      : Program → State → Maybe State            -- fetch-decode-execute
exec      : ℕ → Program → State → Maybe State        -- bounded run
```

The trust point is **the body of `execInstr`, clause-by-clause
against the relevant ISA reference** — the CompCert / Sail
convention. No `--safe`-rejecting axioms; the semantics is real
code.

### Why bridge ≠ semantics

The 2026-05-27 design discussion clarified: there's no missing CPU
semantics. What's missing is the **bridge** from the arith abstract
machine (`ArithAbsState sh`, with ℤ-typed registers) to the
target-specific `State` (with ℕ-typed registers). The bridge needs:

1. An encoding `ℤ ↔ Word` (two's-complement on a 64-bit machine).
2. A `concretise : ArithAbsState sh → State` that maps abstract
   register / scratch contents into the target's register file +
   memory.
3. Refinement proofs: `step (add-rrr d a b)` on the abstract side
   corresponds to `execInstr (add …)` on the concrete side, under
   the encoding and a no-overflow precondition.

The CPU semantics modules already exist. The bridge is what's new.

## Locked decisions

### D-cpubridge-1: `BackendBridge` is a target-parameterised interface

A single generic record type, instantiated per target. Lives in
`Once/Arith/Backend/Bridge.agda`:

```agda
record BackendBridge : Set₁ where
  field
    -- Target's State type (re-exported from the target's Semantics
    -- module; not postulated).
    State : Set

    -- Encoding from the abstract machine's ℤ register file to the
    -- target's ℕ register file. Real definition in each instance.
    concretise : ∀ {sh} → ArithAbsState sh → State

    -- Per-AbstractInstr emit (already done in
    -- `Once.Arith.Backend.<arch>.CodeGen`). The bridge re-exports it
    -- so refinement statements don't depend on the per-arch CodeGen
    -- module directly.
    emit : AbstractInstr → Program

    -- Target's instruction-trace executor (re-exported from the
    -- target's Semantics module; not postulated).
    exec-target : Program → State → Maybe State

    -- No-overflow predicate (per binary op). Per-target because the
    -- ℕ-word size differs (64-bit on x86-64/RiscV64, 32-bit on
    -- X86-32).
    add-fits : ℕ → ℕ → Set
    sub-fits : ℕ → ℕ → Set
    mul-fits : ℕ → ℕ → Set
    neg-fits : ℕ → Set

    -- Per-op refinement. For x86-64 these are REAL LEMMAS (proved
    -- against execInstr's clause-by-clause semantics). For the stub
    -- backends, these are postulated until those backends ship a
    -- real codegen.
    reg-add-correct : ∀ {sh} (d a b : ℕ) (s : ArithAbsState sh) →
                      add-fits (regVal s a) (regVal s b) →
                      exec-target (emit (add-rrr d a b)) (concretise s)
                        ≡ just (concretise (step (add-rrr d a b) s))
    -- ... 8 more analogous fields
```

The record bundles BOTH "real-proof things" (`State`, `concretise`,
`exec-target`, `emit`) and "things-the-target-might-postulate"
(`reg-add-correct` etc.). For x86-64 the latter are real lemmas;
for stubs they're postulated. The interface doesn't care which.

### D-cpubridge-2: `Refinement` module is parameterised on `BackendBridge`

`Once.Arith.Backend.Correct` (renamed from `X86.Correct` to drop the
target prefix) becomes:

```agda
module Once.Arith.Backend.Correct (bridge : BackendBridge) where
  open BackendBridge bridge

  refine : ∀ {sh} (i : AbstractInstr) (s : ArithAbsState sh) →
           NoOverflow i s →                                -- new
           exec-target (emit i) (concretise s)
             ≡ just (concretise (step i s))
  refine (add-rrr d a b) s ok = reg-add-correct d a b s ok
  -- ... 8 more dispatch arms
```

No `postulate` in this file. `NoOverflow` is a structural predicate
on AbstractInstr + state — what the bridge's per-op `*-fits`
predicates need to be true.

### D-cpubridge-3: Per-target `BackendBridge` instances

```
formal/Once/Arith/Backend/X86/Bridge.agda      [NEW]  real bridge,
                                                      real refinement
                                                      proofs against
                                                      X86-64.Semantics
formal/Once/Arith/Backend/X86-32/Bridge.agda   [NEW]  stub: postulates
                                                      the refinement
                                                      fields (matches
                                                      "skeleton-only"
                                                      backend posture)
formal/Once/Arith/Backend/RiscV64/Bridge.agda  [NEW]  same stub posture
```

Each `Bridge.agda`:

- Re-exports the target's `State` / `execInstr` / etc.
- Defines `concretise` definitionally.
- For x86-64: proves the 9 refinement statements by unfolding
  `execInstr` + `step` and reducing ℕ arithmetic. No postulates.
- For x86-32 / RiscV64: postulates the refinement statements with a
  big comment "this backend is skeleton-only; full discharge lands
  when codegen is wired."

### D-cpubridge-4: Single wired postulate per stub backend

For x86-32 / RiscV64, each Bridge.agda postulates its refinement
fields directly inside the same file. The postulate is the entire
trusted surface for that backend; it's transparent.

For x86-64 there are *no* postulates in `Bridge.agda` (the bridge
is real). The only postulate in the safe subtree is then whatever
the boundary's residual claims are (see Phase C / D below).

### D-cpubridge-5: `--safe` boundary

```
{-# OPTIONS --safe #-}
module Once.Arith.Backend.Bridge where ...    -- interface
module Once.Arith.Backend.Correct (b : BackendBridge) where ...  -- parameterised refinement
module Once.Arith.Boundary (b : BackendBridge) where ...         -- parameterised boundary
module Once.Arith.Backend.X86.Bridge where ...                   -- x86-64 instance (real)
```

x86-32 / RiscV64 `Bridge.agda` files are NOT `--safe` (they contain
postulates). The arith pipeline that consumes them via the generic
interface IS `--safe`.

The top-level compile driver instantiates whichever bridge the
selected target dictates, threading the (possibly-postulated) bridge
into the parameterised pipeline.

### D-cpubridge-6: Multi-target compile orchestration

`Once.Compile.compileFunWithTarget` already takes a `Target` value.
It selects the per-target codegen + emitter today. Post-plan it
also selects the per-target `BackendBridge`:

```agda
module Once.Compile where
  open import Once.Arith.Backend.X86.Bridge      using () renaming (bridge to x86-bridge)
  open import Once.Arith.Backend.X86-32.Bridge   using () renaming (bridge to x86-32-bridge)
  open import Once.Arith.Backend.RiscV64.Bridge  using () renaming (bridge to riscv64-bridge)

  compileFunWithTarget : Target → … → CompiledFn
  compileFunWithTarget target ir =
    let bridge = case target of λ where
                   target-X86-64  → x86-bridge
                   target-X86-32  → x86-32-bridge
                   target-RiscV64 → riscv64-bridge
        open Once.Arith.Boundary bridge
        open Once.Arith.Backend.Correct bridge
    in -- … codegen, using bridge.emit, refinement proofs threaded …
```

(Actual syntax may differ — Agda doesn't have first-class modules in
the simple way C++ templates work. The selection might need to live
in three sibling functions, one per target, dispatched at the top by
the target tag. Phase G settles this.)

### D-cpubridge-7: `block-semM` discharged on the side (Phase 0)

Independent of the bridge work. 30 LOC structural recursion mirroring
`eval-arith` at ℕ with monus / 0-neg. Closes Block.agda's 6 postulates.

### D-cpubridge-8: `mkPurePrimResult` reworked for `instr-sigop`

The two `SMP.!!` holes hide the `mov-to-output ∷ []` vs
`instr-sigop si ∷ []` mismatch. Fix: change `mkPurePrimResult.trace`
to `instr-sigop si ∷ []`, re-derive the trace effects against
`instr-sigop`'s per-arch semantics. The "what `instr-sigop si`
actually does on a target" is a `BackendBridge` field
(`sigop-instr-effect : ∀ si → PureSemantics …`). For x86-64 it's a
real lemma; for stubs it's postulated alongside the other refinement
fields. Folded into Phase C.

## Implementation phases

Each phase ends with `make agda` green and tests passing. The
`--safe` boundary creeps as phases land.

### Phase 0 — Discharge `block-semM` (warmup)

1. Define `projectM : ∀ sh → InputPath → M.⟦ shape-as-type sh ⟧ → ℕ`.
2. Replace the 6 `block-semM-*` postulates with definitional bodies
   (ℕ-eval with monus / 0-neg, IntLit convention).

**Estimated cost:** ~30 LOC. `make agda && cabal test -j1` green.

### Phase A — Define the `BackendBridge` interface

1. New file `formal/Once/Arith/Backend/Bridge.agda` defining
   `BackendBridge` as documented in D-cpubridge-1. No postulates.
2. Header: `{-# OPTIONS --safe #-}`.

**Estimated cost:** ~150 LOC of interface + documentation.

### Phase B — x86-64 bridge instance (the real one)

1. New file `formal/Once/Arith/Backend/X86/Bridge.agda`:
   - Imports `Once.CCC.Target.X86-64.Semantics` for `State`,
     `execInstr`, etc.
   - Defines `concretise : ∀ {sh} → ArithAbsState sh → State`
     structurally (each abstract reg maps to a fixed concrete reg,
     scratch slots map to `[rsp + 8*i]`, two's-complement encoding
     for ℤ → Word).
   - Defines the four `*-fits` predicates as bounded-arithmetic
     constraints (`a + b < 2 ^ 64`, etc.).
   - **Proves** each of the 9 refinement statements as real lemmas.
     Proof shape:
     ```
     refine-add-rrr d a b s ok =
       begin
         exec-target (emit (add-rrr d a b)) (concretise s)
       ≡⟨ … unfold emit (add-rrr) into mov+add … ⟩
         execInstr prog (concretise s) (mov …)
           >>= λ s1 → execInstr prog s1 (add …)
       ≡⟨ … readOperand reduces (regs are concrete after concretise) … ⟩
         just (concretise (step (add-rrr d a b) s))
       ∎
     ```
   - No postulates.
2. Header: `{-# OPTIONS --safe #-}`.

**Estimated cost:** ~600 LOC. The bulk is the 9 refinement proofs.
Each is "unfold emit, unfold step, reduce, conclude" — tedious but
mechanical.

### Phase B' — Stub bridges for x86-32 and RiscV64

1. New file `formal/Once/Arith/Backend/X86-32/Bridge.agda`:
   - Same skeleton as the x86-64 bridge.
   - `concretise` is defined definitionally (just lift to that
     target's `State`).
   - The 9 refinement fields are **postulated** with a single
     `postulate` block at the bottom of the file. Big comment: "this
     backend is skeleton-only; codegen returns `notImplemented`; the
     refinement postulates are placeholders."
2. Same for `formal/Once/Arith/Backend/RiscV64/Bridge.agda`.
3. Each file has its own `postulate` block; no `--safe` pragma.

**Estimated cost:** ~150 LOC per backend × 2 = 300 LOC.

### Phase C — Rework `mkPurePrimResult` for `instr-sigop`

1. Change `Helper.agda`'s `mkPurePrimResult.trace` from
   `mov-to-output ∷ []` to `instr-sigop si ∷ []`.
2. Add a new `BackendBridge` field `sigop-instr-effect` documenting
   what `exec-target (instr-sigop si ∷ [])` does for pure-primitive
   SigOps (copies Input1 → Output, no stack/heap touch). x86-64
   proves it real; stubs postulate.
3. Re-derive `trace-correct-pf` / `frontier-stable-pf` /
   `mem-preserved-before` from the new bridge field.
4. The two `SMP.!!` holes collapse to `refl`.
5. Update callers (`add-int-proof`, `block-int-proof`) to thread the
   bridge.

**Estimated cost:** ~200 LOC. Touches Helper.agda + Proofs.agda
+ Boundary.agda. The obsolete `arith-trace-correct` /
`arith-frontier-stable` proofs in `Once.Arith.SigOp.Proofs` (real
proofs about the OLD trace shape) are deleted; their job moves into
the bridge.

### Phase D — Parameterise `Once.Arith.Backend.Correct` and `Once.Arith.Boundary`

1. `Once.Arith.Backend.Correct` renamed from
   `Once.Arith.Backend.X86.Correct` (it's no longer X86-specific).
   Convert to `module … (b : BackendBridge) where`.
2. Replace the 9 `refine-*` postulates with one-line delegations to
   `b.reg-*-correct`.
3. `Once.Arith.Boundary` similarly takes `b : BackendBridge`.
   `block-int-proof` consumes the bridge + a `BlockNoOverflow`
   precondition (structural witness derived from the arith block IR).
4. Both files: `{-# OPTIONS --safe #-}`.

**Estimated cost:** ~80 LOC change + ~30 LOC threading through
consumers.

### Phase E — `--safe` boundary

1. Add `{-# OPTIONS --safe #-}` to:
   - `Once.Arith.Machine.{AbsState,AbsInstr,IR,Compile,Recognise,Rewrite}`
   - `Once.Arith.Backend.Bridge`
   - `Once.Arith.Backend.Correct`
   - `Once.Arith.Backend.X86.Bridge`
   - `Once.Arith.Boundary`
   - `Once.Arith.SigOp.{Block, Builders}` (where their imports allow)
2. New make target `agda-safe`:
   ```makefile
   agda-safe:
       @for m in $(SAFE_MODULES); do \
         agda --safe $$m || exit 1; \
       done
   ```
3. Document the boundary in `docs/formal/safe-subset.md`.

**Estimated cost:** ~30 LOC headers + ~80 LOC Makefile +
~200 LOC documentation.

### Phase F — Multi-target driver orchestration

1. `Once.Compile.compileFunWithTarget` dispatches on the `Target`
   value to select the right `BackendBridge` instance.
2. Each per-target dispatch arm instantiates the parameterised
   `Boundary` / `Correct` modules with that target's bridge.
3. The driver module itself is NOT `--safe` (it imports the
   postulate-bearing stub bridges). But its body is small: just the
   target-tag → bridge-selection table.

**Estimated cost:** ~100 LOC. Possibly more — depends on how Agda's
module system handles per-target parametricity (may need three
sibling instantiations rather than first-class module-as-value).

### Phase G — Test alignment

1. The arith tests still pass: `arith-simple → exit 13`,
   `arith-lambda-1 → exit 10`, `arith-lambda-2 → exit 42`. The
   no-overflow obligations for these programs are trivially `tt`
   (literal arithmetic; result < 2^64).
2. Bridge.hs (compiler bridge) doesn't change — MAlonzo extraction
   ignores postulates anyway. The user-facing executable is byte-
   for-byte identical.
3. The cross-target tests (`Layer4Spec`, the 18 tests Plan 0.19
   wired up) still pass under whatever target they each select.

**Estimated cost:** ~50 LOC.

## Risks / open questions

1. **Agda module-as-value limitation.** Agda doesn't have first-class
   modules in the way ML / OCaml do. Parameterising `Correct` and
   `Boundary` on a `BackendBridge` record is fine — record fields
   ARE first-class values. But threading the bridge through a
   target-dispatching `Once.Compile` may force three sibling
   instantiations (`compileFun-X86-64`, `compileFun-X86-32`,
   `compileFun-RiscV64`) rather than one polymorphic function. Phase
   F decides.

2. **Per-target no-overflow predicate variance.** x86-32's `Word` is
   ℕ as 32-bit; the no-overflow predicate is `a + b < 2 ^ 32`, not
   `< 2 ^ 64`. The `*-fits` fields capture this per-instance, so the
   interface stays generic.

3. **x86-64 refinement proofs may be longer than estimated.**
   `execInstr` reads operands via `readOperand`, which in turn reads
   either registers or memory. For arith ops the operands are
   always registers (we control codegen), so `readOperand` reduces
   to `readReg` immediately. But proving that reduction may need a
   helper lemma per operand position. Total LOC might be 800–1000
   if those helpers are non-trivial.

4. **`emit` vs `Program`.** The bridge's `exec-target` takes a
   `Program`, but `emit (add-rrr ...)` produces some target-specific
   instruction list. The `Program` ↔ instruction-list conversion is
   per-target (some targets emit a labelled program; others a flat
   sequence). The bridge handles this conversion internally; the
   user interface just gives `emit : AbstractInstr → ProgramFragment`
   and `exec-target : ProgramFragment → State → Maybe State`.

5. **MAlonzo extraction.** The per-target dispatch in `Once.Compile`
   currently lives in extracted Haskell code (`compiler/src/Once/...`).
   The Agda-side multi-target dispatch needs to extract cleanly into
   the same Haskell shape. May need a sentinel-pattern in the bridge
   record (e.g., a `target-tag` field) so MAlonzo can pattern-match.

6. **`BlockNoOverflow` decidability for arbitrary programs.** Trivial
   for literal arithmetic; non-trivial for programs with unbounded
   inputs. Out of scope; programs that can't prove no-overflow won't
   compile with `--safe`-clean proofs. Possible future plan: a
   weakening to "the compiler emits overflow-checking code at runtime
   when the static proof fails."

7. **Stub backend correctness.** The x86-32 / RiscV64 stubs postulate
   bridge correctness because their codegen doesn't actually emit
   working code (per Plan 0.20's scope decision). When those
   backends ship real codegen (separate future plans), their
   `Bridge.agda` files migrate from postulates to real proofs by
   the same recipe used for x86-64 in this plan.

## Why this is the principled fix

- **No new CPU semantics required.** The existing per-target
  semantics modules — already written clause-by-clause against ISA
  references — are the trust point. The plan does not introduce a
  parallel semantics layer.
- **Multi-target by construction.** The arith pipeline is generic
  over `BackendBridge`. Adding a new target is "write a new
  Bridge.agda instance"; the arith body doesn't change.
- **`--safe` discipline gets a concrete first beachhead.** The arith
  + boundary subtree is the first body of the codebase to be
  mechanically gated by `--safe`. Future migrations follow the same
  recipe.
- **Stub backends fit cleanly.** x86-32 / RiscV64 keep their
  "skeleton-only" status without polluting the safe subtree —
  their postulates live in their own non-safe Bridge modules.
- **Closes the Validity → Refinement → Boundary chain (for x86-64).**
  With the bridge in place, every arith block on x86-64 has a real
  PreservesCCC proof composed from real layer proofs. Stubs leave
  the chain "real for x86-64, postulated for x86-32 / RiscV64"
  — which is honest, given those backends don't have working codegen.

## Non-goals

- Encoding 64-bit integers as `Fin 2^64`. The existing per-target
  semantics uses ℕ; we match it. Two's-complement is the
  ℤ ↔ ℕ encoding at the bridge.
- Modelling x86 flags / control flow / SIMD beyond what arith
  needs.
- A unified CPU-semantics meta-framework. Each target has its own
  semantics module today; we keep that and abstract over the
  interface differences via `BackendBridge`.
- Migrating all other postulates (`extensionality`, `funext`,
  `generic-semI/M`) to wired form. Follow-up plans.
- Replacing the stub backends' postulates with real proofs.
  Separate per-target plans when those backends mature.

## Open questions to resolve in Phase A or B

- Whether `BackendBridge.State` should be at universe level `Set`
  or `Set₁`. Each target's `State` lives in `Set`; bundling them
  via a record may push the bundle to `Set₁`. Test in Phase A.
- Whether the `*-fits` predicates should be `Set` or `Bool` (a
  decidable bound). Decidable would let recognition statically
  discharge the no-overflow obligation for literal programs;
  Set-valued is simpler. Lean toward decidable; revisit in Phase B.
- Whether stub backends' `Bridge.agda` should also wire their
  postulates via a record (for consistency) or directly (for
  brevity). Brevity wins for stubs that nobody currently uses.
