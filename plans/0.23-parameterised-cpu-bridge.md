# Plan 0.23: Word-based arith semantics + CPU faithfulness

> Revised 2026-05-28 (twice). The first revision reframed around D054
> (`Int` = modular `Word`). This second revision records the
> understanding we reached after a long discussion about *whether arith
> needs a value spec at all*. The **Settled understanding** section
> below is the conclusion — read it before touching this plan, so we
> don't re-derive it.

## Settled understanding (DO NOT RELITIGATE)

1. **`Int` = the CPU's word (D054).** The value of `3 + 5*2` is
   whatever the silicon computes. `+`/`-`/`*` map to the `add`/`sub`/
   `mul` instructions; the result is their result.

2. **`PreservesCCC` is value-blind, and correct.** Its job is "didn't
   corrupt CCC state" (frame, halt, prior memory, heap/slot monotone).
   It does **not** mention any value. CCC treats a SigOp as opaque —
   it only needs the structural contract. Nothing about `%`,
   word-width, or overflow belongs here.

3. **For a single-instruction op (`+`/`-`/`*` at register width) there
   is no value proof to do.** The op *is* the instruction, so
   correctness collapses to **emit-correspondence**: codegen emits
   `add` for `aadd`, `mul` for `amul`, operands in the right
   registers/order. That plus `PreservesCCC` is the whole story. A
   denotational value spec for these ops is vacuous.

4. **A value spec earns its keep ONLY for ops that are *not* one
   instruction:**
   - **division by zero / signed overflow** (D055) — the guard is
     multiple instructions *and* the hardware default differs per
     target;
   - **bignum `+`** (future `BigInt`) — a multi-instruction routine.
   Both are **deferred**. Ignore division for now.

5. **This is consistent with CompCert / CakeML.** Both keep a
   machine-independent value semantics and *prove* the target
   preserves it. But for a single-instruction op that proof is
   trivial — it collapses to exactly the emit-correspondence above.
   CompCert's `Int.add = repr (x+y)` ⇒ matches the `add` instruction
   by definition. So "keep a value spec but its proof is trivial for
   `+`/`-`/`*`" and "no value spec for `+`/`-`/`*`" are the *same
   thing* in practice. We do not need to delete `SigOpInfo.semM`
   (the framework requires it); we just don't owe a substantive proof
   against it for these ops.

6. **`execInstr` should be modular — this is separate from value
   specs.** `execInstr` is the *trusted CPU model* (the floor). To be
   faithful to silicon it must wrap (`d ⊕ v`, not unbounded `d + v`).
   This is true regardless of whether any value theorem exists, and is
   the one place `%`/width legitimately lives. It uses `Once.Word`.

### One-line consequence

Arith-block correctness = **emit-correspondence + `PreservesCCC`**.
The modular `Word` machinery is for (a) keeping `execInstr` faithful
and (b) making the *required-by-framework* `semM` conformance trivial
— not for proving anything substantive about `+`/`-`/`*`.

## Goal

Discharge the arith-block postulates under the model above:

1. `execInstr` (per target) is modular — faithful to silicon — using
   `Once.Word`.
2. The arith block's `SigOpInfo.semM` is the definitional modular
   `Word` evaluator (`block-semM`, already landed) — it fills the
   required field and makes `exec-sigop-respects-semM` trivial once
   `execInstr` is modular.
3. The arith block discharges the `Contract` via **emit-correspondence
   + `PreservesCCC`**, *not* via the `mkPurePrimResult` "Output points
   at the input location" shortcut (which is only valid for
   identity ops and is the actual bug for `add`).

Non-goals: division/overflow value semantics (D055; deferred), bignum
(`BigInt`; deferred), the parameterised multi-target *refinement*
bridge (the original framing — mostly unnecessary now that `+`/`-`/`*`
carry no substantive value proof).

## What is already landed

- **`Once.Word`** (top-level, general; not arith-local): residue
  carrier (`ℕ` in `[0,2ⁿ)`), modular `⊕`/`⊖`/`⊗`/`⊝` + `fromℤ`,
  width via a nested `Width (bits)` module + `Word64`. (Phase 0.)
- **`block-semM`** (Block.agda) is the definitional `Word` evaluator;
  the 6 per-ctor postulates are gone. Type signature unchanged.
  *Status under the new understanding:* this is the `semM` field value;
  it is **not load-bearing** as a value spec for `+`/`-`/`*` — it just
  needs to exist and be definitional so the eventual conformance is
  trivial.

## Remaining work

### A — Make `execInstr` modular (faithfulness)

Switch each target's `execInstr` arithmetic from unbounded `d + v` to
modular `d ⊕ v` (`Once.Word`), at the target's width. Consolidate the
five bare `Word = ℕ` aliases (`CCC/Target/{X86-64,X86-32,RiscV64}/
Semantics`, `Memory`, `Memory/Memory`) onto `Once.Word`. This reworks
the `DirectSimulation` proofs that currently rely on `+` reductions —
budget for that. (`Memory`'s `Word` is addresses, not `Int` arithmetic
— fold in only once pointer-arith semantics are decided.)

### B — Discharge the arith `Contract` structurally

The blocker is `Helper.mkPurePrimResult`: it sets `Output` to point at
the *input* location (`state-eq`), i.e. asserts the value is unchanged
— true for an identity op, false for `add`. That is the real source of
the two `SMP.!!` holes and the `Faithful.agda` `add-semM x = x`
failure.

Fix: the arith block's trace is the actual `add`/`mul` instruction
sequence, and its `Contract` obligation (`IRResultAWF` ⇒ Output
represents `semM si x`) is discharged by emit-correspondence +
(trivial, once A lands) conformance to `block-semM`. Concretely
`mkPurePrimResult` must stop using the value-preserving shortcut for
value-changing ops.

### C — Multi-target + `--safe` (mechanism, secondary)

Keep the pipeline generic over the target and `--safe`-clean. With no
substantive per-op refinement proofs for `+`/`-`/`*`, this is light:
inject each target's `execInstr` / emitter; stub backends (x86-32,
RISC-V) postulate only what their *codegen* can't yet provide. `--safe`
is a packaging concern, not a design decision.

## Deferred (value specs with real content)

- **Division / signed-overflow (D055).** RISC-V-total semantics; x86/
  ARM emit a guard. This is where a value spec is genuinely needed
  (multi-instruction, target-divergent). Separate plan.
- **`BigInt` (D054).** Mathematical integers over a bignum
  representation; real refinement proof. Separate plan.

## Relationship to decisions

- **D054** — `Int` = signed modular `Word`; ℤ is the future `BigInt`
  spec. This plan implements the `Word` side.
- **D055** — total division; deferred here.
- **0.20 (parent)** — discharges the arith postulates 0.20 deferred.

## Why this is the principled fix

- **No invented value layer for `+`/`-`/`*`.** Correctness is
  emit-correspondence + structural preservation — exactly what
  single-instruction ops warrant, and what CompCert/CakeML collapse to
  for the same case.
- **The trust floor is faithful.** `execInstr` wraps, matching silicon,
  so any value observable (e.g. an exit code) is read off a correct CPU
  model.
- **`PreservesCCC` stays clean.** The structural contract never learns
  about width or overflow.
- **Value specs are reserved for where they have content** — division
  and bignum — instead of being paid as a tax on every add.
