# Plan 0.53 — Lambdas ARE Morphisms (bracket abstraction) — discharge `cata-morph-strong`

Decision: **D070**. A closed lambda `A → B` IS a morphism `A → B` (Curry–Howard–
Lambek). Elaborate closed lambdas to point-free `⊢ᵐ` morphisms via bracket
abstraction so cata/ana algebras are always morphisms, `realize-morph` stays in
IR-land, and `cata-morph-strong` is provable with the cheap structural
`morph-realize` (like the other combinators). The IR is ALREADY point-free
(`Once.Surface.Elaborate` lowers `lam`→`curry`, `app`→`apply ∘ ⟨…⟩`); this change
lives at the TYPING/derivation level only. Runtime/denotation unchanged.

## Why this is the honest fix (not the denotational patch)

`StrongElab`'s faithfulness field `m ≡ realize-morph mᵐ` is SYNTACTIC. It holds
cheaply for everything point-free (leaves/combinators via `morph-realize`,
values via `checkG-realize` — `const-morph-strong` landed this way). It breaks
ONLY for a **lambda cata algebra**, because `realize-morph (m-cata _ dalg)` round-
trips a `⊢ᶜ` algebra `elaborate Heap (realize dalg)` vs the elaborator's
`elaborate Heap algE` — meaning-equal, not term-equal. The lambda is the only
non-point-free thing that can reach a morphism IR node. Making it a morphism
removes the gap at its source. (Alternative — denotational `morph-realize` mutual
with `agree` — merely patches the presentation mismatch; rejected.)

## KEY FEASIBILITY FINDING (scopes the work)

`⊢ᵐ` is NOT closed under bracket abstraction. Current vocabulary: `m-id`,
`m-fst`, `m-snd`, `m-terminal`, `m-initial`, `m-inl`, `m-inr`, `m-compose`,
`m-case`, `m-pair`, `m-curry`, `m-cata`, `m-const`, `m-named(-resolved)`.
**No `m-apply`, no de-Bruijn var projection.** But `elaborate` uses
`app f x = apply ∘ ⟨elaborate f , elaborate x⟩` and `var i = proj i`. So a lambda
whose body contains an application bracket-abstracts to IR containing `apply`,
which `⊢ᵐ` cannot currently express. => the fix must EXTEND `⊢ᵐ`.

## Steps

1. **Extend `⊢ᵐ`** with the constructors bracket abstraction needs:
   - `m-apply` : realizes to `IR.apply`. (Check whether de-Bruijn `proj`/context
     projections are needed too — for a CLOSED 1-variable lambda the sole bound
     var is the whole input, i.e. `id`, so `proj` may be avoidable if we only
     admit closed lambdas; a nested/multi-binder lambda would need projections.)
   - Add `realize-morph`/`realize` clauses for the new constructors (direct IR).
2. **Bracket-abstraction translation** `⊢ᶜ`(closed, 1-var body) → `⊢ᵐ`, mirroring
   `Once.Surface.Elaborate` CLAUSE-FOR-CLAUSE (var0→`m-id`, app→`m-apply ∘
   m-pair …`, lam→`m-curry`, pair→`m-pair`, fst/snd/inl/inr→the leaves, morphism/
   value sub-terms→their `⊢ᵐ`/`m-const`). Because it mirrors `elaborate`, the
   resulting `realize-morph` equals the elaborator's IR BY CONSTRUCTION, so
   `morph-realize` stays syntactic.
3. **`checkElabV` RLam at an arrow type** → produce the bracket-abstracted `⊢ᵐ`
   (a `t-morph-lift` of it) instead of `t-lam`. (Keep `t-lam` only if some
   genuinely open/context-carrying use remains; for closed lambdas it becomes
   vestigial.)
4. **`morph-elab` lambda case** — now a `⊢ᵐ` morphism, cheap `StrongElab` like the
   other combinators (`morph-realize` syntactic).
5. **Discharge `cata-morph-strong`** — the algebra is now always a morphism (or a
   realize-syntactic `⊢ᶜ`), so the StrongElab realize field closes structurally.
   Remove the postulate.
6. **Verify downstream** — `RealizeAgrees` `agree` (the `t-lam`/lambda cases and
   `morph-realize` consumers), `SourceFaithful`, apex `make certified`. D066's
   `*-eff-complete` guarantee is preserved (arms become morphisms BEFORE the arm
   position, so still lambda-free).
