# Plan 0.71 — float literals, and the width that is not the same everywhere

**Status**: OPEN, written 2026-08-18. **Depends on plan 0.66** (D109 made the
float encoding a target parameter). Successor to the D109 correction.

## The gap

`Float` is a type in the grammar (`G.TFloat`), a type in the core (`T.Float`), a
constant in the IR (`const : FitsInRegI A → ⟦ Carrier ⟧-baseI A → IR Unit A`), an
instruction in the abstract machine (`instr-load-const fits-float v`), and an
emitted immediate on all three targets. **No source program can produce one.**

    Once/Parser/Token.agda      TInt, TString — and no float token; `TDot` only
                                ever accumulates into an operator/qualified name
    Once/Surface/Elaborate.agda intLit n = const fits-int ∣ n ∣ ∘ terminal
                                — the only literal there is, and `Float` appears
                                nowhere else in `Once/Surface/`

So the whole float-constant path below the frontend is code on a road with no
on-ramp. Float VALUES can still exist at runtime — `intToFloat`, `parseFloat`,
`pi` are SigOps — but a float CONSTANT cannot be written.

This plan builds the on-ramp. It is worth doing carefully because the thing at
the other end changed under us in 0.66.

## Why this is not "add a token"

D109: **a `Float` is not the same width on every target.** It is a double on
x86-64 and riscv64 and a SINGLE on x86-32, because a 32-bit register cannot hold
a double and `ud2` was the honest lowering until the encoding became a target
parameter (`FlatCore.FlatCorrespondence`'s `fenc`).

A literal is a source-level object; its width is a target-level fact. Write
`0.1` and the three targets disagree about what you wrote — not by a rounding
step you can point at, but in the value the program computes. That is precisely
the defect class D109 is about, arriving one layer up.

### THE RULE THIS PLAN COMMITS TO

**A float literal is accepted only if its value is exactly representable at
EVERY supported target width; otherwise it is a compile-time error.**

    0.5   0.25   1.5   2.75   3.0   0.125      accepted — dyadic, tiny mantissa
    0.1   0.2    3.14  1e-40              REJECTED — no exact binary form, or
                                          exact only at the wider width

The rejected cases are rejected LOUDLY, with the value and the reason, not
rounded. Three consequences worth stating plainly:

1. **A literal means one number, on every target.** That is the property worth
   paying for, and rounding-per-target is what buys the bug instead.
2. **Adding a narrower target retroactively rejects programs.** If an 8-bit-ish
   float target ever lands, literals that no longer fit stop compiling. That is
   the correct failure: the alternative is the same program quietly computing
   different numbers on different machines.
3. **`3.14` is not writable.** Constants like π come from the `pi` SigOp, or
   from `parseFloat`, or from arithmetic — all of which already exist and are
   already per-target. The literal syntax is for the values that are exact.

The bound lives in ONE place (a `FloatFormat` record: significand bits and
exponent range, currently single precision), so "which widths are supported" is
one edit and not a survey.

## The representation: dyadic, not `AgdaFloat`

**The AST must not carry an `AgdaFloat`.** Not for purity's sake — for three
concrete reasons:

- Putting a `Float` in the AST means the frontend has already rounded, and then
  the acceptance check above cannot be stated: the evidence it needs is gone.
- `Data.Float`'s `toWord` is a primitive with a NaN edge case (`float-bits`
  encodes NaN as 0) and NO stated range bound — which is exactly why
  `LitFits.float-fits` is a PARAMETER on all three arches today, "provable the
  day the standard library states it".
- Agda's `Float` is a double. Using it as the frontend's notion of the value
  bakes the widest target into the language.

So a literal is a DYADIC RATIONAL: `sign × m / 2^e`, with `m e : ℕ` and `m` odd
(lowest terms). Decimal digits in, exact rational arithmetic on ℕ, no rounding
anywhere in the frontend. Then:

- the acceptance check is decidable ℕ arithmetic with a soundness proof, not an
  appeal to a primitive;
- **the encoders become arithmetic.** `float-bits` / `float-bits-single` stop
  being `primFloatToWord` and become functions of `(sign, m, e)` per width — at
  which point `float-fits` is DISCHARGED rather than assumed, on all three
  arches. That is a residual removed, not moved.

`Once.CCC.Eval`'s `eval (const fits-float v) _ = v` needs the denotation to stay
a real number-ish object; the dyadic triple denotes into `AgdaFloat` at the
denotation boundary only, where rounding is observation and not compilation.

## Phases

### F1 — the token

`Once/Parser/Token.agda` gains a float literal token carrying DIGITS (integer
part and fraction digits as `List Char`/`ℕ`), not a value. `Parser/Lexer.agda`
recognises it; the classifier bridge (`Adequacy/LexerBridge`) and the
sound/complete pair follow. **Budget the proofs, not the clause**: the lexer is
postulate-free today and must stay so.

Gate: lexer sound+complete green, `certified` green.

### F2 — grammar, parser, printer

Concrete syntax + `parseAtom`; `Grammar/Printer.agda`'s round-trip lemma gets a
float case (`round-trip-Float` exists for the TYPE already — this is the LITERAL).
The parser must not become bound-carrying: see the completeness-wall note in
`0.7-parser-strictness-relational`.

Gate: parser sound+complete; printer round-trip; `certified`.

### F3 — surface AST and typing

A `float` literal expression, typed `Float`. Mirrors `int` exactly, including
the QTT multiplicity story (a literal is unrestricted).

### F4 — the acceptance check

`decimal→dyadic : digits → Maybe Dyadic` plus `fits-format? : FloatFormat →
Dyadic → Bool`, both decidable, with soundness: an accepted literal's dyadic
value is exactly representable at the format. The ERROR path is a real
type-checker error with the offending literal, joining the existing error family
(and its error-preservation obligations — see plan 0.9).

Gate: a rejected literal produces an error, not a value; `0.1` is a test case.

### F5 — elaboration and the IR payload

`floatLit` elaborates to `const fits-float …` — and the payload type changes
from `AgdaFloat` to the dyadic triple. Blast radius, measured before starting:
`⟦ Carrier ⟧-baseI`, `CCC/Eval`, the three emitters' const clauses, the three
`block-step-load-const-float` lemmas, `LitFits.float-fits`, and D109's `fenc`
parameter (whose type becomes `Dyadic → ℕ`).

**This is the step that could grow.** If it does, the fallback is to keep the
IR payload as-is and convert at elaboration — but that gives up F6, so it is a
fallback and not a first choice. Decide with a measurement, not a guess.

### F6 — discharge `float-fits`

With dyadic payloads the encoders are arithmetic and their range is provable:
`float-bits-single`'s parts are bounded by 2³¹, 255·2²³ and 2²³. Remove the
parameter from `LitFits` on all three arches — a residual deleted.

### F7 — the tests (the reason this plan exists)

Three layers, cheapest first:

1. **The trap regression, needing NO `Math/Float.<arch>` implementation.** A
   program that merely BINDS a float literal and exits 0. Under the pre-0.66
   x86-32 lowering this is `ud2` — the process dies — so the test would have
   caught D109 on the day float literals landed. Runs on all three arches
   through `Backend.Common.exitCases`.
2. **Value tests through the existing SigOps** — `floatToInt 2.75 = 2`,
   `feq (1.5, 1.5) = 1`. These need per-arch implementations, and here is the
   blocker: `Strata/Interpretations/Math/` has `.x86_64`, `.riscv64`, `.arm64`,
   `.c` — and **no `.x86_32`**. Writing one is a named sub-task of this plan
   (single precision, per D109) and is what "float tests on every arch" costs.
3. **Exit tests** for the same programs, so the counts move together.

Every literal used is dyadic with a small mantissa — `0.5`, `1.5`, `2.25`,
`3.75` — so the expected result is identical at 64, 32 and any narrower width a
future target brings. That is the same property F4 enforces, exercised.

## What this plan does NOT do

- **Float arithmetic in the compiler.** `fadd`/`fmul`/… stay SigOps with
  per-arch implementations. No FPU instruction is emitted by codegen.
- **Transcendentals, `parseFloat`, `floatToString`.** Unchanged.
- **A general decimal→binary conversion.** Rejecting `0.1` is the design, not a
  limitation to be lifted later without re-reading D109.

## Done means

`1.5` is writable in a `.once` file; `0.1` is a compile error naming itself;
the same literal denotes the same number on x86-64, x86-32 and riscv64; the
`float-fits` parameter is gone from all three arches; and `cabal test` exercises
float literals on every backend arch.
