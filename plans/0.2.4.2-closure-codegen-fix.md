# Plan 0.2.4.2: Closure Codegen Lifetime Fix

## Context

End-to-end testing of `main = exit seven` during plan 0.2.4.1
Phase D exposed a cluster of codegen bugs in the closure /
apply machinery. The SigOp framework itself is correct: integer
literals codegen to `mov $N, %rax`, the Linux `exit` syscall
emits `mov $60, %rax; syscall`, and both reach the binary. The
compiled program no longer traps on `ud2`.

What breaks: the binary for `main = exit seven` SIGSEGVs before
the syscall fires. Root cause is the closure-allocation path:

```asm
once_main:
  sub  $0x10, %rsp        ; allocate 16 bytes for closure pair
  mov  %rdi, (%rsp)       ; closure[0] = env
  lea  0x4(%rip), %r9     ; r9 = <wrong offset, mid-instruction>
  mov  %r9, 0x8(%rsp)     ; closure[1] = code pointer (garbage)
  mov  %rsp, %rax         ; rax = closure pointer
  jmp  ...
  ...
  ret                     ; pops from [rsp], but rsp still points
                          ; to closure[0] — pops garbage as return
                          ; address. SIGSEGV.
```

Three overlapping defects, each shippable as its own change:

### B1. Stack-frame lifetime violation

`once_main` builds the closure on its **own** stack frame via
`sub %rsp, 16`, captures a pointer to that memory in `%rax`, and
returns. The `ret` doesn't restore `%rsp`, so it pops the
closure's first word as the return address. Even if `ret`
restored `%rsp` correctly, the closure pointer is dangling — the
caller would deref memory that's about to be reused.

Classic use-after-free on the stack. Both `ret`-order and
lifetime are wrong.

### B2. `lea (rip+disp n)` offset is hand-written

`curry-closure-setup` emits `lea r9 (rip+disp 4)` but the
correct offset (to skip the subsequent `mov`/`mov`/`jmp` and
reach the thunk body) is `10` bytes. The abstract semantics in
`DirectSimulation.exec-x86` models any `lea rip+disp` as identity
(catch-all), so the bug is invisible to the correctness proof.

Plan 0.9 (exhaustive semantic case-splits) catches this class at
the *pattern-match* level — see below under "Relationship to 0.9."

### B3. `AllocMode` ignored in curry codegen

```agda
compile-ir' n (curry f _) = …          -- ← _ discards Stack vs Heap
```

The elaborator marks closures as `Heap` (intended: stable
lifetime). The codegen pattern-wildcards the mode, producing
stack-allocating instructions regardless. This is another catch-
all gap that plan 0.9 would surface: the compiler would require
explicit `compile-ir' n (curry f Stack) = …` and
`compile-ir' n (curry f Heap) = …` clauses, forcing the author
to actually implement heap allocation.

### B4. `apply-instrs` register ABI assumes `%rsi`

Secondary: the apply codegen reads from `%rsi` as if it holds
the arg, but no instruction in the calling sequence writes `%rsi`
beforehand. Probably fallout from an older ABI attempt.

## Goal

Fix closure lifetime and the related codegen bugs so programs
using effectful or first-class closures (`curry` / `apply` /
`effApp`) actually run. The canonical test:

```once
signature exit : Eff Int Unit
seven : Int
seven = 7
main : IO Unit
main = exit seven
```

must compile and produce exit code `7`.

## Scope

**In scope:**

- **B3 (AllocMode dispatch)**: make `compile-ir' (curry f mode)`
  pattern-match on `mode`. Heap path allocates in a region
  whose lifetime survives the creating function. Stack path
  (if retained) carries an escape-proof obligation.
- **B1 (lifetime)**: for the Heap path, allocate either on a
  heap region, or in the caller's frame via a dedicated
  caller-provided slot, or (minimum viable) via a static data
  region / bump allocator. The closure pointer must be valid
  across the creating function's `ret`.
- **B2 (lea offset)**: derive the offset from the lengths of
  the intervening instructions rather than hand-writing `4`.
  `lea r9 (rip+disp (length intervening-instrs))`.
- **B4 (apply ABI)**: audit `apply-instrs`; verify and document
  which registers hold closure pointer vs arg on entry; fix the
  `%rsi` dependency.
- `_start` stub in the assembly header that invokes `once_main`
  and applies the returned closure to `tt` to drive the effect.
  (The stub from the reverted f00e8126 is correct in shape; its
  problems were downstream of the closure bugs, not the stub
  itself.)
- Regression test: compiled `layer0-neg.once` binary exits with
  code `7`.

**Out of scope:**

- Formal correctness proofs for the new codegen (separate plan).
  This plan fixes the emitted bytes; proof-level updates come
  later.
- Introducing a heap allocator in the runtime. If the Heap path
  requires allocation, for this plan we may use `mmap`/`brk` as
  a bump allocator with a fixed-size pool.
- Region-based types in the IR (see "Future work").
- x86-32 and RiscV64 targets. Same bugs likely exist in their
  `DirectSimulation` + codegen but are not this plan's scope.

## Locked architectural decisions

### D1: Closure allocation region follows `AllocMode` strictly

The codegen **must** dispatch on `AllocMode`. No wildcard. If
`--exact-split` is enabled first (plan 0.9 Phase B), this is
enforced by the compiler. Independent of whether plan 0.9 has
landed, this plan explicitly writes two clauses:

```agda
compile-ir' n (curry f Stack) = <stack-alloc instructions>
compile-ir' n (curry f Heap)  = <heap-alloc instructions>
```

If the plan lands *after* 0.9, this is forced by `--exact-split`.
If it lands *before* 0.9, it's still the discipline — 0.9 then
ratifies it.

### D2: `lea rip+disp` offset is derived, not written

Add a codegen helper `rip-offset-to-label : List Instr → ℕ`
that computes byte-offset from an instruction-list length. The
closure setup reads this rather than a magic number `4`.

Benefit: when the intervening instruction sequence changes
(e.g. a new field added to the closure), the offset updates
automatically. The author can't forget to recompute.

Relates to gap class G in plan 0.9's catalogue (hard-coded
constants unverified by the model).

### D3: Heap path uses a single static data region for now

For this plan's minimum viable fix, the Heap allocation uses
a statically-allocated global buffer (fixed-size, bump-pointer).
The buffer lives in the program's `.bss`. This is enough to
make closures survive their creating function's `ret`.

A proper heap allocator (GC, RC, or linear regions) is future
work. The static buffer is a known-limited solution that unblocks
end-to-end execution; out-of-memory behavior is "trap" for now.

### D4: `_start` stub emitted from Agda, not hand-written

Put the `_start` stub in `Once.Target.X86-64.x86-64-asmHeader`
(as in the reverted f00e8126). Keep it Agda-side so it's part of
the formal output, not a CLI workaround.

## Implementation phases

### Phase A — `AllocMode` dispatch

Split `compile-ir' (curry f _)` into Stack and Heap cases. For
this phase, the Heap case can still emit stack-allocating code
(with a comment "TODO: heap allocation"). The goal is to surface
the distinction; correct allocation comes in Phase B.

`make compiler` green. Binary behavior unchanged (still segfaults
until Phase B).

### Phase B — Static heap pool + Heap-path codegen

1. Reserve a `.bss` pool (e.g., 64KB) in the asm header.
2. Add a global variable tracking the bump pointer.
3. Emit codegen for the Heap-curry case:
   - Atomic bump: compute new pointer, write, return old.
   - Store closure env + code pointer into the allocated region.
4. Trap on out-of-memory (a second `ud2` with a clear comment).

Verify: the binary runs without segfault at the closure build
site.

### Phase C — `lea` offset derivation + apply ABI fix

1. Replace `lea r9 (rip+disp 4)` with a derivation from
   instruction-sequence length.
2. Audit `apply-instrs`; identify every register the code reads
   from before writing. Fix any that the calling convention
   doesn't guarantee.
3. Re-run Layer 0 test.

Expected: `layer0-neg.once` exits with `7`.

### Phase D — `_start` stub

Add the stub from f00e8126 to the asm header. Remove any
`--entry=` flags from the linker invocation. Rebuild, test.

### Phase E — Regression test

Add a Haskell-side test (`Layer0ExitSpec`) that builds + runs
`layer0-neg.once` and asserts exit code `7`. Wire into
`make test-x86-level0`.

### Phase F — Decision log D050

Document the static-pool decision and its known limits.
Reference 0.9's D049 as the upstream lever that would have
caught B3 (and B2, at a different level).

## Success criteria

- `layer0-neg.once` binary exits with status `7`.
- `make compiler` + `make malonzo` + `cabal build` clean.
- `compile-ir' (curry f _)` gone; explicit Stack / Heap clauses.
- `lea (rip+disp N)` offsets derived programmatically, not
  hand-written.
- `apply-instrs` register ABI audited and documented.
- `_start` stub is part of the Agda-side asm emission.
- D050 in the decision log.

## Risks

1. **Static pool is a temporary hack.** Programs that exhaust the
   pool will trap. Mitigation: document as known-limited; future
   plan adds proper allocator.

2. **`lea` offset derivation interacts with jump sizing.** Short
   vs long jumps have different byte sizes; if the intervening
   jmp has to become 5 bytes, the offset shifts. Mitigation:
   pessimistically assume worst-case jmp size, or use two-pass
   codegen.

3. **`apply-instrs` fix may cascade.** If the ABI was wrong, some
   upstream proof may have compensated wrongly. Mitigation: audit
   `run-apply` in `CCC.Machine.IR.ApplyWF` for assumptions about
   register state on entry.

4. **Closure Stack path still unsafe.** Even with the mode
   dispatch, Stack-allocated closures whose pointer escapes are
   bugs. This plan doesn't type-enforce safety of the Stack
   path. Mitigation: emit Heap for any closure whose output is
   the function's return value (escape-conservative default);
   document that Stack is reserved for closures consumed before
   return.

## Relationship to other plans

- **Parent: 0.2.4** (Categorical Layer 0). This plan is the
  second layer-0 unblocker (after 0.2.4.1 closed the SigOp side).
- **Sibling: 0.2.4.1** (SigOp framework). Completed end-to-end
  except for the closure bugs this plan fixes.
- **Upstream: 0.9** (exhaustive semantic case-splits). If 0.9
  lands first, the `curry f _` pattern that hid B3 is a compile
  error, and the author is forced into explicit dispatch before
  writing any codegen. 0.9 does **not** fix B1 (lifetime) —
  that's a runtime correctness bug the type system doesn't catch
  without region types. But 0.9 does catch B2 and B3 at the
  source level.
- **Future**: region-typed closures would type-enforce B1. A
  plan for that would be a significant addition to the IR and
  every proof touching closures — out of scope here but worth
  noting as the principled long-term fix.

## Non-goals

- Correctness proofs for the new codegen. The Agda-side machine
  model in `DirectSimulation` will need updates to reflect heap
  allocation; doing that properly is a separate plan.
- Garbage collection or any reclamation strategy for the static
  heap pool. Fixed budget, trap on exhaustion.
- x86-32 and RiscV64 mirror fixes. Same bugs likely exist; same
  plan shape applies; scope separately.

## Author's note

This plan is surgical on runtime correctness. It does NOT attempt
to make the closure system safe-by-construction — that requires
region types or similar heavier type-level machinery (see plan
0.9's gap-class catalogue, row B adjacent). It fixes the
immediate wrong behavior so that the SigOp framework's end-to-end
claim ("`exit 7` actually exits with 7") holds on real hardware.
