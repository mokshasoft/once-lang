# Plan 0.94 — The judgment must not distinguish a definition from its definiens

## 0. The one property

> **`let x = e in b` and a top-level `x ≝ e` used in `b` must be
> interderivable.**

Once's thesis is that programs are mathematical statements. A type system in
which a definition and its definiens are not interchangeable is not stating
mathematics — it is stating facts about the spelling of the program.

The metatheoretic name is the **substitution lemma**, with its module-level
twin, closure under **δ-unfolding**:

        Γ ⊢ᵢ e ∶ A     Γ , x∶A ⊢ᶜ b ∶ B                 u ≝ e
        ───────────────────────────────         ─────────────────────────
              Γ ⊢ᶜ b[e/x] ∶ B                    ⊢ b[u]  ⟺  ⊢ b[e/x]

Neither holds today.

## 1. The measurement — verified 2026-09-19

Machine-checked against the built compiler. Same `u`, same type; the ONLY
difference is top-level name vs. let-bound variable:

```once
u : IO Unit                                                    -- top-level
u = emit@E 9
f = compose exit@S (compose (\_ -> 7) u)                       -- Typecheck OK

f = let u = emit@E 9 in compose exit@S (compose (\_ -> 7) u)   -- REJECTED
```

`let u = emit@E 9 in u` infers fine on its own, so the binding is not at fault.
It is not about effects either: `let g = id in compose id g` fails identically.

### The cause

`Judgment.agda` has **four premises that compute on syntax**:

    Judgment.agda:559   t-compose-check          composeMid ctx f g A ≡ just B
    Judgment.agda:467   t-app                    classifyAppHead f ≡ nothing
    Judgment.agda:484   t-effApp                 classifyAppHead f ≡ nothing
    Judgment.agda:734   t-arg-driven-app-check   classifyAppHead f ≡ nothing

and imports them at `Judgment.agda:60-65`:

```agda
open import Once.TypeCheck.Classify
  using (NamedCtx; lookupLocal; lookupImport; lookupPoly; lookupPolyPrefix;
         removePoly;
         ctxWithImportsAndPolys; extendNamedCtx; classifyAppHead;
         composeArgB; composeMid)
```

**That import line is the defect.** A premise that inspects syntax cannot be
stable under substitution, because substitution changes syntax.

* `composeMid`/`composeArgB` (`Classify.agda`) is a *syntactic partial
  synthesizer*: it matches the argument's SHAPE — `RInt`, `RLam _ (RInt _)`,
  `RLam _ (RFloat …)`, `RLam _ (RStringLit _)`, `RLam _ RUnit`, a nested
  `compose`, or a name — to guess the middle type. `composeArgB-lookup`
  (`Classify.agda:309`) consults `NamedCtx.polys` and `NamedCtx.imports` and
  **never the local context**, which is exactly why a top-level `u` is found
  and a `let`-bound `u` is not.
* `classifyAppHead` is **ctx-free**: it classifies `RApp (RVar "fst") 5` as the
  builtin regardless of a user binding. Plan 0.80 documents this as a
  CONFIRMED BUG inherited from the unfinished generator-namespace migration.

`Classify.agda` states the defect against itself:

> "It stays a LITERAL enumeration for the reason `composeArgB` is a syntactic
> partial synthesizer at all: it sits below the judgment (`t-compose-check`
> names `composeMid`), so it **cannot consult inference**. Plan 0.80 Phase B is
> what would let this be a real synthesis question instead."

## 2. The rule

**Every premise of a typing rule must be a judgment, not a computation on
syntax.**

This is plan 0.80's thesis. 0.80 Phase A landed the deciders-standing-in-for-
properties half (`wellFormedF?`, `isGround`). These four are Phase B, and they
are the remaining violations.

## 3. Why this is not just plan 0.80 again

Plan 0.80 framed Phase B as a **trade**: delete the premise, `check-complete`
goes false, "well-typed ⇒ compiles" weakens to "well-typed AND elaborable ⇒
compiles", and that is an apex decision it is blocked on.

That measures *deleting* the premise. The third option 0.80 does not list is
**replacing** it:

    ctx ⊢ᶜ f ∶ (B ⇒[π] C)   →   ctx ⊢ᶜ g ∶ (A ⇒[π] B)
    ────────────────────────────────────────────────────
    ctx ⊢ᶜ compose f g ∶ (A ⇒[π] C)

declarative in the judgment, with the *elaborator* gaining a
**domain-given / codomain-synthesised** checker — the application/spine mode of
bidirectional typing. `check-complete` then stays true, because the elaborator
can actually find what the rule asserts.

Measured 2026-09-19: plain inference covers only **3 of 10** shapes (`42`, a
top-level name, an applied SigOp — lambdas and bare polymorphic builtins do not
infer). But `compose f g : A ⇒ C` **knows `A`**, and with the domain given all
five failing shapes check:

| shape | infer alone | domain given |
|---|---|---|
| `\_ -> 42`, `\y -> y` | no | **checks** |
| `id`, `fst` | no | **checks** |
| nested `compose` | no | **checks** |

Strictly stronger than `composeArgB`: `\y -> y` works, which the eight-shape
enumeration cannot express at all.

## 4. The known risk

**The middle type is not unique.** `initial : Void ⇒ B` checks at `Int` *and*
at `Float` (both verified). So once the premise is gone, `compose f initial`
has a derivation at every `B`, and `check-complete` becomes "the elaborator
finds *a* `B` that makes the rest check", not "*the* `B`".

POC this single case before committing to the rest.

*(2026-09-25)* The SEMANTIC half is done: `Once.Denotation.Sub.void-middle`
(plan 0.99, D226) proves the composite through `Void` means the same at every
middle type, and does not depend on `f`. What remains here is completeness —
the elaborator must FIND a middle type wherever the judgment admits one.

## 4b. CORRECTION (2026-09-19) — the GENERAL lemma is FALSE, for a reason
##      that has nothing to do with the four premises

Stating the general substitution lemma was the wrong target. It is **refutable
on `t-case`'s usage algebra**, independently of any syntactic premise.

`t-case` (`Judgment.agda:288-297`) concludes `⨾ (Ψs +ᵘ (Ψₗ ⊔ᵘ Ψᵣ))` from
premises at `(qL ∷ᵘ Ψₗ)` / `(qR ∷ᵘ Ψᵣ)` — the two branches may use the
substituted variable at DIFFERENT quantities. With `Ψₑ` the definiens' usage,
induction yields

    (Ψs' +ᵘ as*ᵘΨₑ) +ᵘ ((Ψₗ' +ᵘ aₗ*ᵘΨₑ) ⊔ᵘ (Ψᵣ' +ᵘ aᵣ*ᵘΨₑ))

while the conclusion demands

    (Ψs' +ᵘ (Ψₗ' ⊔ᵘ Ψᵣ')) +ᵘ ((as +q (aₗ ⊔q aᵣ)) *ᵘ Ψₑ)

Counterexample: `Ψₑ=[One]`, `Ψs'=[Zero]`, `as=Zero`, `Ψₗ'=[One]`, `aₗ=Zero`,
`Ψᵣ'=[Zero]`, `aᵣ=One` gives LHS `[One]`, RHS `[Many]`. `One ≠ Many`.

Repairing it needs usage subsumption, and **the judgment has no usage-weakening
rule**, so every consumer would absorb an existential `∃ Ψ′ , Ψ′ ≤ᵘ …`.
Separately there is **no judgment-level weakening lemma at all** (`weaken`
exists only on `SExpr` via `Surface.Thinning`), and weakening is not
unconditionally admissible: `t-var-import` (`:177`) and both poly-instantiate
rules carry `lookupLocal ctx x ≡ nothing`, which a new local named `x`
falsifies.

**With a CLOSED definiens the problem vanishes**: `Ψₑ = zeroUsage`, and
`*ᵘ-zeroʳ` (`Surface/Properties.agda:124-128`) + `+ᵘ-identityʳ` (`:107-109`)
collapse both sides. Both lemmas already exist.

## 4c. THE RIGHT STATEMENT — context transfer, with NO substitution

§0's own wording never mentions substitution: *`b` is the same term on both
sides; only where `x` lives changes.* So state it as a context transfer:

```agda
let-is-def :
  ∀ {Γ x A B e b Ψ q schema}
  → Γ ⊢ᶜ e ∶ A ⨾ zeroUsage                    -- definiens CLOSED
  → lookupLocal Γ x ≡ nothing
  → lookupImport (NamedCtx.imports Γ) x ≡ nothing
  → ( (extendNamedCtx Γ x A) ⊢ᶜ b ∶ B ⨾ (q ∷ᵘ Ψ)
    ⟺ (Γ ⟨polys ↦ (x , schema , e) ∷ polys⟩) ⊢ᶜ b ∶ B ⨾ Ψ )
```

* **No new machinery on syntax.** No `freeVars`, no `renameRaw`, no
  `substRaw`, no freshness lemma — the ~225-280 lines of §5 item 1 are not
  needed.
* **The usage lines up exactly**, and not by accident: let-side occurrences of
  `x` are `t-var-local` (usage `singleUse i One`), def-side are
  `t-var-poly-instantiate*` (usage `zeroUsage`, `:216`, `:781`), so the TAIL
  `Ψ` is identical on both sides.
* **It captures the measured bug exactly** (§1). It does NOT capture
  δ-unfolding — replacing the name by the body — which remains the other half
  of §0 and still wants the closed-definiens substitution lemma (~40 lines,
  no capture-avoidance, since every definiens is typed at `size = 0`).
* **Cost**: ~600-900 lines, one mutual 53-rule induction per direction, zero
  research risk.

**So the target changes**: prove `let-is-def` (context transfer) plus a
closed-δ substitution lemma. Skip general capture-avoiding substitution
entirely — it buys a theorem that is false as stated.

## 8. Phase C′ — eliminations synthesize: `cata` (b′, D228)

**Why here.** Plan 0.99 made `t-sub` the only conversion, at the mode switch.
One corner lost its derivation: `(cata alg) x` checked at an eff arrow when the
fold's result is a pure arrow (0.99 §8). The cause is that `cata` is typed as
check-only although it is the ELIMINATOR of `μF`. By initiality `cata alg` is the
unique morphism `μF → A` determined by its algebra, so its type is determined:
`F` by its argument (or the expected arrow's domain), the carrier `A` by the
algebra. That is exactly the domain-given, codomain-synthesized mode of §3 —
the same machinery phase C builds for `compose`.

**The rule** (shape, to be settled in the POC):

    alg ⊢ᵢ ⟦F⟧ A ⇒[π] A        (the algebra SYNTHESIZES its carrier)
    ───────────────────────────  given the domain μ-type F
    cata alg  ⇒  μ-type F ⇒[π] A        (the result is synthesized)

after which `t-sub` converts the result (e.g. the pure arrow `A` to its eff
version). The existing `t-cata-check` (algebra CHECKED at a given carrier) stays,
so no program that types today stops typing. An algebra that does not synthesize
(an unannotated lambda) gets no synthesis derivation: a type error asking for an
annotation, stated by the rule's premise — so `check-complete` remains true.

**Not doing:** a separate grade rule (`t-grade`, the Freyd `J` on checked
morphisms) or any interim stopgap. Either would be a second conversion mechanism
this phase makes redundant (D228).

**Runtime:** unchanged. The conversion is grade-only (void-free ⇒ `runCoe` emits
no code) and `cata` still compiles to `IR.Cata`. REQUIREMENT: the elaborator's
synthesis path emits the SAME Surface term as the checking path, so the IR is
identical.

**Gates:**
  1. POC first (extends phase A): a throwaway module showing the corner is
     underivable in the current judgment, and derivable with the C′ rule plus
     `t-sub`.
  2. `check-complete` green with the new rule (the elaborator finds the
     synthesis derivation whenever the algebra synthesizes).
  3. No-shrink: the old `t-subsume` is admissible — `⊢ᶜ e ∶ A ⇒[q pure] B →
     ⊢ᶜ e ∶ A ⇒[q eff] B` — which is plan 0.99's owed phase-D gate.
  4. `Certified` green on all three arches; postulate count unchanged; island
     backstop green.
  5. Extraction gate (standalone): exit tests unchanged — the IR does not move.

## 9. Phase A finding (2026-09-25) — the middle type needs NARROWING, and the eliminators block it

With `composeMid`'s premise deleted, `compose f g ∶ A ⇒ C` has a derivation at
every middle `B` that makes both halves check. `void-middle` (plan 0.99) proves the
MEANINGS agree whatever `B` is. The remaining question is completeness: which `B`
does the checker pick? The principled choice is the PRINCIPAL one — the least type
`g` produces, e.g. `Void` for `g = initial` — after which `f` is checked at
`Void ⇒ C`, i.e. its binder is NARROWED from the `B` the programmer meant to `Void`.

That is only complete if narrowing is admissible:

    Γ , x ∶ A ⊢ e ∶ T   and   A′ <: A   ⟹   Γ , x ∶ A′ ⊢ e ∶ T

and today it is not. Twelve elimination rules INFER their principal argument at an
EXACT shape (`Judgment.agda`): `t-neg` (Int), `t-case` (a sum), the five binops
(Int/Float, overloaded), `t-fst-app`/`t-snd-app` (a product), `t-apply-app-infer`,
`t-apply-eff-app-infer`, `t-apply-check` (a closure pair), `t-Out-app-infer` (ν),
and the `t-app`/`t-effApp` heads (an arrow). Inferring the principal argument is
right (eliminations synthesize); demanding the exact SHAPE is what breaks narrowing:

* `x ∶ Void` — `x + 1`, `fst x`, `x y` all fail although `Void <: Int`, `Void <: A * B`,
  `Void <: A ⇒ B`;
* `f ∶ A ⇒[pure] B` narrowed from `A ⇒[eff] B` — `t-effApp` demands an eff head.

The same property is what `t-sub`'s inferred premise (D226) and phase C′'s `cata`
(D228) lean on, so this is the plan's central design question, not a side issue.

**Options (the user's decision):**

  (i) ELIMINATE UP TO SUBTYPING. Each eliminator infers its principal argument and
      then MATCHES the inferred type against its shape up to `<:` — the standard
      bidirectional-with-subtyping form (Dunfield–Krishnaswami's application
      judgment). `Void` as a principal argument needs a rule of its own: it
      eliminates to `Void` (ex falso propagates), which is canonical because `¡` is.
      Narrowing then becomes a THEOREM, and the principal middle type is complete.
      Cost: every eliminator's rule, its elaborator case and its completeness case
      change; the meaning is unchanged (the conversions involved are `⟦ p ⟧<:`).
 (ii) PICK THE MIDDLE FROM `f`'S SIDE when `f` synthesizes (its domain), and only
      fall back to `g`'s principal type otherwise. Smaller, but incomplete exactly
      when `f` is a lambda and `g` ends in `Void` — the `compose f initial` case §4
      named.
(iii) KEEP A MIDDLE-TYPE PREMISE, stated as a JUDGMENT rather than `composeMid`'s
      syntactic computation (0.94 §2 only forbids computations on syntax). Smallest;
      leaves the middle type chosen by the programmer's annotation when ambiguous.

**Decision (2026-09-25, D229): (i).** Recommendation was: (i). It makes narrowing a theorem, which is also what completes
D226 (conversion at the mode switch loses nothing) and D228 (`cata` synthesizing
then converting) — the three decisions become one principle: every elimination
consumes its principal argument UP TO SUBTYPING, every introduction checks.

**Amendment (2026-09-25, D229 β):** narrowing is required, and proved, for `Void`
only. Lowering a grade (`eff` → `pure`) is not narrowing-safe, because `t-app` and
`t-effApp` give `f x` different result TYPES (`B` vs `Unit ⇒[eff] B`); the principal
middle type therefore never lowers a grade — the grade is the one the programs fix.
Grade narrowing is an open question for later (routes: α reverses D127, γ reopens D018).

## 10. Decision (2026-09-26): the middle type is LOCALLY DETERMINED (B)

The meaning of `compose f g` never depends on the middle type (coherence,
`void-middle`), so "some `B` exists" is the extensional statement. But the Spec
also decides ACCEPTANCE, and "some `B` exists" accepts programs whose middle type
is determined only by solving constraints across both halves —
`compose (\k -> k 1) (\y -> \z -> y)` — i.e. unification, which Once's verified
checker deliberately avoids (D044/D045; D072's oracle is untrusted and not proven
complete). A Spec saying "exists" would make `check-complete` false there.

So the Spec follows LOCAL type inference (Pierce–Turner), the discipline the
bidirectional judgment already embodies: the middle type comes from `g` given its
input, or from `f`'s synthesized type, and otherwise an annotation is required.
The decision is local to the `compose` node, not program-wide.

    ctx ⊢ᵈ g ∶ A ⇒[π] ↦ B          -- DOMAIN-GIVEN: given input A, g's output is B
      d-infer   : ctx ⊢ᵢ g ∶ A′ ⇒[q π′] B  →  A <: A′  →  π′ ⊑π π  →  ctx ⊢ᵈ g ∶ A ⇒[π] ↦ B
      d-lam     : (ctx , y ∶ A) ⊢ᵢ body ∶ B  →  …           →  ctx ⊢ᵈ (\y → body) ∶ A ⇒[π] ↦ B
      d-compose : ctx ⊢ᵈ g₂ ∶ A ⇒[π] ↦ M  →  ctx ⊢ᵈ g₁ ∶ M ⇒[π] ↦ B  →  ctx ⊢ᵈ compose g₁ g₂ ∶ A ⇒[π] ↦ B
      (further combinator rules as `check-complete` asks for them)

    t-compose-check-g : ctx ⊢ᵈ g ∶ A ⇒[π] ↦ B  →  ctx ⊢ᶜ f ∶ B ⇒[π] C  →  compose f g ⊢ᶜ A ⇒[π] C
    t-compose-check-f : ctx ⊢ᵢ f ∶ B ⇒[q π′] C′  →  ctx ⊢ᶜ f ∶ B ⇒[π] C  →  ctx ⊢ᶜ g ∶ A ⇒[π] B
                        →  compose f g ⊢ᶜ A ⇒[π] C

`⊢ᵈ` is the "domain-given, codomain-synthesized" mode of §3 as a JUDGMENT (every
premise a judgment, §2); C′ (`cata`, D228) reuses it. `B` is determined by the
derivation, so the elaborator makes no choice — no grade search, and `compose` does
NOT need `Void`-narrowing (D229 stays a desirable metatheorem, not a prerequisite).
The `d-*` rules cover every shape `composeMid` handles today (names, lambdas with a
synthesizing body, nested `compose`), so nothing that types today stops typing.
A program with no locally determined middle type is rejected with a message asking
for an annotation. D072's oracle can later insert such annotations automatically,
above the Spec.
