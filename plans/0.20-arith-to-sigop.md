# Plan 0.20: Arith-to-SigOp pipeline + opaque assembly blocks

## Goal

A Once program containing arithmetic expressions over Int — including
the lambdas

```
\x -> x + 3 * 5 - 2 * x
\x y -> x + 2 * y
exit@S (2 + 2 * 20)        -- exits 42
```

compiles end-to-end on `--alloc heap`, links cleanly (no
`undefined reference to once_arith.*`), and runs producing the correct
observable. Each arith expression is lowered to one **opaque assembly
block** that CCC's dispatcher treats as a single SigOp invocation,
with its `PreservesCCC` contract discharged structurally from the
arith subsystem's own correctness chain.

This plan fills the slot Plan 0.2.4.1 reserved as "0.2.4.2-arith-to-sigop"
(the original 0.2.4.2 number was reassigned to the closure-codegen-fix
plan, so this lives at 0.20 in the flat series).

## Context

Plan 0.2.4.1 landed the SigOp framework for *single-op* primitives
(exit, integer literals): each SigOp carries a `SigOpInfo` (name +
semantic function) and discharges a 6-field `PreservesCCC` contract
(`formal/Once/CCC/SigOp/Helper.agda:66`). It explicitly deferred
arithmetic, and the deferred plan was never written.

The current state is half-built:

- `formal/Once/Arith/SigOp/Builders.agda` defines `SigOpInfo`s for
  `arith.add.int`, `arith.sub.int`, `arith.mul.int`, … with
  **postulated** semantics (the file comment says "0.2.4.2 will make
  these definitional").
- `formal/Once/Arith/SigOp/Proofs.agda` (`ArithProofs` module) sketches
  a single `arith-trace-correct` / `arith-frontier-stable` shape using
  CCC's `mkPurePrimResult`, but isn't wired into the dispatcher.
- The Haskell elaborator recognises `+`/`*`/`-` at the surface level
  and routes them through the legacy `Once.IR.Arith` constructor
  (the older D040 "separate ArithIR" path). x86-64 codegen emits
  `call once_<arith-op-name>.int` for each op as a raw asm call.
- No Strata interpretation defines `once_arith.add.int` / `once_arith.mul.int`
  / etc., so any arith program fails at link time. Captured today as
  the inverted-assertion `ArithSpec` (compiler/test/ArithSpec.hs).

The architectural decision settled in the 2026-05-25 discussion: the
arith compiler's job is **taking complex CCC-shaped expressions and
lowering them to opaque assembly blocks** — not emitting one
`call once_arith.<op>.int` per leaf operation. That tax (a pair
allocation per binary op, a projection chase per variable use, a
SigOp call per primitive) is exactly what the embedded-generators
encoding D040 was meant to bypass.

## Locked architectural decisions

These came out of the 2026-05-25 design discussion. Locked before
implementation begins; revisit only with explicit user pushback.

### D-arith-1: One SigOp per arith *block*, not per arith *op*

A maximal arith subtree (rooted at a value of numeric type, with
all leaves being numeric literals, variable references, or opaque
non-arith inputs) lowers to **one** `SigOp arith.block.<digest>`
invocation, not to a composition of per-op SigOps. The block's
emitted body is a flat assembly sequence operating on registers
(plus stack scratch if needed), and CCC sees it as one opaque call.

This is the load-bearing decision. Per-op SigOps would force the
~40-instruction pair-allocation tax this plan exists to eliminate.

### D-arith-2: Abstract machine = bounded regs + output slot + bounded scratch

The arith subsystem gets its own `AbstractArithMachine` state, kept
deliberately small:

```agda
record ArithAbsState : Set where
  field
    regs        : AbstractRegFile n      -- bounded n abstract regs
    output      : NumValue                -- the result slot
    scratch     : ArithScratch k          -- bounded k scratch words
    input-shape : InputShape              -- read-only: structural shape
                                          --   of the input (Int /
                                          --   Int*Int / Int*(Int*Int) / ...)
                                          -- Indexed by InputPath; no
                                          -- names. See D-arith-3.
```

No frame, no heap, no halted bit. Arith can't get stuck or allocate
(the boundary translates `scratch` into CCC's existing
`BeforeFrontier` stack discipline at the integration point).

### D-arith-3: Input access is *positional*, not named

`ArithIR` carries no source-level identifiers. A reference to the
block's input is a leaf `AInputProj : InputPath → ArithIR` where
`InputPath = List Side` and `data Side = Fst | Snd`. Recognition
resolves every projection at walk time and writes the path into the
leaf; no name environment, no `AVar Text` lookup, no side table.

| Surface | Recognised as |
|---|---|
| `\x. body[x]` at top of single-arg | `id`/`Int → Int` leaf ⇒ `AInputProj []` |
| `\x y. body[x,y]` after curry | `fst` leaf ⇒ `AInputProj [Fst]`, `snd` leaf ⇒ `AInputProj [Snd]` |
| `\x y z. body` after currying | nested chain ⇒ `AInputProj [Fst]`, `[Snd, Fst]`, `[Snd, Snd]` |

Two consequences:

- The validity theorem is structural —
  `eval-arith-ir (AInputProj p) input ≡ project p input` — with no
  quantifier over name environments and no name-resolution lemma.
- Alpha-equivalent lambdas produce structurally identical IRs and
  therefore identical `arith.block.<digest>` symbols (D-arith-8). No
  normalisation pass before hashing.

This is a deviation from the existing `Once.Arith.IR.AVar Text NumType`
constructor (OCP-0001). The migration is small — one constructor
rename, drop the `Text` argument, thread a path accumulator instead
of a name environment through `Once.Arith.Recognize`. Folded into
Phase A.

Recognition refuses to lift a subtree into an arith block if any
leaf is not a literal SigOp, an arith SigOp, or one of those
projections. Any node that fails this test (e.g. an `apply`, a
`case`, a `closure` reference) means the recognition pass leaves the
surrounding subtree as CCC; the arith ops at that root stay as leaf
SigOps inside CCC. See D-arith-7.

### D-arith-4: Three-layer theorems

| Layer | Theorem | Lives in |
|---|---|---|
| Validity | `eval-arith-block e env ≡ output-of (run-abstract (compile-abs e) (init env))` | `formal/Once/Arith/Machine/Validity.agda` |
| Refinement | for each `<arch>` and each `AbstractInstr`, the concrete instructions emitted refine the abstract instruction's state transition | `formal/Once/Arith/Backend/<arch>/Correct.agda` |
| Boundary | for each arith block, the wrapped `SigOp arith.block.<digest>` discharges `PreservesCCC` (frame-eq, heap-monotone with Δ=0, prior-preserved on `BeforeFrontier`, slot-monotone with Δ ≤ scratch-bound, not-halted, output-eq-eval) | `formal/Once/Arith/Boundary.agda` |

Composition gives `eval (SigOp wrap ∘ inputMorphism) x ≡ eval-arith e env`
for any well-formed arith block — the user-level correctness statement.

### D-arith-5: The boundary discharges `PreservesCCC`

Every arith block surfaces to the rest of the system as a `SigOp`,
and every `SigOp` must discharge `PreservesCCC`
(`formal/Once/CCC/SigOp/Helper.agda:66`). This is the contract, not
a choice. The boundary module's job is therefore stated as an
obligation: for each `arith.block.<digest>` SigOp the family
emits, `formal/Once/Arith/Boundary.agda` must populate
`PreservesCCC s s' alloc alloc'` from the abstract validity and
target refinement layers (D-arith-4). There is no
`PreservesArith` record because there is nothing for it to be —
CCC's contract is the only contract on the table.

### D-arith-6: Int currently treated as `*^ω`; linearity available later

For this plan, numeric values are duplicable: `\x -> x + 3*5 - 2*x`
(x appears twice) is well-typed inside an arith block, and the
recognition pass / abstract machine emit a separate load for each
occurrence with no special handling. This is the *current* encoding,
not a permanent stance — a future plan can introduce
linearity-aware optimizations (load-CSE so `x` is loaded once and
reused, register reuse for single-use intermediates, in-place
arithmetic when QTT tells us the input slot is dead after read)
on top of the same abstract machine. Those optimizations sit in
the `ArithIR → ArithIR` rewrite layer (sibling plan 0.21) and need
no changes to the abstract-machine model itself.

Multiplicity at the *boundary* (i.e. how arith-block inputs flow
in from CCC) is whatever CCC threads in; arith does not increase
multiplicity, so QTT linearity at the boundary is preserved by
inspection.

### D-arith-7: There are arith blocks and there are CCC blocks. Nothing else.

Arith blocks and CCC are *disjoint* program categories, not two
flavours of subtree that get mixed. There is no "mixed-arith" object,
because:

- An **arith block** is a SigOp from CCC's point of view. CCC can
  compose it like any other SigOp — feed it an input, take its
  output, sequence it with other CCC nodes. So CCC freely contains
  arith blocks.
- The reverse does not hold: an arith block cannot contain CCC
  structure. Its `ArithIR` body only nests `ArithIR` (literals,
  arith ops, input access); it does not nest `apply`, `case`,
  `cata`, closure refs, etc.

The recognition pass is therefore an *extraction* pass: starting
from a CCC morphism tree, it identifies maximal subtrees whose every
internal node is an arith op and whose every leaf is either an
arith literal or an input access, and lifts each such subtree into
its own `ArithBlock` (a fresh `arith.block.<digest>` SigOp). The
surrounding CCC is unchanged. If a subtree's root would be an arith
op but a deeper node is `apply` / `case` / non-arith, the recognition
pass simply doesn't lift that root — the arith op stays as a leaf
arith SigOp inside CCC, no different from `exit` or `linux.write`.
There is no special "mixed" path because there is no mixed object
to handle.

### D-arith-8: Block content-addressed by IR digest

The opaque SigOp name is `arith.block.<digest>` where `<digest>` is a
deterministic hash of the recognised `ArithIR` tree. Two textually
identical blocks share one emitted routine; distinct blocks get
distinct names. Avoids the explosion of "one routine per occurrence"
and gives stable symbols for linker dedup.

## Scope

**In scope:**

- Recognition pass: CCC IR → `Maybe ArithBlock`, where `ArithBlock`
  carries `InputShape` + `ArithIR Γ τ`.
- `AbstractArithMachine` definition (`ArithAbsState`, abstract
  instruction set, `run-abstract`, validity theorem).
- Per-(abstract instruction) x86-64 codegen + structural refinement
  proof. AArch64 / RISC-V skeleton stubs (one `case` per abstract
  instruction returning `notImplemented`); full target proofs deferred.
- Boundary module: `ArithBlock → SigOpInfo (InputType ib) (Int)` plus
  the populated `PreservesCCC` witness.
- Dispatcher wiring: arith blocks compose into the TargetProvider
  via `_<|>_` alongside `intLitProvider`, `linuxProvider`, etc.
- Replace the legacy `Once.IR.Arith` constructor's codegen path with
  the new recognition+block emission. The constructor itself can
  remain (recognition pass is the consumer) or be removed in a
  follow-up.
- End-to-end tests:
  - `arith-simple.once` (`exit (3 + 5 * 2)`) — flips the inverted
    `ArithSpec` assertion to a positive `exit 13`.
  - `arith-lambda-1.once` — `f = \x -> x + 3*5 - 2*x; main = exit (f 5)`.
  - `arith-lambda-2.once` — `g = \x y -> x + 2*y; main = exit (g 4 19)`.
  - `arith-extracted.once` — a program where two arith blocks live
    inside one CCC composition (e.g. `\x -> case x of …` with arith
    in both branches). Verifies that recognition extracts each block
    separately and that CCC composes them correctly. Only added once
    the surrounding CCC support (`case`-over-Int) is in place.
- Replace the postulated `add-semI`/`add-semM`/etc. in
  `Once.Arith.SigOp.Builders` with definitional semantics (per the
  existing file's "0.2.4.2 will make these definitional" comment).

**Out of scope:**

- Floats (`F32`/`F64`). Same machinery applies — separate plan.
- Other Int widths (I8/I16/I32). The pattern generalises; I64 only here.
- Optimizations: constant folding, CSE, strength reduction, peephole.
  All become tree rewrites on `ArithIR` with abstract-machine
  refinement proofs; deferred to a follow-on plan (call it 0.21).
- AArch64 / RISC-V full target proofs (skeleton stubs only).
- Test scenarios where the *CCC* infrastructure around an arith
  block isn't yet wired (e.g. `case` on a `Bool` returned by `arith.lt.int`
  to drive control flow). Recognition extracts the arith blocks
  cleanly, but the surrounding CCC has to be ready independently;
  not blocking on those features here.

## Architecture overview

```
  Source ──parse──> Surface ──elaborate──> CCC IR (with embedded SigOps)
                                                │
                                  ┌─── recognise-arith ───┐
                                  ↓                       ↓
                          ArithBlock                 (rest of CCC IR)
                          (InputShape,
                           ArithIR Γ τ)
                                  │
                                  │ compile-abs
                                  ↓
                       [AbstractInstr] over ArithAbsState
                                  │
                                  │ validity: trace ≡ eval-arith
                                  │
                       ┌──────────┼──────────┐
                       ↓          ↓          ↓
                  x86 emit   aarch64 emit  riscv emit
                       │          │          │
                       │ refinement: target trace refines abstract
                       ↓          ↓          ↓
                  asm block  asm block   asm block
                                  │
                                  │ boundary: wrap as SigOpInfo,
                                  │           discharge PreservesCCC
                                  ↓
                        SigOp arith.block.<digest>
                                  │
                                  │ TargetProvider <|>
                                  ↓
                          CCC Dispatcher (no change)
```

## Implementation phases

Each phase ends with `make agda && make compiler && make malonzo &&
cabal build` green. Commit per phase.

### Phase A — `ArithAbsState` and abstract instruction set

1. Create `formal/Once/Arith/Machine/AbsState.agda` defining
   `ArithAbsState`, `AbstractRegFile`, `ArithScratch`, `InputShape`,
   `NumValue`.
2. Create `formal/Once/Arith/Machine/AbsInstr.agda` defining the
   abstract instruction set:
   ```agda
   data AbstractInstr : Set where
     load-input  : InputPath → AbsReg → AbstractInstr
     load-imm    : ℤ → AbsReg → AbstractInstr
     add-rrr     : AbsReg → AbsReg → AbsReg → AbstractInstr
     sub-rrr     : AbsReg → AbsReg → AbsReg → AbstractInstr
     mul-rrr     : AbsReg → AbsReg → AbsReg → AbstractInstr
     neg-rr      : AbsReg → AbsReg → AbstractInstr
     spill       : AbsReg → ScratchSlot → AbstractInstr
     reload      : ScratchSlot → AbsReg → AbstractInstr
     move-to-out : AbsReg → AbstractInstr
   ```
   plus `run-abstract : [AbstractInstr] → ArithAbsState → ArithAbsState`.
3. Cmp ops (`lt`/`eq`/…) deferred to Phase G; arith arithmetic only
   for now.

**Estimated cost:** ~200–300 lines Agda. Standalone — no compiler
changes yet. `make agda` green.

### Phase B — Recognition pass

1. `formal/Once/Arith/Machine/Recognise.agda`:
   ```agda
   recognise : ∀ {A B} → IR A B → Maybe (ArithBlock A B)
   ```
   Classifies `id`, `fst`, `snd`, `⟨_,_⟩`, arith SigOps, literal SigOps.
   Rejects (returns `nothing` for) any tree containing `apply`,
   `case`, `cata`, μ-constructors, or non-arith SigOps. Resolves
   each variable reference to its `InputPath` during the walk
   (positional, no name environment — D-arith-3) and records the
   block's `InputShape` from the curry structure peeled off the top.
2. Haskell mirror (`compiler/src/Once/Arith/Recognize2.hs` or extract
   from MAlonzo).
3. Add a unit-level Agda test: round-trip on the three lambda examples
   produces the expected `ArithBlock` shapes.

**Estimated cost:** ~400 lines (200 Agda, 200 Haskell). `make agda &&
make compiler` green.

### Phase C — Compile-to-abstract + validity

1. `compile-abs : ArithBlock A B → ArithAbsState → [AbstractInstr]`
   (naive linearisation; one abstract reg per node, no allocation
   optimization yet — D-arith-2's bounded regs gets bumped to "as
   many as the tree has nodes" for this phase; allocation is Phase F).
2. `formal/Once/Arith/Machine/Validity.agda`:
   ```agda
   abs-validity :
     ∀ (block : ArithBlock A B) (env : Env A) →
     output-of (run-abstract (compile-abs block) (init env)) ≡
       eval-arith-block block env
   ```
   Structural induction on `ArithIR`. Discharges `ALitInt`,
   `AInputProj`, `AAdd`, `AMul`, `ASub`, `ANeg` cases. `AInputProj`
   reduces to `project path input` definitionally; no environment
   lemma needed (D-arith-3).

**Estimated cost:** ~300 lines. `make agda` green.

### Phase D — x86-64 emit + refinement

1. `formal/Once/Arith/Backend/X86/Syntax.agda` — concrete x86
   instruction subset used by arith (mov/imm-mov/add/sub/imul/neg/
   push/pop or stack-spill mov).
2. `formal/Once/Arith/Backend/X86/CodeGen.agda` — translate one
   `AbstractInstr` to its concrete x86 sequence. Initially one
   register-mapping strategy: AbsReg n → %r{12..15} for n<4, else spill.
3. `formal/Once/Arith/Backend/X86/Correct.agda` — per-AbstractInstr
   refinement lemmas:
   ```agda
   refine-add-rrr :
     ∀ s r1 r2 r3 →
     run-x86 (emit (add-rrr r1 r2 r3)) (concretise s) ≡
       concretise (step (add-rrr r1 r2 r3) s)
   ```
   Trivial for each pure arith op (one or two real instructions).
   Spill/reload prove agreement with the abstract scratch.

**Estimated cost:** ~500 lines Agda + Haskell extraction wiring.
`make agda && make malonzo` green.

### Phase E — Boundary + dispatcher wiring

1. `formal/Once/Arith/SigOp/Block.agda`:
   ```agda
   block-info : (digest : String) → InputType → SigOpInfo InputType Int
   block-info d ib = mk-info ("arith.block." ++ d) (...) (...)

   blockProvider : TargetProvider
   blockProvider {A} {B} si with stripPrefix "arith.block." (name si)
   ...
   ```
2. `formal/Once/Arith/Boundary.agda` populates `PreservesCCC` from:
   - frame-eq: trivial (arith doesn't touch CCC frames).
   - not-halted: from abs-validity (arith blocks don't halt).
   - prior-preserved: scratch usage is bounded; CCC's `BeforeFrontier`
     for the block's input-loc holds throughout — read directly from
     refinement.
   - heap-monotone: ≤-refl (arith doesn't allocate).
   - slot-monotone: `≤-trans` from the block's scratch-bound.
3. `formal/Once/CCC/EntryPointCCC.agda`: compose `blockProvider` into
   the target provider via `_<|>_` after `intLitProvider` and the
   per-platform providers.
4. Remove legacy `once_arith.<op>.int` emission from x86-64 codegen.
   The recognition pass + block emission now owns the arith path
   end-to-end.

**Estimated cost:** ~400 lines. `make malonzo && cabal build` green.

### Phase F — Register allocation across the tree

The naive Phase C allocator uses one abstract reg per node; that
balloons the scratch use. Replace with a simple top-down allocator
(Sethi–Ullman or similar) operating on `ArithIR` and emitting
`[AbstractInstr]` with bounded reg count. Allocator correctness is
purely a refactor of `compile-abs`; Phase C's validity theorem
re-discharges with the smaller instruction sequence by induction on
tree shape.

**Estimated cost:** ~300 lines. `make agda` green.

### Phase G — End-to-end test + ArithSpec flip

1. `compiler/test/arith-lambda-1.once`:
   ```once
   import I.Linux.Syscalls as S
   f : Int -> Int
   f x = x + 3 * 5 - 2 * x
   main : IO Unit
   main = exit@S (f 5)         -- 5 + 15 - 10 = 10, exit 10
   ```
2. `compiler/test/arith-lambda-2.once`:
   ```once
   import I.Linux.Syscalls as S
   g : Int -> Int -> Int
   g x y = x + 2 * y
   main : IO Unit
   main = exit@S (g 4 19)      -- 4 + 38 = 42, exit 42
   ```
3. Flip `compiler/test/ArithSpec.hs` from inverted-assertion to
   positive `exit 13` check on `arith-simple.once`. Add tests for
   the two lambdas above.
4. Add `arith-extracted.once` once the surrounding CCC features the
   test needs (e.g. `case`-over-Bool driving control flow off an
   `arith.lt.int` result) are in place. Otherwise the extraction
   test is a follow-on.

**Estimated cost:** ~50 lines test, ~30 lines spec. `cabal test`
green; the new tests pass with the expected exit codes.

## Risks / open questions

1. **Recognition completeness vs. elaborator shape.** Recognition
   needs the elaborator's CCC output to land in a recognisable shape
   (literals as `lit.int.N` SigOps, projections as `fst`/`snd`/`id`,
   binary arith as `arith.<op>.int` SigOps composed with `⟨_,_⟩`).
   If the elaborator currently emits arith via the legacy
   `Once.IR.Arith` constructor *only*, then Phase B has to teach the
   elaborator to *also* emit the SigOp-composed form so recognition
   has something to recognise. Audit needed before Phase B.

2. **InputShape inference under deep currying.** `\x y z. body`
   curries to `Int → (Int → (Int → Int))`. The recognition pass has
   to peel the right number of curries off and accumulate the path
   prefix for each level. Plan: peel curries greedily (the
   recognition pass owns the multi-arg projection convention).

3. **PreservesCCC.prior-preserved with non-zero scratch.** When an
   arith block spills, it writes to stack slots inside its own
   bounded scratch region. Those slots ARE within
   `BeforeFrontier (alloc + scratch-bound)` but NOT within
   `BeforeFrontier alloc`. So `prior-preserved` needs to be
   parameterised: "BeforeFrontier of the pre-block alloc state stays
   intact; the scratch region is exclusively ours." Mitigation: define
   a helper `ArithScratchOwned : AllocState → ScratchBound → Set` and
   the boundary discharges prior-preserved by combining
   `before-frontier-stack-disjoint` (already in the codebase per
   [[closure-loc-shape-independence]]) with the scratch-owned witness.

4. **Sethi–Ullman correctness on QTT-duplicable values.** Standard SU
   numbering assumes the input expression is a tree (each variable
   appears once). For `x + 3*5 - 2*x` (x appears twice) we either:
   (a) treat the tree as a DAG and rematerialise each load (simpler
   correctness, slightly more code); or (b) common-subexpression-share
   the load (more efficient, requires DAG-shaped abstract trace).
   Phase F picks (a) for simplicity; Phase 0.21 (optimization plan)
   adds (b) with the equivalence proof.

5. **Block-digest collisions.** `arith.block.<digest>` uses
   deterministic hashing. If digest length is too short, distinct
   blocks could collide. Mitigation: 64-bit hex digest of a normalised
   `ArithIR` serialisation. Audit period: Phase E.

6. **AArch64/RISC-V stub state.** Phase D ships x86-64 only. The
   skeleton stubs for AArch64/RISC-V mean those backends compile but
   raise a `notImplemented` runtime error for any arith block. Acceptable
   per Scope; document in commit message.

## Relationship to other plans

- **Parent: 0.2.4.1** (SigOp framework). This plan is 0.2.4.1's
  deferred follow-on; it consumes the `SigOpInfo`/`PreservesCCC`/
  `Provider` machinery 0.2.4.1 established and extends it with a
  *family* of SigOps (`arith.block.<digest>`) generated structurally
  from arith expressions.
- **Supersedes part of D040** (Separate ArithIR). The IR layer
  (`ArithIR`, `NumType`) and the recognition pass survive; the
  "natural transformation boundary into IR via an `arith`
  constructor" is replaced by "compile to abstract trace, emit as
  opaque SigOp block, discharge `PreservesCCC` at the boundary." D040
  remains historically accurate; D049 (new) records the supersession.
- **Builds on 0.19** (sigop/closure split). Block invocations are
  plain SigOps from CCC's view, so they use the `sigOp` constructor
  with no special closure machinery.
- **Builds on [[closure-loc-shape-independence]]** (the
  `before-frontier-stack-disjoint` lemma). The boundary's
  `prior-preserved` field reuses that lemma when reasoning about
  scratch slots vs. CCC's pre-block frontier.
- **Sibling/follow-on: 0.21** (to be written) — arith expression
  optimizations (constant folding, CSE, strength reduction). All
  expressed as `ArithIR → ArithIR` rewrites with abstract-machine
  refinement proofs. Lands after this plan because the abstract
  machine + validity theorem are the substrate.
- **Sibling/follow-on: 0.22** (to be written) — float arithmetic
  (F32/F64). Same abstract-machine pattern; XMM register file
  instead of GPR.

## Non-goals

- A general-purpose abstract-machine framework usable for non-arith
  subsystems. The abstract machine is sized and shaped for arith
  specifically.
- Verified register-allocation for the general case (graph colouring,
  spill heuristics). Phase F's allocator is bounded-tree SU; that's
  enough for the lambdas in the goal.
- Inlining arith blocks across CCC composition boundaries (would let
  `f x + g x` share inputs across two blocks). Each arith block stays
  syntactically scoped to one maximal CCC subtree.
- Eliminating the legacy `Once.IR.Arith` constructor entirely.
  Recognition still consumes it as an alternative input shape; a
  later cleanup plan can remove it once we've confirmed no path
  emits it directly.

## Open questions (to resolve during Phase A or B)

- **InputShape granularity.** Does `InputShape` model the input as
  a flat list `[Int, Int, Int]` (positional indices, paths collapse to
  single integers) or as the tree shape `(Int, (Int, Int))` (CCC
  nesting, paths are `[Fst, Snd, …]`)? Flat is easier for the
  recognition pass; tree is easier for the boundary refinement when
  arith blocks consume sub-tuples. Pick one in Phase A; current
  lean: tree-shaped (mirrors CCC, paths stay structural).
- **Abstract reg count.** How many abstract regs before spill? An
  architecture-independent answer is "as many as the tree's
  Sethi–Ullman number"; an architecture-aware answer is "the smallest
  callee-saved set across all supported arches (~4 regs on x86-64
  using r12-r15, conservative)." Pick during Phase F.
- **Cmp ops in the abstract machine.** Comparison ops produce `Bool`
  (`Unit + Unit`), which crosses the arith/CCC boundary. Option (a):
  `lt-rrr : AbsReg → AbsReg → AbsReg → AbstractInstr` writes 0/1 to
  the dest reg, boundary refines to CCC's Bool encoding. Option (b):
  cmp is a leaf SigOp (per-op, not per-block) and stays on the old
  path. Phase G picks (a) once arith arithmetic is settled.

## Why this is the principled fix

- **Performance**: trees emit as flat asm blocks with register
  allocation across them, eliminating the pair-allocation and
  composition tax that motivated D040 in the first place.
- **Layered correctness**: three independent theorems (abstract
  validity, target refinement, boundary `PreservesCCC`) compose to
  end-to-end correctness without any layer reasoning about the
  others' internals.
- **Discharges the only contract that exists**: every SigOp must
  satisfy `PreservesCCC`; the boundary populates it from the
  abstract+refinement layers. No parallel contract to keep in sync
  because there isn't one to invent.
- **Localises arch-specificity**: adding AArch64 or RISC-V is a new
  `Backend/<arch>/Correct.agda` plus a `CodeGen.agda` — no changes
  to recognition, abstract machine, validity, or boundary.
- **Optimisations land structurally**: any future `ArithIR → ArithIR`
  rewrite (constant fold, CSE, peephole) gets its correctness
  statement at the abstract-machine layer and inherits target
  refinement for free.
- **Closes the gap captured by `ArithSpec`**: the inverted-assertion
  test in `compiler/test/ArithSpec.hs` flips to a positive `exit 13`
  check in Phase G; that flip is the user-observable signal the
  plan landed.
