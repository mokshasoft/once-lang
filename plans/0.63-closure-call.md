## FINDING (2026-08-03, before starting): the residual is FALSE, and the
## code-address model is inconsistent

Two facts read out of the model:

1. `execInstr prog s (call target)` (X86-64.Semantics:305) pushes
   `pc s + 1` and sets `pc := <the operand's VALUE>`.
2. `lea rax, [rip+label n]` gives the effective address `n` — the label
   NUMBER — and `enc-sv (SV-Code n) = n`. But every other control transfer
   (`c-jmp`/`je`) resolves through `find-label`, which returns an
   INSTRUCTION INDEX.

So a modelled closure call jumps to `pc := n` (a label number) while the
body actually begins at `find-label prog (once n)` (an index). These
coincide only by accident. **The modelled ISA is internally inconsistent
about what a code address is** — calls use raw values, jumps use label
resolution.

Consequently `events-running-call` is not merely unproven, it is FALSE in
general (same class as the `load-const-float` hole closed by D079): the
abstract machine treats the call as the identity and continues, while the
concrete machine jumps somewhere unrelated (or off the end, ending the
trace). Any program that applies a closure and then emits an observable
witnesses the difference.

THIS RAISES PRIORITY: it is a soundness hole in the correspondence cone,
not a coverage gap.

## The gap

`exec-abstract instr-call-closure = s , alloc` — the IDENTITY — while the
compiled code does `call *0x8(%r12)`: it transfers control to the closure's
code address and later returns. No proof can bridge that; the abstract
machine has to model the call.

`instr-call-closure` IS emitted (`ir-to-trace' n l apply` ends with it), so
this is not a fossil route like `instr-loop`/`lea-indexed`/`case-on-tag` —
it is the lowering of `apply`, a core CCC generator. The residual is
conditioned on the run context, so it is not vacuous; but it is unproven
and unprovable as the model stands.

## Why it is structural, not a proof (verified 2026-08-03)

`ir-to-trace` returns the MAIN trace only — closure bodies come from a
SEPARATE `ir-to-bodies`, which the per-arch emitter emits as its own
labelled blocks (`Once/Target/X86-64.agda` uses both). So the FLAT
machine's program does not contain the bodies at all: there is nothing for
a modelled call to jump to. Inlining is not an option in general — a
closure value's code pointer is only known at runtime (that is what the
`SV-Code` cell is for).

## What the attempt proved (2026-08-03) — read before planning the next run

I made the top-level change (`lea` resolves via `find-label`) and followed

- the only `label` instructions in the MODELLED program come from

### The design surface this exposes (all of it is step 1's)

0'. **PREFER `c-ret` IN `CtrlInstr`, not a new top-level `AbstractInstr`**
   (2026-08-03, from the "jump to labels" framing). A return IS flat
   control flow, and `instr-ctrl` is exactly the control-flow family item 6
   established (`c-label`/`c-jmp`/`c-branch-*`). Putting it there is both
   the design-coherent home AND cheaper: **13 sites treat `instr-ctrl c`
   OPAQUELY** (`sp-abstract`, `pb-abstract`, … `= wf`) and are untouched by
   a new `CtrlInstr` constructor, whereas a new top-level constructor
   forces a clause at every one of them. Only the functions that CASE-SPLIT
   on `CtrlInstr` need a clause — `flat-exec-instr`, `compile-abstract` ×3,
   the five invariant preservations' ctrl clauses, ShapeTable's
   `step-expect`/`ctrl-ok`, `events-running-fetch`, `stable?`,
   `*-keeps-next-slot`, `instr-reloc`.
   `instr-call-closure` STAYS a top-level instruction (it is
   closure-specific — it reads the code pointer out of the record); only
   its semantics changes, from identity to push-return + jump. The
   asymmetry is right: the call is a data-directed transfer, the return is
   pure control.

1. **A `ret`-like abstract instruction.** `AbstractInstr` has none, and the
   per-body `ret` is emitted as text. Adding a constructor ripples through
   EVERY total dispatch — `exec-abstract`, `compile-abstract` (×3 arches),
   `FrameFreeI`, `AllocMinI`, `slot-of`, `stable?`, ShapeTable's
   `step-expect`/`site-ok`/`ctrl-ok`, `InstrSlot`, `CataAtRelocate`, and
   every block-step dispatcher. Mechanical but WIDE. MEASURED 2026-08-03
   by tracing an existing instruction (`instr-save-closure-reg`) through
   the tree: **15 files, ~41 clause sites** — SMCore 2, InstrSlot 1,
   FlatStoreWF 2, FlatRegTagWF 2, FlatStackSlot 2, FlatStackPtr 3,
   FlatPtrBounds 3, ShapeTable 2, CataIRSlotStable 3, CataNextSlot 3,
   CataAtRelocate 2, AbstractToX86 6, AbstractToX86-32 2,
   AbstractToRiscV 2, ConcFlatSim 6. Most are one-liners; the ones with
   real content are `exec-abstract` (the return semantics), the five
   invariant preservations (FlatStackPtr / FlatPtrBounds / FlatStackSlot /
   FlatStoreWF / FlatRegTagWF — a `ret` moves `pc` and pops the return
   stack, so each needs its own clause), and the three
   `compile-abstract`s. Budget a full session, and land it as ONE green
   unit: a half-swept tree does not typecheck at all.
2. **A label namespace for bodies.** `Label` is `once ℕ | sigop String ℕ`;
   body labels need their own constructor (`thunk ℕ`) so `find-label`
   cannot confuse them with `c-label` ids. Small, but do it INSIDE step 1

3. **The per-body prologue/epilogue must move inside `compile-trace`.**

4. Only then does step 0 (D081 resolution) become true and landable.

   untouched. Verified green.

2. **TWO new fields are needed, not one:**
   - `fret : List ℕ` — the return-pc stack. A GHOST list: the abstract
     memory is frame/slot-keyed and has no byte-addressed pushdown, so the
     addresses the concrete machine pushes below `%rsp` are modelled here
     and RELATED by the correspondence (a new `FlatCorr` field).
   - `fclosure : StoredValue FS` — the `%r12` mirror. NON-OBVIOUS and
     easily missed: the concrete call is `call *0x8(%r12)`, i.e. it reads
     the code pointer out of the CLOSURE REGISTER, not out of `Input1`.
     `instr-save-closure-reg` is abstract-identity precisely because that
     register lives at the FLAT level — so the flat machine loads it:

       flat-exec-instr instr-save-closure-reg _ fs =
         record fs { fclosure = readReg (regs (floc fs)) Input1
                   ; fpc = suc (fpc fs) }

3. **`c-ret` goes in `FlatCtrl`** (with `c-label`/`c-jmp`/`c-branch-*`),
   and the semantics is aux-style so downstream proofs can rewrite:

       do-ret []           fs = halt fs
       do-ret (pc' ∷ rest) fs = record fs { fpc = pc' ; fret = rest }
       do-call-to (just pc') fs =
         record fs { fpc = pc' ; fret = suc (fpc fs) ∷ fret fs }
       do-call-to nothing    fs = halt fs
       do-call-code prog (just (SV-Code lbl)) fs = do-call-to <resolve lbl> fs
       do-call-code prog _                    fs = halt fs   -- enumerated
       do-call prog fs = <case fclosure fs: SV-Ptr loc ⇒
                          do-call-code prog (readLoc (floc fs) (sucLoc loc)) fs>

## THE LABEL MARKER — SETTLED (D082): option (a), a `thunk` provenance

How does a CALL find its body in the ABSTRACT program?

- the abstract `find-label : AbstractTrace → ℕ → Maybe ℕ` scans for
  `instr-ctrl (c-label n)` and is ℕ-keyed;
- but `c-label n` compiles to `label (once n)` → `.Lonce_n`, while the
  `lea` that creates a code pointer renders as `.L_thunk_n(%rip)`
  (`showMem (rip+label n)`) and `emit-thunk-body` emits `.L_thunk_n:`.

So marking a body start with plain `c-label` makes the two sides disagree
about the label's NAME, while the label counter is already shared (one
counter threads main and bodies, so ids cannot collide).

Two coherent resolutions:

- **(a) a dedicated marker** — add `c-thunk : ℕ → FlatCtrl` compiling to
  `label (thunk n)` (a new `Label` constructor rendering `_thunk_n`, so the
  EMITTED TEXT IS UNCHANGED), plus `find-thunk` on the abstract side. Keeps
  D033's provenance principle: a call can never land on a jump label,
  definitionally. Costs one more constructor sweep.
- **(b) unify on `once`** — emit body labels as `.Lonce_n:` and change
  `showMem (rip+label n)` to match. Simpler and no new constructor, but it
  CHANGES THE EMITTED TEXT (harmlessly — same labels, different names) and
  drops the definitional separation.

**DECIDED: (a)** — see D082. `_≡ᵇᴸ_` is `false` across provenances by its
catch-all, so a call target can never match a jump label DEFINITIONALLY,
with no appeal to counter uniqueness (which today is only an accident of
the shared counter). Emitted text stays byte-identical.

### Step 1 is therefore fully specified — pure mechanical execution

    Label      += thunk : ℕ → Label          (renders "_thunk_n")
    FlatCtrl   += c-thunk : ℕ → FlatCtrl     (body-start marker)
               += c-ret   : FlatCtrl         (return)
    Flat       :  mkFlatFull + defaulted mkFlat wrapper
               += fret : List ℕ, fclosure : StoredValue FS
               += find-thunk beside find-label
               +  flat-exec-instr clauses: c-thunk (passthrough), c-ret,
                  save-closure-reg (loads fclosure), call-closure (do-call)
    dispatches :  a clause per new FlatCtrl constructor at the ~18 sites
                  that CASE-SPLIT on FlatCtrl (the 13 opaque `instr-ctrl c`
                  sites need none)
    compile-abstract ×3: c-thunk ↦ label (thunk n), c-ret ↦ ret

Land that as ONE green unit (the constructors have no producer yet, so
nothing's behaviour changes), then step 2 (bodies into `ir-to-trace`) gives
them their producer.

### THE REAL BLOCKER — SOLVED 2026-08-03 (`0d8ed90d`)

`FlatComposition.headView` — the pc/label-offset layer, the "one hard
lemma" of the recovered cluster. It classifies each instruction two ways:

    hv-clabel m : compile-abstract i ≡ label (once m) ∷ []   -- a jump target
    hv-plain    : has-label (compile-abstract i) ≡ false      -- no label

A `c-thunk n` fits NEITHER: it compiles to `label (thunk n)`, so
`has-label` is `true` (it IS a label instruction and occupies an index on
both sides) but it is not a `once` label, so neither scan may match it.

What it needs is a THIRD constructor — a FOREIGN-PROVENANCE label:

    hv-otherlabel : compile-abstract i ≡ label ℓ ∷ []
      → (∀ tgt → (ℓ ≡ᵇᴸ once tgt) ≡ false)        -- x86 scan skips, advances
      → (∀ rest tgt acc → fl-go (i ∷ rest) tgt acc ≡ fl-go rest tgt (suc acc))
      → HeadView i                                 -- flat scan skips, advances

i.e. "both scans step over it, and it costs exactly one index on each
side". The second premise is `refl` by D082's provenance disjointness —
which is precisely the property the decision bought. Then `x86-off` and
`find-label-corr` go through unchanged, and the symmetric fact for
`find-thunk` vs `X.find-label … (thunk n)` is the same lemma with the
provenances swapped.

SOLVED exactly as sketched. `hv-otherlabel` went in with the premise
`refl` at its one producer; BOTH scanning directions needed the case —
`find-label-pres` and the negative `find-label-none-go` (the sketch only
named the first). `x86-off`/`find-label-corr` were untouched.

STILL OPEN for step 2 (not needed until calls resolve): the SYMMETRIC
fact, `find-thunk` vs `X.find-label … (thunk n)`. It is the same
development with the provenances swapped — `hv-otherlabel`'s premise is
specific to a `once` target (`∀ tgt → (ℓ ≡ᵇᴸ once tgt) ≡ false`), and the
thunk-target scan needs a matching `hv-clabel`-shaped case for `thunk`
labels. Do NOT pre-generalize `HeadView` over the provenance now — make
the step-2 change first and let the red say what shape it wants.

## STEP 2, MEASURED (2026-08-03 top-down probe; reverted, tree green)

I made the change (`ir-to-trace` returns main ++ bodies) and followed the
red. Three findings, in order of how much they change the plan.

### 1. The layout needs a jump, and that keeps main's bracket absorbed

Appending bodies to the main trace makes main FALL INTO the first body:
today nothing does, because the emitter puts the bodies after main's
`addq`/`ret` TEXT. Two coherent layouts:

    (a) main ++ c-jmp END ++ bodies ++ c-label END      <- take this
    (b) c-jmp MAIN ++ bodies ++ c-label MAIN ++ main

(a) keeps main FIRST (entry pc stays 0 — `EntryLike`/`pc-off` untouched)
and keeps main's prologue/epilogue exactly as absorbed text, so the parked
`budget*8` item stays parked instead of becoming a prerequisite. Cost: one
`jmp` + one label per compiled function. It CHANGES THE BINARY (bodies move
inside the compiled trace), so the extraction gate + exit tests x3 apply.

### 2. The body's FRAME must move inside `c-thunk`/`c-ret`

The per-body `subq $b*8, %rsp` / `addq` is LOAD-BEARING, not decoration:
`call` pushes the return address, so without its own frame a body's slot
`k` sits at `caller_base − 8 + 8k` and CLOBBERS the caller's slots for
`k ≥ 1`. It cannot be dropped, and the flat program must contain it or the
`x86-off` block-offset correspondence breaks.

But emitting it as a standalone `instr-alloc-stack b` / `instr-dealloc-stack b`
gives those constructors a producer again, which is strictly worse than
carrying the budget on the marker:

    c-thunk : ℕ → ℕ → FlatCtrl   -- label, body budget
    c-ret   : ℕ → FlatCtrl       -- budget to release

    compile-abstract (c-thunk n b) = label (thunk n) ∷ sub rsp (slots b) ∷ []
    compile-abstract (c-ret b)     = add rsp (slots b) ∷ ret ∷ []

with the flat semantics doing `enter-frame b` / `leave-frame` on the
AllocState. Why this is better, MEASURED against the invariants:

- `enter-frame`/`leave-frame` touch ONLY `current-frame`/`saved-frames`, so
  `stackSlot` (a REGISTER-file field) is untouched — **`FlatStackSlot`
  survives**, where `exec-abstract (instr-alloc-stack n)` would break it
  (`incrStackSlot`).
- `CataNextSlot`, `FlatStoreWF`, `FlatPtrBounds` survive too: 0.61 already
  proved `leave-frame-next-slot` / `leave-frame-heap-ref` /
  `leave-frame-block-size` for exactly this.
- The frame then moves at exactly TWO control instructions that also move
  the pc — i.e. the frame discipline lines up with the call/return
  structure, instead of being possible at an arbitrary mid-trace point.

`FlatStackPtr` is the one that genuinely needs generalizing: `SPInv` anchors
every stack pointer to the CURRENT frame, and a caller's pointers survive
into the callee. (Mitigating fact worth checking first: `apply` is
heap-only since 0.53 — it passes a HEAP pair — so it may be that no stack
pointer is live across a call in emitted code.)

### 3. The correspondence machinery is ALIVE — better than feared

`sim-alloc-stack` / `sim-dealloc-stack` / `sim-push-frame` / `sim-pop-frame`
(FlatCorrespondence) and `block-step-alloc-stack` / `block-step-dealloc-stack`

### `Pieces2` — THE `case` SHAPE, TWO THIRDS BUILT (2026-08-05)

Generalizing `Pieces` rather than bolting a second thing beside it. The two
shapes differ in exactly one way: cata repeats ONE trace (cross case closes by
the same-trace argument), `case` embeds DIFFERENT traces (cross case closes by
a window clash). `Pieces2` is the second:

    data Pieces2 (a b : ℕ) : ℕ → AbstractTrace → Set where
      p2nil  : seg-idle? I ≡ true → LabelsIn a b I → Pieces2 a b hi I
      p2cons : (c d : ℕ) → seg-idle? I ≡ true → LabelsIn a b I
             → (∀ st → seg-fold at st ≡ st) → SegAgree at → LabelsIn c d at
             → b ≤ c → c ≤ d → d ≤ hi
             → Pieces2 a b c t → Pieces2 a b hi (I ++ at ++ t)

The disjointness is THREADED, not stated pairwise: `hi` bounds every embedded
window in the rest, and each cons recurses at its own window START, so windows
DESCEND along the trace. That is exactly how `case` emits them — `gt` at
`[lf, lg)` comes first, `ft` at `[l+2, lf)` after — and transitivity covers
every pair.

LANDED: the datatype, `pieces2-neutral`, and `pieces2-mentions` (every mention
is the skeleton's, or an embedded one below `hi`). `c ≤ d` had to join the
premises: without a well-formed window, `m < c` does not give `m < hi`.

STILL OPEN — `pieces2-agree`, and attempting it found the one real difficulty:
**a per-position classification like `pieces-pos` is not enough.** Two
positions inside embedded traces must be told APART — same trace (use its
`SegAgree`) versus different traces (clash) — and a per-position view cannot
say which, because Agda cannot compare traces. THE FIX IS SMALL: index the
embedded case by its DEPTH in the structure. Different depths have disjoint
windows by the threading already in the datatype, and depths are ℕ so they
compare. `pieces-agree` needed none of this — that is exactly the price of
allowing different traces.

own recursion, read positionally — nothing about emitted code) composed with
`ff→seg-id` (a frame-free instruction does not move the segment).

So the bridge survives at exactly ONE place — the jump case — and that place

inside an induction over all instructions. When the flip lands, `pv-jump` is
the clause that needs the static label-range argument, and `pv-suc` needs
nothing.

### D086 — STEP 2a WAS OFF BY THE RETURN-ADDRESS SLOT (landed 2026-08-04)

Found while sizing `block-step-c-thunk`, by checking the marker against the
modelled ISA rather than against the plan. `execInstr … (call …)` does
`newSp = sp ∸ slot-size` — the model is faithful to hardware — so at a body's
first instruction `%rsp` is `base_caller − 8 − 8b`, while step 2a's
`enter-frame b` puts the abstract frame at `base_caller − 8b`. `rsp-eq` would
have been unprovable at precisely the step the closure call exists to justify.

FIXED by splitting the move between the two instructions that move `%rsp`: the
CALL enters the frame (shift 1, reserve 0) and pushes the return pc; `c-thunk b`
GROWS it (`grow-frame`: shift `b`, reserve `b`, NO push); `c-ret` is unchanged.

The push belongs at the call and not at the marker, and that is FORCED, not
chosen: `RetMatch` (landed above) requires `saved-frames` and `fret` to have the
same length, and pushing the frame at the marker makes them differ for every
state between a call and its body.

The return-address cell then lies in no window at all — between the callee's
window end and the caller's base — which is exactly the slack D085's floor
leaves (a `≤`, not an equality). Nothing in D085 had to change to accommodate
the call; that is the check that the two decisions agree.

### THE CALL SCAN — **LANDED** (2026-08-04): `find-thunk` ↔ `find-label (thunk n)`

`find-thunk-corr` is proved: the flat machine's `find-thunk` and the emitted
`call`'s label resolution land on the SAME block (modulo `x86-off`). This is
what `instr-call-closure`'s block-step consumes, and it needed no producer —
it is a theorem about the two scanning functions, so it landed green ahead of
the rest of the unit.

HOW IT CAME OUT CHEAP: `HeadView` now records how BOTH scans reduce on the
head, so ONE enumeration (`headView`, 40 clauses) drives both inductions; a
parallel view would have duplicated all of them to say the mirror-image thing.
The two label cases simply EXCHANGE ROLES — `hv-clabel` is the match for the
jump scan and steps past for the call scan, `hv-otherlabel` the reverse — and
BOTH "steps past" premises are the catch-all of `_≡ᵇᴸ_` on mismatched
provenances, hence `refl` at every producer. That is D082's payoff spent a
second time; no label-uniqueness argument appears anywhere.

`hv-otherlabel` also became explicitly the THUNK case (it carries `m` with
`compile-abstract i ≡ label (thunk m) ∷ tail`) rather than a generic foreign
provenance — its only producer is `c-thunk`, and the call scan needs the label's
identity to make the match decision.

### THE RUNTIME JOINT INVARIANT — **LANDED** (2026-08-04), (i) and (ii)

`SegWF prog B fs` carries both halves of the runtime side, proved by ONE
`Reachable` induction:

    seg-cur   : frame-slots (falloc fs) ≡ cur (seg-at prog (fpc fs) (mkSeg B []))
    seg-stack : RetMatch prog B (saved-frames (falloc fs)) (fret fs)

`RetMatch` is the (ii) piece: **the frame stack and the return stack are ONE
stack** — equal length, and each saved frame's reservation is the segment in
force at the pc it will return to. Without that second half a `c-ret` restores
a slot count from `saved-frames` and lands the pc at a return address with
nothing relating the two, so `seg-cur` cannot be re-established. It is a
DATATYPE, so it composes at the pushes and pops the markers produce.

Three supporting changes, all of them real content rather than restatement:
- **`FlatStackSlot` now carries the WHOLE frame stack.** `SameFrames` has three
  equations (`frame-slots`, `saved-frames`, `fret`) where there was one, so a
  frame-free step is known to move none of them. `flat-stack-slot`, the
  single-field projection, is DELETED — every consumer wants the record.
- **`EntryLike` gained `fret ≡ []`.** Without it a "start" state could arrive
  already owing a return and the two stacks would not be relatable at
  `reach-start`. The apex supplies it by construction (`mkFlat` defaults it).
- `run-stack-slot` is now a PROJECTION of `SegWF` (its type is unchanged, so
  nothing downstream moved).

**WHERE THE FLIP LANDS IS NOW ONE NAMED SPOT**: `run-seg-wf`'s step case, which
needs the segment in force to agree at the post-pc and the pre-pc. Today that
is `emitted-seg-const` (no emitted trace holds a marker). With bodies inlined
it splits into exactly two obligations — the marker steps, which move the
segment exactly as they move the frame, and LABEL SCOPING (iii) for the jumps.
That is the whole of what is left of the joint invariant.

### THE SEGMENTED BUDGET — SCOPED (2026-08-04). This is the wall.

Making the parent reserve `max` of its own and every inlined body's budget
would make `All (SlotBelow B)` TRUE — and USELESS. What the correspondence
consumes (`slot-read-in-frame`) is `slot < frame-slots (falloc fs)`, and
inside a body `frame-slots` is the BODY's budget (the marker's `enter-frame`),
so a bound against the parent's budget proves nothing there. The segmentation
is unavoidable.

Its honest shape, worked out here (NOT built):

- a static per-pc budget `seg : ℕ → Maybe ℕ`, a fold over the trace that
  switches at `c-thunk b` and restores at `c-ret`. `nothing` (NO CLAIM) at the
  marker positions themselves — at a `c-thunk`'s own pc the machine still
  holds the CALLER's `frame-slots`, and the caller is not statically known
  (a closure is called from anywhere). Same move `ShapeTable` already makes
  for these two markers (`ctrl-ok = true`, empty expectation).
- the emitter walk in that form: every slot-addressing instruction's slot is
  below `seg` AT ITS POSITION (SlotBudget's `All` becomes the fold).
- a RUNTIME joint invariant, and this is the part with new content:
    (i)   `frame-slots (falloc fs) ≡ seg (fpc fs)` wherever `seg` claims;
    (ii)  `fret` and `saved-frames` are the SAME STACK: equal length, and each
          saved frame's slot count is `seg` at its return pc. Without (ii),
          `c-ret` cannot re-establish (i) — `leave-frame` restores a count
          from `saved-frames` and the pc goes to a return address, and
          nothing relates the two. This is why the segmented budget and the
          `FlatCorr` return stack are ONE piece, not two.
    (iii) **LABEL SCOPING — a NEW static obligation with no existing
          machinery**: for (i) to survive a `c-jmp`/branch, a jump inside a
          body must land inside that body's segment. True by construction (a
          body's labels come from its own counter range) but PROVEN NOWHERE —
          grep finds no label-range lemma anywhere in the tree. This was not
          on the plan's list.

So the remaining unit is, in dependency order: the segmentation walk; the
joint (i)+(ii)+(iii) invariant; `block-step-c-thunk` (+ the honest
`stack-room`); `block-step-c-ret` and the `FlatCorr` return-stack field;
`instr-call-closure` and the `find-thunk` ↔ `X.find-label … (thunk n)`
correspondence; then the layout flip, extraction, and exit tests ×3. None of
these is landable green on its own — the cycle in (1) is why — so it is one
multi-session commit, matching the plan's original 3–5 session estimate with
(iii) added.

### 2b PART-LANDED, AND THE FLIP MEASURED AGAIN (2026-08-04)

**LANDED (`e986f36b`)**: the `FlatStackPtr` half, and it went further than
planned — see the commit. `lea-slot` joined `FrameFreeI`'s ⊥ set with
`FrameFreeTrace` conditional on `HeapModed` (no new walk needed: the

clauses discharge against `IsHeap Stack = ⊥`), `SPInv`'s payload became

**THE FLIP ITSELF, and a BETTER PLACE TO DO IT.** Do NOT flatten the bodies
in the public `ir-to-trace` wrapper. Inline each body AT ITS `curry` CLAUSE:

    <closure construction> ++
    instr-ctrl (c-jmp end-label) ∷
    instr-ctrl (c-thunk this-label body-budget) ∷
    body-trace ++
    instr-ctrl (c-ret body-budget) ∷
    instr-ctrl (c-label end-label) ∷ []

(labels: `this-label = l`, `end-label = suc l`, body starts at `suc (suc l)`;
the bodies list then always comes back empty and `ir-to-bodies` can go).
This is worth a lot: **every emitter walk already recurses into `body` at
that clause**, so covering the body's instructions is a ONE-LINE change per
walk instead of a strengthened "main AND every body" induction. Verified:
`IRToTrace` and `FrameFreeTrace` both went green this way in minutes;
`AllocMin` and `CataIRSlotStable` are the same one-line shape.

**WHERE IT STOPS — `stackSlot` MUST BECOME PER-FRAME.** `SlotBudget`'s
`All (SlotBelow B) (ir-to-trace ir)` is false with bodies inline, and the
reason is not bookkeeping: a body's slot `k` is bounded by ITS budget, and
`body-budget` can exceed the parent's. Chasing it down to what the bound
actually protects: `FlatCorr.stack-eq` covers stack cells `k < stackSlot`,
and `run-stack-slot` says `stackSlot ≡ ir-stack-budget ir` — "the window
never moves". With a real call the window DOES move, so
- `do-thunk`/`do-ret` must also write `stackSlot` (to `b`, and restore it),
  which is the one thing step 2a deliberately did NOT do;
- `run-stack-slot` becomes "…≡ the CURRENT frame's budget";
- and `SlotBelow`'s `All` must become a FOLD that tracks the current budget,
  resetting at `c-thunk b` and restoring at `c-ret` — the segmentation.

That is the whole of the remaining unit's difficulty, and it is a session of
its own. NOTE the tension with step 2a's finding: keeping `stackSlot` still
is what let `FlatStackSlot` survive, so making it move per-frame turns that
invariant into its per-frame form too. Both are true; the per-frame form is
the honest one once calls exist.
