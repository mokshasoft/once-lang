# Plan 0.63 — Model the closure call in the flat machine

**STATUS: SCOPED 2026-08-03, not started.** The last COVERAGE-class gap in
the flat↔x86-64 correspondence: `events-running-call`.

**DECIDED (D081, 2026-08-03): the code-address model.** A code address is
WHERE THE LABEL IS — `lea` of a label resolves it (`find-label` is the
linker in this model); `call`/`ret` are left untouched because they are
already faithful. No emitted instruction changes; there are no performance
implications. See D081 for the two rejected alternatives (resolve at
`call` = a fiction that grows `x86-64-loader-faithful`; full byte
addresses = the much larger redesign).

**ORDERING CORRECTED 2026-08-03 by a top-down attempt (see "What the
attempt proved" below): step 0 is NOT independently landable — resolution
requires the bodies (and their labels) to be in the modelled program
first. The order is BODIES, THEN RESOLUTION.**

## FINDING (2026-08-03, before starting): the residual is FALSE, and the
## code-address model is inconsistent

Two facts read out of the model:

1. `execInstr prog s (call target)` (X86-64.Semantics:305) pushes
   `pc s + 1` and sets `pc := <the operand's VALUE>`.
2. `lea rax, [rip+label n]` gives the effective address `n` — the label
   NUMBER — and `enc-sv (SV-Code n) = n`. But every other control transfer
   (`c-jmp`/`je`) resolves through `find-label`, which returns an
   INSTRUCTION INDEX.

So a modelled closure call jumps to `pc := n` (a label number) while the
body actually begins at `find-label prog (once n)` (an index). These
coincide only by accident. **The modelled ISA is internally inconsistent
about what a code address is** — calls use raw values, jumps use label
resolution.

Consequently `events-running-call` is not merely unproven, it is FALSE in
general (same class as the `load-const-float` hole closed by D079): the
abstract machine treats the call as the identity and continues, while the
concrete machine jumps somewhere unrelated (or off the end, ending the
trace). Any program that applies a closure and then emits an observable
witnesses the difference.

THIS RAISES PRIORITY: it is a soundness hole in the correspondence cone,
not a coverage gap.

## The gap

`exec-abstract instr-call-closure = s , alloc` — the IDENTITY — while the
compiled code does `call *0x8(%r12)`: it transfers control to the closure's
code address and later returns. No proof can bridge that; the abstract
machine has to model the call.

`instr-call-closure` IS emitted (`ir-to-trace' n l apply` ends with it), so
this is not a fossil route like `instr-loop`/`lea-indexed`/`case-on-tag` —
it is the lowering of `apply`, a core CCC generator. The residual is
conditioned on the run context, so it is not vacuous; but it is unproven
and unprovable as the model stands.

## Why it is structural, not a proof (verified 2026-08-03)

`ir-to-trace` returns the MAIN trace only — closure bodies come from a
SEPARATE `ir-to-bodies`, which the per-arch emitter emits as its own
labelled blocks (`Once/Target/X86-64.agda` uses both). So the FLAT
machine's program does not contain the bodies at all: there is nothing for
a modelled call to jump to. Inlining is not an option in general — a
closure value's code pointer is only known at runtime (that is what the
`SV-Code` cell is for).

## What the attempt proved (2026-08-03) — read before planning the next run

I made the top-level change (`lea` resolves via `find-label`) and followed
the red. It reached `block-step-load-code-addr` and stopped there, for a
reason that invalidates the old ordering:

- the only `label` instructions in the MODELLED program come from
  `compile-abstract (instr-ctrl (c-label n)) = label (once n) ∷ []`;
- closure-body labels (`.L_thunk_n`) are emitted ONLY as text by
  `emit-thunk-body` (Once/Target/X86-64.agda) — they never enter the
  modelled `Program` at all;
- so `find-label (compile-trace prog) (once n)` is `nothing` for a body
  label TODAY. Making `lea` resolve would make it HALT, while the abstract
  `instr-load-code-addr` writes `SV-Code n` and continues — turning a
  correct block-step into a false one.

Landing step 0 alone would therefore have replaced one false postulate
with another. (The tempting fallback — resolve-if-present, else keep `n` —
is exactly the kind of shim MERGE.md forbids: it preserves today's wrong
behaviour and hides the gap.) The change was reverted; the tree is green.

### The design surface this exposes (all of it is step 1's)

0'. **PREFER `c-ret` IN `CtrlInstr`, not a new top-level `AbstractInstr`**
   (2026-08-03, from the "jump to labels" framing). A return IS flat
   control flow, and `instr-ctrl` is exactly the control-flow family item 6
   established (`c-label`/`c-jmp`/`c-branch-*`). Putting it there is both
   the design-coherent home AND cheaper: **13 sites treat `instr-ctrl c`
   OPAQUELY** (`sp-abstract`, `pb-abstract`, … `= wf`) and are untouched by
   a new `CtrlInstr` constructor, whereas a new top-level constructor
   forces a clause at every one of them. Only the functions that CASE-SPLIT
   on `CtrlInstr` need a clause — `flat-exec-instr`, `compile-abstract` ×3,
   the five invariant preservations' ctrl clauses, ShapeTable's
   `step-expect`/`ctrl-ok`, `events-running-fetch`, `stable?`,
   `*-keeps-next-slot`, `instr-reloc`.
   `instr-call-closure` STAYS a top-level instruction (it is
   closure-specific — it reads the code pointer out of the record); only
   its semantics changes, from identity to push-return + jump. The
   asymmetry is right: the call is a data-directed transfer, the return is
   pure control.

1. **A `ret`-like abstract instruction.** `AbstractInstr` has none, and the
   per-body `ret` is emitted as text. Adding a constructor ripples through
   EVERY total dispatch — `exec-abstract`, `compile-abstract` (×3 arches),
   `FrameFreeI`, `AllocMinI`, `slot-of`, `stable?`, ShapeTable's
   `step-expect`/`site-ok`/`ctrl-ok`, `InstrSlot`, `CataAtRelocate`, and
   every block-step dispatcher. Mechanical but WIDE. MEASURED 2026-08-03
   by tracing an existing instruction (`instr-save-closure-reg`) through
   the tree: **15 files, ~41 clause sites** — SMCore 2, InstrSlot 1,
   FlatStoreWF 2, FlatRegTagWF 2, FlatStackSlot 2, FlatStackPtr 3,
   FlatPtrBounds 3, ShapeTable 2, CataIRSlotStable 3, CataNextSlot 3,
   CataAtRelocate 2, AbstractToX86 6, AbstractToX86-32 2,
   AbstractToRiscV 2, ConcFlatSim 6. Most are one-liners; the ones with
   real content are `exec-abstract` (the return semantics), the five
   invariant preservations (FlatStackPtr / FlatPtrBounds / FlatStackSlot /
   FlatStoreWF / FlatRegTagWF — a `ret` moves `pc` and pops the return
   stack, so each needs its own clause), and the three
   `compile-abstract`s. Budget a full session, and land it as ONE green
   unit: a half-swept tree does not typecheck at all.
2. **A label namespace for bodies.** `Label` is `once ℕ | sigop String ℕ`;
   body labels need their own constructor (`thunk ℕ`) so `find-label`
   cannot confuse them with `c-label` ids. Small, but do it INSIDE step 1
   (an unused constructor landed early is dead code — MERGE.md's
   no-islands rule).
3. **The per-body prologue/epilogue must move inside `compile-trace`.**
   `emit-thunk-body` currently emits `subq $budget*8, %rsp` … `addq …` …
   `ret` as text, i.e. OUTSIDE the modelled program — the same class of
   silent absorption as the main trace's prologue bracket (the parked
   `budget*8` displacement item). Bringing bodies in means bringing these
   in too, which SHRINKS `x86-64-loader-faithful` — a second reason to do
   it, beyond the closure call.
4. Only then does step 0 (D081 resolution) become true and landable.

## SECOND ATTEMPT (2026-08-03): the machinery, designed and typechecked

Built the flat-machine half far enough to typecheck each piece, then
reverted (the remaining label-design point below must be settled first, and
a half-swept tree does not compile). Everything here is VALIDATED design,
not speculation — reuse it verbatim:

1. **Extending `FlatState` costs ~0 edits.** Rename the record constructor
   to `mkFlatFull` and keep a 3-field wrapper

       mkFlat : LocState FS → AllocState {FS} → ℕ → FlatState
       mkFlat loc alloc pc = mkFlatFull loc alloc pc [] (SV-Tag 0)

   All ~37 existing `mkFlat` applications build exactly such a state (no
   pending returns, filler closure register), so they keep working
   untouched. Verified green.

2. **TWO new fields are needed, not one:**
   - `fret : List ℕ` — the return-pc stack. A GHOST list: the abstract
     memory is frame/slot-keyed and has no byte-addressed pushdown, so the
     addresses the concrete machine pushes below `%rsp` are modelled here
     and RELATED by the correspondence (a new `FlatCorr` field).
   - `fclosure : StoredValue FS` — the `%r12` mirror. NON-OBVIOUS and
     easily missed: the concrete call is `call *0x8(%r12)`, i.e. it reads
     the code pointer out of the CLOSURE REGISTER, not out of `Input1`.
     `instr-save-closure-reg` is abstract-identity precisely because that
     register lives at the FLAT level — so the flat machine loads it:

       flat-exec-instr instr-save-closure-reg _ fs =
         record fs { fclosure = readReg (regs (floc fs)) Input1
                   ; fpc = suc (fpc fs) }

3. **`c-ret` goes in `FlatCtrl`** (with `c-label`/`c-jmp`/`c-branch-*`),
   and the semantics is aux-style so downstream proofs can rewrite:

       do-ret []           fs = halt fs
       do-ret (pc' ∷ rest) fs = record fs { fpc = pc' ; fret = rest }
       do-call-to (just pc') fs =
         record fs { fpc = pc' ; fret = suc (fpc fs) ∷ fret fs }
       do-call-to nothing    fs = halt fs
       do-call-code prog (just (SV-Code lbl)) fs = do-call-to <resolve lbl> fs
       do-call-code prog _                    fs = halt fs   -- enumerated
       do-call prog fs = <case fclosure fs: SV-Ptr loc ⇒
                          do-call-code prog (readLoc (floc fs) (sucLoc loc)) fs>

## THE OPEN DESIGN POINT (settle this FIRST next session)

How does a CALL find its body in the ABSTRACT program?

- the abstract `find-label : AbstractTrace → ℕ → Maybe ℕ` scans for
  `instr-ctrl (c-label n)` and is ℕ-keyed;
- but `c-label n` compiles to `label (once n)` → `.Lonce_n`, while the
  `lea` that creates a code pointer renders as `.L_thunk_n(%rip)`
  (`showMem (rip+label n)`) and `emit-thunk-body` emits `.L_thunk_n:`.

So marking a body start with plain `c-label` makes the two sides disagree
about the label's NAME, while the label counter is already shared (one
counter threads main and bodies, so ids cannot collide).

Two coherent resolutions:

- **(a) a dedicated marker** — add `c-thunk : ℕ → FlatCtrl` compiling to
  `label (thunk n)` (a new `Label` constructor rendering `_thunk_n`, so the
  EMITTED TEXT IS UNCHANGED), plus `find-thunk` on the abstract side. Keeps
  D033's provenance principle: a call can never land on a jump label,
  definitionally. Costs one more constructor sweep.
- **(b) unify on `once`** — emit body labels as `.Lonce_n:` and change
  `showMem (rip+label n)` to match. Simpler and no new constructor, but it
  CHANGES THE EMITTED TEXT (harmlessly — same labels, different names) and
  drops the definitional separation.

RECOMMENDATION: (a). The emitted text stays byte-identical (so the existing
binaries/tests are unaffected by the model change), and provenance
disjointness is exactly the D033 property that makes label resolution
collision-free without a shared-counter argument.

## The work, in dependency order

0. **[DO THIS LAST — see above] Code addresses resolve (D081).** `execInstr prog s (lea r (rip+label n))`
   yields the RESOLVED location of label `n` instead of `n` itself (the
   clause has `prog` in scope, so this is local — `effectiveAddr` itself
   need not gain a parameter). Then `enc-sv (SV-Code n)` must be the same
   resolved value: give the encoding a CODE MAP beside the heap `AddrMap`
   it already carries (static — no extension lemmas, unlike the heap map).
   Ripple: `sim-load-code-addr` and `block-step-load-code-addr` (whose
   `rax-eq` is currently `refl` and becomes the resolution equation), plus
   the mechanical widening of `enc-sv`'s parameter at its use sites.
   AFTER this step the model is coherent about code addresses even though
   the call is still unmodelled — i.e. it is a landable, verifiable
   increment on its own.

   SIZED (2026-08-03): `AddrMap = HeapLocation → ℕ` (FlatCorrespondence:157)
   becomes a two-field record (heap map + code map), `enc-sv-at` gains the
   code clause, and the call sites are ~126 `enc-sv` occurrences
   (FlatCorrespondence 73, FlatSimulation 50, ConcFlatSim 3) — mechanical,
   since almost all are `C.enc-sv hv …` and only the RECORD construction
   sites change shape. Do NOT put the code map in `HeapView`: a new view
   field breaks convertibility at every stuck `enc-sv hv v` (the 2026-07-30
   design note — that is exactly why the encoding takes the map, not the
   view). Budget: one focused session for step 0.

1. **[FIRST] Bodies into the flat program.** `ir-to-trace` becomes
   `main ++ concat (map (λ (lbl , _ , t) → instr-ctrl (c-label lbl) ∷ t ++ [ret]) bodies)`
   (or equivalent). RIPPLES: `x86-off`/`find-label` correspondence
   (`FlatComposition`), `ir-stack-budget` (each body has its OWN budget —
   the current single-budget `Reachable`/`RunAt` indexing assumes one
   frame), and every emitter walk (`FrameFreeTrace`, `AllocMin`,
   `SlotBudget`, `CataIRSlotStable`, and Plan 0.62's `ShapeTable` walk).
   Do this FIRST and follow the red — the type errors are the work list.
2. **A return-address stack in `FlatState`.** New field; `instr-call-closure`
   reads `SV-Code lbl` from the closure record (cell 1 — which Plan 0.62's
   `shape-closure` already guarantees is there!), pushes `suc (fpc fs)`,
   jumps to `find-label prog lbl`; a new `instr-ret` pops. The concrete
   side already does exactly this with the machine stack, so the
   correspondence gains a stack-of-return-addresses component (and `%rsp`
   moves at call/ret — the layout invariants must accommodate it, cf. the
   `stackSlot` discipline).
3. **The per-body frame.** Each body has its own `body-budget`; the
   prologue/epilogue bracket is per-body. `RunAt`'s single
   `ir-stack-budget run-ir` must become "the budget of the frame we are
   currently in", i.e. the return stack carries budgets too. This is what
   makes `run-stack-slot` (currently "the window never moves") a
   per-frame statement.
4. **The block-step + routing.** With 1–3 in place, `block-step-call-closure`
   is an ordinary two-part correspondence (call ↦ push+jump, ret ↦ pop+jump)
   and `events-running-call` is routed like every other instruction.

## Honest size

Bigger than item 6 (case→flat control), because it adds STATE to the flat
machine rather than relaying out a trace. Step 1 alone is a session; steps
2–3 interact with every layout invariant landed in rung D (`FlatStackSlot`,
`FlatStackPtr`, `FlatPtrBounds`, the `lo`/high-water mark). Budget 3–5
sessions and expect to re-run the vacuity probe afterwards (a new state
component means new residual shapes).
