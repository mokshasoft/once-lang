# Plan 0.105 — An FFI contract's meaning is a parameter, not a postulate; `Eff` means an interaction tree

## 0. The property

> **The Spec says what a program means relative to the contracts of what it imports. It never
> invents a value for a contract.**

D061 decided this on 2026-06-17: "the core is parameterized over an abstract `Interpretation`
… `classify-name` / `generic-info` / `generic-semM` are deleted". Plan 0.38 M0.1 landed,
M0.2 (threading the parameter) did not, and since then every plan that touched the area
removed one *use* and left the postulate:

* D225 (plan 0.98) removed its use at `Void` on the effectful path;
* D244/D246 (plan 0.103) took internal calls off it, since an internal call now means its
  callee;
* D231 rejects a pure FFI arrow into `Unit`/`Void` (`HonestFFI`).

## 1. The measurement (verified 2026-10-02)

* **The apex is inconsistent.** `generic-semM : ∀ {A B} → String → TargetNum → M.⟦ A ⟧ →
  M.⟦ B ⟧ᵍ` (`Arith/SigOp/Builders.agda:216`) is in `Once.Certified`'s import cone, and

      bot : TargetNum → ⊥
      bot fmt = generic-semM {Unit} {Void} "x" fmt _

  typechecks. It has been on master since plan 0.2.4.1.
* **The Spec uses it.** The core rule `⊢sigop` means `GradedOps.sigOpRefᵛ`, which goes through
  `value-info` / `arrow-info` to `generic-semM`. D246's "import environment" is the
  environment of imported ONCE modules; FFI contracts are not in it.
* **Restricting the type cannot fix it.** `HonestFFI (μ-type _) = ⊤`, and a μ-type can be
  empty (`μ X. X`, `μ (K Void)`). Any postulate "a value at every honest type" stays
  inconsistent, so there is no cheap stopgap.
* **Sites** (code uses, not comments): `Arith/SigOp/Builders`, `Denotation/{GradedOps, Meaning,
  SourceDenote, Realize}`, `Adequacy/{SourceFaithful, MeaningBridge}`, `Surface/{Desugar,
  Elaborate}`, `TypeCheck/{Elaborate, ElaborateProofs}`.

## 2. The second defect: the meaning of `Eff` cannot receive

An `eff` arrow into a DATA codomain (not `Unit`, not `Void`) falls to `arrow-info-eff`'s last
clause, `value-info`. So `read : Eff Unit Int` is specified as silent and as a fixed function of
its argument: two `getLine`s are equal. The language does not say so — D250 makes only PURE
arrows referentially transparent — but the Spec's model of `Eff` cannot say otherwise.

The cause is the trace monad. `T X` is a budget-indexed trace plus a `Res X`: a WRITER. It can
record what a computation emits, and nothing can flow back in. A Writer coincides with the right
model only when every operation answers `Unit`.

## 3. The design: a computation is an interaction tree

**The general statement (D250 is its pure instance).**

> A computation of grade π means an INTERACTION TREE over the operations π permits: either done
> with a value, or a call `op(arg)` with a continuation awaiting the operation's answer.

* **pure** permits no operations, so its tree is a value. This is D250, unchanged.
* **eff** permits the program's SigOps. `read` is a call whose continuation receives the answer,
  so two reads are two calls with independent answers.
* **Halting needs no flag.** An operation answering `Void` (`exit`) has a continuation that can
  never be invoked; 0.98's `stopped` is that case.
* **Effects stay arrows and stay composable.** This is algebraic effects, not world-passing:
  programs never see a world, and `>>=` grafts continuations.

**The contract (what an interpretation's author owes).** The compiler knows only each import's
NAME and declared type. An interpretation answers calls. The compiler's theorem is

    ∀ interpretation ι that meets its contract →
      the binary, linked against ι's implementation, makes the same calls as ⟦ p ⟧ and continues
      with the same answers

What `getLine` does, or a read from `/dev/urandom` or a bare-metal port, is the interpretation's
business. D061 point 3 holds: per SigOp × target, the implementation is proved (a verified
kernel) or postulated (Linux), off-line, by the interpretation's author.

**Pure contracts are values, not calls.** A pure import is referentially transparent (D250), so
it is a fixed function supplied by the interpretation, never a node of the tree. This keeps the
optimizer and the arith rewrite free to move pure calls and never effectful ones.

**The observable is derived.** D058 stands: correctness is the sequence of effectful SigOp events.
Running a tree against an interpretation yields that sequence (the calls made). Answers are not
observed separately; they are determined by the interpretation and the calls before them.

**Consistency by construction.** A program importing an uninhabited pure contract has no
interpretation, so the theorem says nothing about it. That is correct (no library implements
such a contract), and nothing proves ⊥. `generic-semM` is deleted.

## 4. Decisions to record (decision-log entries)

1. **`Eff` means an interaction tree; `T` is replaced** (§3). This generalizes D250 and subsumes
   0.98's `stopped`. Supersedes the Writer reading of `T` (plans 0.97/0.98).
2. **FFI contracts are the program's parameter** (supersedes the `generic-semM` half of D061's
   implementation note): pure imports are values the interpretation supplies; effectful imports
   are operations it answers.
3. **The world answers; it does not stop.** An effectful call at a data or `Unit` codomain always
   gets an answer; stopping happens exactly at a `Void` codomain. An input that can fail is a sum
   the program sees (`Eff Unit (Int + Err)`), not a hidden stop.

## 5. Phases (top-down, POC first)

**0. Probes.**
* `arith-sigop-contract` (`ConcFlatSim`, x86-64 and riscv64) concludes `env (once-symbol-path
  name) ≡ just pl` for ANY `effect si ≡ Pure`, and a pure FFI op is `Pure`. Probe whether it is
  refutable for a program with one pure FFI call. If it is, Phase D splits the arith contract from
  the FFI one by the `SigOpSem` constructor (D255's `primV` already identifies arith by meaning).
* Grep the Haskell side for interpretation stand-ins in `compiler/`; the extracted compiler must
  not change behaviour (it never reads `semM`, per D061's update).

*Phase 0 result (2026-10-02).*
* Both contracts are FALSE as stated, read off their consumer (`FlatCore.EventDispatch.sigop-step`,
  which dispatches on `effect si` alone):
  * `arith-sigop-contract` is taken for EVERY `Pure` SigOp, and a pure FFI op (`pureV`) is `Pure`.
    Its symbol is not in the arith environment, so the promised payload does not exist.
  * `external-sigop-contract` is stated for EVERY `si` and concludes `env sym ≡ nothing`. That
    is false for an arith block, whose symbol IS in the environment.
  Both are the "state premise, program conclusion" shape. Phase 4 splits the dispatch by the
  `SigOpSem` constructor: `primV` is arithmetic, and every FFI operation (pure or effectful) is
  external. No formal ⊥ term was built: constructing a reachable `CompiledCorr` state costs more
  than it would tell.
* Haskell: no interpretation stand-ins (`compiler/src` never reads `semM`).

**1. The tree, as a POC (the gate for the whole plan).** In a spike module, outside the apex:
* the tree type over an operation signature, its `return`/`>>=`, and the monad laws;
* infinite programs: `main` never returns (plan 0.97), so trees are infinite. Decide the
  representation by the typechecker: a coinductive/guarded tree, or a depth-indexed one in the
  style of today's budget (D058's prefix family). The budget view must survive as the observable;
* running a tree against an interpretation to the depth-`n` event prefix, and the prefix-family
  laws (`extends`/`bounded`/`saturating`) for the result;
* 0.98's `Res` and the halting rows as the `Void`-answer instance.
*Gate:* the laws hold, postulate-free. If the representation fights the budget view, stop and
decide before touching the Spec.

*Phase 1 result (2026-10-02): GATE PASSED.* `Once.Spike.ITree` (12 s, postulate-free beyond the
standing `extensionality`) has:
* the tree, its monad laws, and the run of a bind as the runs of its parts with the history threaded;
* the budget observable `take n` of a run's events, with the prefix-family laws (bounded, extends,
  saturating);
* the instances: no operations is a value (`pure-iso`), operations answering `⊤` give the same run
  under every interpretation (today's Writer), and a halting operation ends the run.
Two findings:
* **The tree is INDUCTIVE.** Once is total, and every trace in the development is `capN n` of a finite
  list. Coinduction stays where it already is, in `νᵈ`'s layers.
* **Halting is its own node, `halt o a`, with no continuation.** Interpretations then answer every
  answering call totally (they are never asked a halting one). With `Res`-returning interpretations
  a world could stop at any call, contradicting decision 3; with total answers a `Void`-answering
  call would have no interpretation at all, making every halting program vacuous. The node is read
  off the declared codomain (`Void`), as `haltsV` already is.

*Integration estimate.* `T` appears in 61 apex modules, about 2200 occurrences (`SourceFaithful` 422,
`TraceMonad` 279, `CoherenceLaws` 162, `SourceDenote` 128, …). The sweep, top-down:
* `T X = Tree OnceSig X`, with ONE universal signature: an operation is a SigOp key (canonical name and
  declared types), its argument the machine value, its answer the codomain's value (`⊤` for `Emits`);
  `Halts` operations are `halt` nodes. `returnT` is `ret`, `>>=T` the tree bind, emitting a call
  answered by `⊤`.
* Pure FFI values come from the interpretation's pure half, a parameter of the meaning (not calls).
* Observables gain the interpretation: `projTrace ι t n = take n (events of run ι t)`; the apex
  quantifies over `ι`.
* Phase 4: the flat machine's SigOp step reads the same oracle for an answering call's result.

**2. The Spec.** `T` becomes the tree; `⊢sigop` at an effectful arrow is a call node, at a pure
arrow the interpretation's value; `runProgram` and `CorrectCompiler` take the interpretation and
quantify over it. Then follow the red: `Meaning`, `SourceDenote`, `GradedOps`, `Realize`,
`MeaningRelation` (`RelT`), `behavior-by`.

**3. The IR and the bridges.** `evalᴰ`'s SigOp clause makes a call node for an FFI info (as `Call`
reads the table, D244); `SigOpSem`'s FFI constructor carries the name and declared type, not a
value. `SourceFaithful`, `MeaningBridge`, `CoreBridge`/`TeleWalk`, `Coherence` follow.

**4. The backend.** The machine side: an FFI call's lowered code calls the symbol, and the
per-arch hypothesis says the code at `c` answers as `ι` does. `external-sigop-contract` (×3
arches) becomes that hypothesis on the apex, next to `BlockRunsHyp`. Decide with the Phase-0
probe whether `arith-sigop-contract` needs the constructor split.

**5. Gate.** Certified green; `generic-semM` has zero references; the `⊥` probe no longer
typechecks; the extraction run (MAlonzo + `cabal test`) with no change to emitted code; an
input-reading test program (two reads that differ) in the exit tests.

## 7. Risks

* **`T` is the most-used structure in the development.** Every `T` law, `RelT`, `behavior-by`,
  `CataErased`/`AnaErased`, the IR meaning and the obligation layer's traces are written against
  it. Phase 1 exists to price this before the Spec changes; budget it as a top-down sweep, not a
  refactor.
* **Infinite trees and the budget.** The observable is indexed by event count. A coinductive tree
  must still give a prefix family; if guardedness fights it, the depth-indexed tree is the fallback.
* Threading the interpretation through the telescope walk is the `σR` / call-environment pattern
  a third time: wide but mechanical.
