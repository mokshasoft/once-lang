# Plan 0.13.2: Separate `ValueLocation` (address) from `StoredValue` (content)

## Why

The current memory model conflates two different concerns:

```agda
-- Today:
StackMem FS = Frame FS → Slot → Maybe (ValueLocation FS)
HeapMem    = HeapLocation → Maybe HeapLocation
```

Memory cells hold `ValueLocation` — i.e. *addresses*. So memory is
"addresses pointing to addresses." Tags, primitives, and code
addresses don't fit naturally — they're values, not pointers. The
existing `encode-const : FitsInReg A → ⟦ A ⟧ → ValueLocation FS`
and `encode-code-addr : ℕ → ValueLocation FS` postulates are
*workarounds*: they pretend a primitive `ℕ` produces a "pointer"
to satisfy the memory cell's type.

Layer 2 sums make this misalignment painful: the sum's tag (0 or 1)
is a value the abstract layer needs to inspect at runtime, but
there's no honest way to put one in memory and read it back. Plan
0.13.1 Phase 1 worked around this by halting the abstract layer
entirely on `instr-case-on-tag`.

The principled fix the user proposed (2026-05-09):

> ValueLocation should really just be a type that tracks where
> values are stored. Values can be pointers, ints, sums, etc. —
> needs its own type.

## What

Introduce a new `StoredValue` type for memory contents:

```agda
data StoredValue (FS : FrameSemantics) : Set where
  SV-Ptr  : ValueLocation FS → StoredValue FS  -- a pointer
  SV-Tag  : ℕ → StoredValue FS                  -- a sum tag (0 = inl, 1 = inr)
  SV-Int  : ℕ → StoredValue FS                  -- primitive integer
  SV-Code : ℕ → StoredValue FS                  -- code-address label
```

Rewire memory to hold `StoredValue`:

```agda
StackMem FS = Frame FS → Slot → Maybe (StoredValue FS)
HeapMem     = HeapLocation → Maybe HeapLocation   -- (heap-only invariant kept)
readLoc     : LocState → ValueLocation → Maybe (StoredValue FS)
writeLoc    : LocState → ValueLocation → StoredValue FS → LocState
```

Heap reads lift to `SV-Ptr (AtDynamic _)` at the boundary; heap
writes still require `SV-Ptr (AtDynamic _)` (rejecting other
`StoredValue` shapes preserves the heap-only invariant).

## Why this is the right answer

1. **`ValueLocation` stays addresses-only**, matching the lesson
   from the retired Stage E `InReg` constructor and the backed-out
   Plan 0.13.1 Phase 1 `TagLit` attempt. Both failed because they
   mixed values into the address type, breaking `readLoc-writeLoc-
   same` and `preserves-mem` lemmas universally.

2. **Tags fit naturally.** `SV-Tag 0` for inl, `SV-Tag 1` for inr.
   Pattern-matching on `SV-Tag` is structural and decidable by
   construction — no `is-zero-tag` postulate needed for `case`
   dispatch.

3. **Subsumes `encode-const` / `encode-code-addr`.** Both are real
   postulates today (trusted-base axioms). With `StoredValue` as a
   real sum type, `instr-load-const` writes `SV-Int n` and
   `instr-load-code-addr` writes `SV-Code n` — real constructors,
   no postulate needed. Two trusted-base axioms removed.

4. **`readLoc-writeLoc-same` stays sound and universal.** The
   lemma's signature is `readLoc (writeLoc s loc v) loc ≡ just v`
   where `v : StoredValue`. Writing a tag and reading it back gives
   `just (SV-Tag n)` — true by construction.

5. **No cascade through `preserves-mem` lemmas.** The lemmas say
   "writes to one location preserve other locations." That's still
   true. Earlier lessons-learned warnings were about putting *values*
   in the *address* type (InReg, TagLit). This proposal puts the
   value type *next to* the address type, preserving the lemmas.

6. **Captures actual machine semantics.** A real CPU memory cell
   holds bits that could be a pointer or an integer or a tag — the
   value's type is determined by what wrote it, not by the address.
   `StoredValue` makes this explicit at the spec level.

## Cost: cascade through ~30 files

`readLoc` / `writeLoc` are used in:

```
formal/Once/Arith/SigOp/{RelaxedPOC,Proofs}.agda
formal/Once/CCC/Machine/{SMCore,SMPrimitives,Validity,
                          ClosureWellFormed,Allocation,WriteOps,…}.agda
formal/Once/CCC/Machine/IR/{ApplyWF,ComposeWF,CurryWF,PairWF2,
                            SimpleWF,SumRecWF,…}.agda
formal/Once/CCC/Target/{X86-64,X86-32,RiscV64}/{DirectSimulation,
                                                 SimulationInterface,…}.agda
formal/Once/CCC/Codegen/IRTraceCorrect.agda
```

Per-file impact:

- **Trivial wraps**: change `writeLoc s loc v` (where v was a
  `ValueLocation`) to `writeLoc s loc (SV-Ptr v)`. Same for
  `readLoc` callers that destructure the result and re-wrap. Most
  call sites take ~5-10 minutes each.

- **Validity predicates**: `valid-inl-wf`'s field `readLoc s
  (sucLoc sum-loc) ≡ just payload-loc` becomes `≡ just (SV-Ptr
  payload-loc)`. Cascades through `decomposeInlWF`,
  `decomposeInrWF`, etc.

- **Lemmas** (`writeLoc-preserves-other`, `readLoc-stackMem-eq`,
  `readLoc-writeLoc-same`, …): signatures lift. The proofs
  themselves are usually straight `refl` or pattern-match — they
  generalise cleanly.

- **`encode-const` / `encode-code-addr` removal**: trace through
  every site that uses these postulates. Replace with `SV-Int n` /
  `SV-Code n`. The two postulates are deleted.

- **DirectSimulation modules** (×3 arches): `Corresponds`'s
  `mem-eq` is `∀ loc → x86-mem xs loc ≡ readLoc ls loc`. Now both
  sides return `Maybe StoredValue`. The x86 side needs a
  per-instruction story for tags / ints (a tag stored in `%rax`
  via `mov $n, %rax` corresponds to `SV-Tag n` at the abstract
  level, etc.). Adds per-arch postulates parallel to `encode-const`
  but probably narrower.

**Estimate: 3-5 days focused work.**

## Phased implementation

1. **Phase A** (~½ day) — define `StoredValue` and lift `StackMem`,
   `readLoc`, `writeLoc`. Update the close-by lemmas in `SMCore.agda`
   (`writeLoc-regs`, `writeLoc-halted`, `writeLoc-heapMem-stack`,
   `writeLoc-regs-commute`, `writeLoc-preserves-other`,
   `writeLoc-read-same-stack`, `readLoc-stackMem-eq`).
   Gate: SMCore typechecks.

2. **Phase B** (~½ day) — `SMPrimitives.agda` cascade (~20
   functions: `readLoc-writeLoc-heap-stack`,
   `writeLoc-regs-commute-{heap,general}`, `readLoc-writeLoc-same`,
   etc.). Mostly mechanical.
   Gate: SMPrimitives typechecks.

3. **Phase C** (~½-1 day) — Validity refinement. `valid-*-wf`
   predicates lift. Update `decompose*WF` extractors. Cascade
   through `ClosureWellFormed`, `Validity`, `MuValidity`.
   Gate: Validity layer typechecks.

4. **Phase D** (~1 day) — WF run-X helpers (`SimpleWF`,
   `PairWF2`, `CurryWF`, `ApplyWF`, `ComposeWF`, `SumRecWF`).
   Mechanical for the existing IRs (id, fst, snd, pair, curry,
   apply, compose) — they wrap pointers. New work for sums:
   `run-inl` / `run-inr` write `SV-Tag` for the tag slot.
   Gate: full WF layer typechecks.

5. **Phase E** (~½ day) — Replace `encode-const` /
   `encode-code-addr` postulates. `instr-load-const` writes
   `SV-Int n`, `instr-load-code-addr` writes `SV-Code n`. Delete
   both postulates from `FrameSemantics`.
   Gate: encode-* postulates gone, two fewer trusted-base axioms.

6. **Phase F** (~1 day) — `DirectSimulation` updates per-arch.
   `Corresponds.mem-eq` lifts. Per-instruction sims for new
   `SV-Tag`/`SV-Int` cases. Some narrow per-arch postulates may
   remain at the encoding boundary (e.g. "x86 `mov $n, %rax`
   corresponds to abstract `regs[Output] := SV-Tag n`") but they
   replace the existing `encode-const` postulate, so net trust
   doesn't grow.
   Gate: `make compiler-x86-64` green.

7. **Phase G** (~½ day) — Layer 2 codegen using the new
   infrastructure: `instr-load-tag : ℕ → AbstractInstr` writes
   `SV-Tag n`; `instr-case-on-tag f g`'s `exec-abstract` reads
   the tag at `*Input1`, dispatches structurally on `SV-Tag 0` /
   `SV-Tag (suc _)`. Replaces Phase 1's halt + named postulate
   with a real abstract step.

8. **Phase H** (~½ day) — Per-arch Layer 2 lowering with real
   branches (cmp/je + label threading). Layer 2 binary tests run
   end-to-end.

## Out of scope

- Heap stays HeapLocation-typed (heap-only invariant kept). Future
  work could relax this to allow heap-stored tags / ints.
- Register state stays `ValueLocation`-typed for now. Plan 0.2.4.5
  D4's `Place` sum type for register-residency is a separate
  concern at result-handle handover points.
- Recursion-scheme codegen (Layer 5/6) — separate plan.

## Relation to other plans

- **Supersedes** Plan 0.13.1 Phase 1's halting-`instr-case-on-tag`
  + `case-codegen-faithful-phase1` postulate. After this plan
  lands, the halt is replaced by a real dispatch; the postulate is
  discharged.
- **Supersedes** the encode-const / encode-code-addr trusted-base
  axioms. Each becomes a real constructor.
- **Aligns with** Plan 0.2.4.5 D4 (register-residency `Place`):
  same architectural lesson — separate value-shape from
  address-shape, use sum types at handover points.
- **Doesn't conflict with** Plan 0.2.4.7 (frontier-mismatch
  postulate discharge): orthogonal — that's about slot frontiers,
  not memory contents.

## Why Plan 0.13.1 Phase 1 stays as-is in the meantime

The halting-case + named postulate is honest about the gap.
Programs reaching `case` SIGILL at runtime, which surfaces the
"this needs the StoredValue refactor to actually work" point
loudly.

When 0.13.2 lands the refactor, Plan 0.13.1's Phases 2-7 (the
ones that needed real tag dispatch) can land in their original
shape — they were always going to depend on a real tag
representation.
