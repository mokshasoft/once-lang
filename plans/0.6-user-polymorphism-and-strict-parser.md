# Plan 0.6: User-Level Polymorphism + Strict Parser Errors

## Context

Two problems surfaced at the end of the 2026-04-20 session while
resuming the Layer-0 plan, and they're entangled:

1. **TVars in user type signatures silently drop the declaration.**
   `swap : A * B → B * A` parses but produces no `DTypeSig` — the type
   parser has no grammar for "an identifier that isn't a known type,"
   so the whole decl is skipped and the module parser moves on. This
   means `Strata/Derived/Canonical.once` (which uses TVars throughout)
   silently typechecks vacuously: its 30+ function definitions are
   ignored because their signatures never made it into the module
   AST. `once parse Canonical.once` emits zero signatures.

2. **The compiler hides errors this way in multiple places.** The
   TVar-drop is one instance of a recurring design pattern: when a
   sub-parser fails, the outer parser recovers silently and continues.
   During this session we already hit a different instance — the
   Haskell-level text preprocessor emitted `primitive S.exit : …`
   (dotted primitive name), the Agda parser silently rejected the
   primitive, and *every subsequent decl including `main` was dropped
   with no warning*. The symptom was a zero-byte assembly output that
   linked into a segfaulting binary. The root cause was the same
   silent-recovery pattern: *"parse failed here, skip and try the
   next thing."*

These are both "clear, unactioned errors" — the compiler knows
something is wrong and says nothing. Layer-0 end-to-end testing can't
close until (1) is resolved and (2) has a strict-error stance.

This plan covers both. Start with the silent-error fix (small, makes
the other work observable), then the TVar parsing restoration, then
the HM-style typechecker work that gives TVars meaning.

## Goals

* `Strata/Derived/Canonical.once` actually type-checks. `once parse
  Canonical.once` emits all 30+ signatures, not zero.
* `swap : A * B → B * A; swap = pair snd fst` works — the user can
  define polymorphic functions.
* Any parse failure becomes a first-class error message, not a
  silent drop. If the input is malformed, the compiler says so.
* `make test-x86-level0` in the `compiler/` package passes all three
  Layer-0 tests (this unblocks plan 0.2.4's completion criterion).

## Non-goals

* Type inference at argument positions (let-polymorphism on locally
  bound names). Only *declared* polymorphism (user-written signatures
  with TVars) is in scope.
* Higher-rank polymorphism / GADTs / any polymorphism discipline
  beyond the rank-1 prenex pattern existing typechecker-builtin
  specializations use.
* Replacing the 7 hard-coded polymorphic builtins (id, fst, snd, …)
  with stdlib definitions. The builtin-classifier infrastructure
  stays; this plan makes user-level poly a parallel path.

## Section A: Silent-error fix (do first)

The compiler's parser recovers from sub-parse failures by returning
`nothing` and letting the caller move on. This is correct for the
low-level bounded-parser combinators but wrong at the top-level
"parse a module" loop — there, a malformed decl should be reported,
not silently skipped.

### Concrete symptoms we've hit

1. **Dotted primitive name**: `primitive S.exit : Eff Int Unit`
   (emitted by old Haskell import preprocessor) → parse of primitive
   fails at the `.`, outer parser skips, the rest of the module
   (including `main`) is skipped too because the state is now out of
   sync with the token stream. Zero-byte assembly output.

2. **TVar in type signature**: `foo : A` → type parser rejects `A`,
   outer parser skips the decl, `foo` is not registered. No diagnostic.

Both presented as "the thing I wrote just isn't there."

### Fix

At the top-level `parseDecls` / `parseModule` loop, when
`parseDeclB` returns `nothing`, emit a structured error and either:

- **(A) hard abort**: stop parsing, return `Error "parse failed at
  token N"`. Current `compile Parse source` returns `Error err` which
  propagates cleanly through the CLI.

- **(B) soft report**: attempt recovery (skip to next likely boundary
  — next newline at column 0, typically) but record all skipped
  regions as errors and return `Error` if any occurred. Report all
  failures, don't hide any.

Recommendation: **(A) to start**, **(B) later** if/when batch
compilation of multi-module programs wants to surface all errors at
once. (A) is simpler and matches the "compiler must not hide errors"
principle strictly.

Also: the decision to skip tokens after a failed decl has no good
heuristic for the current grammar (there's no statement separator
terminator like `;` in most grammars). So (A)'s "stop at first
failure" is also more honest about the parser's actual recovery
capability.

### Scope of the fix

* `Once.Parser.Module.parseDeclsWF`: when `parseDeclB` fails after
  some non-empty prefix of tokens was consumed, produce an error
  result rather than silently terminating the decl list. Currently
  the function returns `just (ds , toks')` where `ds` is what
  succeeded; change to return a sum `String ⊎ (List Decl × …)`.

* `Once.Compile.compile Parse`: surface the new error return as
  `Error "parse failed: …"` instead of the current behavior that just
  stops early.

* Tests: add fixtures that are *meant* to fail parsing (dotted
  primitive name; TVar in type; stray tokens) and verify the error
  message is returned.

## Section B: TVar parsing (minimum-viable to survive)

Once Section A lands, `foo : A` becomes a real error message instead
of a silent drop. Section B makes it actually succeed.

### Fix

Extend `Once.Parser.Type` so that a `TWord name` in type-atom
position, when `name` isn't one of the recognized type keywords
(`Unit`, `Void`, `Int`, `Float`, `Str`, `Buffer`, `Eff`, `IO`),
becomes a `PolyType.TVar name` leaf. Correspondingly:

* `Once.Parser.Type` parses to `PolyType`, not `Type`. The existing
  `parseTypeWF` and related WF machinery migrate to produce
  `PolyType` uniformly (ground types are `PolyType` with no `TVar`
  nodes).

* `Once.Parser.Module.Core.Decl` (specifically `DTypeSig` and
  `DPrimitive`) carries `PolyType` instead of `Type`.

* Ground-type signatures are represented as `PolyType` with no free
  TVars; downstream type-checker can project back to `Type` when a
  signature is closed (no free TVars). Signatures with free TVars
  carry them through to typechecker-level handling (Section C).

### Scope of the fix

Medium: the parser change itself is small (5-10 lines), but the
propagation of `PolyType` through `Decl`, `DTypeSig`, `DPrimitive`,
`FunInfo`, `extractFunctions`, and the typechecker's ingestion path
touches many files. Estimate: one commit ~200-400 lines.

### Risk

The parser grammar shift has a known foot-gun: if a type-atom
accepts *any* `TWord` as a TVar, a typo like `foo : Untit` is
silently accepted as polymorphic instead of reported as "unknown
type `Untit`." Mitigation: add a convention (e.g. lowercase =
variable, uppercase-starting-letter = either variable or keyword,
with keywords checked first) and surface a warning for
single-occurrence TVars that look like typos. But this is a Section
A concern more than Section B — covered by the strict-error fix.

## Section C: HM-style elaboration for user poly

With Sections A+B landed, `parse Canonical.once` emits 30+
signatures with `PolyType` that contain `TVar` nodes. The
typechecker needs to handle them at use sites.

### What's needed

* **Unification**: given an expected ground type at an application
  site and a polymorphic signature, solve for the TVar substitution.
  The pre-2026-04-17 codebase had `matchesPolyType`, `substituteTVar`,
  `matchWithSubst`, `applySubst*` — all removed in the final
  dead-code sweep (`729ea1ae`). Parts of this should be revived or
  rebuilt.

* **Specialization at use sites**: given `swap : ∀ A B. A * B → B *
  A` and a call context expecting `Int * Str → Str * Int`, emit a
  ground-typed Surface term where TVars have been replaced by `Int`,
  `Str`. The body-specialization pattern already exists for the 7
  hard-coded builtins — `specId`, `specFst`, etc. For user code, we
  need the elaborator to do this *on the user-provided body*, not a
  per-name spec function.

* **Bidirectional integration**: the existing bidirectional elaborator
  needs to handle user-polymorphic names. When check mode has an
  expected type, unify. When infer mode has only the call arguments,
  unify against those. Echoes how `id e` is specialized from `e`'s
  inferred type.

### Design questions to resolve in implementation

1. **Let-generalization or not?** If a user writes `let swap = pair
   snd fst in …`, does `swap` become polymorphic in its use sites
   (HM's core feature), or only top-level named decls? Recommendation:
   only top-level, explicitly-annotated decls. Keeps it rank-1, no
   principal-type inference needed.

2. **How are instantiations threaded to codegen?** The existing 7
   builtins produce specialized Surface bodies via per-type `spec*`
   helpers. User polymorphic functions can't have per-type helpers
   (body is user-written). Option: compile the body once at its
   polymorphic type and rely on erased-at-runtime type information;
   or compile per-instantiation (monomorphization). Probably
   monomorphization, since IR is ground-typed.

3. **What about primitives with TVars?** `primitive puts : Eff
   (String ?) Unit` has no TVars currently, but stdlib `arr : (A →
   B) → Eff A B` would. Primitives don't have bodies to specialize
   — they're external. Needs design thought.

### Scope

Large. Multi-session. Most of the substance of this plan. Estimate:
multiple phases, starting from unification revival and building up.

## Related prior art

* Commits `0730ae82` (added bare-builtin check-mode clauses) and
  `290480e8` (removed them, "G2 decision") show the tension this
  plan resolves: the typechecker had partial user-facing polymorphism,
  tied to specific builtin names, but it was removed on principle
  ("polymorphic builtins should come from the stdlib"). Without a
  stdlib actually providing them (Phase 4), that principle stranded
  the user.

* Commit `9ffe323e` (Type/PolyType split) laid the architectural
  groundwork for user poly but didn't wire the parser or elaborator
  through to it. This plan finishes that wiring.

* Commit `729ea1ae` (final dead-code sweep) removed 1286 lines of
  unification machinery (`matchesPolyType`, `substituteTVar`,
  `applySubst*`, `matchWithSubst`) on grounds of unreachability.
  Phase 3 may revive pieces of this — worth consulting the git diff
  before reimplementing.

## Success criteria

* Phase 1: any malformed `.once` file produces a clear diagnostic,
  not a silent "Parse OK" with missing decls.
* Phase 2: `parse Canonical.once` emits its 30+ signatures (with
  TVars exposed in the output). Typecheck fails with a clear
  "TVars not yet supported by typechecker" message — *not* silently.
* Phase 3: `check Canonical.once` succeeds. `swap : A * B → B * A;
  swap = pair snd fst` usable in user code.
* Phase 4: `layer0-compose.once` typechecks and builds. `make
  test-x86-level0` passes all three tests.
